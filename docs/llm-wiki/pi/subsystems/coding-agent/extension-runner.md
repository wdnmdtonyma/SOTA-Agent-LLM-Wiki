> `ExtensionRunner` 是 pi-coding-agent 的扩展执行引擎: 它把 loader 产出的 extensions 和 shared runtime 绑定到当前会话, 构造 `ExtensionContext`, 并按事件类型顺序调用 extension handlers。

## 能回答的问题

- `bindCore()` 具体把哪些 session action 和 context action 绑定进 extension runtime?
- `ExtensionRunner.createContext()` 给 event handler 和 extension tool 暴露哪些运行时能力?
- 通用 `emit()` 和 `emitToolCall()`、`emitInput()` 等专用 emitter 的短路/聚合规则有什么不同?
- extension 注册的 tools、commands、shortcuts、flags、message renderers 如何在 runner 层汇总?
- project trust、provider registration、session-before cancellation 这些特殊路径怎样处理 error 和 result?
- reload/session replacement 后旧 extension context 为什么会变 stale?

## 设计动机与权衡

runner 把 loader 阶段的 declarative contributions 和 session 阶段的 live actions 分开: extension factory 可以先注册 handlers/tools/commands, 等 session 构建完再由 `bindCore()` 把真实 actions 填进 shared runtime [E: packages/coding-agent/src/core/extensions/runner.ts:324] [E: packages/coding-agent/src/core/extensions/runner.ts:354] [I]。这个设计让 extensionsResult 可以先被 resource loader 保存, 再由当前会话决定 UI mode、model registry、active tools 和 command context [I]。

专用 emitters 的存在是为了让不同事件拥有不同 combination policy: `tool_call` 支持 block 短路, `tool_result` 支持字段覆盖, `context` 和 provider payload 支持 chain transform, `input` 支持 handled/transform/continue 三态, `message_end` 有 role guard [E: packages/coding-agent/src/core/extensions/runner.ts:945] [E: packages/coding-agent/src/core/extensions/runner.ts:891] [E: packages/coding-agent/src/core/extensions/runner.ts:997] [E: packages/coding-agent/src/core/extensions/runner.ts:1031] [E: packages/coding-agent/src/core/extensions/runner.ts:1217] [E: packages/coding-agent/src/core/extensions/runner.ts:850] [I]。

stale context guard 是 reload/session replacement 的安全边界: runner invalidated 后, context getters 和 command actions 都会通过 `assertActive()` 抛出 stale message, 而 command context 用 descriptor clone 保留 lazy getter, 避免提前读取旧值 [E: packages/coding-agent/src/core/extensions/runner.ts:543] [E: packages/coding-agent/src/core/extensions/runner.ts:552] [E: packages/coding-agent/src/core/extensions/runner.ts:757] [I]。

## Gotcha

- `emitToolCall()` 没有 try/catch;handler 抛错会直接 reject 该 emitter, 与 `emit()`、`emitToolResult()`、`emitInput()` 等捕获并 `emitError()` 的模式不同 [E: packages/coding-agent/src/core/extensions/runner.ts:940] [E: packages/coding-agent/src/core/extensions/runner.ts:941] [E: packages/coding-agent/src/core/extensions/runner.ts:819] [E: packages/coding-agent/src/core/extensions/runner.ts:907] [E: packages/coding-agent/src/core/extensions/runner.ts:1222]。这是否是刻意让 blocking hook fail-closed, 当前源码未直接说明 [U]。
- `getFlags()` 与 `getAllRegisteredTools()` 都是 first registration wins, 但 `getShortcuts()` 对 extension-extension shortcut conflict 是 later registration wins;不要把所有 contribution conflict policy 统一假设成同一种 [E: packages/coding-agent/src/core/extensions/runner.ts:474] [E: packages/coding-agent/src/core/extensions/runner.ts:478] [E: packages/coding-agent/src/core/extensions/runner.ts:455] [E: packages/coding-agent/src/core/extensions/runner.ts:526] [E: packages/coding-agent/src/core/extensions/runner.ts:533]。
- `emitSessionShutdownEvent()` 先用 `hasHandlers("session_shutdown")` 判断, 没有 handler 时返回 `false`;调用方可据此区分“已发出 shutdown event”和“没有任何 shutdown handler” [E: packages/coding-agent/src/core/extensions/runner.ts:192] [E: packages/coding-agent/src/core/extensions/runner.ts:196] [E: packages/coding-agent/src/core/extensions/runner.ts:197] [E: packages/coding-agent/src/core/extensions/runner.ts:200]。

## 跨包边界

[spine.extension-lifecycle](../../spine/extension-lifecycle.md) 是跨文件生命周期总览: 它把 extension discovery/load、`ExtensionRuntime`、`ResourceLoader`、`AgentSession._buildRuntime()` 和 runner binding 串起来;本节点只详写 `runner.ts` 内部的 binding/context/dispatch 规则 [I]。

[surface.extensions.events](../../surface/extensions/events.md) 是面向 extension 作者的 event API 节点: 它应解释每个 hook 的 public contract;本节点只解释 runner 如何执行这些 handlers、如何组合结果、如何处理 error [I]。

[ref.coding-agent.extension-events](../../reference/extension-events.md) 是 event union/catalog 节点: 它应枚举 `ExtensionEvent` 的所有 event type;本节点不会完整列举类型 union, 只覆盖 runner 中出现的 dispatch 分支 [I]。
