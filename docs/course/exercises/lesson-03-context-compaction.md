## 机制层（有标准解，但答案不在课文里）

### 推演 1 · 一轮内部撑爆，但水位线在尾巴里 `[决策一 / 三 / 四]`

设 codex 一侧。某一轮 `run_turn` 进到 sampling 主循环，模型连续派工具、来回了很多拍。在某一次 sampling 跑完的那一刻，状态是这样的：

- `token_limit_reached` 为真（活跃 token 撞上限了）；
- `needs_follow_up` 为真（模型还没说完，本轮没结束，它要继续干）；
- 此刻历史的**末尾**正躺着一条刚返回的、巨大的 `Read` 工具结果（某个几万 token 的大文件全文），它在「最后一条真实 user 消息」**之后**；
- 这一轮一开始注入的初始上下文（环境、权限、工具清单）早在历史靠前的位置，中间隔了几十轮。

把这台机器从「这次 sampling 跑完」一步步走到「压完接着 follow-up」，逐拍说清：

1. 触发的是四个触发点里的哪一个？它用的注入模式是 `DoNotInject` 还是 `BeforeLastUserMessage`，为什么**这个时机只能用这一个**、用另一个会出什么事？
2. `build_compacted_history` 收集要保留的近期 user 消息时，那条**末尾的巨型 `Read` 结果**会不会被原样保留进 replacement history？说清它进不进、为什么——这直接决定压完到底剩多少。
3. 这次压缩要把初始上下文插回去。插点选在哪？为什么是那个位置而不是直接追加到末尾？如果这一轮**根本没有**「最后一条真实 user 消息」（比如本轮的触发完全来自工具循环、还没有新的用户输入），插点回退到哪？
4. 压完，`reference_context_item` 被设成什么、`history_version` 发生什么？为什么这两件事必须在「替换历史」的**同一个动作**里一起做，分开做会漏出什么？
5. 最后一拍：压完模型接着 follow-up，它看到的历史是「初始上下文 + 近期 user + 摘要（当 user 消息压末尾）」。它下一句话开始生成时，付的是缓存命中价还是全价？为什么？

### 量化 1 · 压缩省的 token 和压缩炸的缓存，放进同一笔账 `[决策一 / 二，缓存接第 9 课]`

课文反复说压缩是「双重付费」：付信息损失，还付一次缓存重建。这道题逼你把第二笔付费**算清楚**，并据此给一个你敢写进代码的目标残留。

设：claude 一侧，模型标称窗口 `W = 200k`、最大输出 `16k`（小于 20k）。某次历史涨到 `H = 190k` 触发压缩。压缩前这 190k 里，前缀缓存基本是热的（前面几十轮一直在命中）。压缩这一刻的动作是：把历史前段换成摘要，留一条尾巴 `T`，压完总残留 `R = 摘要(≈2k) + T`。设输入 token 全价 `p`/token，缓存命中读价是全价的 `0.1×`（即 `0.1p`/token，本课假设，第 9 课会核实 DeepSeek 实际比例）。

先把三件事各自算出量级，再回答硬问题：

1. **先算阈值**：这次压缩的触发阈值是多少（写出 `有效窗口` 和 `压缩阈值` 两个数，列式子）？190k 是怎么越过它的？
2. **这一炮缓存重建到底炸的是哪一段、贵在哪？** 很多人想当然以为「炸的是固定的静态前缀（system prompt + 工具 schema）」，于是觉得损失是固定的一小块。这是隐藏账，算错就全错了。说清楚：压缩改写历史后，**作废的缓存到底是哪一段**？压缩后的第一轮，那段重算付的是 `0.1p` 还是 `p`/token？把这一轮相对「没压、缓存全热」多付的钱写成一个跟 `R` 有关的式子。
3. **`R` 这个旋钮同时拧动两个痛点。** 用 1 和 2 的结论说清：`R` 取大（尾巴留长）会让①这一炮缓存重建更贵、②离下次触发更近。把「离下次触发还有多远」也写成跟 `R`、阈值有关的式子。
4. **给一个你敢写进代码的目标残留 `R`，并为它辩护。** 不要拍一个固定数字，给一条**规则**外加它产出的 `R` 量级。然后回答课文逼你想、但没替你说的点：如果你压完实测 `R = 150k`，这是「压缩本就该剩这么多」还是一个**症状**？是症状的话，它指向哪里出了问题、你该先去拧哪个旋钮而**不是**再压一次？（提示：摘要本身有多大？190k 摘出来能有几 k？那 150k 是谁？）

> 数字随假设可变，结论必须一致。

### 破 1 · 压缩跑完，五条安全底线全过，历史却把模型带沟里 `[决策五，接决策三 / 四]`

课文把决策五的五条底线立成「验收清单」：① 不切开 tool_use / tool_result 对；② 压缩请求超限能降级重试；③ 重试有上限会熔断；④ 插初始上下文有回退链；⑤ 先持久化后替换。读完很容易得到一个推论：

> **「只要这五条全过，压缩产出的历史就是安全的、模型读了不会出错。」**

把这个推论**破掉**。构造一段具体的压缩后历史，让它**逐条满足这五条底线**（配对不破、没孤儿、落了盘、版本号也自增了、初始上下文也插回去了——结构上无可挑剔），**但模型读了之后会做出错误动作**。说清楚：

1. 你的反例踩在哪里——是摘要内容本身（语义层），还是某个该失效却没失效的状态（决策四那张清单里的某一条）？给一个最锋利的：让**摘要诚实、配对完整**，坏只坏在「一个基于压缩前历史建立的状态没跟着重置」。
2. 由此说清：决策五这五条底线**实际保证**的是什么、**不**保证什么？它保证的是历史「形状自洽」（normalize 那一层），还是历史「语义正确 / 状态一致」？这两者的边界画在哪条线上？
3. 决策四里有一条状态，如果压缩后**没清**，会让一段「结构完美」的历史诱导模型干出最危险的事。是哪一条？说清这条没清时，模型会基于什么去做什么。

## 实战层（主菜：欠定、差分、判断——没有「这是哪一课」的标签提示你）

### 故障排查 · 压完没几轮又压，每次都白炸缓存

线上反馈：某些长任务跑到中后段，开始**反复压缩**——压完没多久又触发，一炮接一炮。诡异之处：

- ① 每次压缩**都成功**（不报错、熔断器没跳），不是那种「压缩失败 → 重试 → 又失败」的死循环；
- ② 但每次压完，历史只从阈值上方掉到**阈值下方一点点**就停了，没几轮工具来回又顶上去，于是再压；
- ③ 把压缩后的 replacement history 拉出来看，结构完全合规：边界标记在、摘要在、配对没断、附件也重注入了；摘要本身也写得不错，没丢关键进度；
- ④ 现象只在**带大量文件读写 / 长 shell 输出**的任务上复现；纯对话式的长任务（来回都是短消息）**从不**触发这个反复压。

给出：(a) 你的**排查路径**——依次看什么、用什么**排除**什么（想清楚现象③「结构完全合规、摘要也不错」是个**把你往错误假设引的诱饵**：它在说「压缩本身没坏」，那问题就不在「压缩这个动作」上，而在别处；现象④ 那条「只在文件/shell 重的任务上复现」专门用来排除一整类假设，先想清它排除了什么）；(b) 列出**至少两个**都能产生这组症状的 root cause 假设，并说明你用现象①②③④ 里的哪一条**把其中一个比下去**；(c) 对你选定的 root cause，判定：这是 bug 还是 by-design（注意：这个失败模式课文给了名字，先认出它）；(d) 如果运营提一个硬要求「压一次至少要扛 K 轮不能再压」，你在压缩架构上要动哪、代价是什么？ `[决策一 / 二]`

### 效果优化 · 压完模型「失忆」又「拖慢」，两个投诉一起来，不许换模型

某 deepseek agent 的压缩 works，但用户两个投诉一起来：

- **(A) 压完模型「失忆」**：压缩后模型经常忘记之前读过某个文件的具体内容、或忘了中途试过又放弃的某个方案，于是重复劳动、或问用户「这个文件长什么样」；
- **(B) 压完那一轮明显「卡一下」**：压缩后的第一轮首字延迟肉眼可见地高，之后才恢复。

死约束：**不许换模型、不许加大上下文窗口**（窗口就这么大，压缩必须留）。

针对这两个投诉，各列 **≥2 个** runtime 旋钮 + 效果方向 + **反作用**（调它会让 A/B 里的哪个、或别的什么变差）。投诉 A 至少要覆盖到「尾巴留多长 / kept tail」「附件重注入」「`readFileState` 清不清」这几处；投诉 B 至少要覆盖到「触发阈值贴不贴顶」「目标残留 `R` 留多少」「压缩频率」这几处。

最后两问最关键：

1. A/B 里，**哪一对旋钮一调就互相加剧**？把 kept tail / 目标残留 `R` 调大能直接缓解 A（模型手里留的近期原始细节多、没那么失忆），但它**直接喂大**了 B 的哪个根因？反过来，为压 B（让压完那一轮便宜点、少卡）把 `R` 压到很小，又会怎么反噬 A？把这条耦合写清楚——它正是本课「压缩省成本 ↔ 压缩保稳」互搏的具体形态。
2. 有一个旋钮看起来能**同时**缓解 A 和 B，且不踩上面那条耦合——是哪个？（提示：A 的一部分根因是「该留的运行期信息丢了」，但「重新拿新鲜的拍上去」和「把尾巴留长」**不是同一个**手段，前者几乎不增大 `R`。）说清它为什么能绕开 A/B 的对立。 `[决策一 / 三]`

### 架构设计 · 给 deepseek 设计压缩子系统

给 deepseek 设计一个压缩子系统，**同时**满足三条硬约束：

- **两类触发分开**：一类是「新一轮开始前的预防性压缩」，一类是「一轮内部当场撑爆的应急压缩」，这两类压完对上下文的处理不一样，从一开始就别合成一个函数；
- **压缩家族至少两档**：先有「只刮陈旧工具结果」的轻档，不够再上「整段换摘要」的重档；
- **压完清理是必经步骤**：压缩函数返回后，必有一道清理把「基于压缩前历史算出来的缓存/状态」逐个失效。

用下面 **4 个场景**验证你的设计（含一个跨课边界场景）：

1. 新一轮开始前，历史已经太长，预防性压一次。压完这一轮是「全新一轮」——你的 replacement history 要不要带初始上下文？基线（增量注入参照点）设成什么？为什么这里**不用**在压缩产物里塞初始上下文？
2. 一轮内部，工具来回当场撑爆，应急压一次，压完要在同一个 follow-up 循环里接着采样。这次你的 replacement history 要不要带初始上下文？插在哪？基线设成什么？这跟场景 1 **哪一步**正好相反，为什么？
3. 压缩前，模型读过 `config.ts` 并基于它做了几处编辑；压缩把 `config.ts` 的全文摘要掉了。压完，模型想再编辑 `config.ts`。你的「已读文件状态」清单这时候必须做什么？如果不做，模型会基于什么去改文件、最坏会怎样？这条为什么是决策四里**最反直觉、后果最重**的一条？
4.（**跨课边界，接第 9 课**）你的压缩省下了一大段历史 token，但压缩后的第一轮要为新前缀付一次全价缓存重算。设计上你怎么让上层（缓存协作层）**知道**「我刚改写了历史、把缓存读基线重设到压缩后的新前缀」，而不是让缓存层把压缩后那次 token 骤降误判成一次异常的缓存中断？这道「主动昭告缓存失效」的接口，和「压缩只管缩、自洽性交给统一 normalize 兜底」是不是同一件事？

最后：你的设计里，**复用了课文哪个已有机制**（点名）、**打破了「压缩就是把历史换成摘要、换完就完事」这个 naive 假设的哪一处、必须新增什么**？ `[决策一 / 二 / 三 / 四 / 五]`

## 收口 · 强/稳/自动，压缩这台机器站哪一边（本课牵引题）

把本课五个决策的机制，逐一钉到 **强 / 稳 / 自动** 三性上：自动触发 + 熔断器、压缩家族分档（microcompact → session memory → full）、`buildPostCompactMessages` 锁死顺序 + 附件重注入、压完清理清单（`readFileState` 清空 / `history_version` 自增 / 通知 cache break detector）、决策五五条安全底线。

然后回答主线问题：本课里，压缩这台机器**整体**是在给「强」和「自动」**踩刹车**，还是在**助推**它们？换句话说——压缩本身是个「稳」的护栏机制（拦住「历史无限增长撞墙崩掉」），但它**付的代价**（信息损失 + 炸缓存）又会反噬「强」（模型失忆 = 没那么强）和「省成本」。照这个结论，deepseek 在压缩上的**护栏主要该花在哪里**——是花在「压得更狠更省」上，还是花在别处？

（及格线：能把每个机制各归一性。高分线：看清压缩是一个**「稳」机制，但它自身又内含一对「省成本 ↔ 保稳」的互搏**——压得越狠越省、但模型越失忆越容易在压缩后那一轮出错；指出护栏不该花在「压得更狠」上，而该花在决策四的清理清单和决策五的安全清单上，因为压缩出事**几乎全出在「压完忘了重置某个状态」「压坏了历史形状」**，而不是「压得不够狠」。）

### 热身（对的是第 3 句）

- **1 错**：阈值不是「标称窗口 − 13k」，中间漏了**一整段**。正确是先算**有效窗口** = 模型标称窗口 − `min(模型最大输出 token, 20_000)`（这一段才是给摘要请求留的写摘要空间，常量 `MAX_OUTPUT_TOKENS_FOR_SUMMARY = 20_000`，注意是 `min`、不是无条件 20k）；**然后**压缩阈值 = 有效窗口 − `AUTOCOMPACT_BUFFER_TOKENS(13_000)`。所以总共扣了**两段**：摘要预留 + 安全缓冲。题里把摘要预留那段吞了。`[决策一]`
- **2 错**：微压缩**没删整条 `tool` 消息**，只把它的 `output` 内容换成 `[tool result cleared to save context]` 这类清除标记，**消息壳还在**。为什么不整条删？因为这条 `tool` 消息和它对应的 `tool_call`（同一个 `call_id`）是配对的，整条删掉会留下一个没有结果的孤儿调用，模型会困惑（正是决策五第①条、第 1 课 normalize 要修的那种残状态）。所以做法是**保留配对骨架、掏空内容**——配对关系完好，只是体积归零。`[决策二]`
- **3 对**：这就是 `buildPostCompactMessages` 里 ④ attachments 重注入的本意。plan / skills / 可用 tools / MCP instructions 这些是「模型干活必须知道、但可能被压进摘要里糊掉」的运行期信息，与其指望摘要逐字复述它们，不如压完直接拿新鲜的重新拍上去。（别被带歪去改它——这句是对的。这也正是效果优化里那个「能同时缓解 A 和 B、绕开对立」的旋钮的出处。）`[决策三]`
- **4 错**：恰恰相反。session memory compact **不**走 `compactConversation` 本体，所以它享受不到本体里那次自动 `notifyCompaction`——必须在 `autoCompactIfNeeded` 里**额外单独补调一次** `notifyCompaction`。源码注释专门记了这点（漏了会让约 20% 的 cache-break 事件变成误报）。所以「session memory compact 也会在本体里自动通知一次」是错的；它得自己在外面补。`[决策四]`

### 推演 1

- **第 1 步 触发点与注入模式**：触发的是四个点里的 **④ mid-turn 自动压缩**——判据正是 `token_limit_reached && needs_follow_up` 同时成立（这一轮还没结束、token 已撞上限）。它用的注入模式**只能是 `BeforeLastUserMessage`**。为什么不能用 `DoNotInject`：`DoNotInject` 的语义是「压完本轮结束/下一轮全新，把基线设成 `None`，交给下一轮的正常流程去重注入完整初始上下文」。但 mid-turn 这里**根本没有「下一轮」**——压完要在**同一个 follow-up 循环里立刻接着采样**。如果用 `DoNotInject`，基线被清成 `None`、初始上下文又没当场插回去，那接着采样的这一拍模型手里就**没有初始上下文**（环境、权限、工具清单全丢了），它会瞎调工具或乱来。所以这个时机必须 `BeforeLastUserMessage`——当场把一份新鲜初始上下文重建出来插回历史。
- **第 2 步 末尾的巨型 `Read` 结果进不进保留区**：进。`build_compacted_history` 收集近期 user 消息是**从最近往回倒挑**、按 `COMPACT_USER_MESSAGE_MAX_TOKENS = 20_000` 预算保住最近的对话。但这里要看清：那条巨型 `Read` 结果挂在最近的轮次里，它属于「被保留的近期尾巴」那一段。**这正是这道题的核心**——压完剩多少 = 摘要（小，约 2k）+ 这条没被截断的巨型 `Read`（大）。**摘要是小头，真正决定剩多少的是这条尾巴里的大块输出**。所以这一轮压完，残留不会是健康的 20–30k，而是被这条 `Read` 撑得很高。这不是压缩的正常产出，是个**症状**：尾巴被未截断的大块工具输出撑爆了。正确的上游修法是先让微压缩 / 工具输出按 policy 截断把这条大块刮掉，再压。
- **第 3 步 插点与回退链**：初始上下文插在 **replacement history 里最后一条真实 user 消息之前**。为什么是这里、不是直接追加末尾：因为要让「环境设定 / 权限 / 工具清单」出现在**用户那句话之前**，符合「先有环境、再有用户提问」的自然顺序，模型读起来才顺（也对齐模型被训练时看到的顺序）。如果这一轮没有「最后一条真实 user 消息」，回退链是：**回退到 summary / compaction item 之前 → 再不行追加到末尾**。要点是**永远有个能落地的位置**，不会因为历史形状特殊就插不进去（决策五第④条）。
- **第 4 步 基线与版本号**：压完 `reference_context_item` 被设成**当前 turn context**（不是 `None`——因为初始上下文已经当场插回历史里了，基线要对齐这个新状态）；同时 `history_version` **自增 1**。为什么这两件事必须在「替换历史」的同一个动作（`replace_compacted_history` / `ContextManager::replace`）里一起做：因为替换历史、重设基线、自增版本号是**同一次状态跃迁的三个面**。分开做会漏出**中间态**——比如历史换了、但基线还指着压缩前的旧参照点，或版本号没自增、某个持有旧版本号的缓存比对不出「历史被换过了」于是继续用作废的计算结果。版本号自增的妙处正是：任何持有「我见过的历史版本号」的地方，一比对就知道历史被换过了、基于旧版本算的东西作废——比「压缩时记得手动通知每一个缓存」更难漏。
- **第 5 步 缓存价**：付**全价**。压缩改写了历史、前缀作废，压缩后接着采样的这一拍要为**新前缀**（压缩后剩下的那份历史，含被巨型 `Read` 撑大的尾巴）付全价重算。从下一拍起，这份新前缀又变成可命中的稳定前缀，缓存重新滚起来。`[决策一 / 三 / 四]`

### 量化 1

> 解 = 算对两笔账（阈值 + 缓存重建炸的是哪一段）+ 看穿 R 是同一个旋钮 + 认出「剩 150k」是症状不是产出。数字随假设可变，结论必须一致。

- **第 1 步 阈值**：有效窗口 = `W − min(最大输出, 20k)` = `200k − min(16k, 20k)` = `200k − 16k` = **184k**；压缩阈值 = `184k − 13k(buffer)` = **171k**。`H = 190k > 171k`，越过阈值触发。（注意 16k < 20k，所以摘要预留按 16k 扣，不是 20k——这是热身第 1 句考的那个 `min`。）
- **第 2 步 炸的是哪一段、贵在哪（隐藏账）**：**不是固定的静态前缀**。压缩的动作是**从历史中间改写**——把前段几万 token 换成摘要。而 prompt 缓存只认「从头逐字节一致的前缀」。改写点**往后**的前缀全变了，所以作废的是**改写点之后的整段历史前缀**（不是只有 system prompt + 工具 schema 那一小块固定前缀，那块可能反而不变）。压缩后第一轮要为**整个新前缀 `R`** 付**全价 `p`**（不是缓存命中价 `0.1p`，因为它是全新前缀、缓存里没有）。相对「没压、缓存全热」的对照（那一轮整段读缓存只付 `0.1p × R`），这一轮多付的 ≈ `R × p − R × 0.1p = 0.9 × R × p`。**关键：这笔多付的钱跟 `R` 成正比**——剩得越多，这一炮缓存重建越贵。
- **第 3 步 R 同时拧两个痛点**：
  - **痛点①（这一炮多贵）**：上面已得 ≈ `0.9 × R × p`，正比于 `R`。
  - **痛点②（离下次触发多远）**：下次触发还要再涨 `(阈值 − R)` 才到。`R` 越大，`阈值 − R` 越小，**离下次触发越近** → 越容易抖动（压完没几轮又超）。`R = 150k` 时离 171k 阈值只剩 21k 余量，几轮大工具输出就顶上去了；`R = 25k` 时还剩 146k 余量，很久不用再压。
  - 所以 `R` 是**同一个旋钮**：拧小它，痛点①（这一炮便宜）和痛点②（余量大、不抖动）**一起缓解**。
- **第 4 步 给 R 的规则 + 认出 150k 是症状**：
  - **规则（示例，关键是可辩护）**：`R ≈ 摘要(≈2k) + kept tail(留最近若干轮、且每条工具输出已按截断 policy 刮过) + 重注入的运行期信息(小几 k)`，**目标量级 20–30k**，让余量留到 140k+。判据是「kept tail 只留**截断后**的最近几轮，绝不让单条未截断的大块工具输出进尾巴」。
  - **「剩 150k」是症状不是产出**：算笔账——190k 历史**摘要出来能有多大**？摘要本就是把一大坨浓缩成一小段，几百到两三千 token。所以正常压完 `R` 的小头是摘要、绝不可能因为摘要而剩 150k。剩 150k 只有一个解释：**你的 kept tail 就是 150k**——最近几轮塞了大块没截断的工具输出（某次 `Read` 了巨型文件、某条 shell 吐了几万行）。这时正确动作**不是再压一次**（再压只是再炸一次缓存、治标不治本，而且摘要也压不动那条原样躺着的大块输出），而是**先去查尾巴**：上游的微压缩 / 工具输出按 policy×1.2 截断是不是没把这条大块刮掉。修上游让尾巴瘦下来，`R` 自然回落到健康量级。`[决策一 / 二，缓存接第 9 课]`

### 破 1

- **构造**：让压缩诚实、配对完整、五条底线全过，唯独**漏清「已读文件状态」（claude 的 `readFileState`）**。具体：压缩前模型 `Read` 了 `config.ts`（拿到全文）、并基于它做了几处编辑；`readFileState` 里记着「`config.ts` 已读，是 v1 版本」。现在压缩成功——摘要诚实地写了「已读 config.ts 并改了 3 处」，配对没断、没孤儿（决策五①过），压缩请求没超限（②③不触发也算过），初始上下文回退链没用上但在场（④过），rollout 先落了盘（⑤过），`history_version` 也自增了。**结构上无可挑剔。** 但 `readFileState` **没清**，还标着「`config.ts` 已读、v1」。
- **后果（坏在哪）**：`config.ts` 的全文本来躺在历史里（被 `Read` 工具结果记着），压缩把它**摘要掉了**——模型手里现在只剩摘要里的「改了 3 处」这种只言片语，**看不全 v1 全文了**。但 `readFileState` 还告诉系统「模型已经读过 config.ts、是 v1」。于是模型想再编辑 config.ts 时，系统**不会逼它重读**（因为状态显示「已读」），模型就会**基于它实际上已经看不全的 v1 内容去生成编辑**——极可能基于过时/残缺的认知**覆盖**掉文件，造成数据丢失。这是「压缩有损」这个根本矛盾最危险的一个后果。
- **第 1 步 反例踩在哪**：踩在**决策四那张「失效与重置」清单的一条没执行**——不是摘要语义层（摘要是诚实的），不是历史形状层（配对完整、normalize 挑不出毛病），而是**一个基于压缩前历史建立的状态（`readFileState`）没跟着重置**。这是最锋利的反例，因为它让你看清：底线全过 ≠ 安全。
- **第 2 步 五条底线的边界**：决策五这五条**实际保证**的是历史**「形状自洽」**——送进模型的是一份配对完整、没孤儿、能落地、改写过程不丢状态的历史（这层归 normalize / 持久化 / 回退链管）。它们**不保证**历史**「语义正确 / 状态一致」**——不保证摘要没误导模型，更**不保证「所有基于压缩前历史建立的外部状态都跟着失效了」**。「形状自洽」和「状态一致」是两条不同的线：前者是决策五的活，后者是**决策四（失效与重置）**的活。把决策五全过当成「压缩安全」，正是把「形状对」误当成「状态对」。
- **第 3 步 该清没清的那条**：就是 **`readFileState`（已读文件状态）**。课文专门把它单拎出来强调，正因为它最反直觉、后果最严重：压缩把文件全文摘要掉了，还留着「已读、是 xx 版本」的标记，模型会基于看不全的内容去改文件。压完**必须 `.clear()`**，逼模型用到时重新 `Read` 最新版本。（同类还有 `loadedNestedMemoryPaths`，但 `readFileState` 是后果最重的那条，因为它直接通向「基于过时内容覆盖文件」。）`[决策五，接决策三 / 四]`

### 故障排查 · 压完没几轮又压

- **(a) 排查路径（差分，先拆诱饵）**：现象③「结构合规、摘要也不错」会把你引向「压缩动作本身有 bug」这个**错误假设**——但它恰恰在说**反话**：压缩这个动作（生成摘要、拼 replacement history、配对、附件）**全是好的**。所以问题**不在「怎么压」，而在「压到多低就停」**。第一步不是去查压缩逻辑，而是去看**压完的残留 `R` 有多大**：把每次压完的 `R` 和触发阈值放一起比——如果 `R` 只比阈值低一点点（掉到阈值下方一点就停），那这就是课文点过名的失败模式**压缩抖动（compaction thrashing）**：压完没降多少 → 缓存白炸一次 → 没几轮又超 → 再压再炸。现象② 直接量出了这个特征（「掉到阈值下方一点点就停」）。现象④（只在文件/shell 重的任务复现）是关键差分——它**排除了「压缩目标残留参数配得太高」这一整类纯参数假设**：如果是阈值/残留常量配错，纯对话长任务也该抖；它只在大块工具输出多的任务上抖，说明**抖动的来源是尾巴里的大块未截断输出把 `R` 撑高了**，不是某个常量配大了。
- **(b) 至少两个 root cause 假设 + 用现象比下去**：
  - **假设甲：目标残留 `R` 没设死，自由浮动到刚好卡在阈值底下。** 即「压完剩多少」由「丢水位线之前 / 留水位线之后」自然决定、没有一个独立的「压到多低才停」的目标，于是 `R` 浮到刚好 ≤ 阈值就不再压。**现象④（只在文件/shell 重的任务复现）把它部分比下去**：如果纯粹是「没设目标残留」，纯对话任务也会浮到阈值底下抖；只在大块输出任务复现，说明根因更具体——
  - **假设乙：kept tail 里有未截断的大块工具输出，把 `R` 直接撑爆。** session memory compact 丢水位线之前、留水位线之后的尾巴，但**水位线之后那段尾巴本身就太长**（某次 `Read` 巨型文件、某条 shell 吐几万行原样躺在尾巴里），光丢水位线之前的根本不够，压完 `R` 还很高——甚至高到 session memory compact 直接「仍超阈值 → 返回 null」逼 full compact 兜底，full compact 也压不动那条**原样躺着的大块输出**（摘要摘的是对话和决策，不是把一条 shell 输出重写短）。**现象④ 正面支持乙、现象③ 是诱饵**（结构合规说明压缩动作没坏，坏在喂给它的尾巴）。两个假设的共性根因：**「压完剩多少」被尾巴里的大块输出绑架了，而上游没有先把这些大块截断**。
  - （甲是「没有目标残留这个旋钮」，乙是「即使有旋钮，尾巴里的大块输出也让它拧不动」。乙更贴现象④，是主因；甲是放大器。）
- **(c) bug 还是 by-design**：这是**压缩抖动（compaction thrashing）**这个**失败模式**——本质是**设计缺陷**（缺了「目标残留」这第二个数字、且上游没截断大块工具输出），不是「压缩动作」的 bug。课文说得很直白：「绝不能让压完剩多少自由浮动到刚好卡在阈值底下——那等于亲手设计了抖动。」所以判定：**by-design 的设计缺陷**（不是某行代码写错，而是策略上漏了第二个数字 + 漏了上游截断），要在策略层补，不是去修压缩函数。
- **(d) 「压一次至少扛 K 轮」**：核心是把**单一阈值改成两个数字**——触发阈值（高，贴窗口顶）+ **目标残留 `R`（低，留大余量）**，并保证 `阈值 − R` 大到足够扛 K 轮的平均增量。配套必须动两处：① **上游先截断**：让微压缩 / 工具输出按 policy 截断**先把尾巴里的大块输出刮掉**，否则 `R` 永远被大块撑高、你设的目标残留拧不下去；② **残留还高时先查尾巴、别急着再压**（再压只是再炸一次缓存）。代价：① kept tail 留得短 → 模型手里近期原始细节变少，有「失忆」风险（这正好通到效果优化那条 A↔B 耦合，要权衡）；② 上游截断更激进 → 偶尔会把某个其实还要用的大块输出提前刮掉，模型要重读；③ 多一个目标残留常量要调、要测。`[决策一 / 二]`

## 评点（效果优化 / 架构设计 / 收口——自评用，非标准答案）

### 效果优化

**能动的旋钮（对着 A 失忆 / B 压完那轮卡）**

- **kept tail / 目标残留 `R`。** 把尾巴留长（`R` 大）→ 模型手里近期原始细节多、没那么失忆（**缓解 A**）。**反作用**：直接喂大 `R` → 压缩后第一轮新前缀更大 → 全价重算更贵、首字更慢（**恶化 B**）；且离下次触发更近（抖动）。
- **附件重注入（attachments）。** 压完用 `buildPostCompactMessages` 把当前 plan / 可用 skills / tools / MCP 拿新鲜的重注入 → 模型不丢「该知道的运行期信息」（**缓解 A 的一部分**：丢的不是文件细节而是「我能用什么工具、当前计划」时，这个最有效）。**反作用**：附件本身有体积，注太多会把 `R` 顶高一点（轻微恶化 B）——但远比把整条尾巴留长便宜。
- **`readFileState` 清不清。** 压完清空它 → 逼模型重读最新版本，避免基于看不全的内容覆盖（这是**保正确性**，不直接缓解 A，反而会让模型「重读一次」显得更失忆一点）。**反作用**：不清它后果严重（破 1 那个数据丢失），所以这个旋钮**只能往「清」拧**，不是用来优化 A 的——它是安全底线，列在这里是提醒你别为了「显得不失忆」去保留它。
- **触发阈值贴不贴顶。** 阈值越贴窗口顶 → 压得越晚、一次压缩成本摊到越多轮、压缩越不频繁（**缓解 B 的频率维度**）。**反作用**：贴太顶留给摘要请求的余量不够，压缩请求自己可能因没地方写摘要而失败。
- **目标残留 `R` 压小。** `R` 小 → 压缩后第一轮新前缀小、全价重算便宜、首字快（**缓解 B**）、余量大不抖动。**反作用**：直接恶化 A（尾巴短、模型失忆）。

**① 一调就互相加剧的一对（核心耦合）**：**kept tail / 目标残留 `R` 同时是 A 和 B 的旋钮，但方向相反。** 把 `R` 调大缓解 A（细节多、不失忆），却直接喂大 B（压缩后新前缀大 → 全价重算更贵更慢、还更易抖动）；把 `R` 压小缓解 B，又恶化 A。**这正是本课「压缩省成本 ↔ 压缩保稳」互搏的具体形态**——`R` 是它们共用的同一个旋钮，往哪拧都有一方变差，没有「都满意」的取值，只有按业务取舍的平衡点。
**② 能同时缓解 A 和 B、绕开对立的旋钮**：**附件重注入（attachments）。** 它能绕开对立的原因：A 的失忆有两类，一类是「忘了文件具体内容/试过的方案」（这只能靠留长尾巴 = 喂大 `R`，逃不掉对立），**另一类是「忘了当前计划 / 能用什么工具 / 技能」**——后者**不必靠留长尾巴**，压完直接拿**新鲜的** plan/skills/tools 重注入就能补，而这批附件体积很小，几乎不增大 `R`、不恶化 B。所以「重新拿新鲜的拍上去」和「把尾巴留长」**不是同一个手段**：前者用很小的成本补回了一大类失忆，绕开了 A↔B 那条对立线。看不出这一点的人会把所有失忆都怪到「尾巴留太短」上、于是只会去喂大 `R`、然后撞 B。
**陷阱**：列了旋钮不写反作用；把 `readFileState` 当成「优化 A」的旋钮去保留它（那是安全底线，只能往清拧）；没看穿附件重注入能绕开 A↔B 对立、把所有失忆都归到尾巴长度上。

### 架构设计

**强答案应触及的维度**

- **(两类触发从一开始就分开)** 设计第一刀就该是「预防性压缩」和「应急压缩」两条路径、各带自己的注入模式，**不合成一个函数**。理由就是场景 1/2 的对立：它们压完的「时机」不同（新一轮 vs 接着同一轮），导致「要不要带初始上下文」「基线设成什么」截然相反——一个函数表达不出来。
- **场景 1（新一轮前的预防性压缩）**：replacement history **不带**初始上下文；基线（`reference_context_item` 等价物）设成 **`None`/清空**。为什么不用塞：因为压完是**全新一轮**，下一个 regular turn 会**自然地重新注入一份完整初始上下文**（基线被清成 None，无基线 → 走全量注入，这是第 1 课 C2 的机制）。在压缩产物里塞它纯属浪费。对应 codex 的 `DoNotInject`。
- **场景 2（一轮内应急压缩）**：replacement history **必须带**初始上下文，插在**最后一条真实 user 消息之前**（回退链：summary/compaction item 前 → 末尾）；基线设成**当前 turn context**。和场景 1 正好相反的那一步是「要不要在压缩产物里塞初始上下文」——场景 1 不塞（交给下一轮），场景 2 必须当场塞（**没有下一轮**，压完要在同一个 follow-up 循环里立刻接着采样）。对应 codex 的 `BeforeLastUserMessage`。能把场景 1/2 这对镜像关系讲清，是这题的核心。
- **场景 3（已读文件状态）**：「已读文件状态」清单这时候**必须 `.clear()`**——把 `config.ts` 的「已读、v1」记录清掉，逼模型用到时重新 `Read` 最新版本。不做的话：模型会基于它**实际上已被摘要掉、看不全的 v1 内容**去生成编辑，最坏**基于过时/残缺认知覆盖文件、丢数据**。这条最反直觉、后果最重，因为压缩**把文件全文摘要掉了、却留着「已读」标记**，制造一个「自以为读过、其实手里只剩摘要」的危险错位。（这正是破 1 那个反例。）
- **场景 4（跨课，接第 9 课·主动昭告缓存失效）**：要给缓存协作层一个**主动通知接口**（claude 的 `notifyCompaction` / cache break detector）——压缩成功后**主动告诉缓存层「我改写历史了，把缓存读基线重设到压缩后的新前缀」**，让它别把压缩后那次 token 骤降误判成异常的缓存中断。还可叠一个 codex 式的 `history_version` 自增让旧版本自动失效（更难漏）。**它和「压缩只管缩、自洽性交给 normalize」不是同一件事**：normalize 兜的是**历史形状自洽**（补 aborted、删孤儿、剥图），是「形状」层；`notifyCompaction` 昭告的是**缓存/外部状态失效**，是「状态」层。两层正交——决策五管形状、决策四管状态，别混。能区分这两层是高分点。
- **复用 / 打破**：**复用**了「触发分两类 + 两种注入模式（`DoNotInject`/`BeforeLastUserMessage`）+ 压缩家族分档 + `buildPostCompactMessages` 锁死顺序 + normalize 兜底自洽」。**打破**的 naive 假设：「**压缩就是把历史换成摘要、换完就完事**」——必须**新增**一整套决策四的「失效与重置」清单（清 `readFileState`、清各类历史相关缓存、自增 `history_version`、通知 cache break detector）+ 决策五的安全清单。换摘要只是压缩的**一半**；另一半是「把所有基于压缩前历史建立的状态彻底清干净」，naive 设计正是漏了这后一半。
- **陷阱**：把两类触发合成一个函数（于是场景 1/2 表达不出）；场景 1 也往压缩产物里塞初始上下文（浪费、且和「下一轮自然重注入」打架）；场景 3 留着「已读」标记不清（=制造覆盖文件的数据丢失）；把场景 4 的 `notifyCompaction`（状态层）和 normalize（形状层）混为一谈，以为 normalize 会顺手修缓存基线。

### 收口

- **逐机制归性（参考）**：
  - **自动触发 + 熔断器** → **自动 + 稳的复合**。自动触发是「自动」（不用人盯着喊压），熔断器是「稳」（拦住压缩失败死循环烧钱）。
  - **压缩家族分档（microcompact → session memory → full）** → 偏**省成本 / 稳的地基**。分档让「能轻轻刮一层就别动大手术」，省 token、少炸缓存；它本身不直接是「强」，是把压缩这台机器的代价压到最低。
  - **`buildPostCompactMessages` 锁死顺序 + 附件重注入** → **稳 + 护「强」**。锁死顺序是「稳」（拦住排错把工具调用/结果切散）；附件重注入是在**补救压缩对「强」的反噬**（压完别让模型丢了运行期信息）。
  - **压完清理清单（`readFileState` 清空 / `history_version` 自增 / 通知 cache break detector）** → 纯 **稳**。全是在拦「基于压缩前历史的状态没跟着失效」这类最难查的 bug。
  - **决策五五条安全底线** → 纯 **稳**。配对切割 / 降级重试 / 重试上限 / 插入回退 / 先落盘，每条对应一类真实事故。
- **结论（高分线）**：压缩这台机器**整体是个「稳」的护栏**——它拦住的是「历史无限增长撞窗口、API 报错或粗暴截断让模型崩掉」这个致命失败。但它**自身内含一对互搏**：「压得越狠越省成本（炸缓存的代价小、余量大不抖动）」↔「压得越狠模型越失忆、越容易在压缩后那一轮基于残缺认知出错」。所以压缩不是单纯站在「强」或「省」哪一边——**它是用一点「强」（信息损失）和一次「省成本」的代价，换一个「稳」（不撞墙）**；而它内部那对「省 ↔ 稳」的张力（决策一的抖动、决策四的状态失效），决定了它换得划不划算。
- **护栏花在哪（主线落点）**：**不该**主要花在「压得更狠更省」上——那是顺水推舟的冲劲（家族分档、贴顶阈值已经把省做得很足）。该花在**决策四的清理清单 + 决策五的安全清单**上：因为压缩出事**几乎全出在「压完忘了重置某个状态」（`readFileState` 没清 → 覆盖文件）、「压坏了历史形状」（切开 tool 对 → 孤儿）、「压完自由浮动到阈值底下」（抖动）**，而**不是「压得不够狠」**。一句话：**压缩的护栏 = 给「改写历史」这个高危动作配齐「压完把所有依赖旧历史的状态彻底清干净 + 历史形状必须自洽」的两张清单**，这两张清单是压缩最容易出事、也最容易被省略的地方。
- **陷阱**：把某个「稳」机制误挑成「强」（如把附件重注入当「强」——它是在补救压缩对强的反噬，不是把模型变强）；只看到「压缩省 token」就把它归成「省成本」一边，没看穿它内含「省 ↔ 稳」互搏；把护栏投资指向「压得更狠」（那是顺水推舟，真正难查的事故全在「压完没重置状态 / 压坏了形状」）。
