## 热身（四句话，埋了雷——只有一句完全对）

下面四句关于工具系统的话，**恰好一句完全正确，另外三句各有一处错误**。逐句判断：对的指出它对、并补一句它为什么容易被误判成错的；错的指出错在哪、正确说法是什么。

1. 发给模型的工具 schema 里不包含 `isReadOnly` / `isConcurrencySafe` 这类标志位，是因为这些标志位在工具注册时还没算出来，要等装配那一轮才会被填进 schema 一起发出去。

2. 在 codex 里，一个工具如果声明自己支持并行（`supports_parallel_tool_calls` 返回 true），派发它时会取那把 `RwLock` 的写锁；不支持并行的工具取读锁，于是多个串行工具反而能同时跑。

3. claude 的延迟加载里，MCP 工具一律延迟、`ToolSearch` 自己永不延迟；但若某个 MCP 工具显式带了 `alwaysLoad`，它会在「MCP 一律延迟」这条规则之前就被豁免、不延迟。

4. codex 的 `apply_patch` 在定位 `Update File` 的改动位置时，先按补丁里写的行号精确跳到那一行，行号对不上再退化成上下文模糊匹配。

### 推演 1 · 一次回复里四个调用，谁挡住谁 `[决策一][决策三]`

模型在**同一轮回复**里一口气吐出四个工具调用，runtime 收到的顺序如下：

```
① read({ file_path: "/a.txt" })           —— 读 A 文件
② bash({ command: "cat /b.txt" })          —— cat,无重定向
③ bash({ command: "grep foo /c.txt > /c.out" })  —— grep 带输出重定向
④ read({ file_path: "/a.txt" })           —— 又读一次 A 文件
```

已知：`read` 工具声明了并发安全（按入参，读不同或相同文件都安全）；`bash` 工具的并发安全是**按入参求值的函数**——它会解析命令，只读命令判为并发安全、带写动作的判为不安全。runtime 的并发模型就是课文讲的那套（claude 按并发安全性分批 / codex 一把读写锁）。

请回答：

(a) 把这四个调用按 runtime **实际的并发分批**列出来——哪几个会被放进同一批一起跑、哪几个必须独占一批。**先写出每个调用的并发安全判定结果**，再据此分批。

(b) 第 ③ 个调用 `grep foo /c.txt > /c.out`，它的命令名 `grep` 看着像只读，为什么最终被判成不可并行？runtime 是在**哪个时刻**、**拿什么**做出这个判定的？（精确到课文里 T1–T4 那条时间线的某一拍。）

(c) 现在改一个条件：假设第 ③ 个调用的 `bash` 在解析命令时**解析器抛了异常**（比如命令里有诡异的引号配对，shell-quote 解析失败）。这个解析异常会让这次调用的并发判定变成什么？整批的分批结果会怎么变？说清楚 runtime 这么处理背后的安全原则。

(d) **换到 codex 的并发模型重看这同一组四个调用。** codex 不预先「分批」，而是来一个派一个、每个派发前按 `supports_parallel_tool_calls()` 决定取那把 `RwLock<()>` 的读锁还是写锁。假设这四个调用按 ① ② ③ ④ 顺序几乎同时被派发出去，请说清楚：① ② 各取什么锁、能不能同时在跑？③ 取什么锁、它要等到什么条件满足才能真正开始执行？④ 取什么锁、它会不会被 ③ 挡住？最终这四个调用的「能同时在跑」关系，和你在 (a) 里用 claude 分批得到的结论**是否一致**？（关键洞察：claude 的「连续段分批」和 codex 的「一把读写锁」是两套实现，但它们想表达的并发约束是不是同一个？）

### 推演 2 · 第 201 次调用：发现一个长尾工具要花几轮、付几次 schema `[决策四]`

### 破 · 「模型可见 ≠ 可派发」这套记账，防不住的那种越权 `[决策二]`

课文把工具按「谁执行」分了三种（A 本地 / B 转发 / C 提供方托管），并用两份集合记账：**模型可见集 specs**（序列化发给模型）和**可派发集 registry**（runtime 有 handler 能执行）。课文给的安全直觉是：不想让模型用的工具，就放进 `Hidden`——在 registry、不在可见集，模型看不见就调不到。

现在请你**构造一个反例**：一次工具调用，它跑完之后**这套「可见集 / registry」记账每一格都合规**（没有任何「模型调了一个不在可见集里的工具」这种显式越界），**但实际效果是模型间接驱动了一个它本不该直接驱动的能力**。

提示，但不替你拆完：

- 想想 `Hidden` 工具的定义——它「不在可见集、在 registry，runtime 仍可派发」。课文点了三类 Hidden：code-mode 专用、命令拦截、legacy handler。**谁会去派发一个 Hidden 工具？**如果不是模型直接调，那是谁在调？
- 在 codex 里 `is_direct()` 对 `Direct` 和 `DirectModelOnly` **都返回 true**，但 `DirectModelOnly` 的语义是「只在初始模型工具列表里、不进 code-mode 那层嵌套工具面」。反过来想：有没有一条「模型可见的入口工具」，它的 handler 内部会去**派发别的（对模型不可见的）工具**？

请回答：

(a) 描述你构造的这次调用：模型可见的是哪个工具、它的 handler 内部又派发了哪个 Hidden / 不可见的工具、最终落地的真实能力是什么。

(b) 逐格核对：这次调用里，「模型调用的工具」在不在可见集？被实际执行的那个 Hidden 工具在不在 registry？**有没有任何一格的记账被违反？**（结论应当是：没有。）

(c) 既然每一格都合规、却产生了「模型间接驱动了不该直接驱动的能力」，说清楚这套「可见集 / registry」记账**实际保证的是什么**、**不保证的是什么**。它把安全边界画在哪条线上？真正的越权防线应该加在哪一层（点出课文里指向的那一课）。

### 架构设计 · 给 deepseek 设计工具注册表 `[决策一][决策二][决策三][决策四]`

为 deepseek 设计一套工具注册表（registry），要同时满足三条约束，缺一不可：

1. **每轮只看见该看见的**：不同模式（如简单问答模式 vs 完整 coding 模式）、不同环境（联网 / 离线）下，发给模型的工具清单不同；且工具清单字节要尽量稳定以保 prompt 缓存。
2. **新工具热插拔**：运行期接入一个新的 MCP server（带十几个新工具），不重启会话就能让模型用上；但不能让这十几个新工具一次性把 prompt 撑爆。
3. **工具自声明要不要并行**：每个工具自己声明「我这次调用能不能和别的工具一起跑」，注册表 / 派发层据此调度，业务工具的 handler 里不许出现任何锁。

用**三个具体场景**验证你的设计（其中一个必须跨课边界）：

- **场景一**：简单问答模式切到完整 coding 模式，工具清单怎么变？缓存怎么尽量不废？（对应约束 1）
- **场景二**：会话进行到一半接入一个带 30 个工具的 MCP server，模型要用其中第 28 个。从接入到模型真正调用，注册表里发生了什么？（对应约束 2）
- **场景三（跨课边界，接第 6 课）**：模型调用一个「可见 + 可派发」都满足的写文件工具，但当前权限模式要求「写 `/etc` 下的文件必须人工批准」。你的注册表 / 派发管线在哪一拍、用什么信息把这次调用挡下来等批准？（提示：可见、可派发、可执行是**三层**，不是一层。）

结尾逼问两件事：

- 你的设计**复用了本课哪个已有机制**？（点名具体到决策几。）

## 参考解（热身 + 所有机制层题 + 故障排查）

### 热身

**正确的是第 3 句。** 其余三句各错一处。

- **第 1 句，错。** schema 里不含 `isReadOnly` / `isConcurrencySafe` 是对的，但原因说反了：**不是因为「注册时还没算出来、等装配那轮填进 schema」**——恰恰相反，这些标志位**永远不进 schema、也永远不发给模型**。课文 T1–T4 时间线讲得很死：装配（T1）时模型还没给出具体命令，那一刻**根本不需要也不可能**判 readonly；要等模型给出真实入参（T2）之后、执行之前（T3），runtime 才拿着真实命令去**事后求值**这些函数。它们从头到尾是给调度层 / 权限层 / 执行层用的内部元数据，绝不进发给模型的 schema。贯穿原则：**永远不让模型自己声明安全性。** `[决策一]`

- **第 2 句，错（读写锁取反了）。** 在 codex 里，**支持并行的工具取读锁**（`lock.read()`，读锁可多个并存 → 多个并行工具同时跑），**不支持并行的工具取写锁**（`lock.write()`，写锁独占 → 挡住其它所有工具、强制串行）。句子把读 / 写锁的角色对调了，还顺着错下去说出「串行工具反而能同时跑」这种荒谬结论。这把锁的精妙正在于：**用一把 `RwLock<()>` 的读 / 写语义，天然表达了「可并行 = 共享、必独占 = 串行」**。`[决策三]`

- **第 3 句，对。** 这就是埋的雷——它读起来「太细、太绕」，容易让人想当然去「修正」。但它**完全准确**：`isDeferredTool` 的判定**有先后顺序**，`alwaysLoad=true` 的豁免**排在最前面**，先于「MCP 工具一律延迟」这条规则。所以一个带了 `alwaysLoad`（MCP 工具通过 `_meta['anthropic/alwaysLoad']` 设）的 MCP 工具，会在还没轮到「MCP 一律延迟」之前就被判为「不延迟」。`ToolSearch` 自己永不延迟（否则模型连发现工具的入口都没有）也对。容易被误判成错，是因为「MCP 一律延迟」这条太深入人心，让人忽略了它**上面**还压着一条豁免。`[决策四]`

- **第 4 句，错（apply_patch 没有行号）。** `apply_patch` 的 `Update File` **根本不带行号**，定位**只靠 `@@ 上下文` + 旧行（`-` 行）**，再用**模糊 seek**（精确 → trim 尾空白 → trim 两端 → Unicode 标点归一）逐级兜底。句子凭空给它安了个「先按行号精确跳」的步骤——这正是它和 claude `Edit` 的一个关键区别：Edit 靠精确唯一字符串匹配，apply_patch 靠无行号的上下文模糊定位。`[决策五]`

> **命门**：这份热身的雷埋在「最像错的那句其实是对的」。第 3 句的「`alwaysLoad` 先于 MCP 延迟」听起来像是有人故意把规则讲复杂了，但它就是源码里判定顺序的真实形状；而第 1、2、4 句都长得「顺理成章」，恰恰每句藏一处方向性错误（求值时机、读写锁、有无行号）。**别凭「读着顺不顺」判对错，要凭「机制实际怎么跑」判。**

### 推演 1 · 一次回复里四个调用，谁挡住谁 `[决策一][决策三]`

| ① read /a.txt | 读 | **安全** | read 声明并发安全 |
| ② bash `cat /b.txt` | cat、无重定向 | **安全** | 解析命令：纯读，无写动作 |
| ③ bash `grep foo /c.txt > /c.out` | grep + 输出重定向 `>` | **不安全** | 解析命令：有写入重定向 → 判为会写 |
| ④ read /a.txt | 读 | **安全** | read 声明并发安全 |

分批（连续的并发安全工具进同一批，不安全工具独占一批）：

```
批 1: [① read,  ② bash(cat)]   ← 连续两个并发安全 → 同批并行
批 2: [③ bash(grep > )]        ← 不安全 → 独占一批,串行
批 3: [④ read]                 ← 又是并发安全,但它前面是不安全的 ③,断了连续性 → 自己一批
```

**命门在批 3。** 很多人会把 ④ 也算进「并发安全」就和 ① ② 合并，得出「①②④ 一批、③ 一批」。错。分批是**按调用到达顺序的连续段**切的——③ 这个不安全调用横在中间，把前后的并发安全段**切断了**。④ 虽然自己安全，但它前面紧挨着的是不安全的 ③，连续性已断，只能自己单独成批。课文 `partitionToolCalls` 的注释写得很清楚：批要么是「单个非只读工具」，要么是「**多个连续**只读工具」——**连续**二字是核心。

**(b)** 第 ③ 个调用被判不可并行，是在课文 **T3** 这一拍做出的：模型在 T2 给出真实命令 `grep foo /c.txt > /c.out` 之后、执行之前，runtime 拿着这条**真实命令字符串**去调 `isConcurrencySafe(input)`。这个函数解析命令的语法结构，看到 `> /c.out` 这个**输出重定向节点** → 判定「有写入」→ 并发安全返回 false。**命令名 `grep` 说「读」，但结构里的 `>` 说「写」，结构赢。** 判定的依据不是命令名前缀，而是整棵解析出来的命令结构——否则 `grep >`、`cat >`、`ls && rm` 全能骗过去。`[决策一]` 的 `cat > x.txt` 例子是同一个机制。

**(c)** 解析器抛异常时，并发判定**保守降级为「不安全」（false）**。课文原文：`isConcurrencySafe` 抛错（或入参 parse 失败）时，一律当作「不并发安全」处理。后果：③ 这个调用即便本来可能是只读的，只要解析炸了就被当成不安全 → 独占一批 → 串行。安全原则：**绝不让一个解析异常演变成并发副作用。** 宁可错杀（多串行一个、损失一点并行度），也不放过（万一它其实会写、却被当并发安全和别人一起跑，就可能产生交错副作用）。这是「默认从严」在并发这一层的体现——**拿不准能不能并行时，一律按不能并行办。**

**(d) codex 单锁视角——结论和 (a) 完全一致，只是实现不同。**

- **① read、② bash(cat)**：两者 `supports_parallel` 都为 true → 各取**读锁** `lock.read()`。读锁可多个并存，所以 ① ② **能同时在跑**。
- **③ bash(grep > )**：`supports_parallel` 为 false → 取**写锁** `lock.write()`。写锁要求独占——它必须**等所有在持的读锁全部释放**（即 ① ② 都跑完、放掉读锁）之后才能拿到锁、才真正开始执行。换句话说，③ 被 ① ② 挡在锁外等待。
- **④ read**：`supports_parallel` 为 true → 取**读锁**。但它排在 ③ 这个写锁请求之后——写锁未释放前，它拿不到读锁。所以 ④ 会**被 ③ 挡住**，要等 ③ 这个写锁拿到、执行完、释放之后，④ 才能拿读锁开跑。

把「能同时在跑」的关系列出来：`{① ②}` 同时跑 → 都释放后 `③` 独占跑 → 释放后 `④` 跑。这和 (a) 用 claude「连续段分批」得到的 `批1{①②} → 批2{③} → 批3{④}` **完全一致**。

**关键洞察**：claude 的「把连续并发安全调用切成一批、写工具独占一批」和 codex 的「并行取读锁、串行取写锁，让一把 `RwLock` 的读 / 写语义自己排队」，是**两套实现、同一个并发约束**——「只读的可以共享着一起跑，会写的必须独占、且独占点之后的一切都得排在它后面」。读写锁那套的妙处是：你不用显式去「分批」，写锁请求一插进来，**锁的公平排队语义**自动保证了它之后的读请求也得等——`③` 这个写锁天然把 `④` 这个读锁也挡在后面，效果等同于 claude 那个「连续性被 ③ 切断、④ 只能另起一批」。所以 (a) 里那个「④ 为什么不能和 ① ② 并到一批」的反直觉点，在 codex 视角下变成「④ 的读锁排在 ③ 的写锁后面、拿不到」——同一件事的两种说法。

> **命门**：这道题三个坑——(a) 把 ④ 错并进第一批（忽略「连续」被 ③ 切断）；(b) 以为并发判定发生在装配时（其实在 T3 拿到真实命令后）；(c) 以为解析失败会报错中断（其实是静默降级为串行）。三个坑都指向同一句话：**并发安全是「拿到真实入参后、保守地、按结构」事后求值的，不是装配时按命令名猜的。**

### 推演 2 · 第 201 次调用：发现一个长尾工具要花几轮、付几次 schema `[决策四]`

**(a) 最少 2 次模型→API 往返**才能从「想发 issue」到「真正调用 create_issue」：

```
往返 1:
  模型看到: read/edit/bash/tool_search 全 schema + 200 个 MCP 工具只有名字
  模型想发 issue,但 mcp__github__create_issue 没有 schema、调不了
  模型发出: tool_search({ query: "create github issue" })
  API 返回: [ { type:"tool_reference", tool_name:"mcp__github__create_issue" } ]
            —— 历史里出现了这个 tool_reference

往返 2:
  API 在这一轮请求里,把 create_issue 的【完整 schema】展开进去
            (因为历史里有了指向它的 tool_reference,它进入了"已发现"集)
  模型看到: create_issue 现在有完整 schema 了
  模型发出: mcp__github__create_issue({ … })  ← 真正调用
```

**(b) 要看 slack 工具有没有被「发现」过——没有，所以还要再走一次 ToolSearch。**

关键洞察：**延迟工具凭什么进入「已发现 / 已展开」集？——靠历史里出现过一个指向它的 `tool_reference`。** create_issue 之所以在往返 2 能被调用，是因为往返 1 的 ToolSearch 往历史里塞了一个指向 create_issue 的 `tool_reference`。但 slack 那个工具，历史里**从没出现过指向它的 tool_reference**——它自始至终只是「200 个只有名字」中的一个。所以模型要用 slack，**必须再调一次 ToolSearch**（`tool_search({ query:"send slack message" })`），让历史里也出现一个指向 `mcp__slack__send_message` 的 tool_reference，下一轮 API 才会展开它的 schema。**发现是「一个一个发现」的，不是「发现一个就全开了」。**

**(c) 整个过程跑完，那 200 个 MCP 工具里只有 2 个真正占用过完整 schema**：`create_issue` 和 `send_message`——就是被 ToolSearch 搜到、随后展开的那两个。其余 198 个自始至终只有名字。

**对比 naive 方案（200 个全带完整 schema）**：

- **省的是哪一段**：那 198 个用不上的工具的**完整入参 schema**。schema 是工具定义里最占字节的部分（嵌套的 properties、类型、描述），名字只是一个字符串。所以省下的是「198 个工具 × 各自完整 schema」这一大块 prompt token，每轮都省。
- **没省的是哪一段**：① 200 个工具的**名字**仍然每轮都发（延迟工具露名字）；② 被真正用上的 2 个工具，它们的完整 schema 还是付了（只是按需、且只付这 2 个，不是 200 个）；③ 多花了 2 次 ToolSearch 的往返开销（发现的代价）。

所以延迟机制不是「白省」，是**拿「2 次发现往返 + 200 个名字的常驻开销」，换掉「198 个用不上的完整 schema 每轮重发」**。工具越多、用上的占比越低，这笔交换越划算。

**(d)** 如果把 ToolSearch 自己也设成延迟工具，那么首轮模型看到的是「200 个 MCP 工具的名字 + ToolSearch 的名字」——**全都只有名字、全都没 schema**。模型想发现任何工具，得调 ToolSearch；但 ToolSearch 自己也没 schema、调不了；要展开 ToolSearch 的 schema，又得先用 ToolSearch 去搜它自己……**自举死锁：发现机制的入口被自己锁在了门外。** 这就是为什么 `isDeferredTool` 里硬编码一条「ToolSearch 永不延迟」——它是整套按需发现的**唯一引导入口**，必须始终带完整 schema 常驻。

> **命门**：这道题的两个反直觉点——(a) 答案是「2 次往返」不是「1 次」（很多人忘了 ToolSearch 返回的只是 reference、要等**下一轮**才展开 schema、模型那一轮才能真正调用）；(b) 发现是「逐个」的——用过 create_issue 不等于 slack 也被发现了，每个长尾工具要单独被搜一次。把这两点想通，「延迟加载省的到底是哪段、自举入口为什么不能延迟」就全串起来了。

### 破 · 「模型可见 ≠ 可派发」这套记账，防不住的那种越权 `[决策二]`

**先给结论：这套「可见集 / registry」记账，保证的是「模型不能调用它看不见的工具」，但完全不保证「模型可见的工具，其 handler 内部不会去派发别的（模型看不见的）工具」。** 越权恰恰从后一条缝里钻出来。

**(a) 构造的反例**：模型可见集里有一个入口工具，比如 codex 的 code-mode 工具（或任何「handler 内部会再去派发其它工具」的工具）。模型调用这个**可见的**入口工具，给它一段要执行的逻辑；这个入口工具的 handler 在内部，会去**派发若干 `Hidden` 工具**——这些 Hidden 工具（code-mode 专用、命令拦截、legacy handler）**对模型不可见，但在 registry 里、runtime 能派发**。于是：模型从头到尾只「直接调用」了一个它看得见的入口工具，但**实际落地的真实能力**，是那些 Hidden 工具背后的动作。模型间接驱动了它本不该、也无法直接驱动的能力。

**(b) 逐格核对——每一格都合规**：

| 核对项 | 结果 |
|---|---|
| 模型直接调用的「入口工具」在不在**可见集**？ | **在**（它是 Direct / DirectModelOnly，`is_direct()` 为 true，进了 specs）|
| 被实际执行的那些 Hidden 工具在不在 **registry**？ | **在**（Hidden 的定义就是「在 registry、不在可见集」，runtime 能派发）|
| 有没有「模型调了一个不在可见集里的工具」这种显式越界？ | **没有**——模型调的入口工具是可见的；Hidden 工具不是**模型**调的，是**入口工具的 handler**调的 |

**记账每一格都对，没有任何一格被违反。** 这正是这道题狠的地方：合规的记账，挡不住语义上的越权。

**(c) 这套记账实际保证什么、不保证什么、边界画在哪：**

- **实际保证的**：「模型的**直接**调用」只能命中可见集里的工具——模型发不出一个指向不可见工具的调用名（它根本不知道那个名字）。换句话说，它防的是**模型这一跳的可见性**。
- **不保证的**：可见集里的工具，其 handler 内部**能不能、会不会**去派发别的工具。一旦某个可见工具是「派发别的工具」的入口（code-mode、转发器、编排器），模型就能**隔着一层**驱动任何在 registry 里的工具，包括 Hidden 的。
- **边界画在「谁是调用者」上**：记账区分的是「模型可见」vs「runtime 可派发」，它隐含假设「派发的发起者就是模型」。可一旦**派发的发起者是另一个工具的 handler**，这个假设就破了。可见性记账是**第一层闸**（控制模型这一跳能看到什么），但它**不是权限闸**。

**真正的越权防线在哪一层**：在**权限层（第 6 课）**。课文反复强调：一个工具「可见 + 可派发」，真要执行时**还要过权限**——可见、可派发、可执行是**三层**。Hidden 工具被 handler 间接派发时，**最终那次落地的危险动作（写文件、跑 shell）仍要过权限判定**，权限层不关心「这次派发是模型直接发起的还是被别的工具间接发起的」，它只看「这个动作本身要不要批准」。所以防越权的正解不是「指望 Hidden 把工具藏起来」，而是「**任何危险动作，无论被谁派发，落地前都过权限**」。这也呼应课文那条红线：**永远别把破坏性能力做成 hosted / 不可门控的工具。**

> **命门**：学生最容易卡在「我找不到违反记账的那一格」——因为**确实没有**。这道题不是让你找记账漏洞，是让你认清：**可见性记账压根不是为防越权设计的，它防的是「模型直接调用的可见范围」，而越权走的是「可见工具的 handler 间接派发」这条记账管不着的路。** 把「可见 / 可派发 / 可执行是三层」这句话焊进脑子，你就知道安全防线该加在第三层（权限），不该指望前两层。

### 故障排查 · 「同样的改文件请求，时灵时不灵」

**(a) 差分排查路径：**

1. **先看现象 C 这条「证伪一整类假设」的现象**：关掉所有并发、强制全串行后，**B 消失、A 不变**。这一刀干净利落地把两个现象**劈成两类 root cause**：
   - B 与**并发**强相关（关并发就好）→ B 是「并发交错」类问题。
   - A 与**并发无关**（关了并发还在）→ A 是「单次调用自身的状态校验」类问题，跟并行八竿子打不着。
   - **现象 C 排除的是「A 和 B 是同一个并发 bug」这一整类假设。** 没有 C，你很可能把两者当一个 root cause 去查，南辕北辙。
2. **查 A**：现象是「连续两次编辑、第二次报『文件被改过 / 找不到要替换的串』，但中间重读一次就好」。对照编辑工具的守卫：这正是**新鲜度守卫（staleness guard）**触发——第一次编辑改了文件，文件 mtime / 内容变了，第二次编辑还基于「第一次编辑前读到的旧视图」，守卫发现「读之后文件被改过」就拒。重读一次 → 刷新了视图 → 守卫放行。
3. **查 B**：现象是「同一轮里『编辑 utils.ts』和『读 config.json』一起发，编辑有时落空、写进去的是旧版本」。这是**并发分批**出了问题：编辑是写工具、本应不可并行（独占一批），但若它被误判成并发安全、和别的调用并进同一批一起跑，读改写就可能和别的操作交错，基于旧版本落盘。

**(b) A 和 B 不是同一个 root cause。**

- **A 的 root cause = 新鲜度守卫按预期触发**（`[决策五]` 的 staleness guard）。它根本不是 bug——见 (c)。
- **B 的 root cause = 并发分批 / 并发安全判定让一个写编辑进了并行批**（`[决策三]` 的分批 + `[决策一]` 的 `isConcurrencySafe`）。写工具默认 `isConcurrencySafe=false`、本应独占串行；B 出现说明这条默认从严的链路在 deepseek 实现里破了（要么编辑工具被错误声明成并发安全，要么分批逻辑没把写工具单独成批）。

**(c) 现象 A 的「重读一次就好」是 by-design，不是 bug。**

判断依据：编辑工具的新鲜度守卫**就是故意这么设计的**——课文 `[决策五]` 的「共同安全内核」：**永远不相信模型对文件当前内容的认知是最新的。** 第二次编辑基于过期视图，守卫拒掉它、逼模型重读拿到最新内容，正是为了**防止基于过期视图覆盖、酿成数据丢失**。「重读就好」不是绕过 bug 的偏方，而是这套守卫**期望的正确交互**：发现 stale → 大声报错 → 模型重读 → 基于最新视图重试。如果这里**不**报错、默默用旧视图写，那才是真 bug（静默数据丢失）。

**(d) 运营要求「一轮里多个编辑也要正确」，架构上动哪、代价是什么：**

核心约束：编辑是写文件、会改共享状态（文件系统、读状态缓存），课文原则——**会改全局状态的工具默认就别并行**。所以你**不能**简单地把编辑工具声明成并发安全去「让它们一起跑」，那只会把 B 放大。可行方向：

- **方向一（最稳，推荐）**：编辑工具**保持串行**（`isConcurrencySafe=false`），但保证同一轮里的多个编辑**按顺序、一个接一个、每个都重跑新鲜度守卫**——前一个编辑改了文件，后一个编辑的守卫会看到最新 mtime，要么基于最新内容成功、要么 stale 报错让模型重读。代价：同一轮的多个编辑**不能并行**，多文件批量改会慢一些，但**绝不落空**。这其实就是「正确」的定义——「正确」不等于「并行」。
- **方向二（提供方语义）**：给一个**批量编辑工具**（如 MultiEdit / apply_patch 那种「一个调用里跨多文件、多处改」），把「一轮多处改」收进**一次**工具调用内部、由 handler 在一个临界区里顺序施加。代价：要实现一个带「写前重新对照当前文件校验」的补丁施加器（apply_patch 那套：倒序应用避免行号漂移、写前重解析校验）。

要特别避开的坑（claude 的 `contextModifier` gotcha）：如果编辑工具会改「下一轮上下文 / 读状态缓存」这类全局状态，**它绝不能声明并发安全**——因为并发安全工具的 context 改写会被**推迟到整批结束**才应用，顺序无法保证，正是 B 的温床。

> **命门**：这道排查的分水岭是**现象 C**。没看懂 C「关并发后 B 消失、A 不变」是在**把两个 root cause 劈开**，就会把 A 也往并发上扣、或把 B 往 staleness 上扣，越查越乱。看懂 C，剩下的就是把 A 对到新鲜度守卫（by-design）、把 B 对到并发分批（实现 bug），泾渭分明。运营那个硬要求的正解也反直觉：**「让多编辑正确」不是「让它们并行」，恰恰是「让它们老老实实串行、每个都过新鲜度守卫」**——把「正确」和「并行」分开，是这道题真正要带走的那句话。

## 评点（效果优化 / 架构设计 / 收口——自评用，非标准答案）

### 效果优化 · 评点

**投诉甲（贵 + 慢）强答案应触及的维度：**
- **延迟加载 / 发现机制**：核心工具常驻完整 schema、长尾只发名字、ToolSearch 按需展开（`[决策四]`）。效果方向：每轮 prompt 体积骤降 → token 便宜、首字延迟降。反作用：模型用某个长尾工具要多花 1–2 次 ToolSearch 往返（首次发现有延迟）。
- **工具清单排序稳定保缓存**：内置在前、按名字排序、MCP 不插进内置中间（`[决策二]`）。效果方向：prompt 前缀稳定 → 缓存命中 → 省钱省延迟。反作用：约束了工具清单的灵活性（不能随意重排）。
- 高分答案会指出：贵和慢可能是**两个不同的瓶颈**——「贵」主要是 schema 字节多（延迟加载治），「慢」可能是缓存频繁失效（排序稳定治），要分开诊断、别一个药方治两病。

**投诉乙（改错地方 / 漏改）强答案应触及的维度：**
- **报错粒度**：`old_string` 多处匹配时大声报错（errorCode 9：「找到 N 处匹配但 replace_all 为 false」）+ 强制先读 + 新鲜度守卫（`[决策五]`）。效果方向：模型改错时立即收到明确反馈、能自我修正。反作用：每次都要重发 old+new 串、多文件改动啰嗦。
- **换 / 补编辑哲学**：给 apply_patch 式补丁工具（一次跨多文件、紧凑 diff、模糊定位容错）。效果方向：多文件重构一次搞定、对格式漂移容错。反作用：需要一个真正的解析器 + 语法约束 + 好报错才能把模型拽在轨道上，实现成本高。

**耦合题陷阱（必须答对才算高分）**：投诉甲的「延迟加载 / 只发名字」动的是**发给模型的工具集合与规模**；投诉乙若选「换成 apply_patch 这类需要模型产出合法补丁格式的工具」，这个工具的**语法规范文档**本身可能很长——如果它也走延迟加载、首轮只露名字，模型发现它时拿到的 schema（含那份格式说明）会**重新把 prompt 撑大**，与投诉甲的省 token 目标对掐。更隐蔽的一对：**为省缓存而冻结工具清单顺序**（甲）与**热插拔 / 动态增删编辑工具变体**（乙的某些方案）——动一下工具集就抖缓存。强答案要找出这一对、说清取舍（比如：把「常用编辑工具」钉进常驻核心前缀、只让真正长尾的 MCP 工具延迟）。常见陷阱：只把甲、乙各自答完，**没去找两者的耦合**——这道题一半的分在耦合那一问。

### 架构设计 · 评点

**强答案应触及的维度：**
- **约束 1**：明确「每轮装配、按模式 / 环境门控」+「产出『模型可见集 specs』和『可派发集 registry』两份」+「排序稳定（内置 / 常驻在前）保缓存」。复用了 `[决策二]`。
- **约束 2**：明确「新接入的工具进 registry（可派发）、但默认走延迟（首轮只露名字）」+「ToolSearch 按需展开」+「发现工具自身永不延迟」。复用了 `[决策四]`。
- **约束 3**：明确「每个工具声明 `supports_parallel`，派发层一处实现互斥（一把读写锁或一个分批步骤），handler 里零锁」+「默认串行」+「会改共享状态的工具一律串行」。复用了 `[决策三]`。
- **场景三（跨课）高分点**：把「可见 / 可派发 / 可执行」三层讲清——这次调用在可见集（模型看得见）、在 registry（能派发），但派发管线在 PreToolUse / 权限判定那一拍，拿着**模型给出的真实路径 `/etc/...`** 去过权限规则，命中「写 /etc 需批准」→ 挂起等批准。强调**权限是第三层、用的是真实入参、发生在执行前**（呼应 `[决策一]` 的事后求值时间线 + 第 6 课）。

**结尾两问的强答案**：复用机制要点名到决策几（不能泛泛说「复用了课文思路」）；「打破哪个假设、新增什么」的高分答案，往往是发现「naive 的『一份清单 + 每工具一个本地 handler』假设」必须打破，新增「hosted 标记 / exposure 分流」——这正是课文 `[决策二]` 的核心。常见陷阱：①把「可见」和「可执行」混成一层，场景三答不到点上；②约束 3 让每个工具的 handler 自己写锁（课文明确反对——互斥要收口在一处）。

### 收口 · 评点

**及格线**：能说出「稳」靠的核心机制是**「永远不让模型自己声明安全性 / 永远不相信模型对文件当前内容的认知是最新的」**——并指出它既约束了「让 runtime 而非模型来判读 / 写、能否并行、要不要批准」，又约束了「编辑前必须校验文件未过期」。能点出这是「稳」给「强 / 自动」划的边界条件。

**高分线**：进一步说清这两处其实是**同一条边界的两个侧面**——核心都是「**runtime 不把『当前真实状态的判断权』交给模型**」：安全 / 调度的判断权（是读是写、能否并行、要不要批准）不交给模型，文件当前内容的判断权（有没有被改过）也不交给模型。「强」想最大化模型的行动自由、「自动」想最小化打扰，但二者都建立在「模型对世界的认知可能是错的 / 过期的」这个前提上；「稳」就是那条「不论模型说什么，落地前 runtime 自己再核一遍」的边界。**强和自动同向（都想让模型多干、少被拦），稳是它俩的边界条件**——这正是第 1 课收口那句的延续，工具系统是它在「动作面」上的具体兑现。

常见陷阱：①把「稳」说成「多加审批、多停下来问」——那其实牺牲了「自动」，不是边界，是倒退；真正的边界是「runtime 自己核验」而非「把决定推给人」。②只答了「不让模型声明安全性」或只答了「文件新鲜度」，没看出这两者是同一条边界。
