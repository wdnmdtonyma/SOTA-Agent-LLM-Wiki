# 第 10 课 习题：可扩展性

> 配套课文：[第 10 课：可扩展性 —— 让别人不改源码就能往 agent 里加东西](../lesson-10-extensibility.md)

这一课不像前面九课讲「内核自己怎么转」，它讲「内核写好之后，别人怎么不动你一行源码往里加东西」。所以本课的锚点不是 `[决策一..五]`，而是四个接缝加三条横轴：`[接缝一]`（slash 命令与 skills）、`[接缝二]`（hooks）、`[接缝三]`（MCP）、`[接缝四]`（plugins），以及 `[权力分级]`、`[信任分级]`、`[内部 vs 外部]`。卡住时回课文按这套锚点找零件。

这套习题分四层，难度递增：

- **热身**：四句判断，里头**只有一句是对的**，其余三句各错一处。别逢句就改——你要先认出那句对的，再说清另外三句各错在哪。
- **机制层**：有标准解，但**答案不在课文里**。课文给你零件（机制、字段、控制流），题目把这些零件逼到一个课文没跑过的局面，让你在脑子里把机器跑到底。
- **实战层（主菜）**：故障排查、效果优化、架构设计各一道。**没有「这是哪个接缝」的标签**——局面是欠定的，你得自己做差分、自己拆子问题。
- **收口**：把四个接缝收到「权力分级 × 信任分级」这条总纲上，落到 deepseek 的强 / 稳 / 自动。

参考解在最后。每道有标准解的题，参考解里都有一段「命门」，专讲你最可能栽的那一处。先做，做到卡住、做到怀疑自己，再去翻——那一下「原来如此」才是这门课要给你的。

## 热身（四句里只有一句对，埋了雷）

下面四句，关于「这两样东西到底排在哪个里程碑」和「skill 的 scope 到底意味着什么」。**恰好一句完全正确，其余三句各有一处硬伤。** 找出那句对的，并逐句说清错的那三句错在哪、正确表述是什么。

1. MCP 客户端是四个接缝里最划算的一个——接上就能用整个生态的现成工具，自己几乎一行不写。正因为它杠杆最高、收益最大，所以它该被排进 M0，作为可扩展性最先落地的一块地基。

2. 在 codex 里，skill 从仓库、用户家目录、系统内置、管理员四个 scope 一起扫进来；同名 skill 会按「管理员 > 用户 > 仓库」的信任序互相覆盖，最终管理员那份生效。

3. claude 里「用户敲的 slash 命令」和「模型自调的 skill」走的是同一套 markdown 加载器，区别只在放哪个目录、以及 `user-invocable` / `disable-model-invocation` 这两个触发开关——把 `user-invocable` 关掉，这个 markdown 单元就成了只有模型能用的纯 skill。

4. 命令 frontmatter 里的 `allowed-tools` 字段，是「给这条命令发工具权限」的口子——写上它，这条命令的 `!` shell 块就能绕过权限引擎直接跑，所以它是 frontmatter 里权力最大、最危险的字段。

## 机制层（有标准解，但答案不在课文里）

### 推演 1 · 同名 skill 的「四 scope 渲染」与一次误调 `[接缝一]`

一个 codex 用户，在三处都放了一份叫 `deploy` 的 skill（注意是三处独立物理路径、三份不同 `SKILL.md`）：

- 仓库内 `.codex/skills/deploy/SKILL.md`：描述写「部署到本仓库的 staging 环境」。
- 用户家目录 `~/.agents/skills/deploy/SKILL.md`：描述写「部署到我个人的测试集群」。
- 管理员级 `/etc/codex/skills/deploy/SKILL.md`：描述写「按公司流程部署到生产」。

现在请把机器一步步跑到底，回答：

(a) 加载器把这三份 `deploy` 处理成几个 skill 条目进了那份常驻目录？是只留一份（哪一份？）还是三份并列？判定依据是什么——加载器拿什么做去重的键？

(b) 这份常驻目录在喂给模型前要排序，排出来的顺序是什么？谁在前？这个「在前」**是不是**意味着「优先级更高 / 会被优先选用」？

(c) 关键一问：模型在这一轮看到了三个同名的 `deploy`（描述各不同），它判断「该部署了」，然后挑了**仓库那份**（staging）触发。但用户其实想要的是生产部署。请说清：这次「挑错了」**是 scope 覆盖序没生效导致的 bug，还是这套机制本来就不解决的问题？** 如果是后者，那么「让模型在三个同名 skill 里挑对那个」这件事，机制上到底靠什么保证？

别急着说「按管理员优先级覆盖就行」——先想清楚这套加载器到底做不做名字消解。

### 推演 2 · 一条 PreToolUse 钩子想放行被 deny 的命令 `[接缝二]` `[权力分级]`

一个团队这样配置（claude）：

- settings.json 里有一条 deny 规则：`Bash(rm -rf:*)` —— 任何 `rm -rf` 一律拒绝。
- 同时挂了一个 PreToolUse 钩子（command 型，跑一段他们自己写的 shell 脚本）。这个钩子的逻辑是：如果它判断当前 cwd 是一个「临时沙箱目录」，就对工具调用返回权限裁决 `allow`，想让 `rm -rf ./build` 这种清理命令在沙箱里免确认直接过。

现在模型发起了一次 `Bash(rm -rf ./build)`。请把这一拍从钩子触发到工具最终执行 / 被拦，按顺序跑到底：

(a) PreToolUse 钩子能对这次调用做哪几件事？（不止「裁决权限」一件，列全。）

(b) 钩子返回了 `allow`。这条 `allow` 进了权限引擎复核，引擎里既有那条 `deny` 规则、又有钩子的 `allow`，谁赢？为什么？给出这个先后判定的依据。

(c) 那个团队的真实意图——「在沙箱目录里让 `rm -rf` 免确认」——在 claude 这套机制下，**能不能靠 PreToolUse 钩子实现？** 如果不能，那要实现它得动哪一层、动它的代价是什么？

(d) 现在反过来：同样这个钩子，如果它返回的不是 `allow` 而是 `deny`（想额外拦住某个 settings 里没 deny 的命令），这次它的裁决**作不作数**？为什么 `allow` 和 `deny` 在这里待遇不同？

### 破 · 构造一个「装好了、enable 了、却仍是恶意」的扩展 `[接缝四]` `[信任分级]`

课文把「模型只能建议装、用户拍板、host 执行」这套（codex 的 plugin 安装）当成接缝四里最值得抄的一道安全设计——它把「装东西进来」这个动作的权力从模型手里收走了。课文也把 claude 那套「用户配置即信任、enable 了就生效」列为信任分级里**最宽松、最危险**的一档。

现在你来当攻击者，构造一个反例，证明这两道防线**各自的边界在哪**：

(a) 先攻 codex 那道「模型只能建议」：设计一条攻击路径，让一个恶意插件**最终被装进来并启用**，而**全程没有违反**「模型只能发建议、用户点确认、host 执行 git clone」这套流程——也就是说，这套机制跑完之后，结构上完全合规，但坏东西进来了。说清你利用的是这套机制**不**保证的哪一点。

(b) 再攻 claude 那道「用户配置即信任」：一个钩子 / 命令文件，是通过 `git pull` 悄悄进到项目 `.claude/` 目录里的（不是用户自己写的）。在 claude 「enable 了就生效 / 配置即信任」这套下，它会不会静默挂上并运行？codex 给 hooks 加的那道 `trusted_hash` 检查，**恰好**堵的是哪一类这种情况？它**堵不住**的又是哪一类（提示：想想 (a)）？

(c) 收口：把 (a) 和 (b) 摆一起，说清一句话——「模型只能建议」这道防线，真正防住的是**谁**对**谁**的攻击；它从结构上**防不住**的是哪一类攻击。信任分级这条轴，它分的到底是「信任谁来写这个扩展」，还是「信任这个扩展不作恶」？这两件事是不是一回事？

## 实战层（主菜：欠定、差分、判断——没有「这是哪个接缝」的标签提示你）

### 故障排查 · review 命令越用越贵，还偶发拿不到 diff

deepseek desktop 上线了一套用户自定义的命名指令单元（你们的 skill 一等原语，既能用户敲 `$Review` 唤起、也能模型自调）。其中一个叫 `Review` 的单元，frontmatter 里写了 `model: deepseek-v4-pro`（平时用户用 `deepseek-v4-flash` 写代码），正文里有一个内联 shell 块 `` !`git diff HEAD` ``，把 diff 拼进 prompt 再让强模型审。运营报上来三条现象：

- 现象一：用户反馈「自从开始用 `$Review`，这个月账单涨得离谱」，尤其是那些「写了半天代码、最后敲一次 `$Review`」的长会话，涨得最凶；而「开个新会话、第一件事就敲 `$Review`」的，账单正常。
- 现象二：偶发——大约十次里有一两次——`$Review` 唤起后，模型回复里**完全没提 diff 的内容**，像是它根本没看到改动，凭空泛泛而谈。但同一个仓库、同样的改动，重敲一次往往就正常了。
- 现象三：有个用户把这个 `Review` 单元从一个开源 skill 包里装了进来（不是自己写的）。他报告 `$Review` 唤起时，那个 `` !`git diff HEAD` `` 块**根本没跑**，prompt 里 diff 那段是空的——每次都空，不是偶发。

请你：

(a) 给出差分排查路径——依次看什么、用什么排除什么。注意：这三条现象**不一定是同一个根因**，其中**至少有一条**是用来帮你排除一整类假设的。先想清楚哪条现象在帮你排除什么。

(b) 分别给出三条现象各自最可能的 root cause。

(c) 对每条现象判定：这是 bug，还是 by-design（机制本来就该这样）？

(d) 运营提一个硬要求：「`$Review` 必须能稳定升配到强模型，但绝不能让用户账单这样爆。」架构上你要动哪、代价是什么？

### 效果优化 · 一套「装得进、用得上」的扩展体验，两个投诉撞在一起

deepseek 接了 MCP 客户端（M2 已落地），用户能把外部 MCP 服务器接进来用。同时 skill 一等原语也上了。现在有两个体验投诉，都不是「功能不工作」，是「用起来难受」：

- 投诉 A：用户接了三个 MCP 服务器（一个 GitHub、一个数据库网关、一个内部 API），工具一下子多了几十个。模型现在**经常调错工具 / 漏看该用的工具**，而且每一轮 prompt 都被一大坨工具 schema 撑得很长、又慢又贵。
- 投诉 B：用户每次让模型用某个 MCP 工具（比如那个数据库网关的查询工具），都要**一个工具一个工具地点同意**，点到手软；但他其实是信任整个数据库网关的，只是被一条条确认弹窗烦死。

死约束：**这一版不许动模型**（不许换更强的模型、不许改 reasoning 档）。所有手段只能在 runtime 这一侧。

请你：

(a) 针对投诉 A，列 ≥2 个 runtime 旋钮，每个写清效果方向和**反作用**。

(b) 针对投诉 B，列 ≥2 个 runtime 旋钮，每个写清效果方向和反作用。

(c) 关键一问：A 的优化手段里，有没有哪个会**加剧** B 的问题？或者反过来——你为了缓解 A（让工具少露脸）做的某件事，会不会正好让 B（整服务器授权）更难做、或更危险？找出这一对会互相拖累的旋钮，说清这个耦合从哪来。

### 架构设计 · 给 deepseek 排这四个接缝的落地顺序（含一个跨课边界场景）

你是 deepseek 的架构负责人，要给四个接缝（skill 一等原语、hooks、MCP 客户端、plugins / marketplace）排一个落地优先级，写进里程碑（M0 → 后期）。注意一个反直觉的事实：MCP 客户端是四个里**杠杆最高、最划算**的——接上就有整个生态——但它在你们架构里并**不**排得最早。

请你：

(a) 给出你的排序，并对**每一个**接缝说清：它落在哪个里程碑、**为什么**是这个里程碑。重点解释那个反直觉点——为什么「杠杆最高」的 MCP 客户端不排 M0？拿「杠杆」和「依赖」这两种不同的力来解释：是什么**依赖**把它往后拽？（提示：MCP 一接进来，工具数会发生什么？这件事又依赖哪个还没做的设施？HTTP 出网又依赖什么？）

(b) 用 2–4 个具体场景验证你的排序，其中**必须有一个跨课边界场景**——它同时牵动「接缝」和另一课的某个设施，正是这个跨课依赖决定了排期。`接第 6 课`：想想 MCP 工具 / 命令钩子的权限，落在哪。`接第 9 课`：想想 HTTP transport 的出网，落在哪。

(c) plugins / marketplace 你大概率排到很后面（defer）。但课文说，有一件「便宜事」**现在（M0）就该做**，哪怕整个 plugin 生态还是空的。是哪件事？为什么它现在做几乎零成本、却能在将来省一大笔、还能挡掉一整类风险？

(d) 结尾逼问：你这套排序里，hooks 的设计**复用了本课 / 别课的哪个已有机制**（它的 allow/deny 必须臣服于谁）？又**打破了哪个假设、必须新增**什么（命令钩子是任意代码执行的口子，你得给它新增哪道课文里两家共同验证过的检查）？

## 收口 · 权力分级 × 信任分级（本课牵引题）

这一课真正要你带走的，是两条横轴叠起来的那条总纲：**一个扩展的权力越大，放它进来之前的信任检查就该越严。**

把这两条轴各自分档（课文里权力分三档、信任分五档），然后回答：

(a) 把四个接缝（外加命令钩子、MCP 服务器配置、插件捆带的可执行文件这些具体物件）一一**填进权力分级的三档**里——哪些只能往上下文里塞字、哪些能拦能改动作、哪些能跑任意进程。

(b) 把课文给的五档信任（编译期写死 / 托管企业放行 / 用户显式确认过这份配置 / 用户配置即信任 / 模型只能建议）按「从最信任到最不信任」排好，并各举一个本课里的真实例子。注意一个反直觉点：「模型只能建议」为什么排在比「用户配置即信任」**更不信任**的那一端？模型不是内核的一部分吗，怎么比一个外来配置文件还不可信？

(c) 现在把这两条轴**叉乘**：claude 和 codex 在「同样一个权力很大的口（比如命令钩子 = 能跑任意进程）」上，信任检查的严格度差在哪？用一句话概括两家不同的安全姿态。

(d) 落到 deepseek 的强 / 稳 / 自动：你们要「抄 claude 的扩展标准 + 抄 codex 的信任检查」。请把这件事拆成三性——

- **强**（能力）：抄 claude 的什么，能让你的扩展生态从第一天起就不空？
- **稳**（安全底线）：抄 codex 的哪几道检查，是你**不能省**的？每开一个口，第 6 课要补的那道门是什么？
- **自动**：可扩展性这一层，哪些动作可以放给模型自动做、哪些**绝不能**自动（必须人拍板）？这条线划在权力分级的哪一档上？

给出你的及格线和高分线。

## 参考解（热身 + 所有机制层题 + 故障排查）

### 热身

**对的是第 3 句。** 另外三句各错一处：

**第 1 句错在结论「该排进 M0」。** 前半句全对——MCP 客户端确实是四个接缝里最划算的、杠杆最高的 `[接缝三]`。但「杠杆最高」推不出「排得最早」。按你们 annex-A，MCP 客户端排 **M2**，不是 M0。理由是依赖，不是价值：MCP 一接进来工具数暴涨，得先有渐进式工具暴露（也是 M2）压住 prompt；HTTP transport 又要等 M3 的网络代理才能安全出网。**「杠杆 ≠ 排期」**正是这一课要你记住的——决定排期的是依赖链，不是重要性。这一句就是为了埋这个雷。

**第 2 句错在「按信任序互相覆盖、管理员那份生效」。** 多 scope 扫进来是对的（仓库 / 用户 / 系统内置 / 管理员四处），但 codex **根本不做同名 scope 覆盖**这回事 `[接缝一]`。去重只按**物理路径**（同一份 `SKILL.md` 才算一个），**不按名字消解冲突**——四个 scope 里三份不同路径的同名 `deploy` 会**并列存在**，三份都进常驻目录。唯一跟 scope 有关的处理只是**渲染时的排序**（按 scope 排成仓库 → 用户 → 系统 → 管理员，loader 注释自称这是「优先级高的在前」，即它眼里仓库反而排最前），这**不构成**一条「管理员压过用户」的覆盖序。所以「管理员那份生效」是凭空想象出来的——根本没有谁覆盖谁。

**第 4 句错在两处，都踩在「`allowed-tools` 权力很大」这个最容易上当的直觉上。** 错处一：`allowed-tools` **不是**「给命令发工具权限」，它只给这条命令**自己的 `!` shell 块**预先加一条「允许」（alwaysAllow 注入）。错处二（更硬）：它**绝不能让 `!` 块绕过权限引擎**——恰恰相反，每个 `!` 块仍然**整个走一遍权限引擎**，而引擎里 **deny 规则最先判、直接压死「允许」**，敏感路径强制弹窗谁都绕不过，来自 MCP 的命令更是根本不准跑 `!` 块。所以它非但不是「最危险的字段」，反而是个被权限引擎牢牢管住的便利项——最多帮你把「没被 deny 的命令」免去逐次确认。`[权力分级]` `[信任分级]`

**第 3 句对。** 一字不错：同一套 markdown 加载器、区别只在目录和那两个触发开关；把 `user-invocable` 关掉，这个 markdown 单元就成了只有模型能用的纯 skill（用户直接敲会被挡回「这个技能只能由 Claude 调用」）。这就是 claude「用一套机制实现『命名指令单元』、靠标志决定谁触发」的核心 `[接缝一]`。

> **命门**：这四句里，你最可能去「改」第 3 句（因为它信息密度最高、看着最像在堆细节，容易让人疑心哪里有诈），同时最可能「放过」第 1 句（因为「最划算 → 该最先做」太顺了，顺到你不想质疑）。这正是雷埋的地方——**这一课最反直觉的一条就是「杠杆高 ≠ 排得早」**。判断改错题，先找那句「读起来最顺、最符合直觉」的，它往往就是错的。

### 推演 1：同名 skill 的四 scope 渲染 `[接缝一]`

(a) **三份并列，一份都不去掉。** 去重的键是**物理路径**（`path_to_skills_md`）——加载器用一个「已见路径」的集合做 retain，只有路径完全相同的才算重复被剔。这三份 `deploy` 是三条不同物理路径、三份不同 `SKILL.md`，所以三个条目全部进常驻目录、并列存在。**它不按名字去重。**

(b) 排序按 scope rank：Repo=0 在最前，然后 User、System、Admin。所以顺序是 **仓库 → 用户 → 系统 → 管理员**。loader 注释自称这是「优先级高的在前」，意思是它把**仓库**当成「优先级最高」排最前。但——**这个「在前」纯粹是渲染列表里的位置，不构成「会被优先选用 / 权限更高」的任何语义**。模型看到的是三个并列的条目，谁排前面不决定谁被选。

(c) **这次「挑错了」不是 bug，是这套机制本来就不解决的问题。** 加载器的职责到「把三份都呈现给模型、按 scope 排个序」为止；它**不做名字消解、不做覆盖、不替模型决定该用哪份**。「在三个同名 `deploy` 里挑对生产那份」这件事，机制上**只靠两样东西**保证：① 三份 skill 各自 `description` 写得够清楚、够能区分（仓库那份的描述若没写明「staging」，模型就分不清）；② 模型读描述后自己判断。换句话说，**消歧的责任落在描述文本和模型身上，不在加载器身上**。

> **命门**：你最可能脱口而出「按管理员优先级覆盖不就行了」——但这套加载器**压根没有覆盖逻辑**，你想调用的那个机制不存在。这道题逼你认清：codex 的 scope 只是**来源标签 + 渲染顺序**，不是**优先级仲裁器**。「同名按 scope 覆盖」是个非常自然、非常容易脑补出来的设计，但 codex 偏偏没这么做——这正是「读笔记 / 读印象」会出错、必须回到加载器行为本身的地方。

### 推演 2：PreToolUse 钩子放行被 deny 的命令 `[接缝二]` `[权力分级]`

(a) PreToolUse 这个事件本事最大，能干**四件事**：① 拦掉（exit 2 / block）；② 改写入参（updatedInput，比如换掉文件路径）；③ 权限裁决（allow / ask / deny）；④ 注入上下文（additionalContext）。这题只用到第 ③ 件，但你得知道它不止这一件。

(b) **deny 赢，钩子的 `allow` 作废。** 判定依据是权限引擎的复核顺序——**deny 规则最先判**：引擎先查有没有命中的 deny 规则，命中就直接返回 `behavior: 'deny'`，**根本走不到**「采纳钩子 allow」那一步。课文那条底线说得很死：**钩子的 allow 越不过 settings 里的 deny / ask**。`Bash(rm -rf:*)` 这条 deny 命中了，钩子返回什么都白搭。

(c) **实现不了——靠 PreToolUse 钩子永远做不到。** 因为钩子的 allow 在结构上就压不过 deny，而那条 `rm -rf` 的拦截正是一条 deny 规则。真要让「沙箱目录里 `rm -rf` 免确认」，得**动 settings 那条 deny 规则本身**（比如把它从无条件 deny 改成带路径条件、或降级成 ask），代价是：**你松的是一条全局安全规则**——一旦把 `rm -rf` 从 deny 拿下来，它在所有 cwd 都松了，「只在沙箱目录松」这个限定，权限引擎的规则层未必表达得了，你可能被迫接受一个比预期更宽的口子。这就是「钩子只能加严、不能放宽」的代价转嫁：想放宽，只能去动那个唯一有权放宽的层（settings），而那一层的粒度可能不够细。

(d) **`deny` 作数。** `allow` 和 `deny` 待遇不同，正是因为**钩子只能在权限引擎的框子里加严或补充、不能放宽**。钩子返回 `deny`，是在已有规则之外**额外拦一道**——这是「加严」，引擎乐意采纳；钩子返回 `allow`，想突破一条已有的 deny，那是「放宽」，引擎不认。一句话：**钩子的拦截权是单向的——能往严了拦，不能往松了放。**

> **命门**：很多人会在 (c) 卡住，因为「钩子能权限裁决」这句话会让你以为它**能拍板**。它不能。它只是把一个**建议**递给权限引擎，引擎拿这个建议跟自己的规则做合并，而合并规则是**deny / ask 永远压过钩子 allow**。把「钩子能裁决」误读成「钩子说了算」，是这道题专门要纠的错。记住：可扩展性每开一个口，第 6 课的权限引擎就在那个口后面兜底——**扩展点能加严，但永远越不过那道门**。

### 破：装好了、enable 了、却仍恶意 `[接缝四]` `[信任分级]`

(a) **攻「模型只能建议」这道防线**：这套机制保证的是「**模型不能自己装东西**」——它只能发一个 `request_plugin_install` 的确认弹窗，真正的 git clone 跑在 host 侧、由用户点确认触发。它**不保证**「被装的插件是好的」。所以攻击路径是：**社会工程那个会点确认的人**。模型（或一个被 prompt 注入操纵的模型，或一份措辞诱导的文档）发起一个看着无害的安装建议——「装一下这个『代码格式化工具包』吧」——弹窗弹给用户，用户没细看就点了确认，host 老老实实 git clone 了那个恶意插件并启用。**全程零违规**：模型只发了建议、用户点了确认、host 执行了 clone。这套机制拦住的是「模型**自动**装」，拦不住「模型**说服人去**装」。它**不保证**的那一点是：**用户的确认是经过审查的确认**。

(b) **攻「用户配置即信任」**：在 claude 那套「enable 了就生效 / 配置即信任」下，一个通过 `git pull` 悄悄进到 `.claude/` 的钩子或命令文件，**会静默挂上并运行**——因为 claude 大体上把「出现在配置里」等同于「被信任」，它不区分这份配置是你自己写的、还是别的工具 / 一次 pull 带进来的。codex 给 hooks 加的 `trusted_hash` 检查，**恰好堵的就是这一类**：一条非托管的钩子，必须带显式绕过标记、或它归一化配置的哈希命中你确认过的 `trusted_hash`，才会真的挂上——「`git pull` 带进来的、你没确认过的钩子」哈希对不上，于是不挂。但它**堵不住** (a) 那一类：如果用户**主动确认了**这份配置（亲手留下了那个信任哈希），哪怕它其实是恶意的，`trusted_hash` 照样放行——因为它信任的是「用户确认过」，不是「这东西真无害」。

(c) **「模型只能建议」真正防的是：防『模型（含被操纵的模型）』对『用户 / 系统』的攻击**——它把「装东西进来」这个高权力动作从模型手里拿走，逼一个人类决策横在中间。它**从结构上防不住**：**人本身被骗**（社会工程）。**信任分级这条轴，分的是「信任谁来引入这个扩展」（谁有资格往里塞），不是「这个扩展本身不作恶」**——这两件事**不是一回事**。`trusted_hash` 信任的是「用户确认了这份配置」，不是「这份配置是安全的」；「模型只能建议」信任的是「最终有个人拍板」，不是「那个人拍得对」。所有信任分级机制，都是在回答「**谁有权引入**」，没有一档在回答「**引入的东西是否恶意**」——后者得靠别的（沙箱、权限引擎、代码审查），不在这条轴上。

> **命门**：这道题最大的陷阱是把「信任分级」误读成「安全保证」。你会下意识觉得「codex 这么严，那装进来的就安全了」——不对。信任分级解决的是**准入授权**（authorization：谁说了算），完全**不解决**那个被授权放进来的东西**本身是好是坏**。一个权力很大、但「被正确授权」（用户亲手确认、哈希对得上）的恶意扩展，能堂堂正正地装进来跑起来。认清这条边界，你才知道为什么「权力越大、信任检查越严」这条总纲**只是必要条件、不是充分条件**——它把准入的门看严了，但门里的东西还得靠权限引擎和沙箱（第 6 课）兜着。

### 故障排查：review 命令越用越贵 + 偶发拿不到 diff

先说差分思路：三条现象**根因不同**，别想用一个根因套全部。**现象三是用来排除一整类假设的**——它告诉你「`!` 块没跑」这件事在「装进来的命令」上是**必然**（每次都空），而在自己写的命令上是「偶发」（现象二），这两个「拿不到 diff」根子完全不同，一刀劈开。

**现象一：长会话用 `$Review` 账单爆，新会话敲不爆 → root cause = 切档炸主缓存，by-design（机制如此，不是 bug）。** `$Review` 把模型从 `deepseek-v4-flash` 切到 `deepseek-v4-pro`，而这两档是**两个独立模型、两套独立前缀缓存** `[接缝一]`。但真正烧钱的不是「切」本身（前缀没动），是**时间**：一个长会话先写了半天代码、攒了一大段历史，最后敲 `$Review` 切到 pro——pro 这边对**整段历史**全 miss，按 pro 未命中价重发一遍（deepseek 官方定价，pro 缓存命中 vs 未命中输入价差 **120 倍**：$0.003625 → $0.435 / 1M）。而「新会话第一件事就敲 `$Review`」历史几乎是空的，没什么可重发，自然不爆。这是机制的固有代价，不是 bug——**但它是个该被产品拦住的代价**（见 (d)）。

**现象二：偶发拿不到 diff（重敲就好）→ root cause = 缓存 / 时序而非 shell 块本身；最可能是主对话缓存在长会话里过 TTL 后的一次重建抖动，或 shell 块执行与 prompt 拼装的偶发竞态，bug。** 关键判据是「重敲就好」——说明 `!` 块**机制上是会跑的**（不是现象三那种结构性不跑），只是偶发没拼进去。这排除了「`!` 块被禁用」这一整类假设（现象三才是那一类）。十次一两次、重试好转，指向偶发性故障（执行超时被吞、输出竞态），是 bug，得查 `!` 块执行与 prompt 拼装的时序。

**现象三：装进来的命令 `!` 块每次都空 → root cause = 这个 `Review` 单元的来源是「外部 / MCP 类来源」，被「外部来源不准跑 shell 块」这条安全约束挡了，by-design。** 课文那条铁律：**来自 MCP 的命令永远不准跑 `!` shell 块**（`loadedFrom !== 'mcp'` 才执行 shell）`[接缝三]` `[信任分级]`。如果这个开源包是经由某种外部 / MCP 通道引入的，它的 `!` 块就被无条件跳过——所以**每次都空、不是偶发**。这是安全设计：外部来源不给任意代码执行的口子。判定 by-design。

(c) 汇总：现象一 by-design（切档的固有成本）、现象二 bug（偶发竞态）、现象三 by-design（外部来源禁跑 shell）。**三条里两条 by-design、一条 bug——这正是这道题要你别一锅端的地方。**

(d) 运营硬要求「稳定升配、绝不爆账单」，架构上动这里：**命令的 `model` 覆盖只在 `fork` 路径认**——`fork` 开一个全新子 agent，只带命令正文、**不带主对话历史**，所以 pro 这边最多对「命令正文」全 miss（小），而不是对整段历史全 miss（大）。这至少省掉「整段历史按 pro 价重发」那半。inline 切档要给**明确成本提示**（甚至默认劝退会话内 pro↔flash 换档）。代价：`fork` 路径下 review 拿不到主对话的上下文（它只看命令正文 + 那段 diff），对「需要联系前文才能审」的场景会变弱——这是省缓存和上下文完整性之间的取舍，得让用户知道。

> **命门**：这道题三个坑叠在一起，最容易栽的是把现象二和现象三**当成同一个 bug**（都是「拿不到 diff」）。它俩根子相反：现象三是**结构性的、每次都不跑**（外部来源被安全规则禁了，是 by-design），现象二是**偶发的、重试能好**（自己的命令机制上会跑，只是偶发竞态，是 bug）。「每次都不跑」和「偶发不跑」是两套完全不同的诊断方向——前者去查来源和安全规则，后者去查时序和竞态。把它俩并成一个，你就会在错的方向上挖半天。**「重敲就好」这四个字，是把这两类一刀劈开的判据**，盯死它。

## 评点（效果优化 / 架构设计 / 收口——自评用，非标准答案）

### 效果优化 · 装得进、用得上，两个投诉撞在一起

**强答案应触及的维度：**

- 投诉 A（工具太多、调错 / prompt 太长）的旋钮，至少要命中**渐进式工具暴露**这一档（M2 设施：不把所有 MCP 工具 schema 都常驻进 `tools`，按需把命中的工具 schema 注入下一轮），效果方向 = 每轮 prompt 变短、模型注意力集中、便宜；反作用 = 第一次用某工具有一轮「发现 / 检索」的延迟，且检索本身可能漏掉该用的工具。第二个旋钮可走「整服务器按需挂载 / 工具分组」或「调整工具描述让模型更好分辨」，各自的反作用都要写出来。
- 投诉 B（一个工具一个工具点同意）的旋钮，核心是**整服务器一把授权**（`mcp__服务器__*` 放行该服务器全部工具，抄 claude 的 passthrough + whole-server grant），效果方向 = 用户对信任的服务器一次授权、不再逐工具弹窗；反作用 = 授权粒度变粗，该服务器**将来新增**的工具也自动在授权范围内，等于把信任从「这些工具」扩成「这台服务器连同它以后长出来的一切工具」。

**关键耦合（必须找到这一对）：** A 的「渐进式工具暴露」（让工具少露脸、按需才把 schema 注入）和 B 的「整服务器授权」会**互相拖累**。耦合点在：整服务器授权的前提是用户**看得到、认得清**这台服务器有哪些工具、自己在授权什么；而渐进式暴露恰恰让工具**默认不露脸**——用户在做「整服务器授权」这个决定时，可能根本没见过这台服务器的全部工具清单（它们被 defer 了），于是他授权的是一个**他没完整看过的集合**，还连带授权了将来动态长出来的工具。**「为了 A 让工具藏起来」和「为了 B 让用户对整台服务器一次性授权」叠在一起，结果是用户在信息不全的情况下给出了一个粒度很粗的信任**。这对耦合从「可见性」和「授权粒度」的张力里来：暴露得越少（治 A）、用户授权时的知情就越少（坑 B）。

**常见陷阱：** 只把两个投诉各自治一遍、不去找耦合，是最常见的失分点（题目明说「必有一问逼你发现互相加剧的那一对」）。另一个陷阱是去碰模型（「换强模型就不调错了」「开 reasoning 让它选工具更准」）——死约束写死了**不许动模型**，所有手段必须落在 runtime 旋钮上。还有人会把「整服务器授权」当纯收益，忽略它的反作用（把信任扩到「未来工具」）——而这个反作用恰恰是它和渐进暴露耦合的根。

### 架构设计 · 排四个接缝的落地顺序

**强答案应触及的维度：**

- 排序大致是：**skill 一等原语（M2）与 MCP 客户端（M2）同档** → hooks（M1+，但你们架构里实际落 M2）→ plugins / marketplace（很后期 / defer，schema 提前对齐）。注意 skill 和 MCP **同档（都 M2）**，这本身就是「杠杆 ≠ 排期」最锋利的例子——MCP 杠杆明明最高，却没比 skill 排得早。
- (a) 反直觉点的解释必须用**两种力**：**杠杆**（接进来收益多大）和**依赖**（它得等谁先就位）。MCP 杠杆最高，但被两条依赖往后拽：① 一接进来工具数暴涨 → 得先有**渐进式工具暴露**（M2）压住 prompt，否则每轮 prompt 被几十个 schema 撑爆；② HTTP transport 出网 → 得等 **M3 的本地网络代理**才能安全出网。所以 MCP 客户端排 M2、先做 stdio（本地起进程，最常用、不依赖网络代理），HTTP / OAuth 等代理到位再补。**排期由依赖链决定，不由杠杆决定**——这是整道题的核心。
- (b) 场景验证要含一个跨课边界场景。`接第 6 课`：MCP 工具 / 命令钩子的权限，必须落进你自己的权限引擎（passthrough，不特殊对待），所以「可扩展性每开一个口，第 6 课就得补一道对应的门」——这道跨课依赖意味着你不能在权限引擎（第 6 课）还没稳之前，把一堆外部工具放进来。`接第 9 课`：MCP 的 HTTP transport 出网，依赖第 9 课 / M3 网络代理这条出网通道，没有它 HTTP MCP 就不能安全跑——这正是把 HTTP MCP 往 M3 后拽的那条依赖。
- (c) 那件 M0 就该做的便宜事 = **插件清单 schema 趁早对齐 claude 的 `.claude-plugin/plugin.json`**。零成本是因为现在只是定个 schema、不实现生态；省一大笔是因为：① 抄 claude 的 schema 等于抄一个事实标准，生态里现成的插件能直接为你所用；② 将来做「从 Claude Code 搬家」（codex `/import` 那种）格式一致能省一半功夫。挡掉的那类风险见 (d)。
- (d) 复用 / 打破：hooks 的设计**复用**了第 6 课的权限引擎——它的 allow/deny 必须**臣服于权限引擎的 deny**（钩子只能加严、不能越过 deny）。它**打破**的假设是「配置文件里的东西都是用户自己加的、可信」——命令钩子是**任意代码执行**的口子（以用户全部权限跑、无沙箱），所以你必须**新增** codex 那道 `trusted_hash` 信任检查：命令钩子默认要「用户显式信任过这份配置才挂」，别让 `git pull` 带进来的钩子静默生效。

**常见陷阱：** 把 MCP 排 M0（被「最划算」骗了）是头号陷阱——题目明说它杠杆最高却不排最早，你得能解释清「依赖把它往后拽」。第二个陷阱是把 plugins 整个 defer、连 schema 对齐都不提——漏掉那件「现在做几乎零成本」的便宜事。第三个陷阱是 hooks 排太早还不加信任检查——把一个任意代码执行的口子早早开开、却不配 `trusted_hash`，等于在 M1 就埋一个「配置里冒出来的钩子静默执行」的雷。

### 收口 · 权力分级 × 信任分级

**强答案应触及的维度：**

- (a) 权力三档填对：**只能塞字**（slash 展开的那段话、skill 注入的内容、hook 返回的 additionalContext）→ **能拦能改动作**（hook 的 deny / rewrite 入参）→ **能跑任意进程**（命令型 hook、MCP 服务器、插件捆带的可执行文件）。
- (b) 信任五档从最信任到最不信任：编译期写死（codex 内部 contributor，全信任）→ 托管企业放行 → 用户显式确认过这份配置（codex `trusted_hash`）→ 用户配置即信任（claude，最宽松最危险）→ 模型只能建议（codex 插件安装）。**反直觉点必须答对**：「模型只能建议」排在比「用户配置即信任」**更不信任**的一端，因为它连「用户配置」这一档的信任都不给模型——模型的提议**本身不算数**，必须再经一个人类拍板。模型虽是内核的一部分，但它会被 prompt 注入操纵、会被诱导，所以在「装东西进来」这种高权力动作上，它的话比一份静态配置文件还不能直接信。
- (c) 叉乘：同样是「命令钩子 = 能跑任意进程」这个权力很大的口，**claude** 偏向「把口开足、用策略兜底」（任意 shell、无沙箱，约束只在策略级开关）；**codex** 偏向「同样的口，但加一道 `trusted_hash` 信任检查」（非托管钩子必须用户确认过那份配置才挂）。一句话概括：**claude 把口开足、用策略兜底；codex 同样的口、每一档权力都配一道对应严格度的准入检查。**
- (d) 三性落地：**强** = 抄 claude 的扩展标准（`.claude-plugin` 清单格式、统一 markdown 命名指令单元这套事实标准），让生态从第一天不空；**稳** = 抄 codex 的信任检查不能省（命令钩子的 `trusted_hash`、插件安装「模型只能建议」），且每开一个口、第 6 课都要补一道门（MCP 工具走 passthrough 落进权限引擎、hook 的 allow 越不过 deny、外部来源不准碰 shell）；**自动** = 「往上下文里塞字」这一档可以放给模型自动（skill 自调、hook 注入上下文，最坏只影响模型怎么想），但「能跑任意进程」「装东西进来」这两档**绝不能**自动、必须人拍板——这条线划在**权力分级的第二档和第三档之间**（能拦能改动作 / 能跑任意进程）。

**常见陷阱：** (b) 那个反直觉点答反（把「模型只能建议」当成「比用户配置更可信」，因为模型是内核一部分）是最常见的失分。(d) 里把「自动 / 不自动」的线划错档（有人划在第一档和第二档之间，把「能拦能改」也放给自动）——其实「能拦能改动作」若是模型自动触发的扩展点，也得看它具体改什么，但**任意进程执行那一档绝对不能自动**，这条是死线。还有人把三性答成空话（「强就是功能多、稳就是安全、自动就是省事」），不落到本课的具体机制上——评分看的是你能不能把每一性绑到一个真实的接缝机制和一道真实的检查上。

**及格线：** 权力三档、信任五档都填对，且能说清「权力越大、信任检查越严」这条总纲；落到 deepseek 能说出「抄 claude 标准 + 抄 codex 检查」。

**高分线：** (b) 的反直觉点（模型为何比配置文件更不可信）讲透；(c) 能用一句话精准概括两家姿态差异；(d) 把「自动 / 不自动」的线**准确划在权力分级的第二、三档之间**，并说清这条线背后的道理——**能塞字的可以自动（最坏只影响模型怎么想），能跑任意进程的必须人拍板（动得了真实世界）**。能把这句话当成可带走的总纲收住，就是这一课要给你的那个「原来如此」。

## 下一课预告

第 11 课：优化方法论。前十课你已经把每个机制单独拆透了；下一课换个问法——当这些机制**全都同时在线**、又都要省钱省延迟时，第一个该优化的是哪个？缓存命中率为什么是头号帕累托？那几个被反复改、最后焊死成不变量的「魔法数字」（220k → 250k → 350k → clamp）是怎么一路踩坑熬出来的？下一课讲的不是「再加个机制」，而是「把已有的机制拧到最优」——这里头每一个数字背后，都有一次上线、一次回滚、一笔真实的账。
