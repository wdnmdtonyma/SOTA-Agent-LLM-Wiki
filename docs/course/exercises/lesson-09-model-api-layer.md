# 第 9 课 习题：模型 / API 层

> 配套课文：[第 9 课：模型 / API 层](../lesson-09-model-api-layer.md)

这套题分四层，难度递增。**热身**校准直觉，破除"我大概记得"；**机制层**把这一层最容易想当然的几个机制——重试分层、流式分流、缓存协作、reasoning 回传——逼到你必须真懂控制流才答得上；**实战层**是这一层工程师每天真干的活，局面欠定，没有"这是决策几"的标签提示你，得自己做差分；**收口**把这一层收回到"强 / 稳 / 自动"的主线上。

说在前面：这一层的题有个共同特征——**答案几乎都不在课文某一句里**。课文给你的是零件（429 该不该重试、reasoning 何时该带、缓存为什么会 miss），题目给你的是一个课文没跑过的具体局面，要你把几个零件在脑子里凑到同一个时刻去交互。所以别指望 Ctrl-F；你能 Ctrl-F 到的，都是我故意留给你当陷阱的半句话。

每道题标了 `[决策X]`，那是给你卡住时回课文找零件用的锚点，不是答案位置。决策一 = provider 抽象与 wire 格式；决策二 = 流式解析；决策三 = 重试与退避；决策四 = 缓存协作；决策五 = 回传（用量 / 限流 / reasoning）。

## 热身（四句话里埋了雷：三句各错一处，恰好一句全对，别逢句就改）

下面四句关于模型 / API 层的话，读起来都像那么回事。其中**恰好一句是完全正确的**，另外三句各有**一处**实质错误。请逐句判断对错；对错的那三句，指出错在哪、改对。

> 提醒：这里最危险的不是那三句错的，是那句对的。它写得最像"教科书式的想当然"，你十有八九会顺手把它也改了。改之前先问自己：我是真的在课文 / 源码里见过反例，还是只是觉得"它应该是另一个样子"？

1. codex 现在只剩 OpenAI Responses 一种 wire 格式，Chat Completions 被整条删掉了；所以你要是把 codex 的 provider 配置指向 DeepSeek，会在 `wire_api` 那一关直接报错，因为 DeepSeek 说的是 Chat Completions。

2. 在 DeepSeek 这一层处理 reasoning 的硬规则是"一律把 `reasoning_content` 从历史里剥离干净再发回去，否则服务端 400"，所以最省事的做法就是流一结束就把思考全删了。

3. claude 在高负载下对 529 过载错误的处理是"前台请求重试、后台请求立刻放弃"，判据是这个请求是不是来自带 UI 的主线程；一个 querySource 没打标（undefined）的请求，按这个原则应当归到后台，立刻放弃不重试。

4. codex 的请求层重试明确**不**把 429 当可重试错误——它被映射成"配额到顶"直接上报；会在请求层重试的是 5xx 和传输层故障（超时 / 网络）。

## 机制层（有标准解，但答案不在课文里）

### 推演 1 · 一次流从打开到中途断线，typed 事件各自去了哪 [决策二][决策三]

设一次正常的工具调用流式请求。模型这一轮的输出顺序是：先吐一段思考（reasoning），再吐一句正文，再发起**两个并行的工具调用**（`tool_calls` 里 index 0 和 index 1，函数名和入参 JSON 都是分多个 chunk 流过来的）。请按时间轴推演下面这个**课文没跑过的**局面：

- 流先正常推了一阵：思考增量、正文增量、index 0 的函数名 + 前半段入参 JSON、index 1 的函数名 + 前半段入参 JSON 都已经到了客户端。
- 然后**流在 index 0 的入参 JSON 还没拼完、index 1 也只到一半时，连接断了**（既不是 `finish_reason`，也不是任何块的"完成"事件，就是 socket 挂了）。
- 这一层按决策三重连续传，重发整轮（M0 做法），第二次流从头跑通到 `finish_reason`。

请回答：

(a) 第一次流断的那一刻，已经到客户端的那些增量里，**哪些已经被喂给了 UI、哪些喂给了状态机 / 主循环**？把课文那条"增量喂 UI、完整给状态机"的二分，落到这个具体时刻——断点这一刻，主循环手里到底有没有一个能用的 assistant 轮？为什么？

(b) 重发整轮之后，第二次流又把思考、正文、两个工具调用从头流了一遍。**用户的 UI 在这两次流里会看到什么**？会不会看到思考 / 正文"闪一下、清空、又重来一遍"？这是 bug 还是这层的固有行为？要让用户不难受，UI 侧该怎么处理这两次流之间的关系（提示：问题出在"增量是半成品、随时会被覆盖"这条性质上）。

(c) 现在把场景改一个字：假设流**不是**在工具入参中途断的，而是在 index 0、index 1 两个工具调用都已经"完成"（各自的块完成事件都到了）、只差最后那个带 token 用量的"整轮完成"事件没到时断的。这种断法，决策五里那笔**用量**怎么办？重发整轮重来一遍，会不会把这一轮的 token **算两次**？该在哪一步、用什么判据保证账本只记一次？

### 量化 2 · 重试风暴：服务端延时与自算退避谁压过谁，以及一个敢写进代码的上限 [决策三]

接第 11 课（重试方法论）。设一个容量雪崩的现场：DeepSeek 网关短时过载，对一批请求连续甩 429 / 529。你的 agent 实例里此刻有这么些请求在飞：

- 1 个前台主对话请求（用户盯着）。
- 同一会话后台并发的：1 个自动起标题、1 个压缩摘要（compaction）、3 个 embedding 召回的小请求。
- 这台机器上还有别的 9 个会话，结构类似，也各有 1 前台 + 5 后台。

退避你打算抄两家的并集：指数退避，基值设 B 毫秒、每次翻倍、加 ±10% 抖动、封一个上限 C 秒、次数封顶 N 次。同时服务端在 429 响应体 / 错误文本里**有时**会给一个"过 R 秒再来"。

请回答：

(a) 服务端给了 R、你自己也算出一个退避值 D，**这两个谁说了算**？课文给了 codex 流重连层的做法（`requested_delay.unwrap_or_else(...)`）——把它翻成一句判据：什么时候用 R、什么时候用 D。再说清**为什么是这个方向而不是反过来**（如果反过来，会出什么事）。

(b) 现在算这台机器的"重试压强"。假设**所有**请求都无差别重试（先不做前台 / 后台区分），第一波退避结束、大家几乎同时醒来，会有多少个请求**同一时刻**再次撞向那个已经过载的网关？这个数字说明了什么？抖动 ±10% 在这里到底拦住了什么、又**没**拦住什么（提示：抖动散的是"同一退避值的一批请求"的相位，散不掉的是别的东西）。

(c) 现在加上"前台重试到底、后台限流时立刻放弃"。重算 (b) 的那个并发撞墙数。**省下来的主要是哪部分**？给一个你敢写进代码的 N（次数封顶）和 C（退避上限秒数），并为它辩护——辩护时必须回答："N 再大一点会怎样、C 再小一点会怎样"。

> 结论里写明：B / C / N 的具体数字随你的流量假设和服务端 SLA 可变，但**有一条结论必须不变**——它是什么？（提示：和"谁说了算"那一问、以及前台 / 后台分流，是同一条线。）

### 破 3 · "reasoning 一律剥离" 这个想当然，怎么把你逼到一个配对错误 [决策五]

课文反复强调：DeepSeek 处理 reasoning **不是**"一律剥离 `reasoning_content`、否则 400"，而是一条**配对 / 相邻性**的条件规则。这一题就请你亲手把那个"想当然"跑到坏掉。

构造（或推演）一个**具体的消息序列**，使得：照着"流一结束就把 `reasoning_content` 删干净"这个看起来最安全、最省事的做法去做，**会在某一次请求时报错（配对错误 / 模型接不上）**。要求：

(a) 写出这个序列的关键几轮（assistant 发起 tool_call、tool_result 回填、可能还有后续轮），标清**哪一轮的 `reasoning_content` 被那个"想当然"删掉了、删掉之后哪一次请求会坏、坏在哪**。

(b) 说清这条配对规则**实际保证什么、不保证什么**：它强制"发起 tool_call 的 assistant 轮，在你回 `tool_result` 时必须带回它的 `reasoning_content`"——但它**允许**你在什么时候、对哪些轮的 `reasoning_content` 动手丢弃？把"该删"和"该留"的那条线，画在哪个事件上？

(c) 现在反过来踩另一边：有人听了 (a) 之后矫枉过正，决定"那我**永远不删** `reasoning_content`、全留着最安全"。这在**正确性**上确实不会再违约——但它悄悄破坏了**另一件事**。是什么？（提示：想想这些越积越多的思考块在跨轮历史里占的是什么、又和决策四那条线有没有真正的因果——别把这两条线缠在一起，那正是课文点名的坑。）

> 这一题的命门：很多人会把"reasoning 要不要带回去"和"缓存命不命中"这两件事缠成一根绳。它们**不是**一根绳。(c) 就是用来逼你把它们解开的。

### 故障排查 · "缓存命中率掉到地板，账单翻倍，但谁也没改 prompt"

线上事故，三条现象，互相矛盾，你被叫来定位：

1. 这两天 `prompt_cache_hit_tokens` 占比从平时的 ~85% 掉到不足 10%，输入侧账单几乎翻倍。**但负责 prompt 的同学发誓系统指令、工具定义一个字没动**，git 上那部分也确实没 diff。

2. 掉的不是全部会话——**短会话（三五轮就结束的）几乎不受影响，命中率照旧；长会话、尤其触发过一次自动压缩的，命中率全崩**。

3. 你拉了几个崩掉的长会话的请求体，逐字节 diff 相邻两轮的请求前缀：**系统指令段、工具定义段，前后两轮完全一致**；分叉点出现在**更靠后**的位置。

请回答：

(a) 给出你的**差分排查路径**：依次看哪几样、各用来排除哪一类假设。特别地，现象 2（长 vs 短、压没压过缩）这条，**专门用来排除一整类假设**——是哪一类？它一出现，你立刻可以把哪些方向划掉？

(b) 最可能的 **root cause** 是什么？为什么"系统指令没动"反而是个**误导性线索**，让人往错的方向查？

(c) 这是 **bug 还是 by-design**？

(d) 如果产品经理提一个硬要求："压缩之后也得尽量保住缓存命中率，账单不能这么翻。"——架构上你得动哪一层、和哪一课的机制打架、代价是什么？（提示：这事不只在本课这一层能解，得回到改历史的那一课去想。）

### 效果优化 · "流式体验被投诉两条，但不许换模型、不许动重试层"

一个已经能跑的 DeepSeek agent，QA 提了两条体验投诉，给了一条死约束：

- **投诉 A**：开了 thinking 的复杂任务，用户要**干等好几秒**才看到屏幕上有动静——思考期间界面是死的，等正文开始蹦才有反应，期间用户以为卡死了。
- **投诉 B**：在弱网下，一旦流断、这层重发整轮重来，用户会看到**已经显示出来的思考和正文"哗"地清空、又从头重新蹦一遍**，体感比"转圈等"还糟。
- **死约束**：不许换模型（thinking 该开还得开）、**不许动重试 / 退避层**（重发整轮这个机制本身不准改）。

请为 A、B 各列**至少两个** runtime 旋钮（这一层 / UI 层能动的），每个标明**效果方向**和**反作用**。然后回答那个**必答的耦合问**：

> A 的优化（让用户尽早看到思考在动）和 B 的优化（让重发整轮时画面不要清空重来），这两套手段里，**有没有一对会互相加剧对方**？具体说：你为了 A 做的某件事，会不会让 B 那个"清空重来"的难受**更明显**？反过来呢？把这对耦合找出来，并说你打算怎么取舍。

## 收口 · 这一层怎么同时撑住"强 / 稳 / 自动"（本课牵引题）

这一层是全课的脏活集散地：它既要让上层用得上 DeepSeek 的全部能力（**强**：thinking、工具、缓存省钱），又要在网络和服务端随时翻脸时不崩（**稳**：重试不风暴、流断能续、配对不违约），还要让这一切**不用上层操心**（**自动**：门面背后全兜住）。请回答：

**这一层里，"稳"在什么意义上是"强"和"自动"的边界条件？** 也就是说：举一个具体的设计点，证明"如果在这里图强 / 图省事，会反过来同时把强和自动也毁掉"。

请至少从下面挑两个角度展开（自己挑，别贪多，挑你最能说透的）：

- **重试 × 强**：无差别重试（图"稳"图省事）在雪崩时怎么反而让前台用户**更**拿不到结果（伤"强"）？为什么"前台 / 后台分流"才是真的稳？
- **缓存 × 强 × 自动**：缓存命中率是"强"（省钱、能多塞上下文）还是"稳"？它的"自动"（隐式前缀缓存，上层不用操心）建立在哪条纪律上？一旦那条纪律破了（比如压缩动了历史中段），是"强"先垮还是"自动"先垮？
- **reasoning × 稳 × 强**：把 reasoning 处理错（无脑删 / 无脑留），破坏的是"稳"（配对违约报错）还是"强"（模型接不上工具调用、变笨）还是两个都有？为什么这个错最隐蔽——它平时不报、只在工具调用链那个特定位置才炸？

给一句**能带走的话**：这一层交付的到底是什么？（不是"会调模型"——课文最后那句给了答案的形状，但请你用自己的话、结合"稳是边界条件"说出来。）

### 热身

**恰好正确的是第 4 句。** 另外三句各错一处。

- **第 1 句：错。** 错在最后半句的因果。前半段全对（codex 确实只剩 Responses、Chat Completions 被删、DeepSeek 说 Chat Completions），但"会在 `wire_api` 那一关报错"的**原因**不是"因为 DeepSeek 说 Chat Completions"——是因为你**在 codex 配置里写了 `wire_api = "chat"`** 这个被删掉的取值，codex 直接拒绝、叫你改成 `"responses"`。报错发生在**配置解析**那一刻，跟 DeepSeek 实际说什么协议没有运行期的因果关系——你就算把 base_url 指向一个真说 Responses 的端点、但 `wire_api` 写了 `"chat"`，照样报错。改对：报错是因为 `wire_api = "chat"` 这个取值在 codex 里已被删除、写它即报错；DeepSeek 说 Chat Completions 是"你照抄不了 codex 当前 wire 层"的原因，但**不是**那个报错的触发原因。

- **第 2 句：错（这是课文反复点名作废的那个说法）。** "一律剥离否则 400"已被架构宪法明确作废。真实规则是**条件式配对 / 相邻**：发起 `tool_call` 的那个 assistant 轮，在你回 `tool_result` 时**必须**随它回填 `reasoning_content`——**这里删了反而违约**。"流一结束就全删"恰恰会在工具调用链里删掉模型接着干活要用的思考，触发配对错误。改对：reasoning_content 按配对 / 相邻条件保留或丢弃，工具循环未闭合时必须带、跨过已完成普通 user 轮后才可丢；不是无脑删。

- **第 3 句：错，错在最后那半句对 `undefined` 的归类。** 前半段对（claude 确实对 529 做前台重试 / 后台放弃），但判据**不是**"是不是来自带 UI 的主线程"这么粗——真正的判据是**"用户 / 正确性是不是在 block 这个结果"**：claude 的前台重试集合里**包含了 `compact`（压缩）、`auto_mode`（安全分类器）** 这些并不在"主线程 UI"上、却必须完成的源。而对 `undefined`（没打标的源），claude 的处理是**保守地重试**（"undefined → retry"），不是归到后台放弃——因为没打标的调用路径宁可重试也别误杀。改对：判据是"结果是否被 block / 必须完成"，不是"是否主线程 UI"；`undefined` 按保守原则**重试**，不是立刻放弃。

- **第 4 句：对。** codex 请求层 `retry_429: false`、`retry_5xx: true`、`retry_transport: true`——429 不在请求层重试、被映射成"配额到顶"上报，重试的是 5xx 和传输故障。这句是教科书想当然里**恰好为真**的那一句：很多人会觉得"429 是临时的、当然该重试"而顺手把它改掉——但 codex 在请求层就是不重试 429。

> 命门：这套热身最毒的是第 4 句和第 3 句的张力。第 4 句符合"429 别重试"（codex 视角），第 3 句又讲"429/529 要重试"（claude 视角）——两家**相反**，都对，因为后端语义不同。你要是脑子里只装了一家的规则，必然把另一家那句当成错的去改。这恰恰是课文那句"429 不是普通错误、得专门判、别和 5xx 混为一谈"的真正含义：**它没有一个跨厂商的标准答案，只有"必须单独判"这条元规则。**

### 推演 1 参考解 [决策二][决策三]

**(a) 断点这一刻，主循环手里没有一个能用的 assistant 轮。** 这是这道题的核心。课文那条二分要落实成时序：

- 思考增量、正文增量、两个工具调用的函数名 + 半段入参——这些**全都是 delta（增量）**，它们的去向只有一个：**喂 UI**。UI 已经显示出了思考、正文、和"正在调用某某工具"的样子。
- 但状态机 / 主循环**只信"定稿"**——定稿来自块完成 / 整轮完成事件。断点这一刻，**没有任何一个块完成**（index 0、index 1 的入参 JSON 都没拼完，没有任何"完成"事件），更没有整轮完成。所以主循环手里是空的：它**不能**拿这些半成品增量去推进状态——因为半段的工具入参 JSON 反序列化会失败、思考和正文都还没定稿。

一句话：**UI 看到了一坨"正在长出来"的东西，主循环什么权威结果都还没拿到。** 这正是"增量喂 UI、完整给状态机"二分在断线时刻的体现——断在"完成事件之前"，意味着对状态机而言这一轮等于没发生过，所以才能干净地重发整轮。

**(b) 用户会看到思考 / 正文"闪一下、清空、又重来"——这是这层的固有行为（重发整轮的代价），不是 bug。** 因为第一次流的增量是半成品、第二次流又从头重发，两批增量是同一轮的两次"长出来"过程。要让用户不难受，问题的根在"增量是半成品、随时会被覆盖"这条性质上，所以 UI 侧的处理是：

- 把这一轮的 UI 渲染**绑定到"当前轮的最新一次流"**：重连续传（新流开始）时，把这一轮已经显示的半成品**视为作废、用新流的增量覆盖重渲**，而不是在旧增量后面接着追加（否则会出现"思考出现两遍"）。
- 给用户一个明确的"正在重连"信号（参考 codex 流重连层会推 `Reconnecting... n/N` 这类提示），让"清空重来"被解释成"在重连"，而不是"卡死 / 出错"。
- 关键判据：**只有定稿块才进入不可变的历史区，增量永远画在一个"可被覆盖的活动区"里。** 重发整轮重置的是活动区，不动历史区。

**(c) 会算两次，必须靠"用量只在整轮完成事件里定稿一次"这条来防。** 第二种断法断在"两个工具块都完成了、只差带 token 用量的整轮完成事件"——这个细节是陷阱：**块完成 ≠ 整轮用量到手**。用量（决策五）是跟着**整轮完成**事件回来的，断在它之前，意味着**这次流根本没拿到用量**。重发整轮后，第二次流跑到 `finish_reason` / 整轮完成，才第一次拿到这一轮的真实用量。

所以账本只记一次的判据是：**token 用量只在"整轮完成"事件到达时入账，半途断掉、没拿到整轮完成事件的那次流，本就没有用量可记。** 不需要额外去"去重"——只要坚持"用量随整轮完成定稿"，断在它之前的流自然不入账。栽在这题的人，通常是把"块完成"误当成"这一轮结束了、该记账了"，于是断线重发后记了两次。

> 命门：(a) 和 (c) 是同一条线的两端——"完整 / 定稿才交给状态机"。(a) 是"块没完成 → 主循环没东西可用 → 能干净重发"；(c) 是"整轮没完成 → 用量没到手 → 重发不会重复记账"。只要你把"定稿"这条线咬死，断线在哪个位置断都不会让状态机或账本错乱。反过来，但凡你让 UI 的半成品或块完成事件"漏"进了状态机 / 账本，断线就会立刻把你咬伤。

### 量化 2 参考解 [决策三]

> 数字随你的流量假设和服务端 SLA 可变；下面的具体值是示范，**但结论必须一致**。

**(a) 服务端给了 R 就用 R，没给才用自算的 D。** 翻译 codex 那行 `requested_delay.unwrap_or_else(|| backoff(...))`：**服务端明说的延时优先，自算退避是兜底。** 方向必须是这个，因为：服务端比你更清楚它自己几点能缓过来——R 是它对"什么时候我能接客"的承诺 / 估计。如果反过来（你的 D 压过 R），两种坏：D 比 R 短 → 你在它明确说"还没好"的时候就撞上去，纯属火上浇油、还白白消耗一次重试次数；D 比 R 长 → 你让用户多等了本不必等的时间。所以服务端给了准信，就别用你那个盲算的退避去覆盖它。

**(b) 第一波退避结束、大家同时醒来，无差别重试下会有约 10 × 6 = 60 个请求几乎同时再次撞墙。** （10 个会话 × 每会话 6 个请求 = 60，假设第一波它们退避值相近、几乎同时进入第一次退避。）这个数字说明：**退避本身不消除"撞墙总量"，它只把撞墙从"立刻"推迟到"退避后"——如果大家退避值相近，推迟后还是一起撞，等于把一次踩踏推迟了 B 毫秒重演一遍。**

抖动 ±10% 在这里拦住的是：**"同一退避值的一批请求"的相位对齐**——它把这 60 个本来会在同一毫秒醒来的请求，散到一个 ±10% 的时间窗里，削平那个瞬时尖峰。它**拦不住**的是：撞墙的**总量**（还是 60 个请求要重试）、以及**跨会话的系统性同步**（如果所有会话都是同一时刻开始过载、同样的 B，抖动只散了每会话内部、散不掉"所有会话整体压向网关"这件事）。抖动散相位，不减总量。

**(c) 加上前台 / 后台分流后，撞墙数从 ~60 降到 ~10**（每会话只剩 1 个前台请求重试，5 个后台请求在限流时立刻放弃）。**省下来的主要是后台请求**——而这正是 claude 那个洞见的全部价值：**雪崩时砍掉的 5/6 撞墙压强，全是"用户根本看不到其失败"的后台请求**（起标题、压缩、embedding），留下的是用户真在等的那 1 个。把压向已过载网关的请求量直接砍掉 ~83%，前台那个请求反而更可能挤进去。

敢写进代码的值（示范并辩护）：

- **N（次数封顶）= 5~6 次**。再大：在持续雪崩里多撞几次基本是徒劳（容量没恢复，第 6 次和第 10 次没本质区别），却让单个请求在用户面前挂更久、占着连接和重试预算；想"无限等到恢复"应该走另一条路（像 claude 那个专门的 unattended 模式，配更高退避 + keep-alive），而不是把普通重试次数无脑调大。
- **C（退避上限）= 32~60 秒**（claude 封 32 秒可直接抄）。再小：上限太小 → 指数退避很快就被 clamp 平，后面几次重试间隔几乎一样、退化成固定间隔的"匀速撞墙"，失去指数退避"越撞越让"的意义；上限太大 → 用户在前台干等到一两分钟，体验崩。

**那条不变的结论**：无论 B / C / N 取多少，**"服务端给了延时就尊重它"和"后台请求在限流时立刻放弃"这两条必须成立**——前者保证你不在服务端明说没好时硬撞，后者保证雪崩时你不是问题的一部分。退避参数是调音量，这两条是开关；调音量救不了一个无差别重试 + 无视服务端延时的设计。

> 命门：很多人会把功夫全花在调 B / C / N 上，以为退避算得越精就越不会风暴。错。(b) 已经证明：**退避再精，也只是把同一批撞墙推迟、不减总量；抖动只散相位、不减总量。** 真正把"重试风暴"摁下去的是**减少参与重试的请求总数**（前台 / 后台分流）和**尊重服务端给的延时**（别在它说没好时撞）。参数是末节，分流和尊重 R 才是主干。这也是为什么这题钩第 11 课——那一课正是讲"同一个 429 两种相反处理、服务端延时压过自算退避"。

### 破 3 参考解 [决策五]

**(a) 一个会触发配对错误的最小序列：**

```
轮1  user:      "查一下今天的天气"
轮2  assistant: reasoning_content="我需要调用天气工具"，发起 tool_call(get_weather)   ← "想当然"在流结束时把这轮的 reasoning_content 删了
轮3  tool:      tool_result(get_weather) = "晴，28°C"
轮4  此时要把历史发回去，让模型基于工具结果接着答 ——
              发出的请求里，轮2 那个发起 tool_call 的 assistant 轮，reasoning_content 已被删空
```

坏在**轮 4 这次请求**：发起 `tool_call` 的轮 2，按 DeepSeek 的配对硬约束，在你回 `tool_result`（轮 3）后再发请求时**必须带着轮 2 的 `reasoning_content`**——模型要靠那段思考接住它自己没做完的工具调用。"流一结束就删"恰好把轮 2 的思考在它**还没闭合工具循环**时就删了，于是轮 4 触发配对错误 / 模型接不上。**注意这跟"无条件删能省 400"的想当然正好相反——这里删了才出 400 类错误。**

**(b) 这条规则实际保证 / 不保证什么、线画在哪：**

- **保证（强制）**：发起 `tool_call` 的 assistant 轮，**只要它的工具循环还没闭合**（对应的 `tool_result` 刚回、模型还要基于它继续），它的 `reasoning_content` **必须**带回去。这是硬约束。
- **不保证 / 允许丢**：**跨过一个已经完成的普通 user 轮之后**——也就是工具循环闭合了、用户开了全新一轮——那些旧的 `reasoning_content` 不再被需要，**可以丢**。
- **线画在"工具循环闭没闭合"这个事件上**，不画在"流结束"上，更不画在"缓存命没命中"上。判据是：这轮的 `reasoning_content`，模型接下来还要不要用它接着干活——要，就留；这条线已经跨过一个完成的 user 轮、模型不会再回头用它了，才可以删。

**(c) "永远不删"在正确性上不违约，但它破坏的是上下文预算（token 成本 / 窗口占用），而且这和缓存没有因果关系。** 思考块往往很长，跨轮历史里一轮轮累积下来，会**白白吃掉上下文预算**——每轮请求都把一堆早已闭合、模型再也用不到的旧思考重新发上去，烧 token、挤占窗口（接第 3 课的上下文预算 / 第 11 课）。这才是"跨过 user 轮后该丢"的真正理由：不是为了不违约（不删也不违约），是为了**别让没用的思考链无限占预算**。

但这里有个课文点名的坑必须躲开：**这条"该丢以省预算"的线，和"缓存命不命中"没有因果关系。** 缓存只对**输入前缀**生效，reasoning 那套规则和缓存是两条互不相干的线——官方缓存文档根本没提 reasoning。所以"留着 reasoning 会害得缓存 miss""删掉 reasoning 才能命中缓存"都是没文档依据的错误说法。(c) 该丢，是因为**省上下文预算**，不是因为缓存。

> 命门：这题逼你同时躲开两个坑、且认清它们是不同的坑。(a) 的坑是"删早了 → 配对违约（正确性）"；(c) 的坑是"全留着 → 预算白烧（成本 / 窗口）"。**正确做法不是在两个极端里选一个，是按工具循环闭没闭这条线做条件保留**——这正是 `keep_reasoning` 默认保留、按实测翻转的设计本意：默认留住（先不犯 (a) 那个违约的重错），把"何时安全地丢以省预算"当成可调、可实测的策略。而把这条线和缓存缠在一起，是第三个、也是最常见的坑——课文那张判定图里"没有一个分支问缓存命中没有"，就是专门提醒你别缠。

### 故障排查参考解

**(a) 差分排查路径：**

1. **先看 `hit/miss` token 的分布，确认"miss 发生在前缀的哪个位置"**——也就是逐字节 diff 相邻两轮请求的前缀，找分叉点落在哪一段（现象 3 已经替你做了：分叉在系统指令 / 工具定义**之后**、更靠后的位置）。这一步排除"前缀最前段被动了"的假设。
2. **看现象 2（长 vs 短、压没压过缩）——这条专门排除一整类假设。** 它一出现，你立刻可以划掉**所有"前缀固定段（身份 / policy / 工具定义）被改"的方向**：如果是固定段被改，短会话也会一起崩（它们用的是同一段固定前缀）。短会话**不受影响**、只有触发过压缩的长会话崩——这说明问题**不在固定前缀段**，而在**会话进行中被改动的那段历史**。压缩正是"改历史中段"的那个动作（第 3 课）。
3. 到这里方向已经收窄到"压缩改了历史中段 → 前缀在中段分叉 → 分叉点之后全 miss"。再回看现象 3 确认：分叉点确实在更靠后的位置，和"压缩动的是历史中段"吻合。

**(b) root cause：压缩（第 3 课）重写了历史中段，导致缓存前缀在中段分叉，分叉点之后的全部输入 miss。** DeepSeek 是隐式自动前缀缓存，`A+B` 之后再发 `A+C`，分叉点之后全 miss——压缩恰恰把历史里的 `B` 改成了 `C`（清空旧 tool_result / 换成摘要），于是从被改的那一刻起，后面全部不命中。

"系统指令没动"为什么是**误导性线索**：它把人往"前缀被改"这个最直觉的方向引——大家一听"缓存 miss"，第一反应是"前缀变了，去查系统指令 / 工具定义"。但系统指令确实没动（git 没 diff、字节 diff 也一致），于是查的人卡在"前缀没变怎么会 miss"。真相是：**前缀的固定段没变，但前缀的"会话历史段"被压缩改了**——缓存命中要求的是**整个前缀一字不变**，不只是开头那段固定的。"系统指令没动"是真的，但它只覆盖了前缀的一小部分，剩下的历史段被压缩动了。

**(c) by-design——但是一个有名的、可缓解的设计冲突，不是 bug。** 隐式前缀缓存"前缀一字不变才命中"是 DeepSeek / OpenAI 这侧的底层规则，压缩"改历史中段"是第 3 课为了省窗口必须做的事，两者天然互搏（课文跨课接缝里点名："压缩改的是历史中段，会让前缀分叉、缓存 miss"）。代码层面谁都没坏，是两个正确机制在同一条前缀上对冲。

**(d) 产品硬要求"压缩后也保住命中率"——要动的是第 3 课那一层（压缩），代价是省窗口和省缓存二选一的权衡：**

- 能动的方向：让压缩**尽量晚于缓存断点 / 尽量改更靠后的位置**，把被改动的历史段推到前缀末尾——分叉点越靠后，miss 的尾巴越短。或者：**压缩的产物本身也设计成稳定**（同样的历史压出同样的摘要），减少不必要的前缀扰动。
- 代价：这和压缩"该出手时就出手、尽量多省窗口"的目标直接冲突——你为了保缓存而推迟 / 收敛压缩，就少省了窗口预算，长会话更早撞上下文上限。**这是省窗口（第 3 课）和省缓存账单（本课）的二选一**，没有免费午餐；产品得明确哪个更贵。

> 命门：这题全部的难度在现象 2。它是那条"专门排除一整类假设"的线索——没有它，你会被现象 1（"prompt 没改"）+ 直觉（"miss = 前缀变了"）一路带到死胡同，在系统指令里反复查、查不出。一旦你意识到"短会话不崩、只崩压过缩的长会话"意味着**问题不在固定前缀、在被改的历史段**，root cause 几乎自己跳出来。会查的人和不会查的人，差的就是有没有抓住这条用来证伪"前缀固定段被改"的线索。

### 效果优化 · 评点

**强答案应触及的维度：**

- **投诉 A（思考期界面死）的旋钮**：把 `delta.reasoning_content` 当一等增量**立刻喂 UI**（思考一开始流就显示"模型正在思考……"+ 滚动思考摘要），而不是等正文才有动静；或在请求发出到首个 token 之间显示一个"已发送 / 等待模型"的占位态。效果方向：把"首次有反馈"的时间从"首个正文 token"提前到"首个思考 token / 发送瞬间"。反作用：思考内容直接全量铺给用户可能很长、很乱、甚至泄露你不想展示的中间推理——需要做摘要 / 折叠 / 截断，否则界面被一大段思考淹没。
- **投诉 B（重发整轮画面清空重来）的旋钮**：UI 把这一轮渲染绑到"当前最新流"、重连时覆盖重渲而非追加（见推演 1(b)）；加显式"重连中 n/N"提示把"清空"解释成"在重连"；或更进一步，**保留已显示的旧增量做"乐观渲染"**，只在新流的对应增量到达时再做最小化的差异更新，避免整片清屏。效果方向：把"哗地清空再重来"弱化成"在原地继续 / 平滑替换"。反作用：乐观保留旧增量、增量替换做差分，复杂度和出错面都上升；万一新流的内容和旧的不一致（模型这次想法变了），差分更新可能显示出诡异的"半新半旧"。

**必答的耦合（这是评分核心）**：A 和 B 确实互相加剧。为 A 做的"思考一来就立刻、尽量多地喂 UI 显示"，会让 B 那个"清空重来"**更刺眼**——你越早、越多地把思考铺到屏幕上，弱网一断、重发整轮时要清掉 / 覆盖的内容就越多，"哗地没了又重来"的落差越大。反过来，为 B 做的"少清屏、乐观保留旧增量"，又和 A 的"尽早尽多显示"冲突——你显示得越早越多，重连时要嘛清掉（伤 B），要嘛硬保留再差分（万一新流内容变了就显示错乱）。**取舍方向**：思考 / 正文增量画在一个"明确标注为临时、可被覆盖"的活动区里（视觉上就和定稿区分开），这样既能尽早显示（满足 A），重连覆盖时用户也有心理预期"这块本来就是会变的"（缓解 B）。

**常见陷阱**：(1) 只列旋钮、不答耦合问——这题的分全在耦合上；(2) 把投诉 B 的解法写成"那就别重发整轮"——死约束明确不许动重试层，这是审题失败；(3) 给投诉 A 开"把思考全量原样刷屏"却不提它的反作用（长 / 乱 / 泄露中间推理）。

### 架构设计 · 评点

**强答案应触及的维度：**

- **门面的输出契约要明确三件东西**：流式 typed 事件（增量，喂 UI）、一份定稿的完整轮（喂状态机）、一张 token 账单（四类分记）——并明确"上层只信定稿，增量只给人看"。
- **场景 2（断三次）要答出**：每次断都是"块完成事件之前断 → 状态机没拿到东西 → 干净重发整轮"，UI 侧覆盖重渲、用量只在整轮完成入账（呼应推演 1）。退避 + 抖动 + 上限 + 次数封顶（接第 11 课）。
- **场景 3（跨课，必答）要答出**：缓存协作不打断点、靠隐式前缀；压缩动了历史中段会让前缀分叉、miss——门面要能**从响应的 `hit/miss` token 把"这次为什么 miss / miss 了多少"诊断出来交给上层**（对应 codex 那套缓存断裂诊断、claude 的 break detection）。这是"自动"不等于"黑箱"的关键：门面兜住脏活，但要留一个观测窗口，否则上层永远不知道自己的前缀纪律有没有白费。
- **场景 4（可选）要答出**：前台主对话重试到底、后台压缩摘要在 429 时立刻放弃。

**收尾两问**：复用的已有机制可以点"增量喂 UI / 完整给状态机的二分"或"隐式前缀缓存 + 稳定会话 id"；打破的假设是"上层以为一次调用 = 一个纯函数"，门面被迫在背后藏了一堆**有状态的脏活**——重发整轮时的"账本只记一次"、reasoning 跨轮的配对状态、断线重连的相位 / 次数、缓存命中观测——这些状态全归门面管，上层不知道也不该知道。

**常见陷阱**：(1) 场景全用"一切正常"的 happy path，没有一个跨课边界场景——题目明确要求至少一个跨课（场景 3 是送分但必须真答出"压缩 × 缓存"那层冲突）；(2) 把"自动"理解成"全黑箱、什么都不暴露"——那样上层无法验证前缀纪律、无法定位缓存 miss，运维时抓瞎。好的门面是"兜住脏活但留诊断窗口"；(3) 收尾第二问只说"新增了重试 / 缓存"，没说清这些是**有状态**的、状态归谁管——"上层以为是纯函数、其实门面背后全是状态"才是这问的核心。

### 收口 · 评点

**及格线**：能选两个角度，把"在这一层图强 / 图省事会反过来毁掉强或自动"讲成一个**具体设计点**（不是泛泛说"要平衡"）。比如：无差别重试（图省事）→ 雪崩时前台被后台重试挤垮（伤强）；或：缓存隐式前缀的"自动"建立在"前缀一字不变"的纪律上，压缩一破这条纪律，省钱（强）和"上层不用操心缓存"（自动）一起垮。

**高分线**：能把三个角度串成一条线——**"稳"在这一层不是和"强 / 自动"并列的第三个目标，而是它俩的边界条件**：

- 重试这条：你以为在求"稳"（多重试别失败），无差别重试反而既不稳（雪崩自噬）又伤强（前台拿不到结果）；真正的稳（前台 / 后台分流 + 尊重服务端延时）才让强（前台用户拿到结果）和自动（上层不用管雪崩）同时成立。
- 缓存这条：缓存命中率是"强"（省钱 + 能多塞上下文），它的"自动"靠隐式前缀。但这份强和自动**都以"前缀稳定"这条稳的纪律为前提**——纪律一破（压缩动中段），强（账单翻倍）和自动（上层突然要操心 miss）一起垮。是稳的纪律先破，强和自动才跟着垮。
- reasoning 这条：处理错既伤稳（配对违约报错）又伤强（模型接不上工具调用、变笨），且最隐蔽——平时不报、只在工具调用链那个特定相邻位置才炸。它证明"稳"在这层是**正确性约束**，不是性能优化：配对错了不是慢一点，是直接坏。

**能带走的话**（形状参考，不强求逐字）：这一层交付的不是"会调模型"，而是"把一个会断、会被限流、会算错账、会因思考链回传出错的网络调用，变成上层能闭着眼当可靠函数用的东西"——而**它能当可靠函数用的前提，恰恰是这一层先在'稳'上不偷懒**：重试分流、前缀守纪、配对不违约。**稳是强和自动在这一层的边界条件**：守住了，上面八课的优雅才成立；这一层一图省事，强和自动跟着一起塌。

**常见陷阱**：(1) 把"强 / 稳 / 自动"当三个并列目标各夸一句，没点出"稳是另外两个的边界条件"这层关系——那是收口要的核心洞察；(2) 角度贪多、每个都浅尝——挑两个说透远胜三个都泛泛；(3) "能带走的话"写成对课文末句的复述，没结合"稳是边界条件"做自己的提炼。
