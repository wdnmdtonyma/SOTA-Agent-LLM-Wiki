## 机制层（有标准解，但答案不在课文里）

### 推演 1 · 一句 prompt 进去，主上下文长出几截 `[决策一 / 二 / 四]`

主 agent 正在做一个大任务。它在**同一轮**里发出两个工具调用：

- 调用甲：`Agent({ prompt: "摸清 auth 模块现状", subagent_type: "Explore" })`（同步）。
- 调用乙：`Agent({ prompt: "把所有 .test.ts 跑一遍并汇总失败", subagent_type: "general-purpose", run_in_background: true })`（后台）。

子 agent 甲在自己窗口里读了 12 个文件、grep 5 次，最后一条消息是一段 300 字的结论。子 agent 乙在后台跑了约 90 秒，跑测试、读日志，最后一条消息是一段 200 字的失败汇总。**主 agent 在派完这两个之后没有停，立刻继续处理一条刚到的用户消息「顺便看看 README 写得对不对」，并就此忙了好几轮。**

把这台机器一步步跑到底，逐问回答：

- 甲是同步的：主 agent 这一轮**会不会阻塞**等它？甲那 12 次文件读、5 次 grep 的内容，**有几屏**进了主 agent 的上下文？甲的结论以**什么角色、什么形态**落进主上下文？
- 乙是后台的：主 agent 当轮从乙那里**立刻**拿到的是什么（它长什么样、是不是结论）？乙跑完那 200 字汇总，是**怎么**、**在哪一拍**回到主 agent 的上下文的？
- 现在是关键一拍：乙在第 90 秒跑完、把汇总压进了队列，**但主 agent 正忙着处理「看 README」那串用户消息**。乙的汇总会**立刻**被主 agent 看到吗？如果不会，它在排谁的队、排到什么时候才轮到它？把队列里此刻有哪几类东西、各自什么优先级排出来。
- 最后一问，落到账上：整件事做完，主 agent 的上下文窗口里，因为这两个子 agent 而**净增**了多少「内容」——是「12 次读 + 5 次 grep + 跑测试 + 读日志」的全部过程，还是别的？把这笔账和第 0 节那句话对上。

### 量化 2 · 子 agent 到底替主上下文省了多少，临界点在哪 `[决策二]`

课文反复说子 agent 是「上下文压缩机」，但**没把这笔账算到底**。你来算。

设定（都按一次「摸清现状」的调研任务）：

- 要读 N 个文件，每个文件平均 F 个 token；外加 G 次 grep，每次结果平均 R 个 token。
- 这些原始内容若进主上下文，**原样**占位（不算工具调用本身的开销）。
- 子 agent 跑完，回给主 agent 的结论固定 S 个 token。
- 起一个子 agent 实例本身有成本：它要跑自己的循环，烧掉的是**子 agent 那条独立 cache 链上的输入 token**（这部分钱照付，只是不占主上下文）。

请回答：

- (a) 写出「派子 agent」和「主 agent 自己读」两条路各自往**主上下文**里堆进多少 token。给出「子 agent 省下的主上下文 token」表达式。
- (b) 代一组数：N=20、F=400、G=15、R=200、S=300。子 agent 替主上下文省了多少？这省下来的那部分，最该用第 3 课的哪个机制来理解它的价值（它推迟了什么）？
- (c) 这里有一笔**隐藏账**，专门用来逼你算错：很多人会说「省了 (a) 那么多 token，所以省了那么多钱」。错在哪？子 agent 那条独立 cache 链上的输入 token **付没付费**？把「省主上下文」和「省总账单」拆开——子 agent 在**省钱**和**省主上下文**这两件事上，分别是赚是亏？什么场景下它**省了上下文却没省钱、甚至更费钱**？
- (d) 给一条**敢写进代码**的判据：一个子任务，调研规模小到什么程度时，「派子 agent」反而不划算（被起实例的固定开销吃掉）？用上面的符号写出这条不等式，并说清你拿什么当那个固定开销的代理量。

> 数字随假设可变，但结论必须一致：子 agent 省的是**主上下文**这个稀缺资源，不一定省**总 token / 总钱**；规模太小时固定开销压过收益。

### 破 3 · 绕过递归守卫，让一个子 agent 仍然派出一棵树 `[决策五 / 四]`

课文把「子 agent 默认不能再派子 agent」当成一道**防指数爆炸的安全底线**，并说 claude 的做法比「运行时计数器」更彻底——**把 `Agent` 工具直接从子 agent 的工具集里删掉**（外部用户 `USER_TYPE !== 'ant'`），能力直接不给，物理上没法再派。

现在请你站在「想绕过这道闸」的角度，在**不改这行代码、不把自己变成 ant 内部用户**的前提下，构造一个**子 agent（或它引发的链条）仍然能让系统里冒出一棵 agent 树**的局面。说清楚：

- 你这条路**为什么不算违反**「子 agent 的工具集里没有 `Agent` 工具」这条规则——它在结构上完全合规；
- 那棵树是**怎么**长出来的（谁在派、派的指令从哪来、那个「派」的动作发生在哪个 agent 身上）；
- 既然能绕，课文凭什么还说这道闸有用？这道「删掉 `Agent` 工具」的守卫，**实际**挡住的是哪一类爆炸、**挡不住**的是哪一类？把它的保证边界画在精确的一条线上。
- 附加一刀：你绕过去之后，**codex 那道闸**（默认最多 6 个子 agent 同时活的硬并发限额）会不会也跟着失效？为什么 claude 这条「删工具」的守卫和 codex 那条「限并发」的守卫，**挡的根本不是同一种爆炸**？

### 破 4 · 让一段「子 agent 结论」骗到主 agent 的信任 `[决策三 / 二]`

课文把「子 agent 只回结论、结论回灌父上下文」当成干净的收口机制。但「回灌」这件事本身有个被忽略的细节：**子 agent 回来的那段结论，在父 agent 眼里是以什么身份出现的？** 看 codex 的 `FINAL_ANSWER`——它进父上下文时 `role()` 返回 `"assistant"`，也就是说，**子 agent 的产出，在父 agent 的对话史里长得和「父 agent 自己说过的话」一个样**。

请利用这一点构造一个反例，让收口机制「跑完之后结构上完全合规、语义上仍然把主 agent 带沟里」：

- 设想一个子 agent 在它自己的窗口里被喂了脏数据 / 被 prompt 注入 / 单纯就是分析错了，于是它的最终结论里夹了一条**错误但说得很笃定**的论断（比如「auth 模块没有任何 CSRF 校验，可以放心删掉那段中间件」，而实际上有）。这段结论按机制原样回灌进主 agent 上下文。
- 问：主 agent 此后会**怎么对待**这段论断？它有没有办法**分辨**「这是子 agent 说的、可能错」还是「这是我自己之前的结论、可信」？`role="assistant"` 这个设计在这里帮了倒忙吗？
- 再问：主 agent 决策一二里**看不到子 agent 的中间过程**（那 30 个文件、那些 grep）。这个「信息屏障」在「省上下文」上是优点，在「这段结论靠不靠谱」上是什么？主 agent 能不能「回去核一下子 agent 凭什么这么说」？
- 收口：把这条反例说清——子 agent 收口机制**保证**的是什么（一段结论原样、低成本地回到父），**不保证**的是什么（这段结论的正确性 / 可追溯性）。课文说子 agent 是「上下文压缩机」，那压缩机和「主 agent 中毒」之间，差的是哪一层本该有、却被隔离顺手抹掉的东西？deepseek 要补的是什么（提示：你没法核子 agent 的过程，但你能给这段结论**标记来源**）？

## 实战层（主菜：欠定、差分、判断——没有「这是哪一课」的标签提示你）

### 故障排查 · 「派出去的 agent 像是没动静」 `[决策四 / 二 / 五]`

线上来了一桩怪事故，三条现象凑在一起：

- ① 某用户派了一个**后台**子 agent 去跑一个大调研，然后他自己接着和主 agent 你来我往聊了很久、不停打字。**半小时过去，他始终没在对话里看到那个后台 agent 的任何结果**，以为它「死了」。可事后查日志，那个后台 agent **早在第 2 分钟就跑完了**，结论也确实生成了。
- ② 另一个用户派了一个**同步**子 agent，结论倒是回来了，但回来的是一句「好的，我已经把相关文件都看过了」——**什么有用信息都没有**。子 agent 的日志里明明读了 30 个文件、analysis 做得很细。
- ③ 监控显示：这两台机器全程 CPU / 内存 / API 配额都正常，没有崩溃、没有限流、没有超时；后台 agent 的进程也没有异常退出记录。

请给出：

- (a) **排查路径（差分）**：现象③ 帮你**排除掉哪一整类假设**？把它排掉之后，① 和 ② 各自把你逼向**哪个机制**？（提示：① 和 ② 看起来像同一个 bug，其实是两个完全不同的机制坏了——别把它们并成一条线查。）
- (b) ① 的 **root cause**：那个后台 agent 的结论到底卡在哪儿、为什么这个用户「越活跃越看不到结果」？把队列里此刻排着哪几类东西、谁优先于谁，写清楚。
- (c) ② 的 **root cause**：子 agent 读了 30 个文件、分析很细，为什么主 agent 只拿到一句废话？这是子 agent 干得不好，还是收口机制的**契约**就长这样？
- (d) 判定：① 和 ② 分别是 **bug 还是 by-design**？
- (e) 若运营提一个硬要求——「后台 agent 一跑完就必须立刻弹给用户，不许等」——你架构上要动哪一处、代价是什么？（想清楚：课文为什么**故意**把后台结果的优先级压在用户输入之下，你这一改打破了哪个设计意图？）

### 效果优化 · 子 agent「又慢又不准」，且不许去掉隔离 `[决策一 / 二 / 五]`

deepseek 的子 agent 上线后，内测用户两派投诉：

- **(A) 一派嫌「慢 / 贵」**：主 agent 动不动派一堆子 agent，每个都要起实例、各自跑一长串循环，整体比「主 agent 自己干」还慢、token 账单还高，尤其那些其实没几步的小调研。
- **(B) 另一派嫌「子 agent 老是抓不到重点」**：派出去摸现状，回来的结论要么太笼统、要么漏了主 agent 真正关心的那块，主 agent 拿着没用，还得自己再读一遍。

**死约束：不许去掉「子 agent 上下文隔离」这条**（也就是不许让子 agent 看见主 agent 的全部历史、不许让子 agent 把过程同步回主上下文）——隔离是子 agent 的全部价值，去了就白派。

针对 A、B 各列出你能动的 runtime 旋钮（每派**至少两个**，从本课的「派不派的判据 / fork 多少起始上下文 / 子 agent 系统提示词 / 模型与工具集 / 同步还是后台」这些机制里挑），预测每个旋钮的**效果方向**，并指出它的**反作用**。最后两问最关键：

- A 的优化（少派、派轻、用便宜模型、给少量上下文）和 B 的优化（让子 agent 更准）里，有没有**一对会互相加剧对方**的？想清楚：你为了让 B 更准，最自然的手是「**多给子 agent 一点起始上下文**（多 fork 几轮父历史，让它知道主 agent 在关心什么）」——这一手会怎么直接顶到 A 的死约束和 A 的成本上？
- 在「死约束（不许去隔离）」下，有没有一个手段能**同时**缓解 A 和 B——既不破隔离、又让子 agent 更准更省？（提示：准不准、省不省，未必只能靠「多塞上下文」来调；还有一个旋钮专管「子 agent 该往哪使劲、最后交什么」。）

### 架构设计 · 给 deepseek 设计子 agent 子系统 `[决策一 / 二 / 四 / 五]`

deepseek 是单用户桌面 coding agent。请基于本课「隔离是因、并行是果」的骨架，设计它的子 agent 子系统。至少覆盖：

- **(1) 派发与隔离**：派一个子 agent 的最小接口长什么样（哪些参数是必须的）？子 agent 的起始上下文默认给多少、留不留 fork 旋钮？跑子 agent 的引擎和主循环是**同一个**还是另起一套，为什么？
- **(2) 收口契约**：子 agent 的返回值是什么、中间过程怎么处理？你怎么**逼**子 agent 最后一定吐出一段有用的结构化结论（而不是「好的我看完了」）？
- **(3) 同步 vs 后台**：M0 做不做后台 agent？如果做，后台结果怎么接回同步主循环、它的优先级该排在用户输入之前还是之后，为什么？
- **(4) 安全底线**：递归守卫、并行写文件的隔离、子 agent 权限、并发上限——这四条 M0 各怎么落？哪几条**不分形态、M0 就必须有**？

用下面 **4 个场景**验证你的设计（含一个跨课边界场景）：

- 场景一（主线）：主 agent 要「摸清 auth 模块现状」，会读一大堆文件。走你的派发→隔离→收口，主 agent 的上下文最后多了什么、少看了什么？
- 场景二（并行写）：主 agent 想同时派 3 个子 agent **各自改一个独立模块**的文件。你怎么保证它们不互相踩？这和「只读摸现状」的子 agent 在隔离要求上有什么本质不同？
- 场景三（递归）：某个子 agent 的任务里，模型自作主张想「再派一个子 agent 帮我」。你的系统让它派成了吗？凭什么挡（或凭什么放）？
- 场景四（**跨课边界**，接第 5 课）：用户在子 agent 还在跑时**关掉了 app**，重启回来。子 agent 的产出该不该、能不能恢复？这要求你的子 agent 产出在哪一层落了盘？M0 真要支持「重启恢复整棵 agent 树」吗，还是只恢复一段线性对话就够？

最后：你这套设计里，**直接复用了本课哪个机制**（指名）、**打破了课文哪个假设、因此必须新增什么**？

## 收口 · 隔离是因、并行是果；层级树 vs 对等图（本课牵引题）

本课有两句压舱石的话：一句是 **「派一个子 agent，第一价值不是并行干活，是上下文隔离——隔离是因，并行是果」**；另一句是设计反思里的 **「claude 把多 agent 做成一次性层级 fan-out + 旁挂协作层，codex 把多 agent 做成一等公民的对等图」**。

把它们收到 强 / 稳 / 自动 三性上，具体回答：

- (1) 「子 agent = 上下文压缩机」这个设计，**同时**喂饱了 强 / 稳 / 自动 里的哪几性？它和第 3 课的压缩是同一个目标（省主上下文）的两种手段——一个事前预防、一个事后补救。用三性的语言说清：为什么「事前隔离」在 强 / 稳 / 自动 上**比**「事后压缩」更优？（提示：第 3 课的压缩会炸缓存，子 agent 隔离会吗？）
- (2) deepseek 该抄 claude 的层级树，还是 codex 的对等图？用三性 + 「复杂度守恒」把这个选择讲清楚：codex 那张图（共享控制平面 + 内存总线 + `trigger_turn` 协议 + 持久 spawn 拓扑）多付的复杂度，在 deepseek 的定位（单用户桌面）下，**买到的那部分能力 deepseek 用得上吗**？不上它，deepseek 牺牲了三性里的哪一性、保住了哪几性？
- (3) 最后一句要狠：课文说「隔离是因、并行是果，这个顺序记反了很多设计取舍就解释不通」。把这句话**收成一句关于三性的话**——为什么一旦你把子 agent 理解成「上下文隔离器」而非「多一个干活的」，「该不该派子 agent」「子 agent 能不能边干边同步」「子 agent 默认要不要 fork 父上下文」这几个看似无关的设计取舍，答案就**全部一致**了？

（及格线：能把「子 agent 省主上下文、不炸缓存」收到「强 & 自动同向、稳不被拖累」上。高分线：答出 deepseek 该抄 claude 主干而把 codex 的图留到「真有 agent 集群协作」场景再上，并由此说清「隔离是因」这个判据如何同时决定了「不 fork、只回结论、不许边干边同步、默认不递归」四件事——它们是同一条原则的四个推论。）

### 热身（对的是第 3 句）

- **1 错**：前半句对（claude 正常派子 agent 时 `forkContextMessages` 是 `undefined`，`contextMessages` 为空，`initialMessages` 只有那句 prompt——真隔离）；**错在后半句**——codex 的 `fork_turns` **不写时默认是 `"all"`**，解析成 `SpawnAgentForkMode::FullHistory`，即**把父的全部历史塞给子 agent**。所以 codex 的**默认行为恰恰相反**：默认 fork 全量、不隔离。要让 codex 也空白起步，必须**显式**写 `fork_turns: "none"`。改：claude 默认隔离、codex 默认 fork 全量；两家默认行为**相反**，不一致。**命门**：很多人想当然「子 agent 默认都该是隔离的」，于是顺手把 codex 也说成默认空白——错。这条专门埋在你最容易凭直觉划「对」的地方。`[决策一]`
- **2 错**：`finalizeAgentTool` **不是**把整段对话史拼起来——它只取**最后一条 assistant 消息里的 text 块**。若最后一条是纯 tool_use（循环半路退出），才往回扫到最近一条有 text 的 assistant 消息。它**绝不**遍历拼接所有 assistant 的 text。中间那 30 个文件、所有工具调用与结果，主 agent 一个字都看不到。改：只取最后一条（或回退到最近一条）有 text 的 assistant 消息，不是整段史拼接。`[决策二]`
- **3 对**：`to_model_input_item` 里 `trigger_turn` 为 true 选 `"NEW_TASK"`（叫醒对方、立刻起一个 turn 干活），为 false 选 `"MESSAGE"`（只投进对方上下文、不打断，对方下次自然醒来才看到）。这个布尔把「派活（要立刻干）」和「通知（别打断你）」一刀分开。`[决策三]`
- **4 错**：方向反了。后台结果包成 `<task-notification>` 走的是 `enqueuePendingNotification`，默认优先级 **`'later'`**；而用户输入走 `enqueue`，默认 **`'next'`**。队列优先级 `now > next > later`，所以 task-notification **低于**用户输入——设计注释原话是「so user input is never starved by system messages」（别让系统消息把用户输入饿死）。后台结果**不会插队打断用户**，反而要排在用户输入之后、等主循环空档才被注入。改：后台结果优先级 `'later'`，**低于**用户输入，永远不会插队打断用户。`[决策四]`

### 推演 1

- **甲（同步）会阻塞**：主 agent 这一轮**阻塞等甲跑完**，把甲的结论作为**工具结果**直接返回到同一轮。甲那 12 次读、5 次 grep 的内容**一屏都没进**主上下文——全留在甲自己的窗口里，用完即弃。甲的 300 字结论以一个 `tool_result` 块的形态落进主上下文（`finalizeAgentTool` 取的是甲最后一条 assistant 的 text）。**主上下文因甲只长了那 300 字。**
- **乙（后台）当轮拿到的是回执，不是结论**：主 agent 当轮立刻拿到 `{status: 'async_launched', agentId, outputFile}`——一个「已启动」的回执，**不是**汇总。主 agent 不等乙，继续干。乙跑完那 200 字汇总，是被包成 `<task-notification>`、通过 `enqueuePendingNotification` 压进通知队列（优先级 `'later'`），等主循环某个空档把它当成一条**合成 user 消息**注入，主 agent 才看到。
- **关键一拍**：乙第 90 秒跑完、汇总进了队列（`'later'`），但主 agent 正忙着处理「看 README」那串**用户消息**（`'next'`）。队列优先级 `now > next > later`，**用户那串先被取走**。乙的汇总**不会立刻被看到**，它排在所有用户输入之后，要等主 agent 把用户消息都消化完、出现一个没有更高优先级项的空档，才轮到它注入。所以「派了个后台 agent 它好像没动静」常常不是它没跑完，是它的通知还在队里排着、被用户输入一直插在前面。
- **净增账**：主上下文因这两个子 agent 净增的，**只是甲的 300 字 + 乙的 200 字结论**（共约 500 token），外加乙那一行 `async_launched` 回执。「12 次读 + 5 次 grep + 跑测试 + 读日志」那一大堆过程**一个 token 都没进主上下文**——它们各自留在甲、乙的窗口里，那两个窗口用完即弃。这正是第 0 节那句：「子任务烧掉的几十次工具调用、几十屏文件内容，主 agent 一个 token 都没花。」
- **命门**：① 别把同步子 agent 的「结论回到工具结果」和后台子 agent 的「结论靠合成 user 消息注入」混成一回事——同步是当轮直接返回，后台是排队等空档注入，两条回程路不同。② 后台结果的优先级是 `'later'`，**用户越活跃、它越排不上**——这不是 bug，是「别饿死用户输入」的设计。`[决策一 / 二 / 四]`

### 量化 2

- **(a)** 主 agent 自己读 → 主上下文堆进 `N·F + G·R`（全部原始内容原样进窗口）。派子 agent → 主上下文只堆进 `S`（一段结论）。**子 agent 省下的主上下文 token = `N·F + G·R − S`**。
- **(b)** 代入 N=20、F=400、G=15、R=200、S=300：自己读 = `20·400 + 15·200 = 8000 + 3000 = 11000`；派子 agent = `300`。**省下主上下文 ≈ 11000 − 300 = 10700 token。** 这省下来的价值，最该用第 3 课的「压缩触发阈值 / 水位线」来理解：这 10700 token 如果进了主窗口，会把主 agent 更快推到压缩阈值，逼它触发一次压缩——而压缩还会炸缓存。子 agent **推迟（甚至避免）了主上下文那次压缩**。它省的不是「一次 API 调用」，是「一次本会发生的压缩 + 随之而来的缓存失效」。
- **(c) 隐藏账**：「省了 10700 token 就是省了 10700 token 的钱」——**错**。子 agent 为了产出那 300 字结论，自己在独立 cache 链上**真的读了**那 20 个文件、grep 了 15 次——这些输入 token **照样付费**（只是付在子 agent 那条 cache 链上，不占主上下文）。所以拆开看：
  - **省主上下文**：稳赚 10700 token 的窗口占用（这是真省，且省的是最稀缺的资源）。
  - **省总账单**：**未必**。子 agent 把 `N·F + G·R` 这些 token 在自己窗口里读了一遍，钱照付；它还**额外**付了一份「起实例 / 跑自己那条循环的系统提示词 + 中间推理」的固定开销。
  - **更费钱的场景**：如果主 agent **本来也读得下**这些内容（远没到压缩阈值），那派子 agent 就是**白白多付了一份固定开销、还多了一次结论生成**，省了上下文却没省钱、反而更贵。子 agent 划算的前提是「这些噪音如果进主窗口，会逼出一次压缩 / 把后续每一轮的 prompt 都撑大」——是**避免下游连锁成本**，不是这一笔读文件的钱。
- **(d)** 设起一个子 agent 实例的固定开销代理量为 `C`（它自己那条 cache 链上系统提示词 + 框架 prompt + 最少几轮往返的输入 token，是一个可测的常数级量）。「派子 agent」相对「自己读」在**总账单**上不亏，大致要求子任务的原始噪音规模压过这份固定开销，再叠加它避免的下游压缩收益。一条保守的、敢写进代码的判据：**当 `N·F + G·R < C` 时不派**——子任务噪音连子 agent 的起步开销都盖不住，纯亏。`C` 用「子 agent 系统提示词 + 工具定义 + 约两轮空跑」的 token 数估，量级通常在几千 token。**结论：规模小于这个固定开销的小调研，主 agent 自己干；大到会撑爆主窗口、逼出压缩的，才外包。**
- **命门**：算这题最容易栽在「把省主上下文等同于省钱」。子 agent 的真正价值是**省那个最稀缺的资源（主上下文）+ 避免下游压缩连锁**，而不是省这一笔读文件的 token——那笔钱子 agent 替你付了，没消失。数字随假设可变，但这个结论必须一致。`[决策二]`

### 破 3

- **构造（任选其一，本质相同）**：① 子 agent 在它的任务里跑一条 shell 命令，启动**另一个 agent CLI 进程**（比如再起一个 codex / claude 子进程去干活）——它用的是 `Bash`/`Shell` 工具，不是 `Agent` 工具。② 子 agent 写出 / 修改一个 `.claude/agents/*.md` 文件、或一段会被外层调度的脚本，让**主 agent（或下一次会话）**据此再派一批 agent。③ 子 agent 把「请再派 N 个 agent 去做 X」写进它**回给主 agent 的结论里**，主 agent 读到这段「建议」后照办，亲手 `Agent(...)` 派出一批——派的动作发生在**有 `Agent` 工具的主 agent**身上。
- **为什么不算违反规则**：这道闸的字面规则是「**子 agent 的工具集里没有 `Agent` 工具**」。上面三条**没有一条**让子 agent 调用 `Agent` 工具——①用的是 Bash，②③是把「派」的动作甩给别的进程 / 别的 agent。子 agent 的工具集**仍然不含 `Agent`**，结构上完全合规。闸拦的是「子 agent **直接**调 `Agent` 工具」这一条具体路径，不是「这棵进程 / 任务树里**绝不**再多出 agent」这件事。
- **闸实际挡住什么、挡不住什么**：这道「删 `Agent` 工具」的守卫**挡住的是**——子 agent 在 runtime **内部、用 `Agent` 工具**直接 fan-out 出子子 agent 的那条路（也正是「一个 agent 派 10 个、每个再派 10 个」的 runtime 内指数爆炸）。它**挡不住的是**——子 agent 借**别的能力**（shell 起进程、写文件让外层照办、把「再派」当建议回灌主 agent）绕到 runtime **外面或上一层**去引发派 agent。**保证边界的精确一条线：它保证「子 agent 不能在本 runtime 内、经 `Agent` 工具路径递归 fan-out」，不保证「这棵任务树里永远不再多出 agent」。** 前者（能力剥夺）是确定性的、物理的；后者（任何路径都不冒出 agent）它做不到，也没打算做——真要堵后者，得连子 agent 的 Bash / 写文件能力一起收（接第 6 课的权限闸 + 决策五的工具集收窄：子 agent 的能力面应 ≤ 任务所需）。
- **附加一刀（codex 那道闸会不会失效）**：会、但失效的**不是同一种保护**。codex 的 `DEFAULT_AGENT_MAX_THREADS=Some(6)` 限的是「**经 codex 自己的 spawn 机制**同时活着的 V2 子 agent 数」（且只数 subagent、root 不占额）。你绕过去那些路——shell 另起进程、外层照办——产生的 agent **根本不走 codex 的 spawn 计数**，所以那个 limiter 数不到它们，自然也限不住。这恰好点破两道闸挡的是**两种不同的爆炸**：claude 的「删 `Agent` 工具」挡的是**深度爆炸**（子能不能再派、树能多深），codex 的「限并发」挡的是**宽度 / 资源爆炸**（同一时刻有多少个在烧 CPU / API 配额）。两道闸正交：删工具挡不住「绕到外面起一堆进程同时跑」（那是宽度），限并发挡不住「每个 agent 各自递归得很深但慢慢来」（那是深度）。**真要兜住失控的 agent 树，深度闸和宽度闸都得有，且都得管到「绕过本 runtime spawn 路径」的那些口子。**
- **命门**：学生最容易栽在「能力剥夺式守卫 = 绝对安全」。能力剥夺确实比计数器彻底——但它彻底地堵死的是**一条具体路径（`Agent` 工具）**，不是**一个目标（绝不再生 agent）**。把保证写成「子 agent 不能用 `Agent` 工具递归」，它永真；写成「子 agent 引发不了任何新 agent」，这条反例就把它破了。课文那句「比运行时计数器更彻底」对的是它**堵这条路**比计数器彻底，不是它堵死了**所有路**。`[决策五 / 四]`

### 破 4

- **反例成立**：子 agent 在自己窗口里得出一条错误但笃定的结论（「auth 没有 CSRF 校验，可放心删」），按机制原样回灌——`FINAL_ANSWER` 以 `role="assistant"` 进父上下文。**结构上完全合规**：收口机制干的就是「把子 agent 最后一段结论低成本地放进父上下文」，它一字不差地做到了。**语义上仍然坏**：那条论断是错的，但它已经混进父的对话史了。
- **主 agent 分辨不了**：父 agent 此后处理这条论断时，它在对话史里的身份是 `assistant`——**和父 agent 自己之前说过的话一个角色**。从父的视角，「auth 没有 CSRF 校验」这句话看起来就像**它自己先前分析得出的结论**，而不是「某个隔离子 agent 单方面的、可能错的断言」。`role="assistant"` 这个设计在这里**帮了倒忙**：它把「外来的、未经父核实的论断」伪装成了「父自己的既有判断」，于是父倾向于直接信、接着往下推（「既然没 CSRF，那就删中间件」）——**主 agent 中毒了**。
- **信息屏障的双刃**：决策一二那个「父看不到子的中间过程」的信息屏障，在**省上下文**上是纯优点（噪音不进主窗口）；但在**结论可靠性**上是**致命短板**——父**没有任何材料去核**子 agent 凭什么这么说。它看不到那 30 个文件、那些 grep，也就无法验证「没 CSRF」这个判断的依据。子 agent 说啥就是啥，父只能照单全收。**隔离顺手抹掉的，正是「可追溯性 / 可核验性」**：你省了上下文，代价是父失去了对这段结论的审计能力。
- **机制保证什么、不保证什么**：子 agent 收口机制**保证**的是「一段结论原样、低成本地从子窗口回到父窗口」（一个忠实的、廉价的信息搬运）；它**完全不保证**这段结论**正确**，也不保证它**可追溯**（父没法回溯到证据）。压缩机和「主 agent 中毒」之间，差的就是这一层——**来源标记 / 可信度降级**：把外来结论标成「这是子 agent X 的断言，未经主 agent 核实」，而不是让它冒充「父自己的结论」。
- **deepseek 要补什么**：你确实没法（也不该，否则破隔离）让主 agent 去核子 agent 的中间过程——但你能给回灌的这段结论**显式标记来源**：让它在父上下文里以「子 agent 报告」的形态出现（带 agent 名 / 任务名 / 「以下为子 agent 单方结论」的框），而不是无差别地混成 `assistant` 自述。再叠一层第 4 课的污点追踪思路：从子 agent 来的论断，在主 agent 据此做高危动作（删代码、删文件）前，应触发一次复核而非直接信。**这条不破隔离**（不用回看过程），只是不让外来结论冒充父自己的判断。
- **命门**：学生容易把这题答成「子 agent 会出错，所以收口机制不可靠」——太浅。**关键不在「子 agent 会错」（任何 agent 都会错），而在「错误结论以 `assistant` 身份回灌、主 agent 分辨不出它是外来的」**。收口机制忠实地搬运了一段结论，这没毛病；毛病在它**没给这段结论贴上来源标签**，于是隔离省下的上下文，是用「父对这段结论的可核验性」换来的。看穿这一点，才知道补救不是「让父去核过程」（那破隔离），而是「给结论标来源 + 高危动作前降级信任」。`[决策三 / 二]`

### 故障排查 · 「派出去的 agent 像是没动静」

- **(a) 排查路径（差分）**：现象③（CPU / 内存 / API 配额全正常、无崩溃、无限流、无超时、进程没异常退出）**一刀排除掉「子 agent 真的没跑完 / 挂了 / 被限流卡死」这一整类假设**——子 agent 确实跑完了、确实产出了，问题**不在「跑」这一侧，而在「结果怎么回到主 agent / 回的是什么」这一侧**。排掉之后：① 是「跑完了但用户看不到」→ 逼向**后台结果的回程机制（决策四的通知队列 + 优先级）**；② 是「回来了但没用」→ 逼向**收口契约（决策二只取最后一段 text）**。**关键：① 和 ② 看着像同一个 bug（都是「派了 agent 没拿到有用东西」），其实一个坏在『回程时机』、一个坏在『回程内容』，是两个机制，必须分开查。**
- **(b) ① 的 root cause**：后台 agent 的结论早就生成、被包成 `<task-notification>` 压进了通知队列，优先级 **`'later'`**。但这个用户**全程在不停打字**——他每条输入走 `enqueue`，优先级 **`'next'`**。队列取项按 `now > next > later`，于是**只要队里还有用户输入，task-notification 就永远排在它后面**，一直轮不到注入。用户越活跃，他的输入越是源源不断地插在那条 `'later'` 通知前面，结果就是「半小时看不到、其实第 2 分钟就好了」。这不是 agent 没动静，是它的通知被用户自己的输入一直压在底下。
- **(c) ② 的 root cause**：子 agent 读了 30 个文件、分析很细，但**主 agent 只拿得到它最后一条 assistant 消息里的 text**（`finalizeAgentTool` 的契约）。这个子 agent 干完活，最后一句偏偏是「好的，我已经把相关文件都看过了」这种收尾寒暄——于是主 agent 拿到的就是这句废话。那 30 个文件的分析如果没被**压进最后那段 text**，就等于没产出（中间过程一律不回主上下文）。这**不是**子 agent 干得不好，是它**没按收口契约把结论放在最后一段**——主 agent 只看最后一段，子 agent 却把精华留在了中间。
- **(d) 判定**：**都是 by-design，不是 bug。** ① 是「别让系统消息饿死用户输入」的故意设计（task-notification 就该让位给用户输入）；② 是「子 agent 只回最后一段 text、中间过程一律丢弃」的故意契约（这正是隔离的代价与价值）。两者都不是代码坏了，是机制如此——**但产品体验确实坏了**，得在机制之上补救（见 e 与下一条）。② 的产品补救是：**在子 agent 系统提示词里硬性要求「最终输出一段结构化总结，且这必须是你的最后一段文字」**，把精华逼到最后一条 assistant 消息里。
- **(e) 运营硬要求「后台一跑完立刻弹」**：要动的是**通知优先级 / 注入通道**——把 task-notification 从 `'later'` 提到 `'next'` 甚至 `'now'`，或绕开主循环队列直接推一个 UI 通知。**代价**：你正是**打破了「别让系统消息饿死用户输入」这个设计意图**。提到 `'next'` 或更高，后台 agent 的结果就会**插在用户正在进行的输入之前**注入，把用户的对话流打断——用户打字打到一半，主 agent 突然冒出一段「你两分钟前派的后台任务结果如下……」。课文故意把它压在用户输入之下，就是不想让异步结果抢用户的话头。所以这个硬要求本质是「实时性 vs 不打断用户」的取舍：要么换成「UI 角标 / 侧栏提示」这种**不进对话流**的弱通知（推荐），要么接受打断、把优先级提上去。**命门**：别简单地「调高优先级了事」——先认出你动的是一个**有意压低**的旋钮，它压低是为了保护用户输入不被系统消息抢占；理解了这个意图，才知道更好的解法是「另开一条不抢对话流的通知通道」，而不是在同一条队列里把系统消息抬到用户之上。`[决策四 / 二 / 五]`

## 评点（效果优化 / 架构设计 / 收口——自评用，非标准答案）

### 效果优化

**A（嫌慢 / 贵）的旋钮**

- **收紧「派不派」的判据**：只在「子任务会产生大量过程噪音、否则会撑爆主窗口」时才派，小调研主 agent 自己干（呼应量化题 (d) 那条不等式）。**效果**：少派、少起实例、少烧固定开销。**反作用**：判据收太死，本该外包的脏活流回主上下文，反而更快触发压缩。
- **给杂活子 agent 配便宜模型 / 收窄工具集**：「只摸现状」的 Explore 用便宜模型、只给读 / grep 工具。**效果**：单个子 agent 更省更快。**反作用**：模型太弱，结论质量掉，直接喂给 B 那派的「抓不到重点」。
- **能同步就别后台**：后台要起通知队列、要排队注入，链路更长。**效果**：少一层异步开销。**反作用**：长任务同步会阻塞主 agent。

**B（嫌不准）的旋钮**

- **把子任务说得更具体**：在 prompt 里写明「主 agent 关心的是 X，请重点回答 X」。**效果**：子 agent 使对劲。**反作用**：几乎无反作用——这是最便宜的一手（见下「同时缓解」）。
- **多 fork 几轮父历史**：让子 agent 看到主 agent 最近在干嘛，自己判断什么重要。**效果**：更贴主 agent 的关切。**反作用**：**直接顶死约束的边缘 + 顶 A 的成本**——fork 越多，隔离越弱、子 agent 窗口越大越贵，正是 A 嫌的。
- **强化收口提示词**：要求子 agent 最后吐结构化总结、覆盖指定几点。**效果**：拿回来能直接用。**反作用**：几乎无。

**互相加剧的一对（关键洞察）**：让 B 更准，最自然的手是「**多 fork 父上下文**」——让子 agent 知道主 agent 在关心什么。但这一手**直接顶到 A**：fork 越多，① 越逼近「不许去隔离」那条死约束的边缘（fork 全量就等于没隔离），② 子 agent 起始窗口越大、越贵越慢，正是 A 嫌的「慢 / 贵」。所以「靠塞上下文让 B 准」和「A 要省」是**直接拉扯**的一对。

**能同时缓解 A 和 B 的手段（关键洞察）**：准不准、省不省，**未必只能靠 fork 上下文来调**。另一个旋钮专管「子 agent 该往哪使劲、最后交什么」——就是 **prompt 的精确度 + 收口提示词**：把任务说清楚（「重点答 X」）、把交付物规格写死（「最后一段必须是覆盖 X/Y/Z 的结构化总结」）。这一手**不破隔离、不加起始上下文、几乎零成本**，却让子 agent 既使对劲（B 更准）又不用主 agent 多塞历史（A 不更贵）。它跳出了「准 vs 省靠塞上下文零和」的困境——因为「准」的来源不只有「给更多上下文」，还有「**把任务和交付物定义清楚**」，后者几乎免费。

**陷阱**：列了旋钮不写反作用；没看出「fork 父上下文」同时顶死约束和顶 A 成本；以为「让子 agent 更准」只能靠塞上下文、漏了「精确 prompt + 收口规格」这条几乎免费的路；把「去掉隔离让子 agent 看全」当解药（直接违反死约束、且抹掉子 agent 全部价值）。

### 架构设计

**强答案应触及的维度**

- **(1) 派发与隔离**：最小接口 = `prompt`（子 agent 的全部任务）+ `agent_type`（决定系统提示词 / 工具 / 模型）；可选 `model` / `run_in_background` / 隔离参数。起始上下文**默认空白**（`messages=[prompt]`），**留一个 fork 旋钮**（默认 none，将来可 fork 最近 N 轮）。引擎**必须是同一个主循环**——子 agent = 「新 messages 数组 + 新系统提示词 + 同一个 loop」，参数化掉起始消息 / 提示词 / 工具 / 模型四样，**别造第二套引擎**（这是 claude 验证过的：`query()` 父子共用）。
- **(2) 收口契约**：返回值 = 子 agent **最后一段文字**，中间过程一律不回主上下文（这是契约不是可选项，回灌中间过程 = 子 agent 价值清零）。逼它吐有用结论的办法：在子 agent **系统提示词**里硬性要求「你的最终输出就是交付物，最后必须输出一段结构化总结，覆盖 X/Y/Z」——因为主 agent 只看最后一段，这条提示词是「拿到废话」还是「拿到干货」的分界。
- **(3) 同步 vs 后台**：M0 **先只做同步**（阻塞等、结论直接回当轮，最简单最可控）。后台是大特性（要通知队列、agentId 寻址、UI 进度），等真有「用户想让 agent 后台跑长任务」需求再上。若做后台，结果靠**注入合成 user 消息**回主循环，优先级**排在用户输入之后**（抄 claude 的 `'later'`）——**理由**：用户说话永远该插队在前，别让系统消息饿死用户输入；要实时弹给用户，另开一条不进对话流的 UI 通知，别在主队列里把系统消息抬到用户之上。
- **(4) 安全底线**：① **递归守卫**——子 agent 默认拿不到「派 agent」的工具（能力剥夺，比计数器彻底），要嵌套是高级特性、显式开 + 设上限；② **并行写隔离**——子 agent 要写文件就上 worktree / 独立工作副本，只读摸现状可省；③ **子 agent 权限按角色配、不继承父**（接第 6 课：只读 agent 钉成「从不问、不能写」）；④ **并发上限**——一个 `max_concurrent_agents`，M0 就该有（桌面 app 每个实例吃内存吃配额）。**哪几条不分形态、M0 必须有**：递归守卫 + 并发上限（这两条防的是失控，任何形态都得有）；worktree 在「子 agent 要写」时才必需。
- **场景一（主线）**：主 agent 上下文**只多了一段「auth 是这样实现的」结论**，那一大堆文件读 / grep 全留在子 agent 窗口、用完即弃——主窗口干净如初。
- **场景二（并行写）**：3 个子 agent 各自一个 **worktree**（独立工作副本 + 独立分支），各改各的、事后再合，谁也踩不到谁。这和「只读摸现状」的本质不同：只读子 agent**不碰文件**，进程内隔离上下文就够，**不需要文件系统级隔离**；一旦要写，上下文隔离不够了，必须叠**文件级隔离**（worktree），否则两个 agent 互删对方改动。
- **场景三（递归）**：默认**派不成**——子 agent 的工具集里没有「派 agent」的工具（能力剥夺式守卫）。凭什么挡：防一个 agent 派 10 个、每个再派 10 个的指数爆炸，比运行时计数器彻底。要放（高级场景）须显式开 + 设深度 / 并发上限。
- **场景四（跨课边界，接第 5 课）**：取决于你把子 agent 产出落在哪一层。**M0 推荐**：子 agent 是一次性的、不跨重启——重启后**不恢复**正在跑的子 agent（它的窗口本就用完即弃），只要主 agent 的**事件日志**里记下了「派过一个子 agent + 它回的结论」就够，重放主线对话即可。**真要支持「重启恢复整棵 agent 树」是 codex 的持久 spawn 图那套重机制**，M0 没这场景（子 agent 都是一次性的、不跨重启），别上。把子 agent 的**结论**（不是中间过程）写进事件日志，多 agent 会话就和单 agent 一样可重放、可调试——这是该早做的（接第 5 课）。
- **复用 / 打破**：**直接复用**——「子 agent = 上下文压缩机」的隔离机制、「只回最后一段」的收口契约、worktree 文件隔离、能力剥夺式递归守卫。**打破的假设 + 必须新增**：若要支持后台 + 跨重启，就打破了「子 agent 一次性、不跨重启」这个 M0 假设 → 必须**新增**异步通知队列 + 子 agent 产出落盘（接第 5 课的事件日志）。
- **陷阱**：另造一套引擎跑子 agent（该复用主循环）；让子 agent 把中间过程同步回主上下文（破隔离）；把后台结果优先级抬到用户输入之上；只读子 agent 也强上 worktree（浪费）；以为「重启恢复整棵 agent 树」是 M0 必需（那是集群场景，桌面端用不到）。

### 收口

- **(1) 「子 agent = 上下文压缩机」喂饱哪几性**：**自动**（脏活外包出去、主 agent 不被过程噪音淹没，能一口气把大任务推下去）+ **稳**（主窗口干净、更晚触发压缩、更少踩第 3 课压缩炸缓存的坑）。它和第 3 课压缩同目标（省主上下文），但**事前隔离优于事后压缩**：压缩是窗口满了再砍、且**会炸缓存**（炸掉稳定前缀，下一轮全量重算）；子 agent 隔离是脏活**根本不进主窗口**，主 agent 的缓存前缀**完全不受影响**（子 agent 烧的是它自己那条一次性 cache 链）。用三性说：事后压缩是**用稳换稳**（砍上下文保住不溢出，却炸了缓存这条稳）；事前隔离是**净赚**（既省了主上下文、又没动主缓存）——所以隔离在 强 / 稳 / 自动 上全面优于压缩。
- **(2) 抄 claude 还是 codex**：**抄 claude 的层级树主干，codex 的对等图留着别上。** codex 那张图多付的复杂度（共享控制平面 + 内存总线 + `trigger_turn` 协议 + 持久 spawn 拓扑 + 并发 limiter）买到的是「多个**长期** agent 在一个进程里**对等协作、互相喊话、崩溃后恢复整棵树**」——这是为「无人值守 / 云端 / agent 集群」准备的能力。deepseek 是**单用户桌面 coding agent**，它的多 agent 需求几乎全是 claude 那条主干（父派子摸现状 / 干活、子回结论的一次性 fan-out），**根本没有「多个长期 agent 对等协作」的场景**——上了 codex 那张图，就是给自己背一套用不到的对称性（复杂度守恒：你多付的复杂度没换来对应价值）。不上它，deepseek 牺牲的是**那部分用不到的「强」（对等协作 / 集群恢复）**，保住的是 **稳 + 自动**（少一大堆能出错的机制、主线更简单更可控）。这笔牺牲划算，因为牺牲的能力 deepseek 本就用不到。**但有一个几乎零成本却锁死未来的决定要早做**：spawn 这层别写成阻塞调用栈（`await child.run()` 直接返回结果），要写成「返回 agentId 的异步节点 + 一张花名册」——这条边际成本近乎零，却决定了将来能不能从「一次性 subagent」平滑长成「团队」。
- **(3) 收成一句**：**一旦你把子 agent 理解成「上下文隔离器」而不是「多一个干活的」，几个看似无关的设计取舍答案就全部一致——因为它们是同一条原则（隔离是因）的四个推论。** ① 默认**不 fork** 父上下文（fork 了就漏进噪音、破隔离）；② **只回最后一段结论**（回中间过程就把噪音灌回主窗口、破隔离）；③ **不许边干边同步**（同步就是过程噪音实时流回主窗口、破隔离）；④ 默认**不递归派 agent**（递归会让脏活在你看不见的地方指数膨胀，每一层的隔离契约不变——递归守卫保的是「别失控」，和前三条同源于「让脏活留在别人窗口、别污染我」这条总原则）。把「隔离是因、并行是果」记牢，这四件事就不是四条孤立规则，而是一条原则的四次应用——**子 agent 的灵魂是信息屏障，不是多一双手**。

- **陷阱**：把「子 agent = 上下文压缩机」收成「自动 vs 稳的张力」（它恰恰是二者同向、且比第 3 课压缩更稳的反例）；只说「隔离好」而没说清它好在「不炸主缓存、是净赚」；论证 deepseek 该抄哪边时只比功能多寡、不落到「多付的复杂度有没有买到 deepseek 用得上的能力」；把「不 fork / 只回结论 / 不许同步 / 不递归」当四条独立规则背，没看出它们同源于「隔离是因」。
