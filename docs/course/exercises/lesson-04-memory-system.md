## 机制层（有标准解，但答案不在课文里）

### 推演 1 · 抽到一半被打断，两条水位线分别停在哪、第 3 课压缩接着会切出什么 `[决策二，接第 3 课]`

claude SessionMemory 侧，一个会话正跑着，按时间顺序发生这串事：

1. 历史已涨到 18k token，上次抽取后又涨了 6k、新增了 4 次工具调用——`shouldExtractMemory` 这一拍判定「要抽」；
2. 紧接着 `extractSessionMemory` 派出 forked agent 去跑「更新记忆」prompt；
3. **但就在 forked agent 还在后台写记忆文件、没返回成功之前**，主回路又采样了一拍：模型发出了一个 `Read` 工具调用（`tool_use`），对应的 `tool_result` 还没回来，历史尾巴此刻挂着一个悬空的工具调用；
4. 这时第 3 课的 session memory compact 恰好被触发，要按水位线切历史。

把这一刻的机器状态讲清，逐问作答，别跳步：

- (a) 第 1 步判定「要抽」的那一瞬间，`lastMemoryMessageUuid` 和 `lastSummarizedMessageId` 这两条指针**各自被动了没有**？谁此刻就推进、谁还没动、为什么是这个先后？
- (b) 第 2 步那次抽取**还没返回成功**，可主回路第 3 步又涨了一拍历史并且尾巴挂着悬空 `tool_use`。如果此刻**抽取成功了**回调进来要推进 `lastSummarizedMessageId`，它会推到第 3 步那条挂着悬空工具调用的消息上吗？挡它的是哪一道判断、挡住之后水位线停在哪？
- (c) 第 4 步压缩按 `lastSummarizedMessageId` 切历史：因为有 (b) 那道闸，它切出来的尾巴**自洽不自洽**？如果**没有**那道闸、水位线被推到了悬空 `tool_use` 那条消息上，压缩切完会留下什么、模型下一拍看到的历史坏在哪？
- (d) 顺带回答：第 1 步推进的那条指针（`lastMemoryMessageUuid`）在这整个「抽到一半」的过程里担了什么职责——它防住了什么、又跟压缩切历史**有没有**关系？

> 这道题的核心：两条 uuid 指针不是一条，它们在「判定」和「抽成功」两个不同时刻、按两套不同条件推进；把它们当一条，就会在「抽到一半被打断」时讲错谁停在哪。

### 量化 1 · 「该不该真跑一次整合」——给一个你敢写进代码的判据 `[决策三]`

codex Phase 2 整合是后台跑的，但它**不是每次后台任务都真的调一次整合模型**：同步完碎片后先 `git diff` 工作区，**没变化就标 `succeeded_no_workspace_changes` 直接返回、不花那次模型调用**。现在让你把这条「跳过」从一个布尔判断升级成一笔账，并给出 deepseek 该不该照抄、抄到什么粒度。

设：整合一次的模型调用成本记为 `C_consolidate`（强度 `Medium`，读全部碎片 + 写 summary，量级不小）；后台任务被调度起来的频率是每有一个 turn 成功提交就起一次；一个活跃用户一天可能提交几十上百个 turn，但其中**真带来新碎片**（Phase 1 抽出了新 `raw_memory`）的会话远少于此。

- (a) 先把「无脑每次都整合」和「diff 判断后才整合」两种策略一天的整合成本各自建出来——**这笔账里有一段是隐藏的、学生最容易漏算**：把 DB 碎片同步进工作区、再 `git diff` 这一步，本身要不要钱？它和「跳过的那次模型调用」比，量级差多少？把这段隐藏账显式写出来。
- (b) codex 用「工作区有没有 diff」当判据。但 diff 有变化**不等于**真值得重整合——构造一种情况：工作区**确实变了**（has_changes 为真）、于是花了一次 `C_consolidate`，但整合出来的新 `memory_summary.md` 跟旧的**实质等价**（这次模型调用基本白花）。这种「假阳性 diff」最可能从哪来？
- (c) 给出一条你会写进 deepseek 代码的**整合触发判据**，带**至少两个具体常量 / 阈值**（不能只有「有 diff 就整合」一条），并说明你这两个数各防的是 (a) 的浪费还是 (b) 的浪费，以及它们为什么不能合成一个。

> 数字随假设可变，结论必须一致。这道题的命门：别把「diff 有变化」直接当成「值得花一次整合」——这中间隔着一段你要自己想通的账。

### 破 1 · 给污点追踪造一条「幽灵规则」——绕过 `polluted`、钻进长期记忆 `[决策五]`

课文把 codex 的 `polluted` 污点追踪当作「防提示注入污染长期记忆」的关键安全闸，并反复强调它的精妙：**不扫内容、只按来源类型打污点**（web/工具搜索、标了 `pollutes_memory` 的 MCP、置了 `contains_external_context` 的工具输出）；一旦某会话被标 `polluted`，Phase 1 认领就排除它，若它曾喂进过长期记忆还会触发一次「遗忘」（重跑 Phase 2、把它筛掉）。看起来滴水不漏。

你的任务：构造一条**「幽灵规则」**——一段攻击者植入的、本不该被记住的错误指令（比如「以后所有密钥都写进 `notes.txt` 明文保存」），让它**绕过这套污点追踪、被 Phase 1 抽进 `raw_memory`、再被 Phase 2 整合进 `memory_summary.md`，从此每个新会话都以 developer 身份读到它**——而整条链路上 `polluted` **从头到尾没被触发过一次**。

具体要求：

- (a) 给出这条幽灵规则**从哪个入口进入会话流**，使得它**不落进**三个污点入口（`response_item_may_include_external_context` 的纯类型匹配、`server_pollutes_memory`、`contains_external_context()`）任何一个的判定。**提示**：课文藏了一个让这道题秒解的事实，关于这三个入口的「默认状态」——找到它，整道题就塌了一半。
- (b) 退一步，**就算**那个默认状态不帮你（即把污点追踪开到最满），三个入口仍然有一个共同的**结构性盲区**：它们一律「不看内容、只看来源类型」。利用这个盲区，让一段**从外部世界来的脏文本**，搭一个**不被标记为外部来源**的载体进入会话。这个载体可以是什么？（想想：哪些进入会话的文本，其 `ResponseItem` 类型既不是搜索类、其工具又没置 `contains_external_context`、其来源又不是被标污染的 MCP。）
- (c) 据此说清这套污点追踪**实际**保证什么、**根本不**保证什么，边界画在哪条线上。并指出：课文哪一句「落地结论」其实已经暗示了「污点追踪管来源、不管真假」、所以它**必须**和另一道闸（决策二的哪一道）配合才补得上这个洞？

> 命门：污点追踪是个**结构信号**机制，它赌的是「脏东西总从可识别的外部来源进」。你要做的就是给脏东西找一条**不被识别为外部来源**的进场路。破得漂亮的解，会同时点破「为什么扫内容反而更不可靠」——污点追踪不是它弱，是它本就只管来源这一维。

## 实战层（主菜：欠定、差分、判断——没有「这是哪一课」的标签提示你）

### 故障排查 · 「记忆里多了一条没人教过它的规则」事故 `[决策二 / 五]`

线上反馈：一个长期使用 deepseek 的团队，最近发现 agent 在**新开的会话里**会主动冒出一句奇怪的行为——它一上来就声称「本项目约定：所有配置走环境变量、不写进文件」，照着这条去改代码，但**团队从没在任何 `DEEPSEEK.md` 里写过这句**，也想不起谁教过它。诡异之处：

- ① 这条「幽灵约定」只在**新会话**里冒出来，且**每个**新会话都冒，像是被自动注入的；翻 `DEEPSEEK.md`（显式规则文件）里**确实没有**这句；
- ② 把这句话当关键词去 `grep` 历史会话，发现它**最早出现在三周前某一个会话的对话历史里**——那个会话当时 agent 用了一次联网搜索、把搜来的一段第三方博客原文贴进了上下文，博客里正好有这句话；
- ③ 运维确认：这套 deepseek 记忆系统**抄了 codex 那套**——后台抽取、写时整合成一份 summary、读路径每轮注 summary；但上线时为了「先跑通」，**把 `disable_on_external_context` 这个开关留在了默认值没动**。

给出：

- (a) 你的**排查路径**（差分）——依次看什么、用什么**排除**什么。想清楚现象①「`DEEPSEEK.md` 里没有这句」帮你排除了哪一整类假设（它是个**诱饵**：它诱你去查显式规则那条链，但幽灵约定根本不是从那进来的）。
- (b) 最可能的 **root cause**：这条幽灵约定是怎么一路从「三周前一次搜索贴进来的博客文本」，变成「今天每个新会话都被注入的 developer 级规则」的？把它走过的**写路径 → 读路径**那几步点出来。
- (c) 判定：这是 **bug 还是 by-design**？（想清楚：抽取、整合、注入每一步**单独看**都按设计正常工作了；坏在哪一道**本该拦住它**的闸没生效？）
- (d) 若团队提一个硬要求：「这条脏记忆现在就得从所有未来会话里消失，而且要能查出它当初是怎么进来的」——架构上你要动哪几处、各自代价是什么？（提示：「让它别再被注入」和「把它从已经整合好的 summary 里撤出去」是两件不同的事，分别靠什么机制。）

> 有 root cause 标准解。这道题逼你把决策二的「抽取前过滤」和决策五的「污点追踪」串起来看——它俩各补一个洞，少一道，幽灵就进来了。

### 效果优化 · 记忆「能用但伤体验」，不许换模型、不许加 pull 工具 `[决策三 / 四]`

记忆功能 works，但两类投诉反复来：

- **(A) 注入的记忆「过时 / 没跟上」**——用户这次会话里刚改了一个约定（比如「以后用 yarn 不用 pnpm」），可下一个新会话开起来，agent 注入的 `memory_summary.md` 里**还写着 pnpm**，照旧的来，用户得再纠正一遍；
- **(B) 注入的记忆「太杂 / 占地方」**——`memory_summary.md` 越攒越长，每轮被截到 2500 token 注进 prompt 的那一截里，经常混着一堆跟当前任务**八竿子打不着**的旧记忆，挤掉了真正相关的那几条，用户觉得「它记了一堆没用的、该记的反倒没注进来」。

**死约束：不许换模型，也不许给模型开 pull 工具（`dedicated_tools` 必须保持关）**——你只能在「写时整合（决策三）+ 读路径截断 / 选择（决策四）」这些课文给过的零件里调。

针对 A、B 各列出你能动的 runtime 旋钮（至少各两个），预测每个旋钮的**效果方向**，并指出它的**反作用**（调它会让什么变差）。最后两问最关键：

1. A 和 B 看着是两个毛病，但有没有可能**根子上是同一个设计选择**（codex「写时整合成一份全局 summary」vs claude「读时按相关性选碎片」）**站错了边**导致的？是哪一边、它分别怎么同时喂出了 A 和 B？换边能不能同时治 A 和 B、又会引入什么新代价？
2. 找出**一对会互相加剧对方**的旋钮——一个是为压 A（让记忆更新更快）、一个是为压 B（让注入更干净），但它俩同时上会打架。点出这对旋钮、说清它俩在哪个量上对冲。

> 无标准答案，给评点。这道题的耦合点藏在「整合策略」这个根选择里——别只在表层调阈值，往「写时整合 vs 读时选择」那层想。

### 架构设计 · 给 deepseek 设计记忆子系统，且要同时喂得动第 3 课压缩 `[决策一 / 二 / 三 / 四 / 五，接第 3 课]`

新需求：deepseek harness 要从「没有记忆」升级成一套完整记忆子系统。基于本课五个决策，设计它，并落到接口上：

- (1) **三类分清**：你的代码里把「记忆」拆成哪几类（对应决策一的 A/B/C）？各自谁写、何时写、怎么注入？M0 先做哪一类、为什么是它打地基？
- (2) **写路径**：抽取跑在哪——主回路里还是独立受限 agent 里？这个 agent 的写能力面掐到多小（精确到「它只能对什么文件做什么操作」）？触发用阈值还是后台批处理，给出你的触发判据（带具体常量）。喂给抽取 agent 之前，你**在代码里物理删掉**哪些注入物？
- (3) **整合 + 读路径**：碎片→精炼这步走「写时整合」还是「读时选择」？原料和成品怎么分开存、读路径只碰哪个？注入用什么 role、截到多大、为什么不用 system 级？
- (4) **安全闸**：决策五那套（最小能力面 / 污点追踪按来源标记 / 双向遗忘 / 限流锁租约 / 递归防护）你必须上哪几道、各防什么？尤其：你的「污点标记」按来源还是按内容判、为什么？

然后用**四个场景**验证你的设计，其中**至少两个是失败 / 边界场景**，**且其中一个必须是跨课边界场景**：

- 场景一（正常）：一次干净的会话结束，里面有真实习得的事实（「这项目用 yarn」）——它怎么一路走到下个新会话的 prompt 里？
- 场景二（跨课边界，接第 3 课）：你要让这套记忆**同时**服务第 3 课的 session memory compact——抽取和压缩之间该共享什么状态、又**绝不该**共享什么？那条水位线指针由谁推进、谁消费？如果抽取「抽到一半」就被压缩消费水位线，你靠什么保证压缩不会切出孤儿工具调用？
- 场景三（失败 / 安全）：某次会话里，agent 联网搜了一段外部文本进上下文，里面藏着一句注入指令——你的子系统怎么保证这句**不被记进长期记忆**？如果它**已经**被记进去并整合进了成品 summary，你靠什么把它撤出来？
- 场景四（失败 / 抖动）：后台整合任务被高频调度（每个 turn 都起一次），但大多数 turn 没带来新碎片——你的子系统该做什么、**绝不该做什么**？

最后点明：你的设计**直接复用了本课哪个已有机制**（提示：抽取和压缩的解耦、以及「污点追踪」这种「不信内容信来源」的思路，你不该自己重造）、**打破 / 新增了哪个假设、必须为它补一套什么**（提示：「机器自动写、又自动注入未来每个会话」这个属性，是别的子系统都没有的）。

> 无标准答案，给评点。场景二和场景三是这道题的真考点——一个把记忆和压缩的接缝逼出来，一个把安全闸逼到「不只挡未来、还要撤过去」。

## 收口 · 强 / 稳 / 自动，记忆这台机器把哪一性顶到了最危险的位置（本课牵引题）

记忆这件事，表面看全是为了「强」和「自动」：让 agent 跨会话越用越聪明（强）、还是它自己后台默默攒、不用人管（自动）。但课文用了整整一个决策五，外加决策二的「抽取前过滤」、决策三的「极严沙箱」，全在给它**踩刹车**。

**论证**：记忆这台机器，相比第 3 课的压缩，它把「强 / 稳 / 自动」里的哪一性顶到了一个**比压缩更危险**的位置？给出判断，并具体地——

- (a) 指出记忆里哪一部分是「强 / 自动的冲劲」（它让 agent 多扛了什么、且是几乎不用额外投护栏就默认能跑的）；
- (b) 指出哪一大块**纯粹是稳的护栏**，且说清：这块护栏为什么比压缩那一侧的护栏**更重、更不能省**——「自动写、又自动注入未来每一个会话」这个属性，把一条记错的记忆的危害放大成了什么？（想清楚：压缩压坏了，最多坑**这一个会话**；记忆记错了，坑的是**之后所有会话**，而且没人会去逐条审。）
- (c) 回答：照这个结论，deepseek 做记忆时，护栏投资**主要该砸在哪个决策上**——是把抽取 / 整合的记忆**质量**做得更聪明（决策二 / 三的智力部分），还是把「自动写的东西即使错了也只能动一小块地、且脏来源进不去、进去了还能撤出来」（决策五）做到滴水不漏？为什么。

（及格线：能各举机制，认出记忆的护栏比压缩重。高分线：看穿「记忆把『自动』这一性顶到了最危险的位置——自动写 + 自动注入未来所有会话 = 一条错记忆静默污染整条时间线」，于是稳的护栏不再是边界条件、而是**前置条件**：决策五那套安全闸必须和功能**同时上**，否则记忆这个功能本身就不该开。并把这个结论接回第 1 课收口「稳是强 & 自动的边界条件」——指出记忆是那句话被推到极端的样子：当『自动』的作用域从『这一轮』扩张到『未来所有会话』，稳就从边界条件升级成了开关本身。）

### 热身（对的是第 2 句）

### 推演 1

- **(a) 两条指针在「判定要抽」这一刻各动了没**：只有 `lastMemoryMessageUuid` 动了，`lastSummarizedMessageId` 没动。`shouldExtractMemory` 一旦判定为真，**立即**把 `lastMemoryMessageUuid` 推到当前末条消息（`sessionMemory.ts:172-176`，`shouldExtract` 为真就 `lastMemoryMessageUuid = lastMessage.uuid`）——它的职责是给「自上次以来新增几次工具调用」提供新的计数起点，并防止抽取还在后台跑时又被重复触发。而 `lastSummarizedMessageId` **此刻绝不动**：它要等 forked agent **抽取成功之后**才考虑推进。先后是有意的：决策时先把「计数起点 / 防重入」这条立住，水位线那条留到「确实抽成了」再说。
- **(b) 抽成功回调要推进 `lastSummarizedMessageId`，会推到那条悬空 `tool_use` 上吗**：**不会**。挡它的是 `updateLastSummarizedMessageIdIfSafe`（`sessionMemory.ts:488-495`）里那道 `if (!hasToolCallsInLastAssistantTurn(messages))`——只有「最后一个 assistant 轮没有悬空工具调用」时才推进。此刻第 3 步那条 `Read` 的 `tool_use` 还挂着、没有配对的 `tool_result`，`hasToolCallsInLastAssistantTurn` 为真，于是这道闸**拦下推进**：水位线停在**上一个尾巴自洽的位置**，不动到悬空那条上。
- **(c) 压缩按水位线切，自洽不自洽**：因为有 (b) 那道闸，水位线停在自洽位置，压缩按它切出来的尾巴**自洽**——切点之后留的是完整的、配对齐全的历史。**反过来，假如没有那道闸**、水位线被推到了第 3 步那条悬空 `tool_use` 消息上：压缩按它切历史，就会把一个 `tool_use` 留在「已进记忆、可丢」的一侧、而它配对的 `tool_result` 还在「未进记忆、必须留」的另一侧（甚至根本还没产生）——切完留下一个**有调用、无结果的孤儿** `tool_use`。模型下一拍看到的历史里挂着一个永远等不到结果的工具调用，正是第 3 课安全底线第 1 条「绝不切开 tool_use/tool_result 对」要防的坏。
- **(d) `lastMemoryMessageUuid` 在「抽到一半」里担什么**：两件事——① 给「自上次以来新增几次工具调用」提供计数起点（下次 `shouldExtractMemory` 数工具调用，从它往后数）；② **防重入**——抽取在后台跑着没回来时，它已经被推前了，于是下一拍 `shouldExtractMemory` 再判定时，「新增工具调用数」从这个新起点重新算，不会因为同一批历史又触发一次抽取。**它和压缩切历史没有关系**：压缩消费的是 `lastSummarizedMessageId`，不是它。这正是两条指针解耦的意义——`lastMemoryMessageUuid` 管「抽取自己的节奏 / 防重入」，`lastSummarizedMessageId` 管「抽取和压缩之间那条共享水位线」，互不串台。

> 命门：把两条 uuid 指针当一条，是这道题最容易栽的地方。它们在**不同时刻**（判定 vs 抽成功）、按**不同条件**（无条件推进 vs 末轮无悬空工具才推进）动，管**不同的事**（防重入 vs 跨子系统水位线）。「抽到一半被打断」恰恰把这个区别逼到台前：判定那一刻 `lastMemoryMessageUuid` 已经前进、`lastSummarizedMessageId` 还没动；而那道「末轮无悬空工具」的保险，正是把抽取的不确定性挡在压缩的切点之外的关键一闸。

### 量化 1

> 解 = 把整合的隐藏账（同步 + diff vs 模型调用）建出来 + 认出「diff 有变化 ≠ 值得整合」+ 敢给两个有理由的常量。数字随假设可变，结论必须一致。

- **(a) 两种策略一天的账 + 隐藏账**：
  - 「无脑每次都整合」：后台任务被起的次数 ≈ 一天的 turn 数（设 N，量级几十到上百），每次都花一个 `C_consolidate`（`Medium` 强度、读全部碎片写 summary）→ 一天 `N × C_consolidate`。
  - 「diff 判断后才整合」：每次都做「把 DB 碎片同步进工作区 + `git diff`」，只有**真有新碎片**的那 M 次（M ≪ N）才花 `C_consolidate` → 一天 `N × C_sync + M × C_consolidate`。
  - **隐藏账（最容易漏的一段）**：`C_sync`（同步碎片到 `rollout_summaries/` + `raw_memories.md`，再 `git diff` 工作区）是**纯本地文件 / git 操作，不调模型**——它和 `C_consolidate`（一次 `Medium` 强度模型调用）**量级差几个数量级**。学生想当然会把「每次都同步 + diff」也当成一笔大开销而犹豫，其实 `N × C_sync` 相对 `(N−M) × C_consolidate`（被跳过省下的那一大笔模型钱）几乎可忽略。**结论：diff 跳过几乎是净赚**——拿一笔可忽略的本地 diff 成本，换掉 `(N−M)` 次昂贵的模型整合。这就是 codex 为什么敢「无脑先同步 + diff，再决定要不要整合」。
- **(b) 假阳性 diff（has_changes 为真却白花一次整合）从哪来**：工作区 diff 检测的是「碎片文件的字节有没有变」，不是「整合后的成品会不会变」。最可能的假阳性：**新进来一条 `raw_memory`，但它表达的信息和现有 summary 已覆盖的实质等价**——比如第 N 个会话又记了一条「项目用 pnpm」，碎片文件确实多了一行（has_changes 为真）、于是花了一次 `C_consolidate`，但整合模型读完发现没什么新东西可合，新写出的 `memory_summary.md` 跟旧的实质一样。这次模型调用基本白花。（同质记忆越多，这种假阳性越频繁——这恰好是课文那张对照表说「codex 写时整合适合记忆同质」的另一面：同质记忆的去重收益高，但也最容易触发「碎片变了、成品没变」的空整合。）
- **(c) deepseek 整合触发判据（示例，关键是两个数 + 各防哪类浪费 + 为什么不能合一）**：
  ```
  阈值一 · 新碎片量门槛 K(防 b 类假阳性):
    自上次成功整合以来,新增 raw_memory 条数 ≥ K(如 K=3)才触发整合;
    不到 K 条就攒着,别为一两条同质碎片就跑一次 Medium 整合。
  阈值二 · 最短整合间隔 T(防高频空跑):
    两次整合之间至少隔 T(如 T=30 分钟 / 或「至少 T 个 turn」);
    哪怕碎片够了,离上次整合太近也先压着。
  ```
  **为什么 K 和 T 不能合成一个数**：K 管「**够不够值得**整合」（防 b：碎片太少 / 太同质，整合是白花一次模型钱），T 管「**多久才允许再**整合」（防高频调度下哪怕碎片够了也别贴着跑、和限流 / 全局锁配合）。一个是「量」的门槛、一个是「频率」的门槛，针对的是 (b) 的「白花」和 (a) 的「高频起任务」两类不同浪费。**只留 K 不留 T**：碎片攒得快的活跃用户会让整合贴着调度频率连跑，和后台限流 / Phase 2 全局锁互相挤；**只留 T 不留 K**：到点了哪怕只有一条同质碎片也整合，又掉回 (b) 的空整合。两个数管两件事，缺一个就漏一类浪费。（注：codex 真实代码里这层是用 `git diff` + 全局锁 + lease 兜的，没有显式的 K/T 常量——所以这两个数是**你为 deepseek 做的设计判断、不是抄来的源码常量**，K、T 的具体取值随你的负载假设可调，结论「必须是两个、分管量与频率」不变。）

> 命门：`git diff` 有变化**不等于**值得花一次整合。这中间隔着「碎片变了 ≠ 成品会变」那段账（b 类假阳性），也隔着「本地 diff 几乎免费、模型整合很贵」那段隐藏账（a）。把这两段想通，你才会给出「量门槛 + 频率门槛」两个数，而不是单一个「有 diff 就整合」。

### 破 1

- **(a) 让幽灵规则不落进三个污点入口 —— 课文藏的那个秒解事实**：三个污点入口（`response_item_may_include_external_context` 的纯类型匹配、`server_pollutes_memory`、`contains_external_context()`）**全部由 `disable_on_external_context` 这个开关 gate，而它默认是 `false`**（源码：`config/src/types.rs:333` 默认 false；三个入口分别在 `stream_events_utils.rs:260`、`mcp_tool_call.rs:762`、`registry.rs:693` 处先判这个 flag，false 就直接 `return` 不打污点）。**换句话说：污点追踪是 opt-in 的，默认整套全关。** 所以最廉价的幽灵：什么都不用伪装——只要部署方没显式打开 `disable_on_external_context`（默认就没打开），攻击者**直接用一次正常的 web 搜索**把幽灵规则的文本搜进上下文即可，三个入口全部因为开关默认关而失效，`polluted` 从头到尾不触发，抽取照常把它抽进 `raw_memory`、整合进 summary、注入未来每个会话。这一问的答案就藏在课文那句「**默认是 `false`……污染标记设成 opt-in**」里——找到它，半道题塌了。
- **(b) 就算把开关开到最满，仍有的结构盲区**：三个入口**一律只看来源类型、不看内容**。所以哪怕污点追踪全开，只要让脏文本搭一个**来源类型不被标记为外部**的载体进入会话，就绕过去了。可用的载体，是那些「进了会话、但其 `ResponseItem` 既不是搜索类、其工具又没置 `contains_external_context()=true`（trait 默认就是 `false`）、又不来自被标 `pollutes_memory` 的 MCP」的文本。例如：
  - 一个**普通的本地工具**（比如读文件、跑命令）把脏文本读进来——这类工具的输出 `contains_external_context()` **默认 false**（`tool_output.rs:23` trait 默认返回 false，只有 web 搜索那种会主动置 true）。攻击者只要把幽灵规则**预先写进项目里某个会被 agent 读到的文件**（如一个被污染的 README / 配置 / 测试夹具），agent 用普通 `Read` 把它读进上下文——这条路**不经过任何被标记为外部来源的入口**，污点追踪看不见它。
  - 或者，把脏文本伪装成**用户自己输入**的一部分（社工 / 间接注入用户去粘贴）——user 消息更不是污点入口。
  - 关键：这些载体的 `ResponseItem` 类型不在 `matches!`（`WebSearchCall/ToolSearchCall/ToolSearchOutput`）里、工具没置外部标志、来源不是污染 MCP，所以**纯类型匹配一律放行**，脏文本照进 `raw_memory`。
- **(c) 污点追踪实际保证什么、不保证什么，边界在哪**：它保证的是「**凡是从被识别为外部来源的入口（搜索类 ResponseItem / 标了 pollutes_memory 的 MCP / 置了 external_context 的工具输出）进来的数据，碰过的会话不再作为可信学习来源**」——一个**结构信号**层面的保守隔离。它**不保证**「脏内容进不来」：只要脏文本搭一个**未被标记为外部来源**的载体（普通文件读、用户输入、未置标志的工具），它就既绕过类型匹配、又绕过 `contains_external_context`、又绕过 MCP 标记，畅通无阻。边界画在这条线上：**污点追踪管「数据的来源类型」，不管「数据的真假 / 内容是否是注入」。** 课文那句「落地结论」已经点破——决策五落地第 2 条「**按来源（数据项类型）标记，不靠扫内容判脏**……内容测不准，来源是确定的结构信号」——它老实承认了自己只管来源。所以它**必须**和决策二的「**抽取前结构化过滤注入物**」配合：污点追踪挡「外部来源碰过的会话」，过滤挡「混进历史的指令块 / skill 片段」；但二者**都不**校验「一段普通文本里是不是藏了注入指令」——这个洞，光靠这套机制补不上，最终只能靠「记忆用 developer 级而非 system 级注入（决策四，留被更高权威覆盖的余地）+ 人能一键清空审计记忆（决策五落地 5）」兜底。

> 命门：(a) 是「开关默认关」这个事实级的秒破——污点追踪默认根本没开，是 opt-in。(b) 是结构级的破——就算开满，它只看来源类型、不看内容，给脏文本找一个不被识别为外部来源的载体（普通文件读最典型）就能钻进去。破得漂亮的解会点出：**这不是污点追踪「弱」，是它本就只管来源这一维**——指望它扫内容识别注入，方向就错了（注入可伪装成任何文本，扫内容必漏）；它的价值在「来源是确定的结构信号、好判、不漏」，代价是「来源干净不等于内容干净」。

### 故障排查 · 「记忆里多了一条没人教过它的规则」

- **(a) 排查路径（差分）**：① 现象①「`DEEPSEEK.md` 里没有这句」是个**诱饵**——它诱你去查显式规则（A 类）那条链：是不是某个 `DEEPSEEK.md` 被改了 / 某级覆盖了。但幽灵约定**每个新会话都冒、且不在任何显式规则文件里**，恰恰排除了「它是显式规则」这一整类假设——它不是人写进规则文件的，是**机器自动注入的**（B 类长期记忆的注入特征：每轮 / 每会话自动塞、内容人没手写过）。② 现象②（grep 到它最早出现在三周前一个**用过联网搜索**的会话历史里、且文本来自搜来的博客）直接把范围锁死：这句话是**从一次外部搜索的结果进入会话流的**，后来被记忆系统**抽取 → 整合 → 注入**了。③ 现象③（`disable_on_external_context` 留在默认值没动 = 默认 `false` = 污点追踪整套关闭）是**root cause 的钥匙**：它解释了为什么那个「用了外部搜索」的会话**没有被标 `polluted`**、于是照常被 Phase 1 抽取。三刀下来，矛头指向「外部搜来的脏文本，因为污点追踪默认关，被当成会话习得的事实记进了长期记忆」。
- **(b) root cause（脏文本走过的写路径 → 读路径）**：三周前那个会话，agent 联网搜了一段第三方博客原文进上下文，里面有「配置走环境变量、不写文件」这句。因为部署时 `disable_on_external_context` 留在默认 `false`，**污点追踪整套没生效**——这个本应被标 `polluted` 的会话，`memory_mode` 仍是 `'enabled'`。于是后台 Phase 1 认领它（只认 `'enabled'`，它正好符合）、抽取出一条 `raw_memory` 把这句博客文本当成「会话学到的事实」记了下来；Phase 2 把它整合进 `memory_summary.md`（成品）；此后读路径每轮读这份成品、截到 2500 token、以 `developer_policy`（developer 角色）注入——**每个新会话一开起来，agent 就以「开发者下的策略」这个中等偏高权威级读到这句幽灵规则，照着干。**
- **(c) 判定：不是单点 bug，是一道本该拦住它的闸没生效（配置 by-design 漏开 + 默认值不安全）**：抽取、整合、注入每一步**单独看都按设计正常工作**——它们的职责就是「把会话里发生的事抽出来、合并、注回」。坏在**决策五那道污点追踪闸默认是关的、上线时又没显式打开**：那个会话本该在「搜了外部内容」的瞬间被标 `polluted`、从而被 Phase 1 排除在抽取之外，但因为 `disable_on_external_context` 默认 `false`，这道闸没生效，脏来源畅通直达长期记忆。所以这既是「codex 把污点追踪设成 opt-in」这个设计选择留下的**默认不安全**，也是 deepseek 上线时「为了先跑通没动这个开关」的**配置疏漏**——不是某段代码写错了，是一道安全闸没被打开。
- **(d) 团队硬要求：现在就让脏记忆从未来所有会话消失、且要能查它怎么进来的——动哪几处、代价多少**：这是**两件不同的事**，对应决策五里污点标记的「双向」能力——
  - 「**让它别再被注入未来会话**」（挡未来）：把那个三周前的污染会话标 `polluted`（`mark_thread_memory_mode_polluted`），此后 Phase 1 认领排除 `memory_mode != 'enabled'`，它再不会被重新抽取贡献新碎片。但**这一步还不够**——它只挡未来抽取，**已经整合进成品 summary 的那句话还在**。
  - 「**把已整合进成品的那条撤出去**」（撤过去）：靠 `mark_thread_memory_mode_polluted` 里那段——标污染时它查这个会话有没有「被选进过上次成功的 phase-2」（`selected_for_phase2`），有就 `enqueue_global_consolidation` 入队一次全局整合（doc 注释叫 "phase-2 forgetting"）。**注意：并没有一个专门的「删掉某条记忆」接口**——它就是让 Phase 2 **重跑**一遍，而因为这个会话现在 `memory_mode='polluted'`、会被 Phase 2 的输入筛选（只选 `'enabled'`）排除，于是重新整合出的 `memory_summary.md` 里**不再含它的贡献**，等效于把那句话从长期记忆里撤了出去。
  - 「**查它当初怎么进来的**」（审计）：靠把那句话当关键词 grep 历史会话 rollout（已做到、定位到三周前那个搜索会话），再加上一个「人可一键清空 / 审计记忆」的出口（codex 的 `clear_memory_roots_contents`，且拒绝 symlink 根）——机器自动写的东西，必须给人留检查和清除的口子。
  - **代价**：标污染 + 触发遗忘 = 一次额外的全局 Phase 2 整合（贵但离线、且全局锁串行化，不影响用户交互延迟）；最根本的修复其实是**把 `disable_on_external_context` 打开**（让污点追踪从此真生效），代价是此后凡碰过外部搜索 / 未知 MCP 的会话都不再贡献记忆——这是「containment 优先」的保守取舍，宁可少记，别记错。

> 这道题的核心：一条幽灵规则能进来，是因为决策二的「抽取前过滤」管不到「普通文本里藏的脏内容」、而决策五的「污点追踪」又默认关着——两道闸各有射程，少开一道，脏来源就直通长期记忆。修它也得双管：既标污染挡未来抽取，又触发 phase-2 forgetting 撤回已整合进成品的那条。记住「挡未来」和「撤过去」是**两件事、两套机制**，是这道题最容易只做一半的地方。

## 评点（效果优化 / 架构设计 / 收口——自评用，非标准答案）

### 效果优化

**A 记忆过时 / 没跟上的旋钮**

- **缩短整合延迟 / 提高整合触发频率**（让这次会话学到的「改用 yarn」更快进成品 summary）：效果方向——新会话注入的 summary 更新鲜。**反作用**：整合跑得勤 = 后台 `Medium` 整合模型调用更频繁、更烧钱，且更容易撞「碎片变了成品没变」的空整合（量化题 b 类）。
- **整合 prompt 里加「新事实覆盖旧事实」的去重 / 时序优先**（让「yarn」覆盖掉旧的「pnpm」而不是两条并存）：效果方向——summary 不再自相矛盾、新约定盖旧约定。**反作用**：靠模型判「谁覆盖谁」不可靠，可能误删仍有效的旧记忆；且这是 prompt 软请求、不是硬保证。
- **读路径偏好新记忆**（若用 claude 式读时选择：selector 多看 mtime、偏好新文件）：效果方向——新记忆更易被选中注入。**反作用**：一味偏新会漏掉仍相关的旧稳定事实。

**B 注入太杂 / 占地方的旋钮**

- **降低读路径 token 上限 / 注入更短**（比 2500 更紧）：效果方向——占 prompt 更少。**反作用**：截得太狠，真正相关的那几条也可能被截掉（截断是按位置砍、不挑相关性）。
- **从「读时全注 summary 截断」改成「读时按相关性选碎片」（claude 式 selector）**：效果方向——只注跟当前任务相关的几条，不再混一堆无关旧记忆。**反作用**：每次注入前多付一次 selector 模型调用（小但在线）；注意约束说不许开 pull 工具、但 selector 是 push 内部的相关性选择、不算 pull，仍可用。
- **整合时做更狠的去重 / 分主题**（让 summary 本身更精炼、不堆同质碎片）：效果方向——成品更短更干净。**反作用**：整合更贵、更慢，且过度合并会丢细粒度。

**(1) A 和 B 根上是不是同一个设计选择站错边（核心耦合）**：**很可能是——「codex 式写时整合成一份全局 summary」对这个负载站错了边。** 写时整合成**一份全局 summary** 意味着：① 它**滞后**——这次会话学到的「yarn」要等下一次后台整合才进 summary，于是 A（过时）；② 它是**全局的、不分任务**——所有记忆压成一份，读路径只能截断、没法按当前任务挑，于是 summary 越长越杂，B（太杂占地方）。**换到 claude 式「读时按相关性选碎片」**能同时缓解 A 和 B：碎片不预先合并（写得快、少滞后 → 治 A），读时按当前任务选相关的几条注（不混无关旧记忆 → 治 B）。**新代价**：每次注入前一次 selector 调用（在线小成本）、且注入的多条碎片之间可能重复（没预先去重）。这正是课文那张对照表的核心——**记忆同质选写时整合、记忆异质选读时选择**；这个团队的痛点（不同会话学不同任务的事实、且约定常变）说明它的记忆是**异质 + 易变**的，写时整合那一边站错了。

**(2) 互相加剧的一对旋钮**：**「为压 A 提高整合频率（学到就尽快整进成品）」× 「为压 B 把读路径 token 上限调大（怕截掉相关记忆，索性多注一点）」**。提高整合频率让 summary 长得更快、内容更多；此时若读路径上限又调大，每轮注进 prompt 的那一截就更长更杂——**B（太杂占地方）反被加剧**；且整合更频繁 = 成本更高，两个各自合理的优化（更新鲜 + 不漏注）合在一起，把「prompt 里塞了一大坨频繁更新的杂记忆」这件事顶到了最坏。

**陷阱**：列了旋钮不写反作用；没看出 A/B 根子在「写时整合 vs 读时选择」这个根选择、只在表层调阈值；把约束「不许开 pull 工具」误读成「不许用 selector」（selector 是 push 内部的相关性选择，可用）；忽略「换边」也有代价（selector 在线成本 + 碎片间重复）。

### 架构设计

**强答案应触及的维度**

- **(1) 三类分清**：A 显式规则（`DEEPSEEK.md`，人写、整段注、高权威 role）/ B 长期记忆（机器抽过往会话、跨会话、选一小段注）/ C 会话记忆（机器抽当前会话、阈值触发、喂压缩 + 会话恢复）。**M0 先做 A**——便宜、可控、立刻有用，且不碰任何「机器自动写记忆」的风险（决策五）；B/C 是有了基础设施后的增量。三类**在代码里从第一天就分开**，别用一个 `Memory` 糊（写入者 / 时机 / 注入方式三维全不同）。
- **(2) 写路径**：抽取**必须**跑在独立受限派生 agent 里、不是主 agent 顺手做（一是智力活会拖慢响应、二是权限完全不同）。能力面掐到最小：**写工具只能对那一个目标记忆文件做 Edit**（claude `createMemoryFileCanUseTool` 那把闸照抄），碰不到代码库任何别的文件。触发：要接第 3 课压缩就用阈值驱动（claude 的 10k 初始 / 5k 增量 / 3 工具调用是现成配方，且 **token 阈值永远是必要条件**）；要跨会话就后台批处理。**喂抽取 agent 之前在代码里物理删掉**：developer 消息、`DEEPSEEK.md` 指令块、`<skill>` 片段、各种 system-reminder——**结构化硬删（学 codex），别只在 prompt 里软请求模型「别记」**（claude SessionMemory 只软请求，不保险）。
- **(3) 整合 + 读路径**：碎片→精炼这步**必须有**，写时整合（codex）或读时选择（claude）挑一个；**原料和成品分开存**（`raw_memories.md` 原料 vs `memory_summary.md` 成品），**读路径永远只碰成品**。整合「**无变化就跳过**」（diff 判断，别白跑一次整合模型调用）。注入用 **`developer` 级 role、不用 `system` 级**——记忆是机器抽的、可能错，给 developer 级留「被更高权威覆盖」的余地；**一定要有「截到 token 上限」这一步**（codex 的 2500 是个现成数），别把整份记忆怼进去。
- **(4) 安全闸**：决策五那套**必须和功能同时上**——最小能力面（写工具单文件 / 无网络 / cwd 锁死 / 后台不弹审批就更要锁死沙箱、固定 `Never` / ephemeral）、**污点追踪按来源标记（不按内容！）**、双向遗忘（既挡未来抽取、又能撤回已整合进成品的）、限流 + 全局锁 + 租约 + **递归防护**（记忆 agent 内部关掉「生成 / 使用记忆」防套娃）。污点**按来源**：因为注入可伪装成任何文本、扫内容必漏，「这一轮有没有外部数据进来」是确定可靠的结构信号（污点追踪）。
- **四场景**：场景一（正常）→ 干净会话结束 → 抽取（剥注入物后）抽出 `raw_memory` → 整合进成品 summary → 下个新会话读路径截断后以 developer 注入。场景二（跨课，接第 3 课）→ 抽取和压缩**只共享一条水位线指针**（`lastSummarizedMessageId`：抽取推进、压缩消费），**绝不共享各自内部状态**；指针推进必须过「末轮无悬空工具调用」那道闸，否则压缩切出孤儿 `tool_use`（推演 1 那条）。场景三（安全）→ 外部搜来的注入文本：靠**污点追踪**把那个会话标 `polluted`、Phase 1 排除它；若已整合进成品，靠 **phase-2 forgetting**（重跑整合、把污染会话筛掉）撤回——**挡未来 + 撤过去两件事都要做**。场景四（抖动）→ 高频后台任务但少新碎片 → **diff / 量门槛判断「没新东西就跳过、别白跑整合」，绝不该每个 turn 都真整合一次**。
- **复用 vs 打破**：**直接复用**——① 抽取与压缩靠**一条共享水位线指针**解耦（别让两个子系统互知内部）；② 「**不信内容、信来源**」的污点追踪思路（别自己重造一个扫内容的脏检测器）。**打破 / 新增**：记忆有一个别的子系统都没有的属性——「**机器自动写、又自动注入未来每一个会话**」；为它**必须新增**一整套决策五的安全闸（最小能力面 + 污点追踪 + 双向遗忘 + 可清空审计出口），且这套闸必须**和功能同时上线**、不能「先跑通再补」（故障排查那道题就是「先跑通没开闸」的代价）。
- **陷阱**：三类记忆用一个 `Memory` 糊；抽取塞进主回路 / 抽取 agent 能写记忆文件以外的东西；原料和成品混存（迟早把半成品注进 prompt）；记忆用 system 级注入（错了没法被覆盖）；污点追踪按内容扫（必漏注入）；只「挡未来」不「撤过去」（已污染进成品的撤不掉）；安全闸「先跑通再补」（= 故障排查那道题）；递归防护漏掉（记忆 agent 又触发记忆抽取，套娃）。

### 收口

- **结论（高分线）**：**记忆把「自动」这一性顶到了一个比压缩更危险的位置——自动写 + 自动注入未来所有会话。** (a)「强 / 自动的冲劲」那部分——跨会话越用越聪明、后台默默攒不用人管——是**默认就有、几乎不用额外投护栏**的：抽取、整合、注入做对一次就一直工作。(b)**真正吃工程量、且比压缩那侧更重的整一大块是「稳」**：决策五的污点追踪 + 双向遗忘 + 最小能力面 + 递归防护 + 可清空出口。它**比压缩的护栏更重、更不能省**，因为「自动写、又自动注入未来每个会话」把一条记错的记忆的危害放大成了**整条时间线的静默污染**——压缩压坏了最多坑**这一个会话**（影响面有界、当场可见），记忆记错了坑的是**之后所有会话**，而且是**静默的**（没人会去逐条审记忆，故障排查那条幽灵规则就这么潜伏了三周）。(c)**护栏投资主要砸在决策五**（自动写的东西即使错了也只能动一小块地、脏来源进不去、进去了还能撤出来），**不是**决策二 / 三的智力部分（抽取 / 整合记得多聪明）。理由：记忆抽得再准，只要污点追踪没开（= 故障排查那道题）、或抽取 agent 能写记忆以外的文件、或脏记忆撤不回来，就是一条静默污染所有未来会话的雷——那比「这次少记了一条」严重得多。
- **接第 1 课收口**：第 1 课结论是「强与自动同向、稳是孤儿，稳是强 & 自动的边界条件」。记忆是这句话**被推到极端**的样子：当「自动」的作用域从压缩的「这一轮」**扩张到记忆的「未来所有会话」**，稳就**从边界条件升级成了前置条件 / 开关本身**——决策五那套安全闸不是「让强 & 自动别越界」的护栏那么轻，而是「**没有它，记忆这个功能本身就不该开**」。所以记忆比压缩更尖锐地印证了第 1 课那句：稳依然是孤儿（默认没人替它投资），但在记忆这里，它不投就是灾难——自动写、自动注入的东西错一条，就静默污染所有未来。
- **陷阱**：把记忆当纯「强 / 自动」的功能、忽略它一大半护栏代码；承认「记忆有风险」却说不清风险为什么比压缩重（关键在「自动注入未来所有会话」这个作用域扩张）；把护栏投资砸在「抽得更聪明」而非「错了也兜得住」；没把结论接回第 1 课「稳是边界条件」、更没看出记忆把它推成了「前置条件」。
