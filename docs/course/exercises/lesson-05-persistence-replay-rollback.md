# 第 5 课 习题：持久化、回放与回滚

> 配套课文：[lesson-05-persistence-replay-rollback.md](../lesson-05-persistence-replay-rollback.md)

这份习题分四层，难度递进，目标不是让你"读过课文"，而是逼你把持久化体系真当机器跑起来：

- **热身**：四道判断改错，校准你对 append-only 日志、索引、回放、回滚的直觉。**埋了雷**——四句里恰好有一句是对的，别逢句就改。
- **机制层**：有标准解，但答案**不在课文里**。课文给你零件（rollout 的 6 变体、两阶段重建、文件快照库、回滚标记），题目给你一个课文没跑过的局面，你得在脑子里把机器跑到底。

## 热身（判断每句对错；错的指出错在哪。注意：恰好一句是对的，别逢句就改）

1. codex 的 rollout 是一条线性事件流，`RolloutItem` 恰好 6 个变体；其中 `event_msg` 这一类**全部持久化**，因为会话事件都是回放骨架，一个都不能少。

2. claude 的对话回滚（`rewindConversationTo`）会把磁盘上的 `.jsonl` 截断到目标消息之前，这样 `--resume` 重新加载时就只会看到回滚后的那条链。

3. codex 回放历史时，反向扫描一旦扫到带 `replacement_history` 的 `compacted` 项，就把它当历史检查点，这之前的所有项都不再重放；整个回放过程一次模型都不调。

4. claude 的文件历史快照用 git：在用户工作区开一个影子仓库，编辑前 commit 一次、每个 user turn 后再 commit 一次，回滚时 `git checkout` 把文件拨回去。

## 机制层（有标准解，但答案不在课文里）

### 推演 1 · 一次崩溃落在哪一行，决定你恢复出什么 [决策一] [决策五]

课文说"先持久化，后送出/后处理"是崩溃恢复的本钱，又说 codex 的对话项写入顺序是 `record_items`（进内存历史）→ `persist_rollout_response_items`（落盘）→ `send_raw_response_items`（送出）。

现在构造一个时序。一个 user turn 里，模型先产出一条 assistant 文本消息 `A`，紧接着产出一个工具调用 `T`（`local_shell_call`，要跑 `rm -rf build/`），工具执行成功产出结果 `R`。假设这三项是**分三次** `record_conversation_items` 调用进来的（A 一次、T 一次、R 一次），每次都走那三步顺序。

进程在下面三个不同的瞬间分别崩溃，请对每种情形回答：**重启重放后，恢复出来的内存历史里有没有 A / T / R？磁盘上的 rm 命令到底执行没执行？恢复出的会话状态自洽吗（送模型前会被怎么处理）？**

- 情形甲：在 `T` 的 `record_items` 已执行、但 `persist_rollout_response_items` 还没执行时崩。
- 情形乙：在 `T` 已经 `persist` 落盘、`send_raw_response_items` 还没送出、且工具**尚未开始执行**时崩。
- 情形丙：在 `R`（工具结果）已经 `persist` 落盘之后崩，但 `R` 对应的那次 flush 还没完成（这一行没刷到盘）。

子问题不替你列。先想清楚：内存历史是易失的、磁盘日志是持久的、`flush` 是"这一行到底进没进盘"的开关、`normalize` 在送模型前兜底——这四件事在每个瞬间分别处于什么状态。

### 推演 2 · 一份日志里塞进两个检查点和一次回滚，重建函数怎么走 [决策三] [决策四]

课文讲了两阶段重建：阶段一**反向**扫描找"最新的 `replacement_history` 检查点 + 最新 `turn_context` 基线 + 累计回滚轮数"，找齐就停；阶段二只**正向**重放检查点之后的尾巴。

给你一份 rollout，按写入时间（从旧到新）排列如下（只列关键项，省略 `event_msg` 里的瞬态项）：

```
1.  session_meta
2.  turn_context(turn-1, model=M1)
3.  response_item(user turn-1)
4.  response_item(assistant turn-1)
5.  compacted(window=w1, replacement_history=H1)        ← 第一次压缩
6.  turn_context(turn-2, model=M2)
7.  response_item(user turn-2)
8.  response_item(assistant turn-2)
9.  compacted(window=w2, replacement_history=H2)        ← 第二次压缩
10. response_item(user turn-3)
11. response_item(assistant turn-3)
12. event_msg(ThreadRolledBack, num_turns=1)            ← 一次回滚
13. response_item(user turn-4)
14. response_item(assistant turn-4)
```

请回答：

(a) 阶段一反向扫，它**停在第几行**？换句话说，哪个 `replacement_history` 被选作历史种子，第几行**之后**的项才进入阶段二正向重放？

(b) 阶段一累计的回滚轮数是几？

(c) 阶段二正向重放从哪一行开始、到哪一行结束？重放过程中扫到第 12 行那条 `ThreadRolledBack` 会调用什么、产生什么效果？

(d) **最终重建出的内存历史，逻辑上包含哪几个 user turn 的内容？**（用 H2 / turn-3 / turn-4 这样的记号说清楚。）

(e) 反直觉的一问：第 2 行那个 `turn_context(model=M1)` 和第 6 行那个 `turn_context(model=M2)`，在这次重建里**哪个起了作用、哪个被忽略**？恢复出的会话"当前模型"是 M1 还是 M2？为什么——注意阶段一是反向扫的。

### 破 · 三条铁律各给一个"跑完合规、状态仍坏"的反例 [决策五] [决策三] [决策四]

课文把三条说得像铁桶：①"先持久化后送出，让你白嫖崩溃恢复"；②"回放是日志的纯函数，绝不调模型，恢复出和崩溃前一样的内存状态"；③ claude 的 `/rewind`"对话 + 文件一起拨回，这才是一个完整的重来"。

这三条都**在它们声明的范围内成立**。你的任务是各踩中它们**声明范围的边界外侧**——构造一个场景：相关代码全部正确执行了、所有该刷的盘都刷了、所有该追加的标记都追加了，**结构上完全合规**，但恢复/回滚出来的**整体状态仍然是错的 / 仍然骗得过下一轮**。

- 反例①（攻"先持久化就崩溃不丢/恢复无误"）：构造一个一切都按"先落盘后送出"执行、所有行都 flush 了的崩溃恢复，恢复出的**对话历史精确无误**，但恢复后 agent 的**实际运行行为**和崩溃前不一致。提示：课文有一句很诚实的话，承认这套"还不是 100% 确定性"——它把缺口画在哪里？哪一类状态**不在**日志里？

- 反例②（攻"回放是日志的纯函数、绝不调模型"）：构造一个场景，证明"日志一字未改、回放代码一字未改、确实没调模型"，但**两次回放同一份日志，恢复出的会话对下一次请求的表现可能不同**。提示：派生量是怎么来的？以及——回放重建的是历史正文，可送模型时真正发出去的请求，还掺了别的东西吗（想想第 8 课要讲的那层）？

- 反例③（攻"/rewind 对话+文件一起回 = 完整重来"）：构造一个 `/rewind` 全程无报错、对话数组正确截断、`applySnapshot` 正常跑完的回滚，回滚后**磁盘上的文件状态仍然不是用户想要的那一刻**。提示：被追踪的文件集合（`trackedFiles`）是怎么攒起来的？以及——快照只追踪"被 agent 编辑过的文件"，那 agent **没碰过、但用户或别的进程在这期间动过**的文件呢？

每个反例都要说清三件事：这条铁律**实际**保证了什么、**没**保证什么、边界画在哪条线上。

### 量化 · 文件快照到底吃多少磁盘，cap=100 卡住的是什么 [决策四]

claude 的文件回滚（决策四的 B 半边）：每次编辑前存一份改前拷贝、每个 user turn 后记一份快照，快照上限 `MAX_SNAPSHOTS = 100`，超了 `slice(-100)` 保留最新 100 份。你要给 deepseek 算清这套备份的磁盘成本，并据此给一个敢写进代码的取舍。

先建模型。给定假设（数字随假设可变，你要算的是结论的方向）：

- 一个被频繁编辑的源文件，当前大小 `S`（KB）。
- 一次会话里它被编辑了 `E` 次，每次编辑前都触发一次改前备份。
- 快照机制每个 user turn 记一份，会话共 `T` 个 user turn（`T` 可能 > 100，触发裁剪）。

请回答：

(a) **单文件的备份字节成本**：这个文件在一次会话里，光它自己的改前备份，占多少磁盘？用 `S`、`E` 表示。**注意**：这里有一笔账学生最容易算错——备份是怎么做出来的？是存"这次改了哪几行的 diff"，还是别的？这个区别让你的公式里出现 `S` 还是"改动行数"？回源码或课文把这一点钉死，再写公式。

(b) **隐藏账**：`MAX_SNAPSHOTS = 100` 这个 cap，封住的到底是什么？把下面两件事分清——(i) 100 这个数限制的是**快照记录的条数**还是**备份文件的总体积**？(ii) 如果一个 10MB 的文件在一次会话里被编辑了 300 次，cap=100 能不能把它的备份磁盘占用压在某个上限内？为什么？

(c) **算一个临界点**：假设平均文件 `S = 200KB`、一次长会话编辑 `E = 50` 次。再假设一个工程里同时被追踪的文件有 20 个、都按这个频率改。这一次会话的文件备份大约吃多少磁盘？再问：什么样的 `(S, E)` 组合会让单次会话的备份占用突破 1GB？（给数量级即可，重点是你算的时候 `S` 和 `E` 谁是主导。）

(d) **给一个敢写进代码的常量 / 策略，并辩护**：基于上面的账，你会不会把"全量 copyFile 拷贝"改成别的（diff / 内容寻址去重 / 按文件大小动态调 cap / 对超过某阈值的大文件干脆不做快照）？给出你选的那条，写出**触发它的那个具体阈值或规则**（例如"单文件 > X MB 就不全量拷贝、改存 diff"中的 X 是多少量级、依据是什么），并说清这个改动**牺牲了什么**（claude 当初为什么偏偏选了最朴素的全量 copyFile？它换来了什么简单性？）。

## 实战层（主菜：欠定、差分、判断——没有"这是哪一课"的标签提示你）

### 故障排查 · 回滚之后，文件"半回不回"

线上来了一个工单。用户在一个 coding agent 会话里干了很久，agent 改了一批文件，方向跑偏，用户执行了一次回滚（"回到大约二十几步之前那条消息"）。回滚之后用户报告三个现象：

- **现象一**：被 agent 改过的文件里，**大部分**都回到了正确的旧内容，但**有两三个**文件还停在被改坏的最新状态，像是没被回滚到。
- **现象二**：用户回滚选的那条目标消息，是**很早**的一条（这条会话很长、来回了一百多轮）。回滚后用户发现，他想回到的那个"最初的干净状态"根本回不去——选择器里能选的最早的点，比他想要的点晚得多。
- **现象三**：有一个文件，用户自己在 agent 干活的中途、用编辑器手动改过几行（修了个 typo）。回滚之后，他手动改的那几行**也没了**，变回了 agent 改之前的样子。

请回答：

(a) **差分排查路径**：你会依次看什么、用什么排除什么？三个现象指向的**不是同一个原因**——其中至少有一个现象，专门用来排除"整个回滚机制坏了"这一整类假设。说清你怎么用它做排除。

(b) 三个现象各自**最可能的 root cause** 是什么？（落到具体机制：文件回滚是怎么遍历、怎么决定恢复哪个版本、快照怎么攒、有没有上限、上限怎么裁、追踪哪些文件。）

(c) 逐个判定：每个现象是 **bug** 还是 **by-design**？

(d) 运营提一个硬要求："用户必须能回滚到会话里**任意一条**历史消息，不管会话多长。" 架构上要动哪、代价是什么？（想清楚现象二的 root cause 之后，这个要求戳的是哪根设计假设。）

### 效果优化 · 持久化拖慢了关键路径，又恢复得太"干净"

一个桌面 coding agent，持久化体系已按课文落地（append-only JSONL、先落盘后送出、编辑前快照、每轮快照、回滚拷回）。works，但收到两个体验投诉：

- **投诉甲（慢）**：用户反映"每次敲回车，到 agent 开始回话之间，有一段肉眼可见的卡顿"。你查到，这段卡顿很大一部分来自"接受用户输入的那一刻，先把这条消息 `await` 落盘"那一步——课文说这步在 SSD 上约 4ms、磁盘争用下可到 30ms，是关键路径上最大的一笔可控开销。直接去掉这个 `await`、改成不阻塞，卡顿就没了。

- **投诉乙（恢复后丢东西）**：用户反映"会话恢复回来后，agent 像是忘了它刚才在哪个目录、用的什么权限策略，头一两轮表现得有点不对，得我提醒它才回神"。

**死约束**：① 不许放弃 append-only 日志这个唯一真相来源；② 不许给用户工作区接管 git。

请为每个投诉列 **≥2 个 runtime 旋钮**，每个旋钮写明：**调什么、效果方向、反作用**。

**必答的一问**：投诉甲最直接的解法（去掉那个 `await`、落盘改成 fire-and-forget）和投诉乙的根因，**有没有一对会互相加剧**？具体说：你为了治甲而让落盘"不阻塞、晚一点、批量刷"，会不会让乙（崩溃/恢复后状态丢失）更严重？把这对耦合讲透——这正是这道题的核心。

### 架构设计 · 给 deepseek 设计"回到任意一步重来"

你要给 deepseek（改用户文件的桌面 coding agent）设计回滚子系统。目标：用户能"回到某一条历史消息那个状态重来"，**对话和文件都拨回去**。

课文给了两套范式：codex"线性日志 + 追加回滚标记 + 回放时 `drop_last_n_user_turns`"、claude"transcript 父指针树 + 内存截断换叶子 + copyFile 文件快照库"。你要做的不是二选一抄，而是**为 deepseek 这个具体形态做取舍并自圆其说**。

用下面这些场景验证你的设计（最后一个**跨课**）：

1. 用户回滚到第 N 步，又反悔，想"撤销这次回滚、回到回滚前"。你的设计支持吗？靠什么支持？（线性日志范式和树范式在这一条上表现不同。）
2. 一个文件被 agent 改了 5 次，用户回滚到第 2 次改之前。你的文件快照怎么定位"第 2 次改之前那个版本"、怎么拨回去？非 git 的拷贝快照，版本是怎么编号、怎么寻址的？
3. 用户回滚到的那条消息，**正好是当初建立增量注入基线的那一条**（第 1 课 C2 那个 `reference_context_item`）。回滚把它砍掉之后，下一轮上下文装配会发生什么？你得做什么才不至于让基线"指向一段已经不存在的历史"？**接第 3 课**：回滚和压缩一样改写了"有效历史"，第 3 课决策四那张"压完该清什么"的清单，回滚要不要照着清一遍？哪些项？

收尾逼问：你的设计**复用了本课哪个已有机制**（直接拿来）、**打破了哪个假设、必须新增**（本课没有、你得自己补）？

## 参考解（热身 + 所有机制层题 + 故障排查）

### 热身

1. **错。** 错在"`event_msg` 全部持久化"。课文决策一那道持久化过滤器写得明白：`event_msg` 只持久化约十几个**有语义的**事件（TurnStarted、TurnComplete、UserMessage、TokenCount、PatchApplyEnd、ThreadRolledBack 等），**跳过约四十个**纯流式/生命周期的瞬态事件（每个 delta、每个进度刷新）。"会话事件全是回放骨架、一个都不能少"那句话是**别的变体**的规则——`session_meta` / `turn_context` / `compacted` / `inter_agent_communication` 才是"永远持久化"。`event_msg` 恰恰是**被筛**的那一类。把"6 个变体"和"event_msg 全存"混在一起，是这句埋的雷。

### 推演 1 · 一次崩溃落在哪一行 [决策一] [决策五]

先把四个事实摆正：**内存历史易失**（崩溃即清零）、**磁盘日志持久**（已 flush 的行崩溃后还在）、**`flush` 是"这一行进没进盘"的开关**、**`normalize` 在送模型前补 aborted 结果/删孤儿调用**。重放只认磁盘上**已 flush** 的日志。

- **情形甲**（`T` 已 `record_items` 进内存、还没 `persist`，崩）：内存里有 `T`，但内存崩溃即清零、与恢复无关。磁盘日志里**只有 `A`、没有 `T`**（`T` 还没落盘）。重放只看磁盘 → 恢复出的历史**只有 `A`**。rm 命令：`T` 是在 `persist` 和 `send_raw` 之后才被派发执行的，这里连 `persist` 都没到，**rm 绝对没执行**。恢复自洽：历史到 `A` 为止，干净，`normalize` 无需补任何东西。**结论：丢了 `T`，但没有任何副作用泄漏到磁盘——干净地丢。** 这正是"先持久化后送出"的设计意图：没落盘的东西，等于没发生。

- **情形乙**（`T` 已 `persist`、还没 `send_raw`、工具**尚未执行**，崩）：磁盘日志里**有 `A`、有 `T`**（工具调用项落盘了），**没有 `R`**（结果还没产生）。rm **没执行**（工具是 `send_raw` 之后才派发的链路）。重放 → 历史是 `[A, T]`，但 `T` 是一个**没有配对结果的工具调用**（孤儿调用）。这就是 `normalize` 兜底的典型场景：送模型前，`normalize` 会**补一个 aborted/合成的工具结果**给 `T`（或按策略删掉这个孤儿调用），让历史自洽。**结论：`T` 留痕但无果，rm 没跑，normalize 负责把这个半截工具对收圆。**

- **情形丙**（`R` 已 `persist`、但那一行的 `flush` 还没完成，崩）：这是最刁的一种。`persist` 把字节交给了 writer，但**没 flush = 不保证落盘**。崩溃时这一行**可能在、可能不在**（取决于 OS 缓冲是否恰好刷了）。课文的保证是"已 flush 的不丢"，对**没 flush 的行不提供任何保证**。所以恢复出的历史**要么有 `R`、要么没 `R`**，两种都可能。但注意一个关键：rm **此时已经执行过了**（`R` 是工具结果，说明工具跑完了）——磁盘上 `build/` 已经被删。于是出现一种**最危险**的不一致：**副作用（删了 build/）已落在真实文件系统上，但记录这件事的那一行可能没进日志**。重放若恢复出"没有 `R`"，历史就显示"rm 调用了但没结果"，normalize 会补一个合成结果——可这个合成结果**不知道 rm 真的删成功了**。

**命门**：很多人以为"先持久化后送出"保证了"崩溃绝不丢、绝不出错"。它真正保证的，是**情形甲那种"还没落盘的纯内部状态，丢了也无副作用"**。它**不**保证情形丙——**带真实副作用的操作（删文件、发网络请求），其副作用发生在文件系统上，而记录它的日志行的"落没落盘"由 `flush` 决定，二者不是原子的**。日志能保证"我记下来的都真发生过"，但**不能保证"真发生过的我都记下来了"**——这条缝就在 `persist` 与 `flush` 之间、以及"副作用执行"与"结果落盘"之间。这就是为什么 rm 这种不可逆操作要走第 6 课的审批/沙箱，而不是指望持久化兜底。

### 推演 2 · 两个检查点 + 一次回滚 [决策三] [决策四]

(a) **停在第 9 行那个 `compacted(replacement_history=H2)`。** 阶段一**反向**扫（从第 14 行往第 1 行），第一个扫到的带 `replacement_history` 的 `compacted` 是第 9 行（H2，更新），不是第 5 行（H1，更旧）。一旦锁定 H2，`rollout_suffix` 就设成第 **10** 行起的尾巴——第 9 行**之前**（含第 5 行那次更早的压缩）全部不再重放。H1 被 H2 这个更新的检查点彻底盖掉。

(b) **累计回滚轮数 = 1。** 反向扫只遇到第 12 行一条 `ThreadRolledBack(num_turns=1)`，`pending_rollback_turns` 累加成 1。

(c) **阶段二从第 10 行重放到第 14 行。** 先用 H2 把历史种好，然后正向逐项重放尾巴：第 10/11 行（user/assistant turn-3）→ `record_items`；第 12 行 `ThreadRolledBack` → `drop_last_n_user_turns(1)`，把**最新的 1 个 user turn** 从已重建的历史里丢掉；第 13/14 行（user/assistant turn-4）→ `record_items`。

(d) **逻辑上的最终历史 = H2（turn-1、turn-2 的压缩摘要）+ turn-4。** 关键在第 12 行那条回滚标记落在 turn-3 和 turn-4 **之间**：重放到第 12 行时，历史里最新的 user turn 是 turn-3，`drop_last_n_user_turns(1)` 把 turn-3 砍掉；然后第 13/14 行又把 turn-4 加进来。所以 **turn-3 被回滚吃掉了，turn-4 活着**。最终历史 = H2 + turn-4（turn-3 在重建过程中被丢弃）。这就是课文那句"逻辑上的回滚是每次重放时算出来的"——turn-3 的日志行一行没删，它只是在重放时被 `drop` 掉了。

(e) **第 6 行的 `turn_context(M2)` 起作用，第 2 行的 `turn_context(M1)` 被忽略。** 恢复出的"当前模型"是 **M2**。原因正是阶段一反向扫的"找齐就停"语义：基线取**最新的** `turn_context`。反向从第 14 行往回走，先遇到的是第 6 行的 `turn_context(M2)`（它在 H2 检查点第 9 行之前，但反向扫在锁定 H2 当历史种子的同时，仍会捕获这个更新的基线落到 `reference_context_item`）；第 2 行的 M1 更旧、且早被 H2 检查点连同它之前的一切切掉，根本不进重放视野。

**命门**：这道题的两个陷阱。其一，**反向扫认"最新"不认"最旧"**——两个检查点存在时，更新的 H2 把更旧的 H1 连同它之前的一切全盖掉，新手容易拿第一个出现的（按写入序是 H1）当种子，方向反了。其二，**回滚标记的位置决定它砍掉谁**：`ThreadRolledBack` 砍的是"重放到它那一刻时历史里最新的 N 个 user turn"，不是"日志里最后 N 个 turn"。第 12 行落在 turn-3 之后、turn-4 之前，所以砍的是 turn-3 而不是 turn-4——把回滚理解成"砍掉日志末尾"就会答错。逻辑视图是**算出来的**，得顺着重放的顺序在脑子里跑一遍。

### 量化 · 文件快照吃多少磁盘 [决策四]

> 数字随假设可变，但结论的方向必须一致：**吃磁盘的主导项是"文件大小 × 编辑次数"，不是"改了多少行"；cap=100 封的是条数、封不住单文件被反复全量拷贝的体积。**

(a) **单文件备份字节成本 ≈ `S × E`（每次约等于改前整文件大小）。** 关键先把那笔最容易算错的账钉死：claude 的 `createBackup` 走的是 **`copyFile(原文件, 备份路径)`——整文件字节拷贝，不是存 diff**（源码注释明说用 `copyFile` 是为了"不把整文件读进 JS 堆而 OOM"，并 log 了 `fileSize`）。所以**每一次改前备份的成本 ≈ 当时这个文件的整大小，和这次只改了 1 行还是 100 行毫无关系**。一次会话编辑 `E` 次 → 留下约 `E` 份各约 `S` 大小的全量拷贝（文件随编辑会增大，严格说是 ΣSᵢ，但量级是 `E × S`）。**公式里出现的是 `S`，不是"改动行数"——这就是隐藏账：很多人凭直觉以为"改一行只存一行"，于是把成本算成正比于改动量，整整差了一个 `S/改动量` 的倍数。**

(b) **`MAX_SNAPSHOTS = 100` 封的是快照记录的条数，封不住备份文件的总体积。**
- (i) 100 限制的是 **`snapshots` 数组的长度**（每个 user turn 一份 `FileHistorySnapshot` 记录，超 100 就 `slice(-100)` 丢最旧的**记录**）。它**不是**对"备份文件总字节数"的限制。快照记录本身很小（只是"这一刻每个被追踪文件指向哪个备份版本"的一张映射表）；真正占盘的是 `file-history/<sid>/...@v<n>` 那些**全文拷贝**，它们由**编辑次数**产出，不由快照条数产出。
- (ii) 一个 10MB 文件被编辑 300 次，cap=100 **压不住**它的备份占用。改前备份是"每次编辑触发一次"（`fileHistoryTrackEdit`），300 次编辑就可能产出量级 300 份 ×10MB 的版本拷贝（≈3GB 量级）；cap=100 只把"快照记录"裁到 100 条，**不回收**那些版本备份文件。换句话说：cap 卡的是"你能往回跳到几个 turn"，不是"备份占了多少盘"。**把这两件事当成一回事，是这道题的核心陷阱。**

(c) **临界点估算（给数量级）。**
- `S = 200KB`、`E = 50`、单文件 ≈ `200KB × 50 = 10MB`。20 个文件都这么改 → 一次会话 ≈ `10MB × 20 = 200MB`。量级上"几百 MB / 单次长会话"是现实的。
- 要突破 1GB：`总占用 ≈ 文件数 × S × E`。固定 20 个文件，要到 1GB（≈1024MB），需 `S × E ≈ 51MB`/文件——例如 `S = 1MB、E = 50`，或 `S = 200KB、E = 256`，或 `S = 5MB、E = 10`。**主导项是 `S × E`：大文件 + 高频编辑双高时最凶。** 单看哪个更危险？`S` 和 `E` 在公式里同阶（都是一次方），但现实里**大文件更致命**——因为同一个大文件被反复 `copyFile`，每一拷都是满额 `S`，而"改动只有几行"完全省不下来；小文件改一百次也就几 MB。所以排序：**大文件高频编辑 ≫ 小文件高频编辑 ≈ 大文件低频编辑**。

(d) **敢写进代码的取舍。** 一个站得住的策略组合：
- **阈值规则**：单文件 **> 约 1–2MB** 就不做"每次编辑全量 copyFile"，改走 **diff / 内容寻址去重**（按内容哈希存，相同内容只存一份；只存版本间的差异）。1–2MB 这个量级的依据：低于它，全量拷贝简单又便宜（几次拷贝才几 MB，不值得上 diff 的复杂度）；高于它，`S × E` 增长很快就能把单文件备份顶到几百 MB。
- **或**：保留全量拷贝的简单，但**给备份文件总字节加一个独立于 cap=100 的体积上限**（例如单会话备份目录 > 约 500MB 就开始按 LRU 回收最旧的版本备份）——直接补 (b)(ii) 那个"cap 封不住体积"的洞。
- **牺牲了什么 / claude 为什么偏选最朴素的全量 copyFile**：全量拷贝换来的是**极致的简单和正确性**——恢复时无需"打补丁/重组"，`copyFile(备份, 原文件)` 一步到位、绝不会因 diff 应用错而恢复出错误内容；对非文本文件（图片、二进制）也天然 work（diff 对二进制基本没用）；实现里不需要维护版本链、不需要解决"基版本丢了 diff 就废"的问题。它用"磁盘换简单与正确"。你上 diff / 去重，省的是磁盘，赔进去的是**实现复杂度 + 恢复路径变得可能出错 + 二进制文件失效**——这正是课文那句"claude 故意不用 git、换简单"的同一个取舍在文件备份层的翻版：**当你为省磁盘引入 diff/去重/版本链，你就在把 git 的能力一点点重新长出来。**

**命门**：这道题就栽在一个想当然——"备份嘛，存个 diff 就行，改一行才几个字节"。错。claude 是 `copyFile` **整文件**，每次编辑的成本是**当前文件全大小**，与改动行数无关。一旦认清这点，(b)(c)(d) 全部顺下来：cap=100 是条数闸不是体积闸，主导成本是 `S × E`，省磁盘的代价是把简单性和恢复正确性押出去。**先问"备份是全量还是增量"，再开始算账**——这一步不钉死，整道题的数量级会差出一个 `S/改动量` 的倍数。

### 破 · 三条铁律的边界

**反例①（"先持久化就崩溃恢复无误"的边界）。**
构造：一条会话跑着，agent 通过某个工具把 shell 的工作目录从 `/app` `cd` 到了 `/app/src`，又通过某次交互把 exec 沙箱策略提到了更宽松的一档。这些都是**运行期旁路状态**。所有对话项、`turn_context`、事件都按"先落盘后送出"规规矩矩 flush 了，进程崩，重启重放。
结果：对话历史**精确无误**地恢复了——你能看到那条 `cd` 工具调用和它的结果、那次策略变更的事件。但 agent 恢复后的**实际 cwd / exec 策略**未必和崩溃前一致——因为课文那条很诚实的 TODO 说了：**部分运行期状态（shell 路径、exec 策略、feature 开关）目前没完全持久化进 `turn_context`**，所以严格的"逐字节确定性回放"还在路上。
- 实际保证：**对话历史和 durable 基线**（`turn_context` 里持久化的那部分：model、approval/sandbox 策略、cwd 等）能精确重建。
- 不保证：**没被纳入 `turn_context` 的运行期旁路状态**（shell 当前路径、某些 exec/feature 开关）。
- 边界：在"**进了日志的状态**"和"**只活在内存/进程里的旁路状态**"之间。日志的恢复能力，正好覆盖前者、止于后者。"先持久化"保证的是"**记下来的**都能恢复"，不是"**所有**状态都被记下来了"。

**反例②（"回放是日志的纯函数、绝不调模型"的边界）。**
构造两个层次。其一，**派生量是重算的不是恢复的**：token 用量 `recompute_token_usage` 在回放时**重新计算**，不是从日志里读回。如果重算逻辑依赖了"当前的"分词器/计费规则版本，同一份日志在规则升级前后两次回放，算出的 `tokens_used` 可能不同——历史正文一字未改，派生量却变了。其二，**回放重建的是历史正文，可送模型的请求 ≠ 历史正文**：真正发出去的请求里还会拼上第 8 课要讲的那层——system 指令、`CLAUDE.md`/`AGENTS.md` 注入、`<system-reminder>` 等。这些不在 rollout 历史里。所以"恢复出和崩溃前一样的内存历史" ≠ "下一次请求和崩溃前会一模一样"——拼接层在恢复后是重新组装的。
- 实际保证：**对话历史正文**是日志的纯函数，零模型调用、可重放。
- 不保证：**派生量**（用量、计费）是重算的、依赖当时的规则；**送模型的完整请求**还掺了历史之外的拼接层，不在"纯函数"覆盖范围内。
- 边界：在"**历史正文**"和"**历史的派生物 / 历史之外的拼接物**"之间。"纯函数"成立的对象是历史本身，不是"喂给模型的最终 payload"。

**反例③（"/rewind 对话+文件一起回 = 完整重来"的边界）。**
构造：会话期间，agent 编辑了 `a.ts`、`b.ts`（这两个进了 `trackedFiles`）。与此同时，用户在编辑器里手动改了 `c.ts`（修 typo）、`config.json`（调了个值）——这两个 agent **从没碰过**，不在 `trackedFiles` 里。用户 `/rewind` 回到某点，`applySnapshot` 全程无报错跑完。
结果：`a.ts`、`b.ts` 被精确拨回快照那一刻；但 `c.ts`、`config.json` **纹丝不动**——它们不在追踪集合里，`applySnapshot` 的循环 `for (const trackingPath of state.trackedFiles)` 根本不遍历它们。于是"回到那一刻的磁盘状态"是**假的**：被追踪文件回去了，没追踪的文件停在最新。更刁的反向情形：如果用户手动改的恰好是一个**被追踪**文件（agent 也编辑过的），`/rewind` 会拿快照里的版本 `copyFile` 覆盖回去——把用户的手动修改**静默清掉**。
- 实际保证：**被 agent 编辑过、进了 `trackedFiles` 的文件**，能按快照精确拨回（编辑前 v1 + 每轮快照）。
- 不保证：**agent 没碰过的文件**完全不在快照视野（不回滚）；**被追踪文件上的用户带外编辑**会被快照版本覆盖（被回滚掉，哪怕用户不想）。
- 边界：在"**被 agent 追踪的文件**"和"**整个工作区的真实状态**"之间。快照拨回的是"agent 改过的那些文件"，不是"工作区在那一刻的全貌"。

**命门**：这三个反例共享一个形状——**机制保证的是它"覆盖范围内"的精确，范围外的东西它根本不知道、也不声称负责**。①范围 = 进了日志的状态；②范围 = 历史正文本身；③范围 = 被追踪的文件集合。学生最容易栽的地方是把"这套机制在它范围内做到了精确"误读成"这套机制保证了整体正确"。持久化/回放/回滚每一条铁律，都要先问一句："**它的覆盖范围画在哪？范围外谁负责？**"——答不上来，就会把"局部精确"当成"全局正确"，线上事故就从这条缝里钻进来。

### 故障排查 · 文件"半回不回"

(a) **差分排查路径**：
- 先用**现象一**做最关键的排除。现象一是"大部分文件回对了、只有两三个没回"——这一条**直接排除"整个回滚机制坏了"这一整类假设**。如果是机制总崩（路径错、快照没建、回滚函数抛异常退出），表现应该是"全都没回"或"全报错"，而不是"绝大多数回对、个别没回"。"绝大多数成功 + 个别失败"指向的是**逐文件处理时某几个文件单独出了状况**——即 `applySnapshot` 那个 `for...trackedFiles` 循环里，每个文件**独立 try/catch、失败就 `continue`** 的结构。所以差分第一刀：确认现象一不是机制级故障，而是文件级局部失败。
- 然后分头查现象二、三。现象二的关键词是"会话很长、一百多轮""能选的最早点比想要的晚"——指向**快照数量上限和裁剪策略**。现象三的关键词是"用户手动改的行也没了"——指向**回滚对被追踪文件的覆盖语义**。

(b) **三个 root cause**：
- **现象一 = `applySnapshot` 逐文件失败、静默 `continue`。** `applySnapshot` 遍历 `trackedFiles`，每个文件单独 try/catch：某个文件 `restoreBackup`（`copyFile`）抛异常（备份文件丢了/权限不足/磁盘满/目标路径被占），就 `logError` + 记一条 `tengu_file_history_rewind_restore_file_failed` + `continue` 到下一个。**没有事务、没有全或全无**。所以个别文件回不去、其余照常回——这就是"半回不回"的机制根源。
- **现象二 = 快照上限 `MAX_SNAPSHOTS = 100` + `slice(-100)` 裁掉最旧。** 每个 user turn 记一份快照，超过 100 个就 `allSnapshots.slice(-MAX_SNAPSHOTS)` 保留**最新 100 个、丢弃最旧的**。会话一百多轮，最早那几十轮的**快照记录**已经被裁掉了，所以选择器里能选的最早点比用户想要的晚——他想回的那个"最初干净状态"的快照已经不在了。
- **现象三 = 回滚对被追踪文件是"按快照版本覆盖"，不认用户带外编辑。** 用户手动改的那个文件是 agent 也编辑过的（在 `trackedFiles` 里）。`applySnapshot` 对它走"恢复到目标快照版本"那条路：`checkOriginFileChanged` 发现当前内容和快照版本不一致 → `restoreBackup` 用快照版本 `copyFile` 覆盖回去。用户夹带在里面的 typo 修复，对回滚机制而言只是"当前内容 ≠ 快照内容"的一部分，被一并抹掉。

(c) **bug / by-design 判定**：
- 现象一：**一半一半**。"逐文件独立、单个失败不拖垮整体"是 by-design（防一个坏文件让整次回滚全废）。但"**失败静默、用户不知道哪几个没回**"是 bug 级的体验缺陷——应该把失败文件清单显式报给用户（"这 2 个文件没能回滚，请手动检查"），而不是悄悄 `continue`。
- 现象二：**by-design**。上限 100 是课文写死的常量，目的是不让备份/快照无限膨胀。回不到 100 轮以前是这个设计的**已知代价**，不是 bug。
- 现象三：**by-design（但危险）**。回滚的定义就是"把被追踪文件拨回快照那一刻"，它**不区分**"这个偏差是 agent 造成的还是用户手动造成的"。这是回滚语义的必然结果，不是实现错误——但它是个该警示用户的危险默认。

(d) **运营硬要求"任意一条消息都能回滚"**：
这个要求直接戳**现象二的 root cause——快照上限**。要满足它，架构上的取舍：
- 把 `MAX_SNAPSHOTS` 调大或取消？代价是**备份存储无限增长**——每个 user turn 一份快照、每个被编辑文件留版本拷贝，长会话会吃掉大量磁盘（课文强调过备份是文件全文拷贝，不是 diff）。
- 折中：快照记录可以全留（快照只是"哪个文件是哪个版本"的元数据，很小），真正大的是**备份文件本身**。可以让快照记录无上限、但对**很旧的备份内容**做去重/压缩/冷归档。但这又引入"旧备份被归档后回滚要先解归档"的复杂度。
- 更狠的取舍：要"任意一条消息"，本质要的是**完整版本历史**——这时候 claude 那套"非 git 的 copyFile 快照"的轻量优势就到头了，你可能反而要考虑某种内容寻址的版本存储（每个文件版本按内容哈希存一份、去重），代价是实现复杂度和"它开始长得像一个 mini git"。这恰好暴露了 claude"故意不用 git、换简单"这个取舍的边界：**当你真要无限历史时，你迟早会把 git 的能力重新长出来一遍。**

**命门**：这道题的核心差分是**现象一**——它专门用来排除"机制总崩"。一旦你认出"绝大多数成功 + 个别失败"等于"逐文件独立处理 + 单个静默 continue"，三个现象就各归各位：一是事务性缺失、二是上限裁剪、三是覆盖语义。三者**不是同一个 bug**，新手最容易把它们当成"回滚坏了"一锅炖。真功夫是看出：**这套文件回滚没有事务、有硬上限、且不认用户带外编辑——这三条是三个独立的设计取舍，各自在不同现象上露出代价。**

## 评点（效果优化 / 架构设计 / 收口——自评用，非标准答案）

### 效果优化 · 评点

**强答案应触及的维度**：
- **投诉甲（慢）的旋钮**：① 落盘批量化/异步化（攒几条一起刷、或后台 writer 任务收 channel——codex 本来就这么干），效果=关键路径不等单行 flush，反作用=崩溃丢窗口变大；② 降级策略分模式（交互模式 `await` 落盘保安全，脚本/`--bare` 模式 fire-and-forget——claude 正是这么分的），反作用=两条路径行为不一致、得分别测；③ 把落盘挪出关键路径但保留"用户输入这一条"同步落（只对最关键的那一行 `await`、其余异步），反作用=实现上要区分"哪行必须同步"。
- **投诉乙（恢复后丢运行期状态）的旋钮**：① 把更多运行期状态（cwd、exec 策略、feature 开关）纳入 `turn_context` 持久化——直接补课文那条 TODO 的缺口，反作用=`turn_context` 变胖、每轮写入变大；② 每个 turn 后强制刷一次基线快照，反作用=多一次 IO；③ 恢复后主动重建运行期状态（重新探测 cwd、重设策略），反作用=恢复变慢、且有些状态探测不回来。
- **必答的耦合**：**会互相加剧，而且是同一根因的两面。** 投诉甲的最直接解法是"别在关键路径上 `await` 落盘、改成不阻塞/批量晚刷"；投诉乙的根因是"恢复后某些状态没被持久化下来"。你为治甲而让落盘**更晚、更批量、更不阻塞**，等于**扩大了"已发生但还没落盘"的窗口**——一旦在这个变大的窗口里崩溃，丢失的东西更多，乙（恢复后状态对不上）就更严重。**甲要"晚落盘换快"，乙要"全落盘换稳"，它们在"落盘的及时性/完整性"这个旋钮上方向相反。** 这正是课文那条铁律的代价被你亲手放大了。

**常见陷阱**：
- 把投诉甲无脑改成 fire-and-forget 就交卷——没看见这一刀直接喂大了投诉乙。课文那段 `recordTranscript` 注释**整段**都在讲这个：用户点发送、几秒后被 kill，如果没同步落盘，transcript 里只有队列操作、`--resume` 找不到对话而失败。去掉 `await` 治了卡顿，但把"崩溃可恢复"这条本钱也一起去掉了。
- 只列旋钮、不标反作用。每个旋钮的反作用才是这道题要的——尤其那对相反方向的耦合。
- 违反死约束：有人会想"给工作区上 git 不就完整了"——题目明确禁止接管用户 git。

### 架构设计 · 评点

**强答案应触及的维度**：
- **范式选择要自圆其说**：选线性日志 + 回滚标记（codex 式）、还是树 + 换叶子（claude 式），或混合。关键看场景 1（撤销回滚）：**线性日志范式天然支持撤销回滚**——回滚是日志里一条可重放的事件，你甚至能再追加一条"撤销上次回滚"的标记，或者干脆重放时不应用它；**树范式**里旧分支枯着没删，理论上也能"切回旧叶子"，但需要 UI 能寻址那条枯枝。把这条说清，比"我选 X"重要。
- **场景 2（文件版本寻址）**：非 git 的拷贝快照，版本靠"路径 sha256 + @v 递增编号"寻址（claude 式）；"第 2 次改之前"对应某个 `@vN`，快照记录里存"那一刻这个文件是哪个版本"，回滚就 `copyFile(那个版本, 原路径)`。强答案会点出"快照记录（小，元数据）和备份内容（大，全文拷贝）是两层"。
- **场景 3（回滚砍掉基线消息）跨课**：回滚砍到建立 `reference_context_item` 的那条消息，必须**清掉基线**（置 None / Cleared），逼下一轮全量重注入——否则基线指向一段已不存在的历史，下一轮拿它 diff 会算出错误增量。codex 的 `drop_last_n_user_turns` + `trim_pre_turn_context_updates` 正是干这个。**接第 3 课**：回滚改写了"有效历史"，第 3 课决策四那张"压完该清什么"的清单——增量注入基线、已读文件记录（`readFileState`）、指向被砍消息的缓存编辑（claude 的 `resetMicrocompactState`）——回滚要照着清一遍。强答案会**列出**具体清哪几项，而不是只说"要清缓存"。
- **复用 / 打破**：复用了本课的 append-only 日志 + copyFile 文件快照库（直接拿来）；打破的假设通常是"快照有上限/只追踪 agent 改过的文件"——要支持"任意一步重来 + 完整工作区回滚"，得新增完整版本历史 / 更宽的追踪范围，并承认这会把系统推向"长得像 git"。

**常见陷阱**：
- 只设计对话回滚、忘了文件回滚（或反过来）。课文反复强调这是**两个独立机制**，缺一不可。
- 设计了回滚，但忘了"回滚后要重置依赖旧历史的状态"（基线、已读记录、缓存）——这是回滚最容易留的暗坑，和第 3 课压缩善后是同一类活。
- 场景 1 不做差分：没看出"撤销回滚"这条是**区分两种范式**的试金石，泛泛答"都能支持"。
- 收尾的"复用/打破"答得空。这一问要的是诚实盘点：哪些是白嫖的、哪个假设是你为了需求亲手打破的。

### 收口 · 评点

**及格线**：能把五个决策大致映射到三性——日志/索引/回放主要喂"稳"（崩溃恢复、会话恢复），回滚同时喂"稳"（纠错恢复）和"自动"（敢让 agent 多跑、跑错能回）；能说出"先持久化后送出"服务"稳"、牺牲了一点"自动/流畅"（关键路径多一笔落盘开销）。

**高分线**：
- (a) 能指出**横跨**的决策在哪一性是主、哪一性是代价。例如：结构化索引（决策二）主喂"自动/体验"（快速列历史、并发作业协调）、代价压在"稳"（多一套要守"日志才是真相"纪律的投影，守不住就出不一致 bug）；回滚（决策四）主喂"稳+自动"、代价是文件快照的存储和"半回不回"风险。
- (b) 看出"先持久化后送出"服务的是**稳**（崩溃恢复的本钱），牺牲的是**流畅/延迟**（投诉甲那笔 4~30ms）——而且这个牺牲是**有意的、可控的**，claude 用模式降级（交互 `await`、脚本 fire-and-forget）把代价分摊。
- (c) 这句收口要落到本课主线：**持久化体系把"稳"做到"出了任何错都能完整恢复 + 完整回滚"的程度，"强 + 自动"才敢往前迈那一步——让 agent 自动改用户的代码。** 没有崩溃恢复，你不敢让 agent 长跑（崩了 40 轮白干）；没有文件回滚，你不敢让 agent 自动改文件（改坏了回不去）。**文件回滚（稳）是"敢让 agent 自动改代码"（强 + 自动）的安全网**——这正是课文最后一句话：文件回滚是 coding agent 敢放手自动改代码的安全网。把"稳是强和自动的前提/边界条件"这句话，用本课的具体机制兑现成"哪个稳的机制，解锁了哪个强+自动的胆量"。

**常见陷阱**：
- 把五个决策都笼统答成"都为了稳"。回滚和索引明显横跨，不点出横跨就丢了这道题的核心。
- (c) 答成口号"稳很重要"。要的是**具体因果链**：哪个持久化机制不到位，哪个"强+自动"的动作就不敢做。
- 漏掉"先持久化后送出"对"自动/流畅"的牺牲——以为它只有好处。课文给了投诉甲那笔账，就是要你看见稳的代价。
