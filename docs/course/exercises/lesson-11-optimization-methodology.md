# 第 11 课 习题：优化方法论

> 配套课文：[lesson-11 优化方法论](../lesson-11-optimization-methodology.md)

这一份习题分四层，难度递增，每一层练的东西不一样：

- **热身**：四句判断改错。先说清楚——这四句里**恰好有一句是对的**，其余三句各错一处。别逢句就改，把那句对的也改了，等于没看懂。这一层治的是「凭印象答题」。
- **机制层**：推演 / 量化 / 破，三种题。答案**不在课文里**——课文给你零件（缓存怎么崩、reasoning 那条弧、阈值怎么演化、退避怎么算），题目给你一个课文没跑过的新组合，逼你把零件在脑子里拼起来跑到底。有标准解。
- **实战层（主菜）**：故障排查 / 效果优化 / 架构设计。这是高级工程师每天真干的活：局面是**欠定**的，没有「这是第几节、该用哪个机制」的标签提示你——看出该先问哪几个子问题，本身就是一半难度。
- **收口**：把这一课的优化方法论收到「强 / 稳 / 自动」三性主线上。

锚点用 `[§N]`，对应课文六节：§1 缓存命中率 / §2 reasoning 那条弧 / §3 上下文预算 / §4 延迟 / §5 重试 / §6 方法论 + 想当然清单。卡住了就回那一节翻零件——锚点是给你找零件用的，不是答案。

这一课的特别提醒：它是十二课里**最适合用真实价算账**的一课。下面的量化题不会让你估，会给你 DeepSeek 的真实单价，逼你算出一个临界点、并为一个**敢写进代码的常量**辩护。算的时候盯紧那笔「想当然会算错」的隐藏账——通常就藏在「这一段到底命中没命中缓存」「这个 token 到底进没进账本」这种地方。

题目会很难，但每一道的标准解都能从**课文机制 + 题目给的条件**推出来，不靠任何课外冷知识。难在推理深度，不在信息缺失。做的时候痛，做出来畅快——这是这门课该有的样子。

## 热身（四句里恰好一句对，埋了雷，别逢句就改）

下面四句关于本课机制的话，**恰好一句完全正确**，另外三句各有**一处**实质错误。逐句判断：对的指出它对、并说清为什么对；错的改到对、并说清错在哪。

1. 缓存读取的单价大约是普通输入的 1/10，所以「命中缓存」是一个三维一起变好的帕累托改进；为了拿到这个收益，静态前缀里凡是会变的字段（时间戳、项目路径、策略相关串）都应该**后置或抠掉**，让前缀逐字节稳定。

2. codex 删掉「上一轮以前的跨轮 reasoning」是为了缩小请求体积、躲跨组织 400 错误，这个优化在线上跑了大约两个月、稳定省钱之后才被一个更激进的方案替换。

3. 自动压缩的触发阈值从绝对 token 数（220k、250k、350k）改成「窗口的 90%」，是因为有个模型的上下文窗口只有约 27 万 token，而 350k 的阈值**高过了窗口本身**，导致软触发永远先撞不到、等于被悄悄关掉。

4. 收到 429 时，配额 / 计费类的 429（如 `usage_limit_reached`、`insufficient_quota`）应该进入重试循环、按指数退避多试几次，因为这类错误往往是服务端临时过载、过一会儿就好了。

## 机制层（有标准解，但答案不在课文里）

### 推演 1 · 三个改动撞在同一轮里 [§1][§2]

课文 §1 把「缓存被什么打碎」拆成五场战役，§2 讲了「保留全部加密 reasoning、跨轮回放」的方向。现在给你一个课文没单独跑过的**组合时刻**，请你在脑子里把这一轮一步步跑到底。

设定：一个多轮会话已经进行到第 8 轮，前 7 轮的前缀缓存一直热着。在第 8 轮**同时**发生了三件事：

- (a) 用户在上一轮结束后按了一次 `/approvals`，把审批策略从「每次问」改成了「自动批读类操作」；
- (b) 这一轮模型发了**两个并行工具调用**（两个读文件），运行时按可并行处理了它们；
- (c) 这一轮的 assistant 在发工具调用之前，产出了一段加密 reasoning（`encrypted_content`），需要随这一轮带回去。

请回答：

1. 这三件事里，哪几件**会**打碎前缀缓存、哪几件**不会**？对每一件，说清它打碎的是缓存的哪一段（静态前缀？还是只影响本轮新增部分？），以及为什么。
2. 对会打碎缓存的那些，课文给出的修法分别是什么？为什么这些修法能让它**不**打碎缓存，而不是「换一个有序数据结构」或「干脆别让用户改策略」？
3. 把 (b) 和 (c) 放到一起：并行工具调用 + 本轮要回放的加密 reasoning，对「append-only 前缀」这个要求各自提出了什么约束？这两个约束会不会冲突？如果某一版实现把 `function_call` 和 `function_call_output` 交错排了，缓存会从哪一轮开始对不齐？

### 量化 2 · 一个被污染的前缀，到底每轮在烧多少钱 [§1][§6]

这道题逼你把第 1 节那些「缓存被打碎」的 bug，换算成一个**敢写进代码 review 评论的数字**。

设定：一个长会话用 `deepseek-v4-flash`，有一段 **80k token 的静态前缀**（系统提示 + 工具定义 + scaffold）。本该每轮都命中。但有人在工具描述里插了当前项目的绝对路径——于是换项目后这 80k 前缀**全 miss**。会话平均跑 **200 轮**。

已核单价（每 1M token）：flash 命中 \$0.0028 / 未命中 \$0.14；pro 命中 \$0.003625 / 未命中 \$0.435。

1. 单看这 80k 前缀，**每一轮**「全 miss」比「全命中」多烧多少钱？整个 200 轮会话因为这一个 bug 多烧多少？
2. 如果这个会话用的是 `deepseek-v4-pro`，同样这一个 bug，200 轮多烧多少？为什么两个模型的「倍数」一样、但「绝对多烧的钱」差这么多？
3. 现在请你为团队定一条**敢写进 CI 的硬规则**：缓存命中率每轮掉多少、就报警拦住合入？课文里 claude 用的是一个**双条件**——请给出这条规则的两个分量各自防的是什么，并说清：为什么光有「掉了百分之几」一个条件不够、必须再加一个「绝对掉了多少 token」的条件？（提示：想想一个只有 500 token 缓存的小会话，掉 50% 是不是值得报警。）
4. **隐藏账**：第 1 问你算「多烧的钱」时，如果直接拿「80k × 未命中单价」当作损失，错在哪？正确的损失是哪两个数的**差**？为什么不能用「未命中单价 × 80k」本身当损失？

### 破 3 · 「我排序了，缓存就稳了」——给一个排了序仍然崩的反例 [§1]

课文 §1 说：MCP 工具存在哈希表里、迭代顺序每轮变，会让多轮前缀缓存基本失效；修法是发出去前**按全限定名排序**。这听起来像是「只要排了序，工具这一段的前缀就逐字节稳定了」。

请你构造一个反例：一个实现**确实**对工具列表按全限定名排了序（顺序这一项完全合规、稳定），但前缀缓存**仍然**在多轮里崩。说清楚：

1. 你的反例里，是什么东西在变、打碎了缓存——而它**不是顺序**？（课文 §1 的五场战役里，除了「顺序」之外还有哪几类崩点？至少举两类落到「工具」这一段上。）
2. 因此「按全限定名排序」这个修法，**实际**保证了什么、**不**保证什么？把边界画在哪条线上——一句话说清「排序」解决的是工具集的哪一个属性、缓存友好还需要工具集的哪些**别的**属性同时成立。
3. 课文里那个标题写着「**again**」的 opencode 提交（动态路径被重新泄进工具描述、缓存又崩了一次），是你这个边界的正面还是反面案例？为什么一个已经修过的崩点会**回归**？这说明「排序固定」之外，还需要一道什么样的防线才能挡住回归？

### 量化 4 · 重试上限定多少、压缩请求又该砍到多少 [§5]

这道题逼你给两个**重试预算常量**定值，并为它们辩护——一个是「用户可配的重试数硬上限」，一个是「昂贵操作（压缩）的重试预算」。课文 §5 给了零件（默认请求 4 次 / 流 5 次、硬上限、昂贵操作砍预算），但没给你下面这个具体局面的账。

设定：一个会话用 `deepseek-v4-pro`。每次主回合请求大约带 **120k token 上下文**；在一次限流高峰里，请求反复收到「请慢点」类的可重试 429（不是配额类），每次重试都重新发整段 120k、且因为前一次失败缓存已凉、**全部未命中**。pro 未命中单价 \$0.435 / 1M。

1. 如果一个用户把重试数配成了 **100**（正好踩在课文那个硬上限上），最坏情况下，单这一个反复失败的回合，光 input 就要烧多少钱（算上首次 + 100 次重试 = 101 次请求）？如果没有这个硬上限、用户配成 1000，又是多少？用这两个数说清：为什么「不设上限 = 用户能把服务器（和自己的账单）锤爆」不是一句吓唬人的话。
2. 现在轮到压缩请求。课文说压缩这种昂贵操作的重试预算被砍成 `min(流重试数, 2)`。假设默认流重试是 5。请算：把一个失败的压缩请求的重试预算从 5 砍到 2，**最坏情况**下省下几次重试、占原预算的多大比例？再说清一个**比省钱更重要**的理由——为什么偏偏是「压缩」这种操作要给更小的预算，而不是普通回合？（提示：压缩请求自己有多贵、跑多久，和普通回合比。）
3. **隐藏账（必踩）**：第 1 问里我让你按「每次重试都全部未命中、重发整段 120k」算。但真实的退避不是「立刻连发 101 次」——课文 §5 的退避是 200 毫秒起、每次翻倍、加 0.9~1.1 抖动，且**服务端给的延时优先于你自己算的退避**。请说清：这个「时间维度」的事实，如何让「101 次重试烧 X 元」这个纯成本数**在实践中几乎不可能真的发生**？也就是说——硬上限 100 真正挡住的，到底是「钱」，还是「时间 × 放大」这个更要命的东西？把硬上限的真正作用重新表述一遍。

### 破 5 · 「删 reasoning 是为了省钱」——给一个删了反而更贵的反例 [§2]

课文 §2 讲了那条上线两天就回滚的弧：删跨轮 reasoning → 两天后撤回 → 方向定为「保留全部加密思考、跨轮回放」。学生最容易把它背成一句结论：「删 reasoning 错了，应该保留。」但这道题不让你背结论，让你**复原因果**，并构造一个把因果讲反就会栽的反例。

请回答：

1. 那个删除的提交，理由写得**完全合理**：「缩小请求体积、防止跨组织切换时的 400」。请你不靠「后来回滚了所以它错」这个事后结论，**只用缓存机制本身**，论证为什么「删跨轮 reasoning 省请求体积」这个**看起来在省钱**的操作，在多轮会话里**反而更贵**。（提示：删掉跨轮 reasoning，会改变什么？改变的那个东西又怎么连到缓存命中？）
2. 构造一个**反例局面**：一个团队为了省钱，写死了「每轮发请求前，把所有 reasoning 块剥掉」。这个实现请求体积确实小了、跨组织 400 也躲了——结构上看完全合规。请说清它在哪两件事上**反而坏了**：一件关乎成本（缓存），一件关乎**正确性**（接 §2 末尾和宪法的配对 / 相邻规则）。为什么「正确性」这件事，比「更贵」还要命？
3. 收口一句：「删 reasoning 省钱」这条直觉，和「删 reasoning 是正确性 / 配对要求」这条事实，**有没有因果关系**？课文反复强调的那句「删 reasoning 跟省钱、跟命中缓存没有因果」到底在否定什么——它否定的是「该不该删」，还是「为什么删」？把这两件事彻底拆开。

## 实战层（主菜：欠定、差分、判断——没有「这是哪一课」的标签提示你）

### 故障排查 · 「省了钱，结果越用越慢、还时不时报错」

线上来了一个事故报告，三条现象，没人告诉你是哪个机制坏了：

- **现象 A**：上周做了一次「优化」之后，账单上的 token 成本确实降了一些，但用户开始抱怨「同一个长任务，越往后越慢，到后面明显卡」。
- **现象 B**：少数用户报告「偶尔请求会失败，重试一下又好了，过几次又失败，很迷惑」——但这些用户的用量都很大。
- **现象 C**：有个用户的会话**还剩 76% 的上下文窗口没用**，却收到了 `input exceeded context window`（输入超出上下文窗口）的错误。这条现象很怪——明明窗口还空着大半。

请回答：

1. **差分排查路径**：这三条现象**几乎一定不是同一个 root cause**。请说清你会怎么把它们拆成几条独立的线去查——每一条先看什么、用什么排除什么。特别地，**现象 C 专门用来排除一整类假设**：它能立刻排除掉「是不是上下文真的塞满了 / 是不是该压缩没压缩」这一类猜测吗？为什么？它把你的注意力逼向哪一类 bug？
2. 给出现象 A、B、C **各自最可能的 root cause**（落到课文里的具体机制）。
3. 对每一个 root cause，判断它是 **bug** 还是 **by-design**：哪些是「实现漏了一条路径 / 算错了一笔账」的真 bug，哪些是「设计本就如此、只是被用在了不该用的地方」？
4. 如果运营提一个硬要求——「我不管，长任务到后面也不许变慢、也不许莫名报错」——架构上你要动哪几处？每一处的代价是什么？（提示：现象 A 那个「省了钱」的优化，和「越用越慢」之间，可能正是同一个改动的两面。）

### 效果优化 · 「能用，但又慢又贵，还不能换模型」

一个 agent 产品 works，但产品经理拿着两个投诉来找你，并且甩下一条死约束：

- **投诉一**：「首屏太慢了，点开到能开始干活要等好几秒。」
- **投诉二**：「长会话太贵了，跑久了账单吓人。」
- **死约束**：默认模型已经定死了，**不许换更便宜或更贵的模型**，也**不许给会话中途切换模型**（产品上已经承诺「全程同一个模型」）。

请回答：

1. 针对**投诉一（慢）**，在不换模型的前提下，列出 **≥2 个 runtime 旋钮**，每个写清：它怎么调、效果朝哪个方向、以及**反作用**（调了它会让什么变差）。
2. 针对**投诉二（贵）**，同样列出 **≥2 个 runtime 旋钮** + 效果方向 + 反作用。
3. **耦合题（必答）**：你为「降延迟」选的旋钮，和你为「降成本」选的旋钮里，**有没有一对会互相加剧对方的反作用**？找出这一对，说清这个耦合是怎么产生的——调了 X 去降延迟，会从哪个机制上把 Y（成本）顶回去，或者反过来。（提示：缓存这条线，同时连着延迟和成本两端；预热、并行、压缩频率，每一个动了都不止影响一维。）

### 架构设计 · 给「会话内临时升档做 review」设计一套机制

产品想加一个能力：长会话里，当用户说「帮我仔细 review 一下刚才这段改动」时，这**一个回合**临时用更强的模型（`deepseek-v4-pro`）跑，跑完回到默认模型（`deepseek-v4-flash`）继续。

请你设计这套「会话内临时升档」的机制，并用下面几个具体场景验证你的设计：

- **场景一**：一个 10 万 token 上下文的会话，触发一次 pro review。请先算一笔账：如果这个 review 回合直接在主对话线程上、用 pro、且**未命中**主对话攒下来的缓存，单这一轮的 input 成本大约是多少？而如果它留在 flash 且命中，又是多少？（用上面那组单价。）这笔账如何影响你的设计——你会让 review 回合跑在主线程上，还是开一个分叉？
- **场景二**：review 回合结束、切回 flash 之后，主对话的后续轮还能不能命中 review 之前的缓存？为什么「会话内切换模型」会是个缓存陷阱？（接 §1 / §6 的缓存键与模型维度。）
- **场景三**（跨课边界，接第 7 课多 agent）：如果把 review 做成一个**子 agent** 分叉，而不是主线程临时换档——子 agent 的缓存键该怎么设，才能让它**复用**父会话已经攒热的前缀缓存、而不是用自己的线程 id 当键导致全 miss？（课文 §1 提过 codex 的 review 分叉就栽在这上面。）

结尾必答：你的设计**复用了本课哪个已有机制**（缓存键、派生路径、子 agent 隔离……），又**打破了哪个默认假设、必须新增**什么？

## 收口 · 优化循环怎么同时服务强 / 稳 / 自动（本课牵引题）

课文 §6 把优化收成一个循环：**测量 → 定位 → 分类（帕累托还是取舍）→ 验证（重测）**。这道题逼你把这个循环和全课的主线——「强 / 稳 / 自动」三性——咬合起来。

请回答：把优化循环的四步，分别对应到三性上：

1. 「**先量出三个维度、先遥测再优化**」——这一步主要在服务哪一性？为什么「不测就只能拍脑袋」本质上是一个**稳**的问题，而不只是一个性能问题？
2. 「**分清帕累托还是取舍**」——为什么说「帕累托改进（缓存友好、上下文卫生）闭眼做」同时服务**强和自动**，而「取舍旋钮按场景配」是一个把**强**交还给人去判断的动作？
3. 「**动完一定回仪表盘重测**」——这一步是整个循环里最容易被跳过、也最致命的一步。请用课文里至少**两个**「试了、错了、两天 / 当场改回来」的真实战役，说清：为什么「重测验证」这一步本身，就是这一课对**稳**最硬的要求？
4. 把全课压成**一句能带走的话**：在「强 / 稳 / 自动」里，「优化是实证的、不是显然的」这条总纲，最先保护的是哪一性？为什么连 codex 自己都「试了、错了、改回来」这个事实，恰恰证明了这一性必须焊死在流程里、而不能靠经验或直觉代替？

及格线：能把四步各挂到一性上，并举对至少两个回滚战役。
高分线：能说清「重测验证」为什么是稳的边界条件——没有它，强和自动的每一次推进都可能在你看不见的地方把另一维烧穿（缓存被悄悄打碎、reasoning 删了破坏配对、阈值调过头撞墙），而你不重测就根本不知道。

## 参考解（热身 + 所有机制层题 + 故障排查）

### 热身

**正确的是第 3 句。** 其余三句各错一处。

- **第 1 句：对。** 缓存读约为普通输入的 1/10（claude 定价表里缓存读单价正是输入的 0.1 倍），命中三维一起变好或不变（成本降、延迟省、内容一字不差所以质量不变），是帕累托改进的定义；而拿到这个收益的前提，就是静态前缀逐字节稳定——会变的字段（时间戳、项目路径、策略相关串）一律后置或抠掉。这句把「为什么是帕累托」和「怎么拿到它」都说对了。**别去改它。** 最容易手痒的地方是「1/10」——会有人想改成别的比例，但 0.1× 是核过的真值。

- **第 2 句：错在时间跨度。** codex 删「上一轮以前的跨轮 reasoning」（2025-10-28，理由确实是缩小请求体积 + 躲跨组织 400），但它**两天后**（2025-10-30）就被整个回滚，不是「跑了两个月稳定省钱之后」。这正是本课的活教材：保留全部加密 reasoning、跨轮回放带来的缓存命中和推理连续性，价值压过「请求小一点」，所以删它是错的、上线两天就改回来。把「两个月」改成「两天」，并把因果讲对：不是被更激进的方案替换，是被**回滚**——方向反过来了。

- **第 3 句：对。** 阈值从绝对数（220k、250k、350k）改成「窗口的 90%」，正是因为那个模型窗口只有约 27 万 token（实测 272k），350k 高过窗口本身，软触发永远先撞不到、等于被悄悄关掉、会话直接撞硬墙。这是「想当然把阈值调大」的典型反例。

- **第 4 句：错在处理方向，整个反了。** 配额 / 计费类 429（`usage_limit_reached`、`insufficient_quota`）**不该**进重试循环——它们要在重试预算检查**之前**就返回成**致命错误** + 清楚提示。原因恰恰相反：这类错误重试一万次也没用（额度到顶 / 计费问题），而盲目重试制造的是「时好时坏、很迷惑」的间歇性困惑，比直接失败更糟。该重试的是**另一种** 429——「请慢点」的短暂限速。把「进重试循环、多试几次」改成「在进重试循环前就返回成致命错误」。

**命门：** 这一题的雷埋在第 1 句——它太「像标准答案」，又带一个具体数字（1/10），最容易被当成「肯定动了手脚的那句」去改。判断「哪句对」的功夫，不是找最顺眼的，是逐句去验每一处 load-bearing 的事实（比例、时间跨度、阈值与窗口的大小关系、429 的处理方向）。四句里只有第 3 句每一处都经得起核。

### 推演 1 · 三个改动撞在同一轮里

**1. 哪些打碎缓存、打碎哪一段：**

- **(a) 改审批策略 → 打碎静态前缀。** 这是 §1 第二场战役。如果工具描述会随审批 / 沙箱策略变，用户一改策略、工具描述就变、整段工具定义（属于静态前缀）就炸——从这一轮起，前 7 轮攒的前缀缓存基本作废。打碎的是**最贵的那一段：静态前缀**。
- **(b) 并行工具调用 → 不打碎已有前缀，但威胁「本轮及之后」的 append-only 性。** 并行本身不改前缀；危险在于它让「模型产出」（`function_call`）和「工具结果」（`function_call_output`）在历史里**交错**，前缀就长不成 append-only。如果交错了，从交错那一点之后的前缀都对不齐。
- **(c) 本轮加密 reasoning → 不打碎已有前缀。** 加密 reasoning 是**本轮新增**的内容、append 在历史末尾，它不动前面 7 轮的前缀。只要它和它所属的那一轮配对、相邻地带回去，就不破坏前缀稳定性。

**2. 修法及为什么：**

- (a) 的修法：**工具定义恒定不变**——统一成一个带「提权参数」的 shell 工具，策略改在**调用时**强制，不进缓存前缀。为什么不是「换有序结构」（那是另一场战役的修法）或「禁止用户改策略」（砍功能、不可接受）——因为根因是「会变的东西混进了静态前缀」，正确的修法是把「会变的部分」从前缀里搬到调用时，而不是禁止它变。
- (b) 的修法：**规范化布局**——所有 `function_call` 排在所有 `function_call_output` 之前，缓存才对得齐。

**3. (b) + (c) 的约束与冲突：**

- (b) 要求：同一轮内，模型产出（含 `function_call`）整体在前、新输入（`function_call_output`）整体在后，不交错。
- (c) 要求：本轮 assistant 的加密 reasoning 必须和它所属的这一轮**配对、相邻**地带回去（这正是 §2 / 宪法的条件式 reasoning 规则）。
- **它们不冲突，但必须按一个统一顺序排**：reasoning 属于「模型产出」侧，应和 `function_call` 一起排在 `function_call_output` 之前。如果某版实现把 `function_call` 和 `function_call_output` 交错排了，**从交错的那一轮起**前缀就对不齐——注意不是从「改策略的第 8 轮」起，而是从「第一处交错」起；这两个崩点（策略炸前缀、交错炸 append-only）是**独立**的，可能在不同位置同时发生。

**命门：** 学生最容易栽的是把三件事笼统说成「都打碎缓存」。关键是分清**打碎的是哪一段**：(a) 炸的是静态前缀（最贵、影响全局），(b) 威胁的是 append-only 结构（从交错点起失效），(c) 根本不炸前缀（只是本轮新增、必须配对相邻）。三者性质完全不同，修法也完全不同——这正是 §1 把崩点逐场拆开、而不是说「缓存很脆」一句带过的原因。

### 量化 2 · 一个被污染的前缀，到底每轮在烧多少钱

> 数字随假设可变（前缀大小、轮数、模型），**结论必须一致**：一个把动态值泄进静态前缀的 bug，每一轮都在以「未命中 − 命中」的差价烧钱，倍数是 50（flash）到 120（pro）。

**1. flash，80k 前缀，每轮多烧 + 200 轮总账：**

- 每轮全命中：80k × \$0.0028/1M = \$0.000224
- 每轮全未命中：80k × \$0.14/1M = \$0.0112
- **每轮多烧 = 0.0112 − 0.000224 = \$0.010976**（约一分一）
- 200 轮多烧 = 0.010976 × 200 ≈ **\$2.20**

单看一次会话两块多不吓人——但这是**一个 bug、一个会话**。乘以日活会话数，这一个「绝对路径泄进工具描述」的 bug 是在持续烧钱，而且**不测命中率根本看不见它在烧**。

**2. pro，同一个 bug，200 轮：**

- 每轮命中：80k × \$0.003625/1M = \$0.00029；未命中：80k × \$0.435/1M = \$0.0348
- 每轮多烧 = 0.0348 − 0.00029 = \$0.03451；200 轮 ≈ **\$6.90**

**为什么倍数一样、绝对值差这么多**：未命中 / 命中的**比值**只由定价结构决定（flash 0.14/0.0028 = 50×，pro 0.435/0.003625 = 120×），和前缀多大、跑多少轮无关——所以「倍数」是模型的固有属性。但「绝对多烧的钱」= 前缀大小 × 轮数 ×（未命中单价 − 命中单价），pro 的单价本身高一个量级，所以同一个 bug 在 pro 上烧得多得多。**结论可带走：缓存 bug 在贵模型上更致命，但「该不该修」不取决于绝对值——50~120 倍的比值意味着它永远值得修。**

**3. 双条件报警规则（这正是 claude 在做的）：**

两个分量——

- **相对条件**：本轮缓存读取量比上一轮掉超过 **5%**。防的是「比例上的显著下滑」。
- **绝对条件**：绝对掉了超过 **2000 个 token**。防的是「小会话里的正常抖动被误报」。

为什么光有相对条件不够：一个只有 500 token 缓存的小会话，正常波动掉个 250 token 就是「掉 50%」——但这点量根本不值得报警、也省不下几个钱。只有「比例显著下滑」**且**「绝对量也够大」**同时成立**，才判定是真的缓存断了。两个条件是**与**关系，缺一个就会要么漏报（只看绝对、小比例大基数的慢性流血看不见）、要么误报（只看相对、小会话天天报警）。claude 还会进一步**归因**到底是系统提示、工具、模型、思考强度、还是 TTL 过期打碎的——报警只是第一步，归因才能定位。

**4. 隐藏账（这是这道题的雷）：**

如果你拿「80k × 未命中单价 = \$0.0112」当损失，你算的是「这一段的总价」，**不是 bug 造成的损失**。因为就算没有 bug、缓存全命中，这 80k 也不是免费的——它要花「命中单价 × 80k = \$0.000224」。**bug 造成的真实损失，是「未命中」和「本该命中」两个价的差**：0.0112 − 0.000224 = \$0.010976。

用「未命中单价 × 80k」当损失，会**高估损失约 2%**（命中那部分本来就要花），更重要的是它在概念上错了——它把「这段前缀的固有成本」也算进了 bug 的账。在 flash 上这 2% 不致命，但在做「这个优化值不值得投人力修」的判断时，永远要算**差额**、不算总额。这笔账想当然最容易算错的就是这里：把「这段东西很贵」误当成「这个 bug 让我损失了这么多」。

**命门：** 损失 = 差额，不是总额。倍数由定价结构决定、与规模无关；绝对损失才随规模放大。报警必须双条件，因为单条件不是漏报就是误报。

### 破 3 · 排了序仍然崩的反例

**反例：** 一个实现严格按全限定名对工具列表排了序——顺序这一项完全稳定、合规。但它的某个工具（比如 bash / shell 工具）的**描述文字里**插了当前项目的绝对工作目录（opencode 真踩过），或者描述会随审批 / 沙箱**策略**变（codex 真踩过）。于是：换一个项目、或改一次策略，工具描述就变了——**顺序没变，内容变了**，前缀照样逐字节对不上，缓存照样崩。

**1. 变的是什么、不是顺序：** 是工具**描述的内容**在变，不是工具的**排列顺序**。§1 五场战役里，落到「工具」这一段上的崩点至少有三类：① 顺序（哈希表迭代序每轮变）——这才是排序修的；② 描述随运行时策略变（审批 / 沙箱）；③ 描述里插了项目绝对路径。排序只治第 ① 类。

**2. 排序实际保证什么、不保证什么：** 「按全限定名排序」只保证工具集的**排列顺序**逐轮一致——它把工具集当成一个**集合**，固定了集合元素的**呈现次序**。它**完全不**保证集合里每个元素的**内容**（描述文字、schema）逐轮一致。边界画在这条线上：**排序解决「同一组工具的顺序稳定」，缓存友好还需要「每个工具的描述 / schema 本身也逐字节稳定」「工具集的成员不随轮次增删」同时成立。** 顺序、内容、成员——三个属性都稳，工具这一段的前缀才稳；排序只锁住其中一个。

**3. 「again」提交是反面案例，说明需要回归防线：** 那个标题写「again」的提交，正是「动态路径被**重新**泄进工具描述、缓存又崩了一次」——一个修过的崩点**回归**了。它说明：把动态值从描述里抠掉是个**一次性修复**，但只要这条「描述必须静态」的约束没有被一道**自动防线**钉住，后人（或重构）很容易再把某个动态值泄回去。所以「排序固定」之外还需要的那道防线，正是 §1 末尾 claude / codex 的做法——**把「前缀逐字节一致」钉进集成测试 + 运行时盯命中率并能归因**：测试在合入时挡住回归，命中率监控在线上抓住漏网的。光靠人记得「别往描述里塞动态值」是挡不住回归的，「again」就是证据。

**命门：** 排序固定的是**顺序**这一个维度，缓存友好需要**顺序 + 内容 + 成员**三个维度同时稳。学生最容易把「我排序了」当成「工具这一段就缓存友好了」——而真实的崩点里，「描述内容变」比「顺序变」更常见、更隐蔽（它不需要哈希表，一个项目路径、一次策略切换就够了）。修复单个崩点不等于关上这一类崩点，回归防线（测试 + 监控）才是。

### 量化 4 · 重试上限定多少、压缩请求又该砍到多少

> 数字随假设可变（上下文大小、模型、退避参数），**结论必须一致**：硬上限挡的不是「钱」这一维，是「时间 × 放大」；昂贵操作给更小预算，省的是「单次失败把成本翻几倍」的尾部风险。

**1. 重试 100 次 vs 1000 次的成本（pro，120k 全未命中）：**

- 单次请求 input = 0.12M × \$0.435 = \$0.0522
- 配 100：首次 + 100 次重试 = 101 次 → 101 × 0.0522 ≈ **\$5.27**
- 配 1000：1001 次 → ≈ **\$52.25**

一个**反复失败**的回合就能烧掉五块到五十多块——而它最后**大概率还是失败**（限流没过去就是没过去，多试一百次不会变好）。这就是课文那句「不设上限的话，用户理论上能配一个近乎无限的重试数、把服务器锤爆」的算术版：无上限意味着单个失败回合的成本和对服务端的压力**没有天花板**。硬上限 100 把这个尾部钉死。

**2. 压缩请求砍预算：5 → 2 省几次、为什么偏偏砍压缩：**

- `min(流重试数, 2)`：5 砍到 2，最坏情况下少试 **3 次**，占原 5 次预算的 **60%**。
- 但**比省钱更重要的理由**是：压缩请求**比普通回合贵得多、跑得久得多**——它要把整段历史发过去、让模型生成一大段总结。所以一次失败的压缩重试，单价和耗时都是普通回合的好几倍。如果给它和普通回合一样的预算（5 次），一个失败的压缩就能把这一段的成本和延迟翻好几倍。砍成 2 次，是因为「昂贵操作的失败」尾部风险更大，要更早放弃、别让它把账单和等待时间拖垮。**关键不是 5 和 2 谁省，是「越贵的操作，重试的边际伤害越大、越该早停」。**

**3. 隐藏账（这道题真正的雷）：**

第 1 问那个「\$5.27 / \$52.25」是按「立刻连发 101 / 1001 次」算的**纯成本上界**，但它**在实践中几乎不可能真发生**——因为退避有**时间维度**：200 毫秒起、每次翻倍（`200ms × 2^(n-1)`）、加 0.9~1.1 抖动，而且**服务端给的重试延时优先于你自己算的**（`requested_delay.unwrap_or_else(|| backoff(...))`）。指数退避意味着第 10 次重试本身就要等几十秒、第 20 次要等十几分钟——还没烧到 100 次，要么限流早就过去了、要么用户早就 Ctrl-C 了，根本攒不到 101 次全发出去。

所以**硬上限 100 真正挡住的不是「钱」这一维**——退避的时间墙早就把成本拦在前面了。它挡的是**「时间 × 放大」**这个更阴的东西：一个被配成无限重试的客户端，会在限流高峰里**永不退场地反复敲服务端**，每个这样的客户端都是 3~10 倍的放大；成千上万个一起敲，就是雪崩。硬上限是给**单个客户端的纠缠时长**封顶，从而保护**整个服务端**不被一群「永不放弃」的客户端拖垮。重新表述：硬上限不是省你一个人的钱，是防你这一个客户端变成压垮服务端的那根稻草——成本只是顺带被限住的。

**命门：** 这道题的雷是「纯成本上界」这个陷阱——按 101 次连发算出五块多，看着像答案，其实是个**几乎不可达的上界**，因为指数退避的时间墙在成本墙之前就生效了。真正想清楚的是：重试机制有两道独立的预算——**次数预算**（硬上限 100、压缩 2）和**时间预算**（指数退避 + 服务端延时优先）。次数预算防的是「放大与纠缠」，时间预算防的是「连发风暴」。把硬上限只理解成「省钱」，就漏掉了它真正在保护的东西——服务端的稳，不是你的账单。

### 破 5 · 「删 reasoning 是为了省钱」——删了反而更贵的反例

**1. 为什么「删跨轮 reasoning 省请求体积」在多轮里反而更贵：**

只用缓存机制就能论证。删掉跨轮 reasoning，改变的是**请求里那段历史的内容**——也就是缓存前缀的一部分。前缀缓存的命中靠「这一轮发的前缀，和上一轮发的前缀，逐字节一样」。如果你这一轮把以前的 reasoning 块剥掉了、上一轮没剥（或剥的位置 / 多少不一致），那么从被剥的那一点起，前缀就和缓存里存的对不上、**缓存失效**。于是你为了省下「reasoning 块那几 KB 的请求体积」，代价是**整段本该命中的前缀全部转成未命中**——按第 2 节那笔账，未命中是命中的 50~120 倍价。省下的是线性的一点体积，赔进去的是整段前缀的缓存命中。**所以它看起来在省、实际在烧。** 这正是回滚提交写明的方向：「把 reasoning 在整段会话里保留下来，以提升性能和缓存」——保留 + 跨轮回放，前缀才稳、缓存才命中。

**2. 「每轮剥掉所有 reasoning」反例坏在哪两件事：**

- **成本（缓存）**：如上——剥掉的内容破坏了前缀逐字节一致性，缓存命中崩，反而更贵。
- **正确性（配对 / 相邻）**：这是更要命的一件。发起 tool_call 的那一轮 assistant，**必须**随它的 tool_result 回填自己的 reasoning（配对 / 相邻是硬约束）。「无差别剥掉所有 reasoning」会把**当前这一轮、正在配对中的** reasoning 也剥掉，于是配对断裂——下一个请求可能直接 500 / 400，或模型行为出错。**为什么正确性比「更贵」还要命**：贵只是多花钱，系统还能跑；配对断裂是**直接报错 / 跑不通**，是功能性故障。一个让你多花 100 倍钱的 bug 再糟，也比一个让请求直接失败的 bug 轻——前者烧钱，后者根本不工作。

**3. 「省钱」和「正确性要求」有没有因果——拆开这两件事：**

**没有因果。** 这是这道题最该带走的一点。

- 「删 reasoning 省钱」——**错**，且方向反了（如上，删了反而更贵）。
- 「删 reasoning 是正确性 / 配对要求」——这指的是：跨**已完成的普通 user 轮**，那些不再参与配对的旧 reasoning **可以**丢（这是配对 / 相邻规则允许的，不是为了省钱）。

课文那句「删 reasoning 跟省钱、跟命中缓存没有因果」，否定的是**「为什么删」**——它在说：你删某些 reasoning，理由只能是「配对 / 相邻规则允许丢」，**不能**是「这样省钱 / 这样命中缓存」（后两个是错的因果）。它**不**否定「该不该删某些旧 reasoning」——该删的（跨已完成普通轮的）还是该删。把两件事拆开：**删不删，由配对规则决定；而『为省钱去删』是一个被实证证伪的错误动机。** 一律删（破坏当前配对、炸缓存）和一律留（请求略大但缓存命中、配对完整），后者对——但「后者对」的理由是缓存 + 配对，不是「留着省钱」。

**命门：** 学生最容易栽在把「该不该删」和「为什么删」混成一件事。课文否定的是**动机**（「为省钱 / 为缓存而删」是错的因果），不是**动作**（按配对规则该丢的旧 reasoning 仍该丢）。删 reasoning 这件事，由配对 / 相邻的**正确性规则**唯一裁决；省钱、命中缓存都是无关的错误理由——而且事实恰恰相反：跨轮保留 reasoning 既保配对、又保缓存。

### 故障排查 · 「省了钱，结果越用越慢、还时不时报错」

**1. 差分排查路径：** 三条现象几乎一定不是同一个 root cause，拆成三条独立的线。

- **现象 C 先查，因为它能排除一整类假设。** 「还剩 76% 窗口却报 input exceeded context window」——这条立刻**排除**掉「上下文真的塞满了 / 该压缩没压缩」这一整类猜测：窗口还空着大半，不可能是「装满了」。它把注意力逼向另一类 bug——**有一条输出路径绕过了截断**，一条没被截的巨型内容（典型是错误路径 / 超时路径的 stderr）单独把这一次请求撑爆，而总体窗口占用还很低。这是 §3 那个真实提交的现象。
- **现象 B（大用量 + 时好时坏）**：盯「用量大」这个线索。时好时坏 + 重试有时管用——这是**对一个不可重试的配额 / 计费类 429 做了重试**的典型症状（§5）。重试一个本就不可重试的错误，制造的正是「间歇性」困惑。
- **现象 A（省了钱但越用越慢）**：把「省钱的那次优化」和「越用越慢」当成同一个改动的两面去查（§3 / §2 的 token 账本）。

**2. 各自最可能 root cause:**

- **A**：上周那次「省钱优化」很可能动了 **token 账本 / 压缩触发**——比如删了跨轮 reasoning 省请求体积（省了钱），或某个改动让自动压缩按**偏小的 token 数**算（漏算了加密思考 / 本地追加项 / 图片），于是**压得太晚**。压得太晚 → 上下文越攒越大 → 每轮预填越多 → **越往后越慢**。省的那点钱和越来越慢，是同一笔账算错的两面。
- **B**：配额 / 计费类 429(`usage_limit_reached` / `insufficient_quota`)被放进了重试循环，而不是在重试预算检查前就返回致命错误。
- **C**：错误路径 / 超时路径的工具输出**绕过了截断**，一条巨型 stderr 撑爆单次请求。

**3. bug 还是 by-design:**

- **A**:**bug**（账本算漏了占窗口的东西，导致压缩太晚）——压缩本身是 by-design，但「按错的数字触发」是 bug。
- **B**:**bug**（把不可重试的错误当可重试）。重试机制本身 by-design，但「该致命的没致命」是 bug。
- **C**:**bug**（截断策略没覆盖到错误 / 超时路径）。截断是 by-design，「漏了一条路径」是 bug。三条都是 bug，但都是「机制对、覆盖 / 计数漏了一处」的那种 bug，不是设计错。

**4. 运营硬要求「长任务不许变慢、不许莫名报错」，架构上动哪、代价：**

- 修 A：把 API 没算的（加密思考、本地追加项、图片）**补估进 token 账本**，让自动压缩按真实占用触发。代价：补估是**估算**，有误差；估高了压得太勤（费钱）、估低了仍撞墙——要校准，且每加一类新内容（新的多模态）都得补一条估算。
- 修 B：把配额类 429 在重试预算检查**之前**返回成致命错误 + 清楚提示。代价几乎为零，纯收益（本就该这么做）。
- 修 C：让截断**覆盖错误 / 超时路径**——「一个截断策略，强度等于它覆盖最差的那条路径」。代价：要审计**所有**产出工具输出的路径（正常 / 错误 / 超时 / sandbox），漏一条又全功尽弃，是个需要穷举路径的体力活。

**命门：** 这道题的核心是**现象 C 的排除作用**——「76% 窗口却 overflow」一句话就否掉了「是不是该压缩没压缩」，把你从「调压缩阈值」的错误方向上拽回到「有路径绕过了截断」。三条现象看着都像「上下文 / 重试出问题」，但它们是**三个独立的 bug**，差分的功夫就是不把它们混成一个 root cause。最容易栽的是看到 A 的「越用越慢」就去调压缩阈值——而 A 的根因是账本算漏、压得太晚，调阈值治标；真正要修的是把漏算的 token 补回账本。

## 评点（效果优化 / 架构设计 / 收口——自评用，非标准答案）

### 效果优化 · 「能用，但又慢又贵，还不能换模型」

**强答案应触及的维度：**

- **降延迟的旋钮（投诉一）**，至少触及：① 把非必需的同步调用挪到后台（拉配额、拉元数据等，先起界面、晚补数字）——反作用：首屏短暂信息不全；② 连接预热（只握手不发 prompt）——反作用：预热卡住会挂住首回合，必须超时兜底、绝不阻塞；③ 开并行工具（独立的读并发跑）——反作用：有依赖的调用被错误并行会出错，且每个新工具要显式声明可并行否则默认串行抵消；④ 先建 TTFT / 阶段遥测再动手——这本身不降延迟，但不建就只能瞎调。
- **降成本的旋钮（投诉二）**，至少触及：① 缓存友好（静态前缀稳、排序固定、派生路径复用键）——这是帕累托项，几乎无反作用，该闭眼做；② 上下文卫生（工具输出截断 / 落盘只回预览、脏活外包子 agent 只回结论）——反作用：截太狠会丢信息、影响质量；③ 调压缩频率 / 阈值——反作用：压太勤花压缩请求的钱、压太晚撞墙变慢（注意这一条**同时**踩到投诉一）。
- **耦合题（必答的那问）**：强答案要找出一对真耦合。最干净的一对是**压缩频率**：为降成本你想「多压、上下文小一点省钱」，但压缩本身要发一个模型请求（花钱 + 加延迟），而且**每次压缩都打碎缓存**——压完前缀变了，后面几轮要重新攒缓存。于是「为省钱而多压」反手既加了延迟（投诉一）、又因为反复炸缓存而**多花了钱**（投诉二自己打自己）。另一对：**并行工具**降延迟，但并行让模型产出和工具结果交错，若不规范化布局就打碎 append-only 前缀、炸缓存、推高成本。能指出「缓存这条线同时连着延迟和成本两端，所以动它必然不止影响一维」即为触及核心。

**常见陷阱：** ① 把「换便宜模型」当降成本旋钮——被死约束明确禁掉了，且课文反复说「换便宜模型不一定更省」；② 把旋钮列出来但不写反作用——优化的全部难度就在反作用，只列方向等于没答；③ 耦合题答成「两个都做就行」——没找到那对**互相加剧**的；真正的耦合是「压缩」既是降成本手段又因炸缓存而推高成本、还加延迟，这种自我拮抗才是要害。

### 架构设计 · 给「会话内临时升档做 review」设计机制

**强答案应触及的维度：**

- **场景一的账要算对**：10 万 token,pro 未命中 input = 0.1M × \$0.435 = **\$0.0435**;flash 命中 = 0.1M × \$0.003625 = \$0.00036（若按纯命中读价更低）。课文给的对照是「单这一轮贵约 155 倍」（\$0.0435 / 0.00028 ≈ 155）。这笔账应当直接逼出设计结论：**别让 review 回合污染主线程的缓存**——要么开分叉，要么明确接受这一轮的高成本但保护主对话缓存不被模型切换打碎。
- **场景二**：会话内切换模型是缓存陷阱，因为**模型是缓存键 / 前缀的一部分**——切到 pro 这一轮的前缀和 flash 的前缀不是同一份缓存，切回 flash 后主对话能不能命中，取决于 pro 那一轮有没有把主线程的历史结构改掉。强答案要点明：就算切回同一个 flash，中途插进去的 pro 回合也可能让主缓存在那十几分钟里过期 / 错位，「会话内换档」要么走分叉、要么认了这次缓存损失。
- **场景三（跨课，接第 7 课）**：子 agent 的缓存键**不能用自己的线程 id**——那样本该共享父前缀的分叉会全 miss(codex review 分叉真栽过）。正确做法：把缓存键做成**可覆盖的函数**，让 review 分叉去哈希一个**稳定的共享身份（父线程 + 复用键）**，从而复用父会话已攒热的前缀。
- **结尾必答**：复用的已有机制 = §1 的「派生路径复用同一个缓存键」+ 第 7 课的子 agent 隔离；打破的假设 = 「一个会话只有一个模型 / 一条缓存键」——必须新增「分叉能携带父身份去复用缓存」这层机制。

**常见陷阱：** ① 直接在主线程上换模型跑 review，不算缓存代价——这正是 155 倍那笔账要砸醒的；② 子 agent 用自己的 id 当缓存键，以为「反正是同一段历史就会命中」——缓存键不对就是全 miss;③ 忘了「切回 flash 后主缓存可能已过期 / 错位」，只算了 review 那一轮的钱、没算它对主对话后续缓存的连带损失。

### 收口 · 优化循环怎么同时服务强 / 稳 / 自动

**强答案应触及的维度：**

- **测量 / 先遥测 → 稳**：能说清「不测就只能拍脑袋」本质是稳的问题——没有仪表盘，你的每一次优化都是盲动，无法判断它是改好了还是把另一维烧穿了。测量是稳的**前提条件**，不是性能优化的附属。
- **分类（帕累托 vs 取舍）**：帕累托（缓存、卫生）闭眼做 → 同时让结果更强（质量不降而省了延迟 / 成本）、让系统更能自动跑（成本可控才敢长跑）；取舍按场景配 → 把「这一段质量提升值不值这个差价」的判断**交还给人 / 配置**，这是 review 升档那类决定的本质——强不是免费拿的，是花代价换的，要人来定。
- **重测验证 → 稳的边界条件**：能举至少两个回滚战役——删 reasoning 两天回滚、阈值调过头撞墙、预热挂五分钟、配额 429 乱重试造间歇困惑——说清「不重测就发现不了自己把另一维烧穿了」。这一步是稳对强 / 自动的**守门**。
- **一句带走的话**：「优化是实证的、不是显然的」最先保护**稳**。codex 自己都「试了、错了、改回来」这个事实，恰恰证明直觉在这个领域不可靠，所以必须把「重测」焊进流程——稳是强和自动的**边界条件**（呼应第 1 课收口那句），没有重测这道闸，强和自动的每一次推进都可能在你看不见的地方反噬。

**常见陷阱：** ① 把四步机械对到三性、不讲为什么（尤其「测量为什么是稳不是性能」讲不清）；② 收口讲成「三性都重要」的正确废话，没点出「稳是边界条件、重测是它的闸门」这一层；③ 举回滚战役只背结论（「删 reasoning 错了」），没复原因果（「为什么缓存 + 连续性压过请求体积」「为什么不重测就发现不了」）——这一课的全部分量就在因果，背结论等于没学。
