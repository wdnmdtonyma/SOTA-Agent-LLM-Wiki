## 机制层（有标准解，但答案不在课文里）

### 推演 1 · 一个 turn 从撞墙到收尾 `[决策一 / 二 / 三]`

一个 turn 正在跑。按时间顺序发生：

1. 某次 sampling（记作 S_k）里，模型在**同一次回复**里发出三个工具调用：`read(a.ts)`（声明**支持**并行）、`read(b.ts)`（声明**支持**并行）、`fmt(c.ts)`（声明**不支持**并行，会写盘）。
2. 这三个还在 `in_flight` 里没 drain 完时，用户 submit 了一句「顺便把 d.ts 也看一下」。
3. S_k 的流在 `Completed` 里带 `end_turn = Some(true)`。
4. drain 时，`fmt(c.ts)` 执行**失败**返回 error（但它在失败前已经把 c.ts 改了半个文件），两个 `read` 都成功。
5. 三个工具都 drain 完，本 turn 累计 token **此刻还没**撞上限。

把这个 turn **从 S_k 的 `Completed` 那一刻走到它真正结束（或继续）**，逐步回答：

- (a) 这三个工具在运行时层**实际的并发形态**是什么？谁能和谁真并发、谁把谁挡住、`fmt` 取的是哪种锁？
- (b) S_k 之后 `needs_follow_up` 是真还是假？把它**拆成两个独立来源**分别判：模型这边贡献了什么、pending input 这边贡献了什么。注意第 3 条给的是 `end_turn = Some(true)`，别想当然。
- (c) 那个**失败**的 `fmt` 结果去了哪？模型下一拍看不看得到它？它会不会让 turn 提前结束？
- (d) 用户那句「看下 d.ts」最终在**哪一步、第几次 sampling**里被模型看到？
- (e) 这个 turn 最终在**哪一步、因为什么判定**才（没）结束？

**这道题的狠处在 (b)**：模型说 `end_turn = Some(true)`、又没要新工具，凭直觉这个 turn 该结束了——但你得想清楚还有**另一个独立信号**没被消掉。把这条钩出来，整道题就通了。

### 量化 2 · 一次会话内，缓存到底替你省了多少 `[决策四 A / A2，接第 3 课]`

设一次会话：静态系统块（身份 + 安全红线 + 工具定义）≈ 12,000 token；动态系统块（memory、env_info_simple、language）≈ 2,000 token；对话历史从 0 起，每轮在末尾追加 ≈ 1,000 token（模型那一段 + 工具结果）。任务连跑 10 轮，每轮一次 sampling。命中缓存的部分按全价 **1/10** 计费，未命中按全价 1.0。**前提：这是你自己机器上的一次普通会话，provider 支持账号级前缀自动缓存，且两轮间隔都在 TTL 内。**

1. 先把**「全程不压缩」**这 10 轮的**总计费 token** 算到量级。把每一轮拆成三段（静态块 / 动态块 / 历史）分别记命中或全价，第 1 轮和第 N 轮要分开算。
2. **隐藏账（必须自己想通，我不替你说）**：第 1 轮里，静态块那 12,000 是**全价**还是**命中**？说清楚为什么——别被「静态段几乎永远热」这句话晃了。这一笔算错，后面全错。
3. 现在有人在第 6 轮**做了一次压缩**，把前 5 轮历史压成一段 ≈ 800 token 的摘要。请回答：这一次压缩，在缓存账上**炸掉的到底是哪一段前缀**？那 12,000 静态块 + 2,000 动态块会不会被炸？压缩后的第 6 轮，**额外**要为什么付一次全价？
4. 给一个**你敢写进 deepseek 代码的压缩触发判据**（带一个具体常量），并为这个常量辩护。再回答：把触发判据写成「**每 6 轮压一次**」，错在哪个根本判断上？

### 破 1 · `needs_follow_up` 这道「不让 turn 早退」的闸，能被什么绕过 `[决策二 / 三]`

课文把 codex 的续跑判定讲成一道挺稳的闸：`needs_follow_up = model_needs_follow_up || has_pending_input`——只要模型还要工具、或者还有插队输入没消化，turn 就不结束。听上去这道闸保证了「**有未尽之事就不会停**」。

请构造一个具体情形：这道闸**逐字按定义跑完、结果完全合规**（该真的真、该假的假，没有任何 bug），但 turn 仍然在「**任务客观上还没做完**」的状态下结束了，或者反过来，在「**已经没有任何有意义的事可做**」时还在空转续跑。二选一构造一个即可（能两个都构造更好）。

然后说清楚三件事：`needs_follow_up` 这道闸**实际保证**的是什么、它**不保证**什么、它的边界画在哪条线上。

> 提示：这道闸读的是两个**机械信号**（模型要不要工具、队列里有没有输入）。它从不读「任务做完了没」这种语义判断。盯着这条缝去构造。

## 实战层（主菜：欠定、差分、判断——没有「这是哪一课」的标签提示你）

### 故障排查 · 「改完文件，模型像没看见」事故

线上反馈：一个 agent 在长任务里改了文件后，**偶发**地表现得像没看到自己刚做的改动——它会再读一遍同一个文件、或者基于改之前的旧内容继续推理，仿佛上一步工具调用没发生过。诡异之处：

- ① 这只在**很长**的会话里偶发；短会话从没出现过。
- ② 复现时去翻持久化的会话记录（rollout / transcript），那条工具调用和它的结果**都在、都配得上对（call_id 对得上）**，内容也正确。
- ③ 监控显示出问题的那几轮，**模型 API 没有报错、没有超时、没有限流**，token 用量曲线在出问题前一轮有一个明显的台阶式上跳。

给出：

- (a) 你的**排查路径**——依次看什么、用什么**排除**什么。想清楚：现象② 帮你排除了哪一整类假设？现象③ 里那个「token 台阶式上跳」又把你往哪个方向推？
- (b) 最可能的 **root cause**。
- (c) 判定：这是 bug 还是 by-design？
- (d) 如果运营提一个硬要求——「模型必须永远能看到自己最近一次工具调用的结果，绝不能丢」——你在架构上要动哪里、代价是什么？

> 这题的关键一刀在 (a)：现象② 是专门用来**排除一整类假设**的。先看出它排除了什么，路径就收窄了一大半。`[?]`

### 效果优化 · 两个体验投诉，不许动模型、不许加缓存设施

agent 能把任务做完，但用户反复投诉两件事：

- **(A) 多前端体验割裂**：同一会话开在桌面端和 CLI 两个客户端，一端干活、另一端**要等很久才看到进度**，有时干脆只在一端能看到完整产出。
- **(B) 长任务里『越往后越啰嗦、越慢』**：会话拖长之后，每一轮的首字延迟肉眼可见地变高，模型还总在回复里重复早就说过的环境信息（「当前在 /app 目录、用 pnpm……」）。

**死约束：不许换模型，不许引入任何新的缓存设施 / 缓存层。** 只能动 runtime 这一侧的旋钮。

针对 A、B 各列出你能动的 runtime 旋钮（至少各两个），预测每个旋钮的**效果方向**，并指出它的**反作用**（调它会让什么变差）。

最后一问最关键：A 的优化手段和 B 的优化手段里，有没有**一对会互相加剧对方**的？把这对耦合点出来。

### 架构设计 · 给一个会「断线重连」的远程前端，设计事件补发 `[接第 5 课]`

新需求：runtime 跑在一台服务器上，前端（桌面 GUI）通过网络连过来，**网络会抖、会断、会重连**。要求：前端断线期间 runtime **不停**、继续把当前 turn 跑完；前端重连后，必须**不多不少地补上**断线期间错过的所有产出，然后无缝接上实时流。基于第 1 课的 SQ/EQ 与状态分层设计这套补发机制：

- (1) 重连的前端怎么知道自己「落下了哪些」？它该带什么游标 / offset 上来，这个游标对齐到哪个东西？
- (2) 「不多不少」里的**「不多」**怎么保证（重连别把它已经收过的事件再发一遍）、**「不少」**又怎么保证（断线期间产生的事件别丢）？分别说清楚靠的是哪个机制。
- (3) EQ 是**无界**的。断线 10 分钟、turn 一直在跑、EQ 一直在堆——这会不会把内存撑爆？如果会，你打算怎么办，代价是什么？
- (4) 用一个边界场景验证：前端在「runtime 刚把一个 Event 推进 EQ、**还没** deliver 出去」的那一瞬间断线，又立刻重连。这个 Event 会不会丢？为什么？

最后：你的设计里，第 1 课**哪个已有机制被你直接复用了**、**哪个假设被打破、必须新增**？（第 (4) 问会直接咬到第 5 课「持久化 / 回放」的一条底线，想清楚那条底线是什么。）

## 参考解（热身 + 推演 1 + 量化 2 + 破 1 + 故障排查）

> 做完再看。带 `[决策X]` 方便回课文核对。每道有一段「命门」，专讲你最可能栽的那一处。

### 热身（对的是第 4 句）

- **1 错**。`run_turn` 确实在每次 sampling 开始前 drain 一次 pending input——但「sampling 开始前」是关键：drain 发生在**下一次** sampling 的循环顶部、`for_prompt` 构建模型输入**之前**。一个正在流式进行的 sampling 是**不会**被中途插话改写的；插的话进 pending input 队列，要等**当前这次 sampling 整个跑完、进入下一次循环**才被 drain 进去。所以那句话错在「并进当前这一次 sampling」——应是「并进**下一次** sampling」。`[决策二]`
- **2 错**。这句把「有一个写锁工具在跑」直接推成「全程没有任何两个能真正同时执行」，跨了一步。读写锁的语义是：**写锁独占（挡住所有读锁和其它写锁），但多个读锁之间可以并发**。所以一个不支持并行的工具取写锁、独占运行时的那**一段时间**里，确实没有别的工具能跑；但它跑完释放写锁后，那些支持并行的读锁工具**仍然可以两两并发**。「全程没有任何两个能同时执行」是错的——只有当所有正在跑的工具**全都**取写锁时才成立。`[决策二]`
- **3 错**。是经典埋雷。`isDiminishing` 的条件是 `continuationCount >= 3 && deltaSinceLastCheck < 500 && lastDeltaTokens < 500`——即「已续跑 ≥ 3 次」且「**最近这两段**增量（本次的和上一次记下的）都 < 500」，**只看最近两段**，不是「每一次都 < 500」。`[决策三]`
- **4 对**。这正是 A2 节纠正的那个常见误解：动态段会话内能命中，**不是**因为代码给它显式打了 per-session 的缓存断点——切前缀时静态块拿到 `cacheScope:'global'`、动态块拿到的是 `cacheScope: null`（根本不加 `cache_control`）。动态段「会话内还能命中」是**效果**，机制来自 provider 对稳定前缀的**默认自动缓存**（默认作用域是账号 / 组织级）。`[决策四 A2]`

> **命门**：第 3 句最容易被想当然「确认」成对的——「续跑了好几次都没产出，停掉合理啊」，于是放过它。但课文的精确条件只盯**最近两段**，留出了「中间几段没产出、但最近一段突然又产出了一大坨」时**不**判递减、继续干的余地。把「每一次」错当成判据，你设计的 deepseek 续跑器就会在「卡了几轮又突然来活」的任务上提前掐死。

### 推演 1

- **(a) 并发形态**：`ToolCallRuntime` 持**一把** `RwLock`。两个 `read` 都声明支持并行 → 各取**读锁** → 它俩可以**真并发**。`fmt` 不支持并行 → 取**写锁（独占）**。写锁和任何读锁互斥，所以 `fmt` 运行的那段时间独占运行时、把两个 `read` 挡在外面（谁先谁后取决于取锁顺序，但 `fmt` 与 `read` **绝不重叠**）。结论：两个 `read` 之间能并发，`fmt` 和谁都不能并发。并发互斥统一在运行时这一层，三个工具 handler 自己不写锁。
- **(b) `needs_follow_up` 拆两源**：
  - **模型这边**（`model_needs_follow_up`）：S_k 里模型发了三个工具调用——每处理一个 `OutputItemDone` 是工具调用，就把 `needs_follow_up` 置真。所以哪怕 `end_turn = Some(true)`，**因为有工具调用，模型这边的 follow-up 已经为真**。（`end_turn == Some(false)` 是**另一条**让 follow-up 置真的路；这里是 `Some(true)`，不走那条，但工具调用那条已经把它顶上去了。）
  - **pending input 这边**（`has_pending_input`）：用户那句「看下 d.ts」在 S_k 还没 drain 完时 submit、落进 pending input 队列 → `has_pending_input` 为真。
  - 合起来 `needs_follow_up = 真 || 真 = 真`。**这就是命门**：`end_turn = Some(true)` 把人往「该结束了」骗，但工具调用和 pending input 任一为真都顶着 turn 不结束，这里两个都真。
- **(c) 失败的 `fmt`**：`drain_in_flight` 把每个 `in_flight` 里的 future await 出结果、转成历史项**写回历史**——失败也是一个结果（一条 error 输出），照样写回。模型**下一拍看得到**这条 error。工具失败**不**改变控制流、**不**让 turn 提前结束。（注意：磁盘上 c.ts 已被改了半个，但历史里记的是「这次调用失败了」——这处「世界变了、历史说没成」的语义裂缝，正是「破 1」要你去撬的那条缝，这里先记下。）
- **(d) 「看下 d.ts」何时被看到**：它在 pending input 队列里，要等**下一次 sampling 循环的顶部**被 drain，并进**下一次** sampling 的模型输入。所以是 **S_{k+1}**——不是 S_k（S_k 那次的输入早在它开始前就定下了）。
- **(e) 最终判定**：S_k 之后 `needs_follow_up` 为真、且 token **没**撞上限（第 5 条），所以**不**触发 mid-turn 压缩、也**不**结束——直接进下一轮循环：drain 出「看下 d.ts」+ 三条工具结果（含那条 error），克隆历史 → `for_prompt` 归一化 → 发起 S_{k+1}。turn 在 S_k 这一步**继续**，不结束。

> **命门**：S_k 给了 `end_turn = Some(true)` + 没要新工具中的「没要新工具」是**假**的（它要了三个），很多人只盯 `end_turn` 这个字段就判 turn 结束。要记住 follow-up 是**两个独立来源的或**，`end_turn` 只是模型这条来源里的**一个**触发条件，工具调用和 pending input 都能各自顶着 turn 不退。

### 量化 2

> 数字随假设可变，结论必须一致。

- **1. 不压 10 轮的量级**。每轮三段分别记：
  - 静态块 12k：第 1 轮**全价**（这次会话第一次发，没暖过），第 2~10 轮**命中**（逐字节不变，按 0.1 计 ≈ 1.2k/轮）。
  - 动态块 2k：第 1 轮全价，第 2~10 轮命中（≈ 0.2k/轮）。
  - 历史：第 N 轮历史里，「上一轮新增的那 1k」是全价（这次才出现），更早的 (N-2)k 命中。
  - 粗算量级：第 1 轮 ≈ 12 + 2 = 14k 全价（历史为空）；第 2~10 轮每轮 ≈ 1.2（静态命中）+ 0.2（动态命中）+ 1.0（上轮新增全价）+ 0.1×（历史里更早段）≈ 2.5~3k。9 轮 ≈ 25k 上下。**总计费 token ≈ 40k 量级**——而「假装没有缓存、每轮都全价」会是 (12+2)×10 + 历史 ≈ 180k 量级。缓存把账压到约 1/4 ~ 1/5。
- **2. 隐藏账（命门）**：第 1 轮里那 12k 静态块是**全价，不是命中**。「静态段几乎永远热」说的是**跨会话 / 跨组织**的全局缓存红利——那要求 provider 支持 `scope:'global'` 级共享、且这段前缀已被别的会话焐热。本题前提写死了「provider 只支持账号级前缀自动缓存」，**没有跨组织全局层**，所以你这次会话的第一炮，静态前缀在**你自己账号的缓存里也还没暖过**（除非你自己上一个会话刚发过同样的前缀且没过 TTL）——按冷启动、全价算。把第 1 轮静态块当命中，是这题最容易栽的一笔。
- **3. 压缩炸的是哪段**：压缩**改写历史**——把前 5 轮历史换成一段 800 token 摘要。缓存按**前缀逐字节**匹配，从改写点往后的前缀全变了。但静态块 12k + 动态块 2k 排在**所有历史之前**，压缩**动不到它们**——这 14k 前缀照旧命中。被炸的是**「历史这一层」从改写点往后的前缀**：你之前花全价暖出来的那段历史缓存作废。压缩后的第 6 轮，要为**新的（摘要 + 保留尾巴的）历史前缀**付一次全价重算。**额外成本 = 重付那段压缩后历史前缀，不是重付 14k 系统块。** 很多人会以为「压缩炸缓存」是把整个前缀都炸了，错。
- **4. 触发判据 + 反驳**：写一个由**历史体积 / 窗口占用**驱动的判据，例如：`当 历史 token > X% × 有效上下文窗口（如 X=70），或 历史 token > K × 固定系统前缀（如 K=3），触发压缩；且距上次压缩 ≥ M 轮（如 M=3，防抖动）`。辩护：压缩的代价（炸历史缓存 + 重付摘要前缀）和它要解决的风险（撑爆窗口）**都来自历史体积**，所以触发该绑在体积上；`M` 防「压完缓存还没暖热又压」的来回抖动。**「每 6 轮压一次」错在哪**：把触发绑在**轮数**这个和真正风险无关的量上。轮数多但每轮短（历史还小）→ 白压一次、白炸一次历史缓存；轮数少但某轮某工具吐了一大坨（历史暴涨）→ 不压、撑爆窗口。**时机该由体积驱动，不由计数驱动。**（这条直接接第 3 课「何时压、触发阈值」。）

> **命门**：第 2 笔（第 1 轮静态块全价 vs 命中）和第 3 笔（压缩只炸历史层、不炸系统块）是两个反方向的陷阱——一个让你**高估**了缓存（以为静态段第一炮就命中），一个让你**高估**了压缩的破坏（以为它把整个前缀都炸了）。两笔都算对，你才真懂「缓存作用域 + 前缀逐字节」这套机制到底护住了什么、护不住什么。

### 破 1

二选一构造均可，这里各给一个：

- **构造甲（有未尽之事却停了）**：模型在某次 sampling 里**没发任何工具调用**、`end_turn` 给 `Some(true)`、此刻 pending input 队列也是空的——于是 `model_needs_follow_up = false`、`has_pending_input = false`、`needs_follow_up = false`，turn 干净利落地结束。但「任务客观上没做完」：模型只是**自以为**做完了（漏了一个文件没改、或误判了需求），它主观收手，闸完全合规地放它走。`needs_follow_up` 读的是「模型**要不要**工具」「队列里**有没有**输入」，从不读「任务**做完了没**」——所以模型的过早收手，这道闸一点都拦不住。
- **构造乙（没有有意义的事可做却还在续跑）**：模型陷入一个无意义的工具循环——每次 sampling 都发一个 `read(同一个文件)`，于是每次 `model_needs_follow_up = true`、turn 永远继续。闸逐字合规（确实有工具调用），但 agent 在原地空转、没有任何实质进展。`needs_follow_up` 只看「有没有发工具」，不看「这次工具调用有没有意义 / 是不是在重复」。

**这道闸实际保证 / 不保证 / 边界**：

- **实际保证**：turn 不会在「**模型机械地表达了还想继续**（发了工具 / `end_turn=Some(false)`）」或「**还有插队输入没消化**」时提前退出。它是一道**机械完整性**闸——把两个客观信号兜住。
- **不保证**：任务**语义上**做完没、续跑是否**有意义**、模型自评是否正确。它从不做语义判断。
- **边界画在**：「机械信号有没有」与「任务做完没 / 续跑值不值」之间那条线。前者它管，后者它一概不管。要兜住「过早收手」和「空转」这两侧，得靠**别的来源**——这正是 claude 多塞了 stop hooks（外部否决：测试没过不许收手）和 token 预算续跑（90% 推一把对抗过早收手、≥3 次续跑后最近两段都 <500 判空转对抗原地打转）的原因。codex 把判定收敛成这两个机械信号、更克制可预测，代价就是**「该不该继续」的语义判断被推给了模型自己和外部 hook**，闸本身不替你兜。`[决策二 / 三]`

> **命门**：很多人会想去「修」这道闸——给 `needs_follow_up` 再加一个「任务是否完成」的判断。但「任务做完没」**没有一个机械信号能算**（它要么靠模型自评、要么靠外部规则 / 人）。这道闸故意只管机械完整性、把语义判断外推，是**设计**不是缺陷。看穿这一点，你才知道 deepseek 的终止逻辑为什么必须是「机械闸 + 否决入口 + 预算」三个来源叠着用，而不是把一切塞进一个 `needs_follow_up`。

### 故障排查 · 「改完文件，模型像没看见」

- **(a) 排查路径（差分）**：
  - ① 先怀疑**持久化丢数据**——但现象② 明确说 rollout / transcript 里那条调用和结果都在、配得上对。这一刀**排除了「持久化层丢了 / 工具结果没落盘」一整类假设**：盘上是好的，所以问题不在「记没记下来」，而在「**发给模型的那份输入**里有没有它」。差分到这里，目标从「存储」收窄到「**每轮装配出来的 prompt**」。
  - ② 现象③ 排除了 API 报错 / 超时 / 限流——所以不是「这次调用没真的发出去 / 结果没回来」。
  - ③ 现象③ 里那个「**token 台阶式上跳**」是关键信号：历史涨到某个量级、撞了上下文 / token 上限。结合现象①「只在很长会话偶发」，强烈指向**压缩 / 历史改写**在出问题前那一轮被触发了。
  - ④ 把②③④ 串起来：盘上数据完好（②），但发给模型的输入里那条改动结果不见了，且就发生在历史涨到撞墙、触发了一次历史改写之后（③①）。
- **(b) root cause**：撞 token 上限触发了一次**压缩 / mid-turn 历史改写**（codex 里是 `token_limit_reached && needs_follow_up` 触发的 mid-turn 自动压缩，切点 `BeforeLastUserMessage`）。压缩把一段历史换成摘要——如果**那条工具调用结果落在被压掉的区间里、且摘要没把「改了什么」如实带出来**，那么发给模型的输入里这条改动就「消失」了（盘上还在，但模型这轮看到的是摘要）。模型于是基于压缩后的、丢了细节的历史推理，表现为「像没看见自己刚改的」。这也解释了为什么**只在长会话偶发**（短会话根本撞不到压缩阈值）、为什么**盘上数据完好**（压缩只改「发给模型的历史」，不动 append-only 的持久化记录）。
- **(c) 判定**：**by-design 的副作用，不是数据 bug**。压缩本就是**有损改写**——它用「省历史 token / 不撑爆窗口」换「丢一部分细节」。这条改动结果被摘进摘要时损失了，是压缩这个机制的**固有代价**，不是哪里写错了。（但「摘要该不该保住最近的工具改动」是个可调的**策略**问题，见 d。）
- **(d) 运营硬要求「最近一次工具调用结果绝不能丢」**：架构上动**压缩的「保留窗口」策略**——压缩时强制把「最近 N 次工具调用 + 结果」原样保留、不进摘要（claude 压缩后重建的历史本就有「保留的消息」这一段，把工具改动钉进这段）；或给压缩摘要器一条硬约束「文件改动类结果必须逐条列出、不许概括」。代价：保留窗口越大，压缩省下的 token 越少、压得越频繁、炸缓存越频繁——这是「稳（不丢改动）」和「省（压缩收益）」的直接互搏，得权衡 N 取多大。

> **命门**：现象② 是这题的**排除刀**——盘上数据完好，直接把整条「持久化 / 工具执行」假设链砍掉，逼你去看「**发给模型的输入** ≠ **盘上的历史**」这个差。没看出这俩是两份东西（一份是 append-only 的真相、一份是每轮装配 / 可被压缩改写的视图），就会一头扎进「是不是工具结果没写回」的死胡同里查半天。`[决策四 / 决策五，接第 3 课]`

## 评点（效果优化 / 架构设计 / 收口——自评用，非标准答案）

### 效果优化

**A 多前端体验割裂的旋钮**

- 把产出通道从「单消费者」改成**广播 / fan-out**：core 把每个 Event 扇出给所有订阅的前端，而不是只喂一个。**效果方向**：两端都能同步看到进度。**反作用**：core 要维护 N 个订阅者状态、每个订阅者独立的消费游标，复杂度上去了。
- 确保**先持久化后送出**：每个 Event 先落 rollout 再 deliver，慢的那一端可以从 rollout 补，而不是被快的那一端甩下。**反作用**：每个 Event 多一次落盘开销。
- （这题的死约束是「不许动模型 / 不许加缓存设施」，所以 A 全在**消息架构**这一侧动，不许往缓存上想。）

**B 长任务越往后越啰嗦越慢的旋钮**

- **增量注入（基线 + diff）**：环境 / 权限 / 设定首轮全量发、之后只发变了的那几样——历史里不再堆 N 份几乎一样的设定块，省 token / 窗口、也少了重复信息分散模型注意力。**效果方向**：首字延迟降、不再重复环境信息。**反作用**：要维护基线、处理压缩 / 回滚时的基线重置，写错了会发漏 / 发错设定。
- **压缩 / 控制历史体积**：历史涨到一定体积就压。**效果方向**：prompt 体积下来、首字快。**反作用**：压缩炸历史缓存、且有损（可能丢细节，见前面那道故障排查）。

**互相加剧的一对（关键洞察）**：A 想让两端同步、可靠补发，会倾向**先持久化后送出 + 广播**，这本身不和 B 冲突；真正的耦合在另一处——B 为了降延迟去**压缩历史**，而压缩是一次**历史改写**，对 A 的多前端补发是个麻烦：一旦历史被压缩改写，正在断线 / 落后的那一端重连后想从 rollout 补，会发现「补的那段历史」和「现在的历史」对不齐（基线被重置过）。**即 B 的「压缩降延迟」会加剧 A 的「多端一致 / 补发」难度**；反过来 A 为保多端严格一致而禁止任何历史改写，又会**堵死 B 的压缩**、让长任务延迟降不下来。这对耦合点出来才算到位。

**陷阱**：列了旋钮不写反作用（等于没优化）；在死约束下偷偷往「加缓存」上想（题面明令禁止）；没发现 A↔B 在「压缩 / 历史改写」这个点上的耦合。

### 架构设计

**强答案应触及的维度**

- **(1) 游标对齐到什么**：重连前端带「我最后收到的 Event 序号 / offset」上来。这个 offset 必须对齐到**持久化序**——即 rollout 里 Event 的落盘顺序，**不是**前端自己数的。因为「先持久化后送出」保证了落盘序 = 唯一真相序，两端 / 重连都按这个序对齐才不会乱。
- **(2)「不多不少」**：**「不少」**靠 EQ 无界 + 先持久化后送出——断线期间 turn 照跑、Event 照落 rollout，一条不丢；重连后从 rollout 把落下那段回放出来。**「不多」**靠 offset 去重——core 只补「offset 之后」的，前端已收过的不再发。两件事各有各的机制，别混。
- **(3) EQ 无界会不会撑爆内存**：会——这是无界队列的真实风险。断线 10 分钟、turn 一直产出、没人消费，EQ 一直堆。对策：**EQ 本身不当长期存储**，真相在 rollout（持久化）里；断线超过某阈值就**让那个前端的 EQ 订阅泄洪 / 丢弃**（反正它能从 rollout 补），或给每个订阅者的内存缓冲设上限、超了就只留「从 rollout 补」这条路。代价：重连时补发要读盘回放、比内存里直接拿慢。**别把「EQ 无界」理解成「内存里无限存」——无界是为了「输出永不阻塞 turn」，不是为了「永久留存」，永久留存是 rollout 的活。**
- **(4) 边界场景**：Event 已推进 EQ、**还没** deliver 出去那一瞬间断线——**这个 Event 不会丢**。因为「先持久化后送出」：Event 在进 EQ / deliver **之前**就已经落了 rollout。前端重连后带着旧 offset 来，core 从 rollout 回放，这条 Event 因为已落盘、序号在 offset 之后，照样被补上。**如果顺序反了（先 deliver 后持久化），这条就真丢了**——这正是第 5 课「先持久化后送出」那条底线存在的理由。
- **复用的已有机制**：EQ 无界（输出不阻塞 turn）、先持久化后送出、rollout 是唯一真相序、状态分层里「会话级状态跨 turn 留」。**被打破、必须新增的假设**：「EQ 单消费者」——原架构假设一会话一前端消费 EQ，现在要多 / 重连消费者，得新增「每订阅者独立 offset + 从 rollout 回放补发 + 订阅者内存缓冲上限」。
- **陷阱**：把 offset 对齐到前端自己数的序而非持久化序；以为「EQ 无界」就能当永久缓冲（没想到要靠 rollout 回放、EQ 缓冲要设上限）；第 (4) 问没扣到「先持久化后送出」这条底线，答成「看运气」。

### 收口

- **结论（高分线）**：**强与自动大体同向，稳是那个对立面。** 强（能力上限）和自动（自驱多干、少人盯）常被**同一个机制**一起推动：三层执行模型让 agent 能做更复杂的事**且**自己多跑几轮；自动续跑 / token 预算 nudge 让它把活干完整**且**不用人催；mid-turn 自动压缩让它能在长任务里跑下去**且**不用人手动清history；steering 让它能边跑边接新指令**且**不用停下来等。每一个都同时把「强」和「自动」往上抬。而几乎所有**稳**的机制——先持久化后送出、状态四层分离、`in_flight` + RwLock 并发闸、`normalize_history`、三道硬闸（`max_turns` / `max_tool_calls` / `token_budget`）、优雅关机——都是给这股「强 + 自动」的冲劲**踩刹车 / 装护栏**。
- **统一成一句话**：前面每个决策里反复出现的「装护栏，不是把它关掉」，本质都是——**稳是强 & 自动的边界条件**。deepseek 的护栏投资，主要不该花在「让某机制更强 / 更自动」（那是默认就有的冲劲），而该花在「**让强 & 自动不越过稳的那条边界**」：自动续跑要配硬闸防空转、自动压缩要配「最近工具改动不许丢」防丢细节、多前端 / steering 要配「先持久化后送出」防丢事件。
- **可加的反驳细节**：局部确有 强×自动 争资源的影子（自动派一大堆并行工具 / 子任务能提吞吐 = 更强，但失控 = 不稳 + 不可预测）——但根上仍是**稳**在约束这对冲劲，不改变「稳是对立面、强与自动同伙」的结论。
- **陷阱**：把「稳」和「自动」挑成同一处机制的两种说法（那就找不到真正对立的那一性了）；承认「两两都有张力」却举不出强 & 自动**被同一机制一起推**的例子——那才是这题真正要你看穿的。
