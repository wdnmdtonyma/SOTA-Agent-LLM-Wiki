# 第 12 课 习题：把十一个子系统装成一台 agent（capstone）

> 配套课文：[`../lesson-12-capstone.md`](../lesson-12-capstone.md)
>
> **这是终章。前十一课你逐个学会了零件；这一课逼你把它们装在一起还不散架。** 所以这套题不再考单课机制——它考的是**装到一起才冒出来的东西**：谁先建谁后建、哪条规则横穿好几个子系统、哪个旋钮今天不拧死明天就要全量迁移。结构仍是四层，越往下越像「真在给 deepseek 拍板」：
>
> - **热身**：判断改错，快速校准——但**埋了雷**（四句里恰好有一句是对的，别逢句就改）。本课最大的雷区是「重要 vs 排得早」「杠杆 vs 依赖」「四角色 vs developer 桶」这几对最容易想当然的地方。
> - **机制层**：`推演`（脑里把整张依赖图跑一遍）/ `量化`（给一个里程碑算账、给一个敢写进路线图的边界）/ `破`（给你课文当「全局一致性保证」的某条横切不变量，构造一个它跑完之后结构上合规、系统却照样炸的反例）。答案**不在课文里**，题面也**故意不替你把子问题拆好**。
> - **实战层（主菜）**：`故障排查` / `效果优化` / `架构设计`。这层**欠定**——不告诉你是哪一课、哪条不变量出了事，你得自己做**差分诊断**。capstone 的事故都是**跨课连锁**：一个横切不变量在某个子系统里被破，崩在很远的另一个子系统上。架构设计这道就是那张**总装蓝图**：只给你 M0 的预算，你装哪几个机制。
> - **收口**：把全课程收到 强 / 稳 / 自动 三性上，落到你们宪法的 parity-first 北极星。这是**结课题**——做完它，你应该能拿这套框架去检查任意一个 agent 设计。
>
> **怎么用**：全部闭卷先做。`热身/推演/量化/破/故障排查`**有标准解**（但要你自己推/算/破/诊断出来），做完对照「参考解」；`效果优化/架构设计/收口`**无标准答案**，先独立写再看「评点」自评。难度是**「难但公平」**——所有标准解都能从课文那三样（装配顺序 / 五条横切不变量 / 早决定旋钮）+ 题目给定条件推出来，**不靠任何课外冷知识**。卡住了顺 `[§N]` / `[不变量N]` 回课文找零件。

## 机制层（有标准解，但答案不在课文里）

### 推演 1 · 把一颗动态信息塞错位置，沿依赖图追到它在哪一拍炸 `[不变量1 / 不变量3 / §3]`

一个新人给 deepseek 的 prompt 装配链加了「当前模型名 + 当前 sandbox 状态」两个字段，想让模型「时刻知道自己跑在什么环境里」。他装得很「干净」：把这两个字段**拼进了那条 system 静态前缀的末尾**（在身份和工具规范之后、安全话术之前），理由是「这是常驻指令性质的环境告知，本来就该进 system」。本地跑通了，模型确实能正确报出自己的模型名和沙箱状态。

把这条改动**从它进 system 静态前缀的那一刻，沿依赖图一路追到它真正出问题的地方**。逐拍回答：

- 这两个字段进了静态前缀，**第一拍**违反了哪条横切不变量？为什么本地「跑通了」却完全没暴露这个问题——本地测试看不见的是什么？
- 这台 agent 多跑几轮、用户切了一次模型、或者从 plan mode 切到 default mode 之后，**那条「逐字节稳定」的前缀**发生了什么？用户根本没碰那两个字段，为什么它们还会变？
- 这个破坏**最终崩在哪个看起来八竿子打不着的子系统**上、以什么现象暴露？（提示：第 11 课有一个监控指标专门会先掉。）
- 这个新人本来想要的「让模型知道环境」是合理需求。**正确的落点**在哪——这两个字段该进哪个桶、那个桶在 wire 上又会被序列化成什么？为什么那样放就既满足了需求、又不碰前缀？

### 量化 1 · 给 M0 算一笔「装得起 vs 装不起」的账，定一个敢写进路线图的边界 `[§1 / §4]`

有人主张「把渐进式工具暴露提前到 M0 一起做」，理由是：「反正早晚要做，M0 一起做省得返工。」请用一笔账判断这个主张**能不能成立**，并给出一个**敢写进路线图的工具数边界**。

已知（全部来自课文/宪法的真实设定）：M0 的工具集是固定的 **6 件**（read / write / edit / glob / grep / bash）；渐进式工具暴露的触发**门槛约 40 个工具**；让工具数从个位数涨到逼近这个门槛的，是 **skill 和 MCP**（它们把生态里的工具一批批接进来），而这两样都排在 **M2**。

先建账、算量级：

- **（甲）** M0 阶段，真实在册的工具数是多少？它离那个约 40 的触发门槛**还差多远**？
- **（乙）** 渐进暴露这套机制（client-side 检索 + 命中后下一轮把 schema 注入 `tools` 数组）在 M0 阶段**实际会被触发几次**？它在 M0 拦掉的 prompt 膨胀是多少 token？

然后回答两个**课文没替你说、但能从这笔账推出来**的点：

- （i） 「早晚要做，M0 一起做省返工」这个主张错在哪？它把哪两种**排期的力**（课文 §1 那张表里的四种）**混成了一种**？把这两种力分开说清：一个机制「**该不该做**」和它「**什么时候才装得起**」分别由哪种力决定。
- （ii） 给出你**敢写进路线图的那条边界**：渐进暴露应当在「工具数逼近 ___」时上线，而这个条件**最早**在哪个里程碑才可能成立、为什么是那个里程碑而不是更早。（数字随假设可变，但你的边界**必须挂在一个真实的依赖上**，不能是拍脑袋的常量。）

### 破 1 · 让「deny 最先判、谁都绕不过」这条裁决顺序原地失效 `[不变量4]`

课文把权限引擎那条裁决顺序——**所有动作汇进同一个引擎、deny 规则最先判、直接压死任何 allow、谁都绕不过**——当作可扩展性放开后的安全保证，并说「可扩展性每开一个口，第 6 课就得补一道对应的门」。

请构造一条路径：**这个权限引擎本身没有任何 bug,deny-first 的裁决逻辑也一字没动、跑得完全正确，但一个本该被 deny 的危险动作照样跑成了。** 也就是说，引擎在它能看到的东西上判得没错，危险动作却根本没进到引擎面前、或进来时已经换了副无害的皮。（提示：课文 §2 不变量四自己点了名——`hooks` 里有一类 handler 是「绕过 typed 工具审查的**任意代码口**」；再想想，引擎是按「它收到的动作描述」判的，那「动作描述」是谁生成的、可不可靠。）

至少给出**两条**结构不同的绕过路径。然后说清楚：

- 这条裁决顺序**实际保证**的到底是什么、**不保证**的是什么——它的边界画在哪条线上？（「deny 压死 allow」是关于**优先级**的保证，它顺带保证了「动作一定如实地、完整地到达引擎」吗？）
- 课文那句「每开一个口就补一道门」，在你这两条绕过路径面前，**「补门」具体要补成什么样**才真的堵得住——光把新接缝的动作「接进同一个引擎」够不够？

## 实战层（主菜：欠定、差分、判断——没有「这是哪一课」的标签提示你）

### 故障排查 · 一台「越跑越贵、还时不时罢工」的 agent

线上反馈：某个重度用户的 agent，最近一周体验断崖式变差。三条诡异现象：

- ① **成本曲线**显示，这个用户每个任务的花费，在一周内翻了三倍多；监控里那条 `cache hit ratio` 从平时的 ~80% 掉到了个位数，**几乎一直贴着地板**；
- ② 偶发地，任务跑到一半**直接报 `input exceeded`（上下文超限）而中止**；但每次抓现场去看，**账本显示当时上下文明明还剩三成空间**；
- ③ 另一个用量、任务类型几乎一样的用户，**这一周没装过任何新东西**，成本和 cache hit ratio 一切正常，从没报过超限。

已知这个出问题的用户，这一周里做过不少「折腾」：装了两个 MCP server、开了好几个 hook、还在工作区里堆了一大堆 AGENTS.md 和 skill。运维一开始判断是「MCP server 太重、拖慢了一切」，准备让用户卸载 MCP。

给出：

- **（a）** 你的**差分排查路径**——依次看什么、用什么**排除**什么。想清楚现象③（同负载、没装新东西的用户一切正常）帮你**排除了哪一整类假设**；现象①和现象②**看起来像两个独立故障**，你怎么判断它们是**一个根因的两张脸**还是**两个互不相干的毛病**？（提示：课文 §2 里，有一条横切不变量同时穿过「缓存」和「上下文账本」这两件事吗？）
- **（b）** 最可能的 **root cause**——落到课文的**某一条横切不变量**上，并说清它是怎么**同时**制造出①和②两种现象的。
- **（c）** 判定：运维「卸载 MCP」的方向**对不对**？为什么？（MCP 本身是不是病根，还是它只是「把某个一直存在的隐患的触发条件凑齐了」的那根稻草？）
- **（d）** 如果这个用户坚持「这些 MCP / hook / AGENTS.md 我都要，一个不卸」，你**在不让他卸任何东西的前提下**怎么根治？动哪里、代价是什么？（回扣：§2 不变量一、五；§3 早决定旋钮。）

### 效果优化 · 一台「能跑但又慢又笨又时好时坏」的 M2 agent

一台已经进到 M2 的 deepseek agent，功能都在（压缩、记忆、多 agent、skill、MCP 全装上了），但用户投诉两条：

- **（A） 长任务里，模型「越跑越忘事」**：跑到任务后半段，它经常想不起来前面定的约束、做过的决定，质量明显下滑，得用户反复提醒；
- **（B） 同样一句话，有时秒回、有时要等很久，体验很不稳定**，用户摸不准什么时候快什么时候慢。

给你一条**死约束：不许换模型、不许加预算（上下文窗口大小、月度成本上限都不许动）**。

针对 A、B 各列出你能动的 runtime 旋钮（**至少各两个**，落到课文里的真实机制：压缩的两个数字、记忆的写/读路径、reasoning 回填、token 账本、缓存前缀纪律、子会话预算……），预测每个旋钮的**效果方向**，并指出它的**反作用**（调它会让什么变差）。

最后一问最关键，也是 capstone 该有的难度：A 的优化手段和 B 的优化手段里，**有没有一对会互相加剧对方**？（往这想：你为治 A 而「多留点历史、多注点记忆」，会不会正好动了某条横切不变量，把 B 拖得更糟？反过来，你为治 B 而「狠狠保住缓存、能不压就不压」，会不会让 A 更早撞上遗忘？）指出这对耦合**共用的那个变量**是什么。 `[不变量1 / 不变量5 / §5]`

### 架构设计 · 只给你 M0 的预算，你装哪几个机制（终极开放题：画出 M0 总装蓝图）

这是这门课的**终极开放题**，也是你作为 deepseek harness 架构师真要拍的那一板。

设定：你手上**只有 M0 的预算**——能且只能先实现**有限的几个机制**，把端到端最 risky 的那条线跑通（`deepseek-v4-pro`、thinking、流式驱动的 agent loop，能调工具、能持久化、能流式呈现）。前十一课每课都给了 deepseek 一个落地结论，但你**装不下全部**。

请交付一张 **M0 总装蓝图**，回答：

- **（1） 你装哪几个机制进 M0、为什么这几个是「地基」？** 不是按「哪个功能听起来重要 / 杠杆高」选，而是按「哪个是别的东西的依赖、哪个的洞不能带着上线、哪个改起来贵必须早定」选。逐个给出你选它的**那一种力**（§1 那张表的四种力：依赖 / 风险不可延 / 杠杆 / 可逆性）。
- **（2） 把蓝图里所有的横切边界标出来**：这张 M0 图上，哪条线是**缓存边界**（静态前缀 vs 动态桶）、哪条是**持久化边界**（什么先落盘后送出）、哪条是**审批门**、哪条是 **token 账本的单一真相源**。`[§2 / §3]`
- **（3） 标出你 M0 **明确不装、推迟到后面**的东西，以及你怎么「不堵死」它**：挑**至少三个**你推迟的机制（比如压缩、记忆、MCP、多 agent、OS 沙箱……），说清楚它推迟到哪个里程碑、为什么现在装不起（它的地基还没到），以及你在 M0 要留下什么**留位 / 账本注释**，保证将来接上时不用推倒重来。（回扣：§1 MCP=M2 的依赖论证；§3 那条「stub 必须带 `// replace in milestone X` 账本注释」的纪律。）
- **（4） 跨课边界验证**：有人主张「M0 既然要持久化，顺手把压缩也做了吧，反正压缩就是省上下文、对省钱有好处」。用你这张蓝图驳掉他——压缩**依赖**什么（它自己是什么）、那些依赖在 M0 齐不齐？以及更尖锐的：就算硬把压缩塞进 M0，它会**违反哪条横切不变量**、把 M0 最该保住的那条线（cache hit ratio）怎么样？

收尾逼问：你的 M0 蓝图里，**复用了前面哪个机制当所有「重入」的底座**（子 agent、压缩、resume 都站在它上面）？以及，你这张蓝图**新增了一个什么假设**，是单看任何一课都不会逼你做、只有「装到一起」才逼出来的？ `[§1 / §3 / §4 / §5]`

## 收口 · 用这门课检查一个 agent 设计：三性、parity-first、与你们宪法对齐（结课题）

这是**结课题**。给你一个**别人**的 agent 设计提案（不是 deepseek 的），你要用这门课教的整套框架去审它，并给出一个 deepseek 架构师该给的裁决。

提案是这样的：某团队要做一个 coding agent，主打「**全自动、无人值守**」——它的卖点是一套 codex 式的**对等 agent 图**：多个长期 agent 在一个共享控制平面下互相喊话、`trigger_turn` 互相唤醒、崩溃后能恢复整棵活着的 agent 树。提案主张：「我们一上来（相当于 M0）就把这套对等图做扎实，因为这是我们最大的差异化卖点、杠杆最高，先把最强的能力立住。」

请用这门课的框架审它，具体回答：

- **三性归位**：这套「对等图 + 崩溃恢复整棵树」主要加强了 强 / 稳 / 自动 里的**哪一性**？它为此**付出的复杂度**主要压在**哪一性**上？（回扣第 7 课你已经做过的那次归位，但这次要落到「该不该 M0 就上」。）
- **装配顺序的硬伤**：用 §1「依赖决定排期、重要性 / 杠杆不决定排期」这把尺子，指出这个提案**最大的排期错误**是什么。它和课文里 MCP 那个反面教材**犯的是同一个错吗**？（都是「只盯杠杆 / 重要性，没看地基」吗？这套对等图的「地基」是什么、M0 齐不齐？）
- **横切不变量的连带代价**：这套对等图一旦上了，它会逼着**哪几条横切不变量**变得更难维持？（想：多个长期 agent 互发消息进了谁的账本？fork 出去的对等 agent 还复用同一条缓存键吗？崩溃恢复要重建的状态，和「先持久化后送出」「token 账本一个口径」怎么咬合？）
- **parity-first 北极星裁决**：站在 deepseek 的北极星（先对齐、后超越；每个「超越」的念头先问「这是帮我们更接近与 claude / codex 效果对齐，还是引入了我们**还没挣得的范围**」）上，给这个提案一个裁决——**做 / 推迟但架构不堵死 / 不做**，并说清你的理由。

（及格线：能把对等图归位到「自动」、能看出「该不该做」和「什么时候装得起」是两回事。高分线：看穿这个提案犯的正是 capstone §1 那个核心错误——**把「杠杆 / 重要性」当成了「排期」，而对等图的地基（稳定的 turn loop、rollout、持久化、缓存纪律、权限引擎）一个都还没在，M0 就上对等图等于在没有地基的地方盖最高的那层楼**；并据此给出 deepseek 式裁决：**对等图属于「还没挣得的范围」，推迟到 post-v1、架构上用「子 agent 注册表 / 通信抽象预留」不堵死，M0 先把那张依赖图的根（turn loop + 一次性层级 fan-out）装稳**。）

### 推演 1

- **第一拍违反的不变量**：**不变量一（缓存前缀确定性）**。模型名、sandbox 状态都是**会话动态信息**，课文点名「绝不进静态前缀」。把它们拼进那条逐字节稳定的 system 前缀，前缀就不再「逐字节稳定」了——它现在含有一段会随会话变的内容。
- **本地为什么没暴露 / 本地看不见的是什么**：本地单跑一遍，模型名不变、sandbox 状态不变，那条前缀**这一次**确实是稳定的，功能（模型能报出环境）也正常——所以「跑通了」。本地测试看不见的是**「多轮之间、多会话之间的字节一致性」**：缓存命中是一个**跨请求**的效果，你得连发好几轮、且中间真的发生过模型切换 / mode 切换，才看得见前缀在轮与轮之间是否还逐字节相同。单次功能测试天然测不到这个维度。
- **用户没碰字段，它们为什么还会变**：因为这两个字段的值**本身就是会话状态**——用户切一次模型（v4-pro ↔ v4-flash），模型名变了；从 plan mode 切到 default mode,sandbox / 权限姿态变了。字段是「环境的快照」，环境一动它就动，**与用户有没有手动碰它无关**。一旦它在前缀里，前缀就跟着这些状态一起漂移。
- **最终崩在哪、什么现象（命门）**：崩在**第 11 课那条 `cache hit ratio` 监控**上——它会先掉。每当那段前缀的字节变一次，服务端的前缀缓存就**从变动点之后整段失效**，后续 token 全部按 miss 重新计费。现象是「**功能完全正常，但成本悄悄上涨、缓存命中率掉**」。这正是这条不变量最阴的地方：错在 prompt 装配（第 8 课），**崩在成本曲线**（第 11 课），中间隔着好几个子系统，极难顺着「成本涨了」反推回「有人往前缀里塞了模型名」。这也是为什么 deepseek 要配一道 cache-break 回归守卫——靠人去发现这种漂移太慢。
- **正确落点**：这两个字段属于**会话动态信息**，该下沉到**动态消息**里——具体说，环境告知（cwd / git / 时间 / 模型名 / sandbox）进 **`environment_context`（user 侧）**，而带「常驻指令」性质的权限 / mode 片段进 **`developer` 桶**。模型名 / sandbox 状态是纯环境快照，落 environment_context 即可。关键是：**它们在逻辑组装上是独立的动态消息，绝不上移进 system 静态前缀**。至于「developer 桶在 wire 上是什么」——接下一条不变量：DeepSeek 只有四个角色、没有 developer,adapter 序列化时把 developer **塌缩成 provider 支持的 system 形态**；但那是**动态那条 system 消息**，和**静态前缀那条 system** 是两回事——静态前缀锁死，这条每轮可变。这样放，需求（模型知道环境）满足了，前缀纪律也没破。 `[不变量1 / 不变量3 / §3]`

### 量化 1

> 解 = 算出 M0 的工具数离门槛差多远 + 看清渐进暴露在 M0 触发零次 + 把「该不该做」和「什么时候装得起」两种力分开 + 给一条挂在真实依赖上的边界。数字随假设可变，结论必须一致。

- **（甲）M0 在册工具数 vs 门槛**：M0 工具集是固定 **6 件**。渐进暴露的触发门槛**约 40**。6 离 40 差 **34**——也就是说 M0 阶段工具数**连门槛的零头都不到**（约 15%）。
- **（乙）渐进暴露在 M0 触发几次 / 拦掉多少**：**触发 0 次**。这套机制是「工具数逼近门槛才命中」的；M0 只有 6 个工具，**永远到不了 40**，所以这套检索 + 注入逻辑在 M0 **一次都不会触发**。它在 M0 拦掉的 prompt 膨胀 = **0 token**——因为 6 个工具的 schema 本来就该全量直接进 `tools` 数组，根本没有「太多装不下」的问题需要它来解决。换句话说，在 M0 把渐进暴露做出来，等于**造了一台这个里程碑根本不会启动的机器**。
- **（i） 主张错在哪 / 混了哪两种力（命门）**：「早晚要做，M0 一起做省返工」把**杠杆**和**依赖**这两种力**混成了一种**。正确的拆法是：
  - **该不该做**——由**杠杆**（回报）决定。渐进暴露该做，没争议（工具一多就必须有它）。
  - **什么时候才装得起**——由**依赖**决定。渐进暴露的「用户」是「逼近门槛的工具数」，而把工具数推到门槛的是 **skill 和 MCP，它俩都在 M2**。所以渐进暴露**最早**也只能在 M2 才「装得起」——在那之前它没有触发条件，做了也是死代码。
  - 「省返工」是个伪收益：M0 做它**不省任何东西**（M0 不触发），反而**提前背上**一套没法验证（无法在 M0 造出 40 工具的真实场景）、却要维护的代码。这正是课文 §1 那句：**杠杆决定该不该做，依赖决定什么时候才能做，两种力别混。**
- （ii） **敢写进路线图的边界**：渐进暴露应在「**工具数逼近约 40**」时上线，而这个条件**最早在 M2 才可能成立**——因为只有 M2 接进 skill 和 MCP，工具数才会从个位数涨到逼近门槛。它挂的真实依赖是「**skill / MCP（M2）把工具数推高**」，不是一个拍脑袋的常量。所以路线图写法：**渐进暴露 = M2，门槛 ≈ 40，触发条件 = skill/MCP 接入后工具数增长**——架构上 M0 就让 `ToolSpec` 支持 `defer` 标记、system prompt 支持列名，**不堵死**，但**实装等 M2**。 `[§1 / §4]`

### 破 1

- **构造（两条结构不同的绕过）**：
  - **路径一：命令型 hook = 任意代码口，绕过 typed 工具审查。** hook 的 PreToolUse / 其它生命周期事件可以挂一个 **Command handler**——它执行的是用户配置里的一段 shell 命令，**不是**一个经过 schema 审查的 typed 工具调用。权限引擎是冲着「typed 工具调用」那套动作描述去判 deny / allow 的；一段藏在 hook 里的 `rm -rf` / 外发数据的命令，**根本不以「工具调用」的形态进到引擎面前**，引擎压根没机会对它跑 deny-first。deny 逻辑一字没动、判得也对——它只是**没看见**这个动作。
  - **路径二：动作描述失真 / 偷换。** 引擎是按「它收到的那份动作描述」判的。如果某个接缝（比如一个 MCP 工具、或一段 hook）上报给引擎的描述，和它**实际**要干的事不一致（描述成「读一个文件」，实际触发了别的副作用），那引擎对着一份「无害的皮」判了 allow，危险动作照样跑成。deny-first 保证的是「**在它收到的描述上**，deny 压过 allow」，它**不保证**「描述如实、完整地反映了真实动作」。
- **实际保证 / 不保证 / 边界（命门）**：这条裁决顺序保证的是**优先级**——「**汇进同一个引擎的、如实到达的**动作，deny 一定压死 allow，谁都绕不过」。它**不保证**两件事：（1）**所有**危险动作都会**以可审查的形态、完整地到达引擎**（命令型 hook 这种「任意代码口」就可能整个绕过 typed 审查）；（2）到达引擎的**动作描述是如实的**（描述被偷换，引擎就判错了对象）。边界线：**它是「到达引擎之后」的优先级保证，管不到「到达之前」的完整性与真实性。** 「deny 压死 allow」和「动作一定如实到达引擎」是**两件正交的事**，前者真，不蕴含后者。
- **「补门」具体补成什么样**：光把新接缝的动作「接进同一个引擎」**不够**——那只解决了「到达之后」。真正堵得住要补两层：
  - 对**任意代码口**（命令型 hook）：它绕过 typed 审查，所以默认就该带「**用户显式信任过这份配置才挂**」的检查（课文点的 codex `trusted_hash`：配置内容哈希过、用户信任过，才允许这段命令存在并执行）。没信任就根本不挂——这是把「到达之前」那道缺口在源头封住。
  - 对**所有接缝的动作描述**：来路不明的命令要**降级、不予特殊信任**——课文那句「来自 MCP 的命令**永远不准跑 shell 块**」就是这个意思：不信任 MCP 上报的动作能如实代表它要干的事，所以**结构性地禁掉它走最危险的那条路**，而不是寄望引擎去逐条判一份可能失真的描述。
- 一句话收：**「补门」不是「把动作接进引擎」，是「保证危险动作只能以可审查、如实的形态到达引擎，且任意代码口必须先过信任门」**——前者是优先级，后者是完整性 + 真实性，缺了后者，deny-first 判得再对也是对着空气判。 `[不变量4]`

### 故障排查 · 一台「越跑越贵、还时不时罢工」的 agent

- **（a） 差分排查路径**：
  - 现象③（同负载、**没装新东西**的用户一切正常）是**关键一刀**：它**排除**了「是 agent 本体 / 后端版本 / DeepSeek 服务端这一周变坏了」一整类假设——病不在公共代码里，**就在「这个用户这一周折腾出来的那堆配置」**（MCP / hook / AGENTS.md / skill）身上。把矛头从「平台」死死指向「这一个用户的环境」。
  - 现象①（cache hit ratio 贴地 + 成本翻三倍）和现象②（账本说还剩三成、却报超限）**别急着当两个故障**。先问课文 §2 那个问题：**有没有一条横切不变量，同时穿过「缓存」和「上下文账本」？** 有——但更要命的是，①直接是**不变量一（缓存前缀确定性）**塌掉的招牌现象（前缀漂移 → 缓存整段失效 → 成本暴涨），②直接是**不变量五（token 账本一个口径）**算错的招牌现象（76% 还剩着却报 exceeded，是账本漏了一道 cap / 算错了）。
  - 判它们是「一个根因两张脸」还是「两个毛病」：看**触发时机是否同源**。这个用户这一周往环境里塞了大量 **AGENTS.md / skill 清单 / MCP 工具表**——这些**全是会话动态信息**。如果有一处把它们**漏当成静态、拼进了前缀**（或工具表顺序不稳），那**同一个根因**就会**同时**：（a）污染前缀 → 缓存塌（现象①）；（b）让本该稳定、可缓存、可计入「静态」的那段东西每轮重算、膨胀，token 账本对「这段算静态还是动态、计不计、计几次」一旦口径不一，就会在某些边界（错误/超时路径漏 cap）上**把剩余空间算错** → 误报超限（现象②）。所以**优先按「一个根因」假设去验**，而不是开两条独立排查线。
- **（b） root cause**：**这个用户新堆进来的那批会话动态信息（AGENTS.md / skills 清单 / MCP 工具表），有一处漏了「静态前缀 vs 动态桶」的边界纪律，渗进了缓存前缀 / 让前缀每轮重算**——根因落在**不变量一（缓存前缀确定性）**上。它**同时**制造①和②：前缀一被这些每轮都变的内容污染，服务端前缀缓存就从污染点起整段失效（→ ① cache hit ratio 贴地、成本翻倍）；而这同一段「本该静态、现在每轮变」的内容把 token 账本的口径搅乱（配上错误/超时路径那道漏掉的 cap），触发判断算错，于是「明明还剩三成」却报 `input exceeded`（→ ②）。两张脸，一个根因：**一条横切不变量被新接入的动态信息破了。**
- **（c） 卸载 MCP 对不对**：**方向不对（治标不治本，且会冤枉 MCP）。** MCP **不是病根**——病根是「**新接入的动态信息没守缓存边界纪律**」这条横切不变量被破。MCP（以及 hook / AGENTS.md / skill）只是**把这个一直潜伏的隐患的触发条件凑齐了**的那根稻草：正是因为这个用户接了一大批动态内容，边界纪律上那处疏漏才被放大到「缓存全塌、账本算错」。卸了 MCP，现象可能缓解（动态内容少了），但**只要边界纪律的洞还在，下一个重度用户照样会踩**。况且 MCP 是 M2 正经能力，为一个 prompt 装配的 bug 去砍掉它，是拿错了刀。
- **（d） 一个不卸、怎么根治（命门）**：在**不卸任何东西**的前提下，根治要落到那条横切不变量本身：
  - **把边界纪律修对**：审计 prompt 装配链，确认 AGENTS.md / skills 清单 / MCP 工具表 / 权限片段 / mode / 模型名 / sandbox 状态**全部下沉为独立的 developer / user 动态消息**，**一个字都不许留在 system 静态前缀**；工具表（含 MCP 接进来的工具）按**名字排序**保证字节顺序稳定（课文那个 codex 真实事故：MCP 工具一度存哈希表、顺序每轮变 → 缓存失效 → 按名排序才修好）。这直接修掉现象①。
  - **修 token 账本的口径**：让主循环 / 压缩 / 多 agent **读同一本账**，并补上错误 / 超时路径那道漏掉的 cap，保证「剩余空间」在所有路径上算法一致——这修掉现象②（76% 还剩却报超限）。
  - **加守卫防回归**：上那道 **cache-break 回归守卫**（哈希稳定前缀输入、响应后比对 cache-hit token 跌幅，一旦会话变量泄进前缀就告警），让下次有人再往前缀塞动态内容时**当场被测试逮住**，而不是等成本曲线一周后才报警。
  - 代价：这是一次 prompt 装配链的「扫雷」（课文 §3 把「缓存边界」列为早决定旋钮、定错的代价就是「事后把整条 prompt 装配链扫一遍雷」——现在正在还这笔债）+ 一次 token 账本的口径统一。**不动用户任何配置，动的是你自己的边界纪律。** `[不变量1 / 不变量5 / §3]`

## 评点（效果优化 / 架构设计 / 收口——自评用，非标准答案）

### 效果优化

**A「越跑越忘事」的旋钮**

- **压缩的两个数字（何时压 / 压到多低）调保守一点**：晚一点压、压完多留一点（handoff 摘要厚一点、保住更多 user 消息）→ 后半段记得住更多约束。**反作用**：上下文占用更高、更贵；压得晚还可能撞上反应式的 413 兜底；摘要厚了也吃 token。
- **把会被压掉的约束 / 决定提炼进工作区记忆，让模型自主 grep 召回（pull）**：跨压缩、跨会话都能把关键约束捞回来 → 治本式地治「忘事」。**反作用**：记忆是「自动写」的高危动作——写多了 / 写错了会注回噪音甚至污染（更不稳）；召回注回 prompt 也占预算；还可能引「自动写记忆 → 整合 → 又触发模型调用」的递归（课文 §2 提的「压缩递归压缩」「自动写记忆引污染 / 递归」一类）。
- **reasoning_content 按配对纪律保住、别乱丢**：推理连续性在，模型「想到哪了」不断片 → 后半段决策更连贯。**反作用**：每轮带 reasoning，请求体更大、更贵（这正是 codex 当年想省、结果上线两天回滚的那笔账）。

**B「时快时慢」的旋钮**

- **死守缓存前缀纪律 + 上 cache-break 回归守卫**：前缀逐字节稳 → 缓存高命中 → 大部分轮「秒回」、延迟稳定。**反作用**：约束了你能往前缀里放什么（动态内容一律下沉），装配更死板。
- **审计延迟、把「该缓存的别每轮重算」「子会话别另起一套前缀」修对**：消除那些「偶发很慢」的尖刺（往往是某轮缓存意外失效 / 某段被重算）。**反作用**：逐段审计是慢功夫；有时为了缓存稳定要放弃一些「每轮给模型最新信息」的灵活性。
- **给子会话 / 多 agent 各自的预算走同一本 token 账**：让调度更可预测 → 减少「某轮突然卡很久」。**反作用**：统一账本是工程成本；预算卡死也可能让某些重任务被过早压。

**互相加剧的一对（命门）**：**为治 A 而「多留历史、多注记忆、保住 reasoning」**，和**为治 B 而「死守缓存前缀稳定、能不压就不压、别动前缀」**，这两组手段**共用的那个变量是「上下文里到底放什么、放在哪、变不变」**——也就是**那条缓存边界 / 前缀纪律（不变量一）**叠加 **token 账本口径（不变量五）**。具体的互相加剧：你为治 A 把**记忆召回的内容、更厚的历史**注回 prompt，如果注的位置 / 时机没守住边界，就**动了前缀的稳定性或让某段每轮重算**，直接**加剧 B 的「时快时慢」**（缓存忽中忽不中）；反过来，你为治 B **死保缓存、能不压就不压、尽量不往上下文里加东西**，就**留不下足够的约束 / 记忆给后半段**，**加剧 A 的「越跑越忘」**。正解不是在「多留」和「保缓存」之间二选一，而是**用「静态前缀锁死 / 动态桶承载」这条边界把两件事解耦**：把要长留的约束 / 记忆放进**动态桶 / 召回通道**（治 A），同时**绝不碰静态前缀**（治 B），代价转移到「把边界纪律和账本口径做扎实 + 上回归守卫」。 **陷阱**：列了旋钮不写反作用；没看穿 A↔B 那对耦合的公共变量是「缓存边界 / 前缀纪律 + token 账本」这两条横切不变量；把「治忘事 = 无脑多注上下文」当免费午餐（忽略它对缓存和稳定性的连带破坏）。

### 架构设计 · M0 总装蓝图

**强答案应触及的维度**

- **（1） 装哪几个、每个挂哪种力**：强答案的 M0 装的应是那张依赖图的**根 + 不可延的门 + 早决定旋钮**，逐个挂力：
  - **主循环 / turn loop + 唯一权威 history**——力 = **依赖**（DAG 的根，一切的底座）。
  - **模型 / 自写 Chat Completions wire（含条件式 reasoning 回填、自建 429 退避带 jitter）**——力 = **依赖**（loop 没东西可调就跑不起来）+ 这条 wire 本身是**早决定旋钮**（codex 删 chat wire 是它的奢侈，deepseek 必须自写，定错就把内核绑死在抄不动的 wire 上）。
  - **6 工具（含 apply_patch 式模糊编辑）**——力 = **依赖**。
  - **最小 system prompt（3 资产）+ 缓存边界**——力 = **依赖** + **可逆性**（缓存边界 / 动态哨兵那条线必须 M0 拧死）。
  - **append-only rollout 记录格式 + 最小 resume**——力 = **可逆性**（用它的人晚到 M1/M2，但格式是会话唯一真相源，定错 = 用户已有会话全量迁移）。
  - **应用层审批门 risk mode**——力 = **风险不可延**（无门跑 shell 不能上线）。
  - **三道硬闸（max_turns / max_tool_calls / token_budget）**——力 = **风险不可延 / 可逆性**（成本低 ≠ 可失控，别学 codex 无 maxTurns 赌收敛）。
  - **M0 就开始记 cache token**——力 = **不变量五的纪律**（埋点必须先于任何优化）。
- **（2） 横切边界标注**：缓存边界 = **system 静态前缀（身份 / 工具规范 / 安全话术 / 输出契约，逐字节锁死）vs developer/user 动态桶**那条线；持久化边界 = **先持久化、后送出**（rollout.append 错误必须上报，不许 `let _ =` 吞）；审批门 = 一切 shell / 写入动作汇进引擎、**deny 最先判**；token 账本单一真相源 = 主循环读的那本账，M0 即记 cache token。
- **（3） 推迟什么 + 怎么不堵死（挑 ≥3）**：强答案会挑**压缩 / 记忆（M2，依赖 rollout + 模型层 + 压缩自身是模型调用）、MCP（M2，依赖渐进暴露 + M3 网络代理）、多 agent（M2，依赖稳定 loop + rollout fork）、OS 沙箱（M3，需求要被前面的能力挣出来）**里至少三个，各自说清「地基没到」，并落「不堵死」的留位：`ToolSpec` 支持 `defer` 标记、`ThreadItem` 预留 skill item、rollout schema 能记 skill 加载、子 agent 通信抽象预留……以及那条纪律——**type-reserved 但没接线的 stub 必须带 `// replace in milestone X` 账本注释，不许只留裸 TODO**。
- **（4） 驳「M0 顺手做压缩」**：压缩**自身是一次模型调用**（handoff summarizer），它**依赖**模型层 + rollout 格式，还需要「触发判定要排除压缩 / 记忆抽取等内生子调用源，防压缩递归压缩」这套门控——这些在 M0 不齐（M0 的恢复只做三件套，压缩属于能力深化）。更尖锐的：硬塞压缩进 M0，压缩跑完若**没复用同一条缓存键**，就**违反不变量一**——一次压缩把整条前缀换了，M0 最该保住的 `cache hit ratio` 当场塌掉。所以「压缩 = 省上下文 = 对省钱有好处」是只算了一半账：它省了历史 token，却可能**炸了缓存**（稳 / 省成本互搏），这是 capstone 最典型的跨课陷阱。M0 装不起，也不该装。
- **重入底座 + 新增假设（收尾）**：**复用的底座 = 第 1 课那个「无状态模型 + 只追加历史 + 每轮从权威 history 重建请求」的 turn loop**——子 agent（换一组起始参数重入）、压缩（往 history 追 checkpoint）、resume（从 rollout 重建 history）全站在它上面。**新增的假设**：那个 loop 必须从「只服务主 agent」变成「**可被任意起始上下文 / 任意一组起始参数重入**」——这是单看第 1 课不会逼你做、只有把子 agent / 压缩 / resume 装到一起才逼出来的假设。
- **陷阱**：按「哪个功能听起来重要 / 杠杆高」选 M0（把 MCP / 压缩这种高杠杆但地基没到的塞进来）；没给每个机制挂明它**那一种力**；推迟了却不留账本注释（裸 TODO，将来接线要返工）；没看穿「M0 顺手做压缩」会炸缓存（跨课陷阱）；说不清那个「loop 可被任意上下文重入」的新增假设。

### 收口 · 审「对等图当 M0 卖点」的提案

- **三性归位（及格线）**：这套「对等图 + 崩溃恢复整棵树」主要加强**自动**（多个长期 agent 自己在图里协作、互相唤醒、无人值守 / 集群级运转）。它付出的复杂度——共享控制平面、内存通信总线、`trigger_turn` 协议、持久 spawn 拓扑、把 agent 间消息接进 rollout、并发管控——主要压在**稳**上（更多状态要持久化、要恢复、要并发管控才不出乱子），这正是第 7 课那个「复杂度守恒」的再现。
- **装配顺序的硬伤（高分线核心）**：提案最大的排期错误 = **把「杠杆 / 重要性」当成了「排期」**——「这是我们最大的差异化卖点、杠杆最高，所以 M0 就上」整条推理，犯的**正是 capstone §1 那个核心错误**，和课文里 **MCP 那个反面教材是同一个错**：只盯回报（杠杆），没看地基（依赖）。这套对等图的「地基」是**稳定的 turn loop、rollout、持久化、缓存前缀纪律、权限引擎**——这些**M0 一个都还没在**。M0 就上对等图，等于**在没有地基的地方先盖最高的那层楼**：连单个 agent 的 loop / rollout / 缓存纪律都没立稳，就去做「多个长期 agent 互相喊话 + 崩溃恢复整棵活树」，必然返工。**杠杆决定它该不该做，依赖决定它什么时候才装得起——两种力被这个提案混成了一种。**
- **横切不变量的连带代价**：对等图一上，**至少三条不变量更难维持**：（1）**不变量一（缓存前缀确定性）**——fork / spawn 出去的对等 agent 若不复用同一条缓存键，就各起一套前缀，缓存全面碎裂；（2）**不变量五（token 账本一个口径）**——多个长期 agent 互发的消息进了谁的账本？各自预算怎么汇总？账本口径极易裂开；（3）**持久化 / 「先持久化后送出」**——「崩溃恢复整棵活 agent 树」要重建一大坨跨 agent 的活状态，这远超 M0「append-only + 最小 resume」能扛的，和「先持久化后送出」的简单契约咬合困难。一句话：**这套图把好几条横切不变量的维护难度一起拉满，而这些不变量在 M0 都还没立稳。**
- **parity-first 裁决（高分线收口）**：站在 deepseek 北极星上，这个提案属于**「还没挣得的范围」**——它加强的「自动」（集群级、无人值守）**不是「与 claude / codex 效果对齐」的必需**（claude 的主干用「子 agent 跑完就死、父收报告」就覆盖了 80% 场景，根本不付这套复杂度）；它是**花活**，不是对齐。所以裁决：**推迟（到 post-v1），但架构不堵死**——用「子 agent 注册表 / 通信抽象预留」留位，不焊死；**M0 先把那张依赖图的根装稳**（turn loop + 一次性层级 fan-out + rollout + 缓存纪律 + 权限引擎）。**先对齐、后超越**；对等图是「超越」，得等地基挣出来再上。
- **可加的反驳细节**：有人会说「对等图也加强了『强』（能干集群级的活）」——对，但那个「强」**对你要对齐的形态（单用户桌面 coding agent）用不到**，在 M0 它**只表现为复杂度（压稳）**；「强不强」取决于你要支撑的形态，不改变「对 deepseek、这张图现在的净效果是压稳 + 排早了」的结论。
- **陷阱**：把对等图无脑判成「更强所以更先进、该早做」（脱离 deepseek 定位谈强弱、脱离地基谈排期）；没看穿它和 MCP 犯的是同一个「杠杆当排期」的错；没把连带代价落到「**哪几条横切不变量被一起拉满**」上，只泛泛说「太复杂」；裁决给成「不做」而不是「推迟但不堵死」（违反 parity-first 那条「花活推迟、架构不堵死」）。

## 结课语

这门课到此结束。它教的不是十一个子系统各自怎么写——那是前十一课的事；它教的是**它们怎么装在一起还不散架**。而「不散架」靠的就是你在这套题里反复练的三样：

1. **装配顺序对**——按「地基到位没」排，不按「听起来重不重要」排。每次想把一个高杠杆的东西提前，先问一句：它的地基齐了吗？（MCP、那套对等图，都是这一问的反面教材。）
2. **横切不变量齐**——缓存前缀确定性、reasoning 配对相邻、四角色 / developer 桶塌缩、审批 deny 最先判、token 账本一个口径，这五条任意一条在某个子系统里破了，都会崩在很远的地方（推演 1、故障排查那台「越跑越贵」的 agent，练的都是这个连锁）。
3. **早决定的旋钮 M0 就拧死**——格式类、边界类、裁决类的旋钮，用它的人再晚，定它也要早；轻量、推迟可以，但义务要写进账本，不许只留裸 TODO。

现在你手上有了一套**可操作的检查动作**。拿到任何一个 agent 设计——你们自己的，或者将来评估别人的——按这个顺序过一遍：**先画依赖 DAG、拓扑排序定里程碑 → 列横切不变量、逐条确认全局一致 → 标早决定旋钮、确认 M0 拧死 → 每个「超越」的念头先问北极星那一句（帮对齐还是还没挣得的范围）→ 任何 load-bearing 的外部 API 行为先查官方文档再写进设计，残余不确定性编码成 config 开关 + 实测项、别硬化成新铁律。**

对齐效果 = 机制覆盖齐 + 效果不输，最终落在你们宪法那组工程不变量和产品指标上：tool_call / tool_result 配对零失配、取消零孤儿进程、secret 零泄漏、回放可重建、缓存命中率、每任务成本——这些数字达标了，「对齐」才算数。

把这门课收成一句话带走：**一台能用的 agent，不是十一个结论的并集，是它们装在一起时那张依赖图、那五条不变量、那几个早拧死的旋钮共同撑起来的、不散架的整体。** 下课。
